# 真實時刻表研究

作者提供了台灣鐵道的真實時刻表，涵蓋台鐵、高鐵與捷運。這份文件記錄時刻表裡有哪些概念可以放進遊戲，以及它們各自屬於 [ROADMAP](ROADMAP.md) 的哪個 Stage。另一份參考是作者的網頁版交通經營遊戲（[WEB_REFERENCE_STUDY.md](WEB_REFERENCE_STUDY.md)）。

## 原則

- **只吸收概念。** 原始資料不進 repo。真的要用資料時（例如做真實藍本情境），只轉成遊戲自己的格式，並標示來源。
- **授權**：
  - 時刻表來自政府開放資料，可以使用，但必須標示來源。
  - 如果用到 OpenStreetMap 的軌道幾何，必須標示來源；做出的衍生資料庫若公開散布，也要以 ODbL 釋出。
- **不把即時資料接進模擬。** 遊戲要離線運作，而且同一份存檔在每台裝置都要跑出同樣的結果；即時誤點與列車位置做不到這點。

## 時刻表裡的概念

1. **逐班時刻**：每一班車依序停靠的車站，以及各站的到站與離站時刻。有些站只通過、不停。
2. **車種與停站模式**：區間車站站都停；區間快、自強號只停部分車站。同一條路線上有快慢車。
3. **時段與班距**：同一條路線，尖峰班次密、離峰班次疏。支線的班距比幹線長很多。
4. **跨午夜**：深夜的班次延續到隔天，時刻會超過 24:00。
5. **停站時間**：中途站多數停 30 到 90 秒，中位數約 1 分鐘。
6. **路線結構**：有單線與雙線的區間，單線上的列車要在交會站錯車。車站也分等級（特等、一等、二等、三等、簡易站等）。
7. **行駛時間與誤點**：站間的行駛時間取決於車種與路段；實際運行有誤點，而且誤點有一定的分布。

## 在遊戲裡的用法

| 概念 | 遊戲裡的對應 | Stage |
| --- | --- | --- |
| 逐班時刻 | 直接對應 `ScheduledStop` 的到站與離站；每天重複用 Q1 的重複時刻表（週期 1440 分鐘） | 已有（O、P、Q1） |
| 停站時間 | 停站 1 分鐘、終點 2 分鐘，與真實的中位數一致 | Q2a（已吻合） |
| 時段與班距 | 尖峰、離峰各跑幾台列車，或各時段的目標班距（例如每小時一班），由線路自動派車 | Q2a、Q2b（已實作） |
| 跨午夜 | 營運時間可以延續到隔天清晨 | Q2a（已吻合） |
| 車種與停站模式 | 快慢車：快車是停靠站的子集合；交路只跑一段 | Q3（已實作） |
| 單線與交會 | 佔用、進路預約、交會與待避；線路的最多列車數改依單線區段與交會站推導（Q2a 目前假設雙線） | Phase 4.5、4.6（見下面的「實體鐵路層」） |
| 車站等級 | 車站規模與需求等級的預設值 | 5A |
| 行駛時間 | 各車種的速度（rate），之後改用行駛曲線 | W |
| 誤點分布 | 誤點與中斷事件 | Phase 6、7 |
| 大量班次 | 真實規模的效能量測（一天上千班） | 跨階段 |

**時刻換算規則**（實作時決定）：真實時刻有秒數，遊戲以整分鐘計算。建議到站時刻無條件捨去、離站時刻無條件進位，這樣列車永遠不會比真實時刻早走（決策 20 的出發閘門），也保持 `arrival <= departure`。換算工具還要處理兩種邊界情況：

- **站間不到 1 分鐘**：前一站的離站進位、下一站的到站捨去後，到站可能早於前一站的離站，遊戲會拒絕這種時刻表（時間不能倒流）。換算後要把這類到站改成等於前一站的離站。
- **行駛時間被壓縮**：同樣的捨去與進位，會讓每段行駛時間最多少將近 2 分鐘，可能比列車以它的速度實際需要的還短，列車就會一直晚點。換算工具要檢查每段的行駛時間，不夠時把之後的時刻往後推。

**班距怎麼表達**：真實路線通常先定班距（例如每小時一班），多出來的時間讓列車在終點站等。Q2b 讓線路的每個時段可以設定目標班距，由系統算出需要幾台車；沒有設定的時段照舊用列車數推導班距。

## 實體鐵路層（2026-09 詳讀）

時刻表資料除了班表，還把班表放到實體股道上跑。這一層和網頁參考遊戲剛好互補：
- 網頁參考遊戲是經營層：開什麼服務、需求在哪裡、乘客怎麼走（[WEB_REFERENCE_STUDY.md](WEB_REFERENCE_STUDY.md)）。
- 這一層是鐵路的物理層：列車實際怎麼在鐵軌上跑、怎麼共用股道。

以下都已對原始程式與資料抽查。這一層就是作者 `Railway/` 網站的實體層：作者自己的程式照 faithful-port 規則翻譯（[WEB_REFERENCE_STUDY](WEB_REFERENCE_STUDY.md#來源與使用方式)），函式層級的對照見 [RAILWAY_REFERENCE_MAPPING.md](RAILWAY_REFERENCE_MAPPING.md)。從 OpenStreetMap 導出的股道與真實時刻表的資料不移植。

1. **股道拓樸**
   - 路網由節點與邊組成，邊是兩個相鄰節點之間的一段股道。股道是否相接由節點身分決定，不會因為座標接近就合併。
   - **道岔的轉向規則**：從主線可以轉進任一支線，但不能從一支線倒車轉進另一支線。平面交叉只能直行。沒有標記的分岔，只在兩支近乎平行時才當成道岔；四叉交會不猜可以換線。
   - **股道群**：兩個道岔之間相連的一串股道是一組。同一站的不同股道，就是用股道群來區分。
   - **佔用資源**：每一段邊是一個資源。資料裡重複畫出的同一段股道共用一個資源，不能冒充成第二股。平面交叉的每個穿越方向共用一個衝突資源。
   - **求路**：以「從哪條邊進來」為狀態找最短路。可以排除已被佔用的資源、替資源加權，也可以限制總長度。預設不走調車場與側線，渡線加重權重，所以會盡量不換股道。
   - **對照本專案**：格子鐵軌的 T 形分岔目前三個方向可以任意互通（只禁止原地掉頭），比真實道岔寬鬆。真實道岔的兩支彼此不能直接互通。
2. **單線與雙線**
   - 相鄰兩站之間，平行正線佔路段長度一半以上算雙線，否則算單線。不同來源互相衝突時，以官方的路線沿革為準。
   - 同時記錄兩站之間實際派過的最長路徑長度，當作行駛里程的下限。
3. **整列車的資源預約**
   - 依實體路徑與班表，對整列車（連同列車長度）預約它會經過的資源。
   - **衝突的解法是「排定的等待」**：在某一站多停若干秒，讓對向或後面的車先過，而不是讓兩車互穿。
   - 這是推估出來的安排，不宣稱是調度員實際使用的股道。實際需要等待的班次很少：約 4%，單次最長約 3 分鐘。
   - **預約用的長度和畫面上的長度分開**：預約用的是派車預留值（例如區間車只留 60 公尺），防追撞則用實際編組的長度。
4. **班表綁定實體路徑**
   - 每班車的每一段（相鄰兩站之間）綁定一條實體路徑，所以同一站可以停不同的股道。
   - 改點的班次沿用自己原本的路徑，前提是站序與停靠型態相同，而且原本沒有待避。
   - 加開車向既有班次借用一段連續的路徑，優先借停靠型態相同的。沒有一班跑完整條路線時，改成一截一截接力借用，交接處必須接得上：節點相同，而且不在道岔倒車。
   - 特定車種專用的股道（例如非電化月台）不借給別的班次。
   - **站場規則的例子**：停站的列車走外側月台的到發線，通過的列車走內側正線。
5. **待避與交會**
   - 後車快追上前車時，往回找一個煞車距離足夠的車站，讓前車在那裡待避；停哪一站依車種的煞車性能決定。優先利用前車原本的停站時間，避免多停一次。
   - 單線交會：等對向車到站後再開，或讓對向車先開。待避與交會都保留安全間隔。
   - 同股道上的後車依前車的位置減速跟隨，並依實際編組長度保持距離。
6. **行駛曲線**
   - 站間不是等速行駛。曲線描述「時間 → 里程」，有兩種：
     - 加速、定速、惰行、煞車四段組成的梯形曲線；
     - 通過實測時刻點的平滑曲線。
   - 曲線由表定時刻、路線里程、通過站的實測時刻與單雙線資訊算出。算出的長度或時間對不上時就不採用，退回等速。
   - 公開班表沒有列出的停車時間（例如之字形爬坡的折返點）不捏造，只在站間的時窗內漸停再起步。
7. **月台與編組**
   - 月台有實際的位置與長度。有月台幾何的，取兩端最遠的點；沒有的，依車站等級的中位月台長度推估。
   - 編組依車型列出每節車長與車寬。沒有逐班資料的，節數標示為推估。
8. **轉乘站**：不同系統的車站，名稱正規化後相同、而且相距 450 公尺以內，就視為同一個轉乘點。
9. **平交道與立體交叉**
   - 平交道記錄位置、股數與是否電化，可以預測接下來哪幾班會經過。
   - 兩條路線立體交叉時，記錄誰在上、誰在下。

**和網頁參考遊戲的分工**：`Ci/` 的網頁參考遊戲沒有號誌、閉塞或待避站，快慢車彼此「看不見」；這一層（`Railway/`）正好補上「多台列車怎麼共用實體鐵軌」。反過來，這一層沒有玩家蓋站蓋線、需求、客流、票價與城市成長，這些照舊參考網頁遊戲。

## 真實藍本情境

- 依 Phase 6 的地圖方針：主要模式是虛擬地圖，真實藍本情境是另外的選項。
- 情境由 GameCore 以外的轉換工具產生：用車站座標產生格子地圖，用車站等級決定車站規模，用單線或雙線決定軌道配置，再把時刻表轉成列車的時刻表。
- **第一個候選是平溪線**：站數少、全線單線、班次不多，又有真實的交會需求。

## 不採用

- 即時資料接進模擬（即時誤點、列車動態、到站倒數）。
- 原始時刻表資料、即時資料，或從 OpenStreetMap 導出的資料放進 repo（作者自己的網站程式照 WEB_REFERENCE_STUDY 的規則處理）。
- 未決定授權方式前，直接散布 OpenStreetMap 衍生的幾何。
- 把真實地圖當主要模式（已決定以虛擬地圖為主）。
