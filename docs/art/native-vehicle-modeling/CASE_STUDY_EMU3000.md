# EMU3000 實例：側面對了，為什麼正面還會變形

這次最重要的經驗是：**用一張側面圖修好縱向輪廓，不能證明橫向截面、正面燈窗或立體曲面也正確。** 另一個教訓是：模型封閉、有厚度、有支承，仍可能把玻璃遮住。

使用者在第五版交付後明確回覆「可以了」，再要求將製程補進 skill／art 文件。[接受範圍紀錄](https://github.com/a91453/railway-game-ios/issues/1226#issuecomment-6398260552)對應下列第五版，僅表示該版外觀接受，不代表工程復刻、真機效能、動畫或合併／發版授權。本輪文件化保持原模型、工具、圖、viewer、ZIP與producer不變。

## 3. 側面修好後，為什麼正面出問題

第四版根據ED側圖重做艙頂、斜鼻與下角。側面成立後，使用者指出正面「大變形」；製作者撤回先前正面已符合的自評，沒有拿測試通過反駁看圖結果。

| 可見偏差 | 原因與修正方向 |
|---|---|
| 側窗在正面露出過寬，像兩片耳朵 | 縱向輪廓與橫向收束沒有同時成立；調前端寬度與肩部截面，保護側面高度／鼻長 |
| 側燈變成長條 | 舊角度參數在斜鼻上有不同方向的縮放；改用正面實體座標定輪廓，再貼合真殼 |
| 黑罩下緣出現折角／鋸齒 | 粗三角內的少量線性分色值不足以表現圓U邊界；明確切入圓弧輪廓並傳遞共享切點 |
| 遠景風擋部分被車殼遮住 | 角點貼殼後用大面連接，面內部仍跨進凸殼；按實際朝前殼三角切分，而非整片再外推 |

這些是不同層的問題，要分開處理。換色不能修正截面，法線平滑不能修正剪影，增加雨刷也不能修正燈的投影比例。

## 4. 保住側面，獨立修橫向截面

配方以沿縱向排列的截面控制車殼；每段的頂高、底高、半寬與曲率分開定義。第五版保留第四版的頂高／底高與站位，修改橫向寬度與肩部圓收，再重新貼合受影響的門窗、罩縫與設備。

保護範圍用實際輸出證明：

1. 從原生三角辨識真正殼面連通體。
2. 在101個縱向位置切平面，分別取第四／五版側面上下包絡。
3. 以本案例20微米模型容差核對差異，近遠景頭尾各做一次。
4. 比原生三角多重集合，確認改動在前艙；12件中間單元payload全同，走行／車下設備／連結器與總bounds保持。
5. 實看同相機、公尺尺度的側／正／俯／斜對照，再下外觀結論。

實作見[revision-audit.py](https://github.com/a91453/railway-game-ios/blob/66a515e8f84ddb5001bae2dd0ce5d79f49063113/tools/emu3000-refresh/revision-audit.py)。**側面上下包絡保持，不等於全部側面頂點、色塊或投影像素保持。** 20微米也只描述虛擬模型差異稽核，沒有因此取得真車工程精度。

## 5. 圓燈、風擋與圓U罩的做法

### 在需要辨識的視角定輪廓

先在正面實體座標定燈與風擋的大小／位置，再沿觀看方向與真正殼面求交，產生有厚度與背襯的實體。換一種車／另一種曲面時要重看；此法沒有要求圓燈從所有視角都必須呈圓形。

本案新回歸直接讀實際發光連通體的正面寬高。真第四版在近遠景兩側主燈共失敗4項，舊主燈高寬比約1.78–1.87，指出已拉成長條；第五版近景主燈約1.11。這是模型投影量測，**不是與參考圖的相似度分數**。門檻依本車可見形狀訂定，不是所有車燈的通用規格。

### 讓面內部也貼合

風擋與燈座先定凸輪廓，再逐片裁切真正朝前殼三角，沿投影方向擠出薄實體；共享邊保持一致，僅在邊界形成側壁。以多邊形有向面積判斷輪廓方向，左右鏡像各自處理，避免只生出一邊。

只投射四個角、再用大扇形連接，不能保證凸面內部貼合。遠景更容易因減面重現此問題；少三角的貼合方式也要過真正遮擋檢查。凸輪廓裁切遇到凹形須先分解，不直接套這個假設。

### 讓圓U分色落在真正殼面上

本案以多個半平面近似凸圓弧，再裁切實際殼三角。新切點傳給鄰接原三角與同面其他色區；端點順序一致，處理近界值／退化面，保留邊界分點，才不會出現T接縫、微小缺面或不穩定重疊。

不是用外掛黑片遮住白殼，也不是把700T的分色常數整套搬過來。每次裁切方式改變都重新驗封閉有向邊／正體積／法線，並實看圓弧是否真的自然。

## 6. 車門破圖的教訓：支持與可見性分開

較早一版的門葉／玻璃雖有封閉實體，玻璃仍被白葉或凸殼遮住。修法是白殼本身作門葉，只加封閉薄門縫及真正分段貼合的玻璃；端車漸縮區還需處理縱向三角對角線造成的實際截線。

| 檢查 | 能回答的問題 | 不能代替的檢查 |
|---|---|---|
| 封閉有向邊／正體積 | 是否為朝向合理的封閉面 | 玻璃會不會被其他面蓋住 |
| 背襯距離／支點／輪淨空 | 是否有合理靜態支持與裝配間隙 | 每個觀看方向的可見性 |
| 從觀看側對玻璃正面取樣射線 | 是否先撞到白殼／框，是否有同深度衝突 | 所有像素、全部視角或動態碰撞皆無問題 |
| 原生配色／白模／剪影實看 | 曲面、色塊與貼合是否符合外觀目標 | 工程尺寸或真機成本 |

射線不把薄邊壁、背面當作必須可見的正面；雨刷的預期遮擋依真正窄零件辨識，不一律放寬玻璃門檻。故障反例移動實際連通玻璃：門玻璃埋入100mm、風擋埋入120mm，遮擋檢查仍須拒收。這些是本案診斷量，不是通用門縫、玻璃厚度或安裝公差。

工具：[front-audit.py](https://github.com/a91453/railway-game-ios/blob/66a515e8f84ddb5001bae2dd0ce5d79f49063113/tools/emu3000-refresh/front-audit.py)、[door-audit.py](https://github.com/a91453/railway-game-ios/blob/66a515e8f84ddb5001bae2dd0ce5d79f49063113/tools/emu3000-refresh/door-audit.py)、[support-audit.py](https://github.com/a91453/railway-game-ios/blob/66a515e8f84ddb5001bae2dd0ce5d79f49063113/tools/emu3000-refresh/support-audit.py)。新車需重新定ROI、材質／零件辨識、視線與合理容差，不照抄本案例座標。

## 7. 確認每個近遠景，再重出同版素材

順序是：

    真參考與前版 → 保護已接受視角 → 改截面／貼合
    → 原生配色／白模／剪影四向 → 近遠景可見性與故障反例
    → 固定相機真前後 → 提交producer → 最終匯出／全量驗證／看圖
    → viewer／ZIP逐檔與真下載 → 草稿PR／來源／交接

這不是只在預覽工具修漂亮：所有最終單元、編組、GLB、PNG與viewer都來自同一原生配方。若重新改模型，就重做最終匯出與看圖；不同版本的預覽不能混包。

## 8. 給下一個AI的可重複規則

1. 先看參考與實際原生四向，再讀製作者「已符合」的結論。
2. 確認本輪改哪個視角、保護哪個視角；分開寫輪廓／硬體／payload的保持證據。
3. 分別修縱向輪廓、橫向截面、分色、投影與裝配，不把所有問題都當鼻長。
4. 測映射後的形狀與可見性，不只測參數、封閉或支承；近遠景各自檢查。
5. 修改後固定相機真前後、原生四向白模剪影與配色全部重看，撤回被否定的舊自評。
6. 保留真前版，提交真正producer後全量重出與驗證；模型、viewer、ZIP與來源同版。
7. 接受只記該producer的外觀；工程／另一側資料不足、Metal／效能／動畫未驗仍要保留。靜態包、營運映射、合併與已安裝App的狀態分開說明。

日常開工用[製作指令](PROMPT.md)，交付前用[獨立驗收表](REVIEW_CHECKLIST.md)。移植的是觀察、解耦、貼合、看圖和驗證方法；EMU3000的曲線、門窗、編組、ROI、容差與三角預算都須由新車的資料重新決定。
