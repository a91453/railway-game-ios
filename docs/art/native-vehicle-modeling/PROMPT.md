# 給不同 AI 的製作指令範本

先填任務卡，再貼「完整製作指令」。ChatGPT／Codex、Claude、Gemini 或其他 AI 都使用同一份任務卡與證據清單；不要依賴上一個對話的隱藏記憶。

這是工作指令，不是保證一次成功的美術咒語。執行者需要能實際看參考、修改原生模型、渲染及讀取驗證輸出；缺少哪項能力要明說，不能用文字描述或概念圖冒充已完成原生資產。

## 2. 完整製作指令

把填好的任務卡與下段一起給 AI，並提供它有權讀取的來源。

~~~text
請依任務卡完成一件可重建、可審查的原生3D車輛素材。
先閱讀專案的原生3D車輛製作手冊、AGENTS／CLAUDE／HANDOFF、
art-style與相關格式／工具README；這份指令不取代使用者最新要求與專案規則。

目標是比例可信、輪廓清楚、曲面自然、色塊有層級、
與遊戲既有霧面／低彩度／細節密度一致。
不能只做一張漂亮圖、列計畫，或用技術測試成功代替外觀驗收。

一、接手與參考
1. 取得最新遠端與前置PR狀態；認領自己的檔案，從正確base開自己的分支／worktree。
2. 實際查看每張來源圖；GLB／模型在本機匯入並渲染多視角。
   無法讀取就明說，不得以檔名／摘要冒充看過。
3. 區分實車照片、實體模型、插畫、工程資料與遊戲模型。
   有可靠尺寸先用；只有圖片時標「比例推估」，不把透視像素當工程尺寸。
4. 建模前簡短列特徵表：類別、單體／編組、側正俯斜輪廓、頭尾／左右差異、
   相對尺寸、門窗／設備、走行系統與資料缺口，然後繼續做。
5. 新來源決定新車結構。已接受車輛只作風格／色票／材質與細節密度比較；
   能否直接沿用程式或零件，依本次授權確認，不能因為容易就複製整個車體。
6. 私有來源不公開、不送外部生成服務；不留下品牌、商標或個資。

二、先大形，再細節
1. 依序完成長寬高／鼻長／前後懸、側正俯主輪廓、頭尾與肩部曲面。
2. 先輸出原生白模／剪影四向，自己查看；主輪廓不符就修幾何。
3. 車頭分開控制中央鼻罩、左右肩部、前唇與下裙板，不能只拉長整個鼻子。
4. 再做底盤／輪組、門窗／大型設備，最後做薄框、燈、雨刷等小細節。
5. 門板貼合車身、框與中縫薄；玻璃、設備有厚度／背板／支點。
6. 確認單位、軸向與單次轉換；輪胎逐個貼軌／地面，
   裙板有包覆但輪組仍有淨空。
7. 公車核對門側／軸數／軸距／前後懸／風擋與大設備；
   列車核對單元種類／順序／朝向／長度／門窗／輪架／風琴／集電設備，
   中車不能殘留駕駛窗或頭燈。
8. 側面來源不能單獨決定橫向截面。側面已接受而只修正面時，
   保護鼻長與上下輪廓，另調橫向寬度／肩部曲率；以真殼切片和固定相機核對。
9. 檢查燈／風擋經曲面映射後的實際投影；圓形UV不保證正面仍是圓。
   面板按真殼三角或截線貼合，不能讓大面跨凸殼；近遠景各自看圖及驗遮擋。

三、配色與局部修改
1. 依任務卡與現有色票決定車身、大主帶、深色罩／裙板、燈色。
2. 檢查色塊面積與形狀，不只是色碼；正面、側面、俯視都要成立。
3. 色帶隨原殼面切分，接回車身要平順，不用重疊外掛色片掩飾。
4. 修訂前保存真正已交付前版及來源／配方／manifest。
5. 使用者只要求改色帶時，保護殼、罩、燈、門窗、輪架與其他單元。
   使用者要求修形時，真的修改幾何，不用換色充當修形。
6. 對受保護部分提出實際頂點／三角／bytes／bounds或共面覆蓋證據；
   三角細分增加時，不可謊稱整個檔案bytes不變。

四、外觀驗收
1. 所有預覽來自實際原生模型，不能使用另一套替代mesh或生成概念圖。
2. 批次輸出前親自看側、正、俯、斜的配色／白模／剪影。
3. 以同相機、同單位、同公尺尺度、同光線做真正前後；
   兩張各自auto-fit不能當比例比較。
4. 每輪列「已符合／仍不符合／資料不足」，指明視角與檔案。
5. 發現主要偏差就回到相應層修正、重匯出、重看，
   不用更多裝飾／棚拍光／技術測試來掩飾。
6. 加上遊戲觀看尺度與既有車輛的同尺度風格比較。
7. 不捏造相似度分數，不聲稱使用者認可未看過的版本。
8. 使用者否定某視角時撤回該項自評，保護其他已接受部分；
   後續接受只記到明確producer／修訂，不外推到真機、動畫、工程精度或合併授權。

五、原生與素材包
1. 配方獨立，入口只做必要註冊；重建工具放自己的目錄。
2. 單元各自合法；多單元提供完整編組與順序／平移／旋轉／間距／共同基準。
3. 輸出原生、GLB、每件上下左右前後立體透明PNG、
   完整單元／編組預覽、四向配色／白模／剪影、同尺度風格比較、
   真前後、可旋轉縮放並真下載的viewer、bounds／三角／來源／SHA、完整ZIP。
4. 各單元、所有視圖、viewer與ZIP來自同一份最終模型；
   改模型後重新輸出並查看。
5. 公開私有分工依任務卡與專案規則；原始私有參考不得意外混入交付包。

六、技術與來源驗證
1. 使用指定工具鏈／warnings-as-errors及相關測試。
2. 驗原生讀回、法線、封閉、退化面、實體支持、輪軌／淨空、組裝與既有模型共存。
3. 加能抓到可見缺陷的反例，如刪面／反面／玻璃浮空／組裝錯位／移動殼面，
   不只核對配方常數。
   支承與可見性分開驗；把實際連通玻璃埋入殼內應被射線拒收，
   排除邊壁與真正雨刷的預期遮擋。遠景同樣獨立驗，不借近景的通過結論。
4. 用獨立GLB importer與PNG完整解碼器；檢查透明、不裁邊。
5. 實際操作viewer載入、旋轉、縮放與下載，核對下載bytes／SHA。
6. ZIP完整解壓、CRC與逐檔比對。
7. 來源紀錄填實際producer commit並核對來源bytes，
   不把未提交工作區或別版預覽掛到該commit上。
8. 外觀結論、本機VERIFIED／UNVERIFIED、最新head CI、Simulator、
   真機Metal／效能／動畫分別記錄；抽樣不代表全碰撞。

七、完成與交接
1. 在已授權範圍完成實作與可審查結果，不停在計畫或等待造型批准。
2. 推自己的分支／建立或更新draft PR、issue、必要HANDOFF；不覆蓋他人工作。
3. 不推main、不合併、不開auto-merge、不啟動TestFlight。
4. 說明本次是靜態素材、註冊或實際營運替換；
   合併後是否會在遊戲中出現，要有實際映射依據。
5. 交付實際最終圖、全套素材與重建文件連結，列出仍不足與未驗項目。
~~~

## 3. 收到局部回饋時，接著貼這段

~~~text
以下是本輪唯一外觀修訂：
【問題】……
【新參考】……
【真正前版與producer】……
【已接受、不可順手修改】……

請實際重看參考和前版原生四向，先指出問題是幾何、分色、
裝配、相機還是光線；不要直接憑印象調參數。
在指定區域修改，保留真前版；重出同相機同公尺前後、
最終配色／白模／剪影四向並自己查看。
用適合這次修改的實際幾何／bytes／共面面積或接點證據檢查保護範圍。
只修正面時，明確檢查已接受的側面上下包絡；
包絡不變不等於側面全部頂點／色塊／像素不變，需分開陳述。
只適用舊稿的稽核不能拿來證明新稿，例如改殼後不能沿用「只改色」結論。
完成後更新全套最終輸出與來源版本，分開回報外觀、技術、CI和真機狀態。
~~~

## 4. 給獨立審查者的指令

這可以交給另一個 AI，也可以由同一 AI 在製作完成後依序執行；不要求開額外 agent。

~~~text
請用獨立驗收表審查這批原生車輛。
先實際看來源與原生渲染，再讀製作者的自我結論。
先查長寬高／側正俯輪廓／頭尾曲面，再查門窗輪組設備與色帶，
最後查細節／材質與技術包。
不要因為測試通過就認定外觀合格，也不要把工程資料缺口當已確認事實。

每項發現記：具體問題、視角／檔案／位置、證據、影響、建議修法、
已符合／仍不符合／資料不足。優先列最多三項影響最大的可見偏差。
驗證真前版、共同相機與尺度、來源producer、下載／ZIP及保護範圍是否成立。
指出真正阻擋交付的問題，以及只屬小細節或需真機確認的項目。
不得自行改使用者已接受部分或把未看過的版本說成已認可。
~~~
