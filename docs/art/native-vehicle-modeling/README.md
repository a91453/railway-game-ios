# 原生 3D 車輛製作手冊：從參考圖到可交接的遊戲模型

這份手冊把 E200／700T 製作中有效的方法整理成可重複流程，供 Claude、ChatGPT／Codex、Gemini 或其他具備看圖、程式與渲染工具的 AI 使用。它不依賴某個 AI 的隱藏記憶，也不要求用外部圖片／3D 生成服務。

核心不是「加很多細節」，而是依序解決：**比例、各視角輪廓、曲面關係、色塊面積、門窗與設備的位置、材質與細節密度**。每一步都有可看的原生模型輸出；有偏差就回去修該層，不把問題留給最後的配色。

一份提示詞不能保證每個模型或每個 AI 一次就漂亮。本流程把判斷過程、失敗訊號與驗收證據寫明，讓下一個 AI 能發現並修正偏差，而不是相信自己說「已完成」。

本手冊的路徑連結以本 repository 為例。搬到別的專案時，替換工具、座標、預算、來源政策和交付格式；保留觀察、製作、渲染、修正、驗證這條流程。

## 1. 為什麼模型會看起來比較好

| 決定觀感的層級 | 要做對的事 | 常見錯法 |
|---|---|---|
| 整體比例 | 長寬高、前後懸、鼻長、車頂與底盤高度互相成立 | 用通用長方體再堆窗戶、燈和配件 |
| 主輪廓 | 側面、正面、俯視都像參考；車頭與肩部各有自己的曲率 | 一張斜視看起來像，其他方向露出尖頭或扁板 |
| 大色塊 | 白區、主帶、黑罩、裙板的形狀和面積各有層級 | 顏色選對，但主帶太大、黑罩過高，掩蓋車體 |
| 中型結構 | 門、窗、轉向架、車頂設備有合理位置、比例與厚度 | 門像外掛箱，窗像貼在殼外的粗灰框 |
| 小型細節 | 能說明結構、在遊戲尺度仍有辨識用途 | 密集螺絲、管線和刻線把主形體變成雜訊 |
| 材質與光線 | 與遊戲既有物件同一套霧面、頂點色、柔和光線 | 漂亮的棚拍光掩飾錯形，或質感像另一款遊戲 |

如果只剩黑色剪影仍不像，先不要加配件。如果白模的頭部與肩部接得不好，換色不會救回來。如果白模已經成立、配色後卻變笨重，應檢查色塊邊界與面積，不要先改車體。

## 2. 接手：先確保做的是對的版本

1. 取得最新遠端狀態，確認來源 PR、前置模型與自己的 base 是否已合併。
2. 讀 AGENTS、CLAUDE、HANDOFF、art-style、模型格式與相關工具 README。其他 AI 沒有自動載入 skill 時，要主動讀檔。
3. 看工作登記，認領自己的檔案，使用獨立分支／worktree；不要在其他 AI 正接入遊戲的分支改造型。
4. 指定「本次目標」和「保持不動」：例如本輪只收薄色帶，已接受的殼面、風擋、燈、門窗、輪架與編組保持。
5. 找出真正前版：實際已交付的原生檔、GLB、配方、manifest、producer commit。保留後再開始改。

一開始就填這張小表：

| 欄位 | 要記錄的內容 |
|---|---|
| 本次對象 | 車型／造型研究名；不要把未確認的模型當已確認真實編號 |
| 新建或修訂 | 新建從輪廓開始；修訂列出改動區域與受保護部分 |
| 原始資料 | 每張圖／模型的來源、讀取狀態、用途、權利或使用限制 |
| 真前版 | commit、檔案位置、SHA；沒有就明說這是第一版 |
| 遊戲狀態 | 靜態研究、素材註冊、已接營運、已上真機，分別記錄 |
| 範圍 | 會改哪些配方／工具／測試／文件；是否含遊戲映射 |

**這份手冊不授權修改 GameCore、存檔、golden／replay、別人的分支或遊戲規則。** 製作素材與接入遊戲是不同工作。

## 3. 參考資料：先看懂，再開始捏

### 3.1 逐張實際查看

建立參考清單，不只列出檔名。每張至少記：

    編號：ref-front-02
    類型：實車照片／模型照片／工程圖／插畫／既有遊戲模型
    視角：正面偏右，略有俯角
    已實際查看：是／否；用何種本機工具
    可以支持：黑罩上方留白、左右燈位置、色帶包覆方式
    不能支持：真實寬高、另一側門位、被裙板遮住的軸式
    用途與限制：視覺參考；不搬圖素／mesh／品牌
    來源與 SHA：……

不能讀取圖片或 GLB，就寫「未讀取」。不能用搜尋摘要、檔名或別人說明冒充自己看過。

只有一張透視圖時，先做能確認的大輪廓，記錄資料缺口；不要靠想像補出「已確認」的另一側設備或隱藏輪組。若缺口影響整體類型或左右門側，應先找專案／可靠資料。

### 3.2 各種來源的用途不同

| 來源 | 適合判讀 | 需要保留的疑問 |
|---|---|---|
| 官方規格／工程圖 | 尺寸、軸距、編組、設備規格 | 圖是否同一年代、同一改造型 |
| 多視角實車照片 | 外殼、輪廓、門窗、可見設備 | 透視、焦距、遮擋、景深與拍攝變形 |
| 實體模型照片 | 色塊、結構分區、車頭形狀的輔助理解 | 模型可能縮短、誇張細節或不同尺度 |
| 側面插畫／示意圖 | 車種次序、方向與大致設備差異 | 可能非工程比例；有些圖明確標示虛構編組 |
| 私庫 GLB／原生模型 | 在本機旋轉，看各斷面、裝配與建模方式 | bounds 可能未校準；作者／授權／製作方式須確認 |
| 已接受的遊戲車輛 | 色票、霧面、光線、細節密度、遊戲尺度 | 不是新車的車體、車頭、門窗、底盤或編組模板 |

先查專案規格與有來源資料。沒有可靠尺寸時使用相對比例，明確寫「比例推估」；例如「鼻長約占車身長度的某段」，而不是把透視像素比直接換成公尺。

本案使用者允許沿用 Codex 製作的車輛，其他來源模型只作參考。**這是本案的來源規則，不是跨專案通用授權。** 新任務先讀當次使用者與 repository 的規則。

### 3.3 建模前特徵表

| 項目 | 至少要回答 |
|---|---|
| 類別／單體或編組 | 機車、動車組、公車？各單元有哪些類型？ |
| 側／正／俯／斜輪廓 | 最大寬度在哪、鼻尖如何收、車頂何處開始下壓？ |
| 頭尾／左右差異 | 尾端是否旋轉、兩側門位是否不同、設備是否不對稱？ |
| 相對尺寸 | 長寬高、前後懸、輪徑、軸距、鼻長、設備高度；哪些有來源？ |
| 門窗／大設備 | 數量、位置、大小、間距、是否貼合車身？ |
| 走行與接點 | 軸數、輪距、轉向架、車底高度、風琴／連結器、軌面基準？ |
| 缺口 | 哪些不可見、只是補全假設、要向接手者交代？ |

表格寫完就繼續製作，不把它當等待造型批准的關卡；只有必需資料確實缺失時才釐清。

## 4. 單位、軸向與預算先定好

本專案的最終原生模型使用公尺：+X 前、+Y 左、+Z 上，軌面／地面 Z=0。

StationKitBuilder 的製作空間則是 x 前、y 上、z 右。`Model.flat` 轉換一次：

    native = (builder.x, -builder.z, builder.y)
    glTF   = (native.x, native.z, -native.y)

不要因為 GLB 看起來躺倒就再隨手旋轉，造成原生與 viewer 各用一套座標。位置、法線、朝向與組裝平移都要遵守同一份契約。搬到其他引擎時重新讀取其規定，不照抄本表。

先預留三角數，而不是建到最後才硬砍：

| 預算 | 含義 |
|---|---|
| 單檔格式上限 | 本案 M3DM v1 每檔最多 15,000 三角，見 Map3DModelFile |
| 每節展示預算 | 依車種複雜度與觀看距離決定，不等於單檔上限 |
| 全編組／全場景預算 | 要乘上節數、同時出現的列車數、燈光與其他物件 |
| 遠景預算 | 保留輪廓和大色塊，減少窗框、輪架、小設備；需測試切換 |

「沒超過 15,000」只代表能進該格式，不代表手機跑得順。700T 的高細節十二節約 7.45 萬三角，是近景個案，不能給所有普通車輛照抄。

## 5. 第一遍只做大形體

順序固定為：

    車身長寬高 → 側／正／俯主輪廓 → 頭尾曲面
    → 底盤與輪組 → 門窗與大型設備 → 細節

第一遍可以只有殼、車底與輪組佔位。用白模與剪影看：

- 側面：鼻長／鼻高、前後懸、車頂下壓起點、底盤是否過厚。
- 正面：肩寬、車頂圓角、中央鼻罩與下方外唇的寬度關係。
- 俯視：鼻尖是圓、尖、寬扁還是過長？最大寬度是否提早塌掉？
- 斜視：以上幾個斷面能否連成自然的一個形體？有沒有局部接成階梯？

不要在殼形還錯時做雨刷、鉚釘或貼字。增加細節通常會讓錯形更難辨識，也增加返工成本。

### 5.1 用斷面生成長車體

對列車／公車這類長物件，可沿 x 軸安排斷面站位。每站保存頂高 H、半寬 W、底高 B，必要時另存肩部寬度／高度。

一種圓角斷面的製作空間公式：

    lateral(a) = W × sign(cos a) × abs(cos a)^p
    height(a)  = B + (H-B) × (0.5 + 0.5 × sign(sin a) × abs(sin a)^q)

相鄰斷面對應頂點相連，端面封閉。p、q 控制斷面飽滿程度；1 接近橢圓，小於 1 會使側／頂更平、更像圓角車體。這是建模工具，不是真實車型的通用工程公式。

要點：

1. 直車身可以少放斷面；駕駛艙轉折、肩部與鼻尖要加密。
2. 不要用一條「從車頂直插鼻尖」的斜面代替有分段的鼻形。
3. H(x) 與 W(x) 分開控制。鼻頂下降，不代表下方肩部要同步收成細針。
4. 線性分段能快速控制輪廓，但站位太少會顯出折線；平滑曲線也可能過衝，須看白模。
5. 鏡像對稱只用在來源支持的區域；設備與車門不必跟著鏡像。

### 5.2 車頭要分清中央鼻罩、肩部、前唇、下裙板

「鴨嘴」不只是把整個鼻子拉長。先判讀哪一層向前或向外突出：

- 中央鼻罩：由駕駛艙向前下降，可能比肩部更窄。
- 左右肩部：在中央已收窄時仍保持一定寬度。
- 前唇：接近軌面的圓鈍外緣，不應變成扁平鏟子。
- 下裙板：包覆底部並接回車身，不能靠懸空的盒子假裝有結構。

可用獨立的縱向／高度包絡控制肩部，讓它在指定高度附近保寬，到了鼻尖自然消失。包絡的起點與終點要平順，不能在車身接點突然鼓一包。

這種做法的價值是「分開控制相互不同的曲率」，不是把 700T 的所有控制點套給 N700S、機車或公車。

## 6. 曲面怎麼接得自然

外觀上的平滑，至少有三件事：

| 層次 | 要看什麼 |
|---|---|
| 位置連續 | 接點沒有裂縫、台階、浮片 |
| 斜率連續 | 側面／俯視的輪廓不突然改方向 |
| 視覺連續 | 分色、窗帶、肩線與表面一起走，不製造假折線 |

可用 `ease(t)=t²(3−2t)` 連接兩個高度／寬度；它在兩端的斜率為零。若接的原曲線不是水平，應使用符合實際端點斜率的曲線，不要以為任何 smoothstep 都能接好。

每調一段，重看側與俯兩個正交方向。只在斜視調到順，常會把另一方向拉扁。

法線與真實形狀也要分開：平滑法線可能把錯形暫時藏起來，卻不改剪影；本案原生用平面法線，輪廓與斷面本身必須成立。

## 7. 門窗、風擋與設備：薄、貼合、有支承

### 7.1 門與側窗

- 門葉應跟隨車身側面。先用正確位置和比例，再加薄框／中縫／把手。
- 框與中縫保持窄，不要把灰框做成主體；每個細框也有三角成本。
- 圓角用真正的輪廓頂點生成，並檢查大圖與縮小後的辨識。
- 玻璃和門板不能只是飄在殼外的平面；要有厚度／背板／接觸。
- 車側有曲率時，依高度計算側面位置，不能把所有窗都擺在同一個外推平面。

### 7.2 車頭黑罩與風擋

黑罩不是駕駛室高度的替代品。分別控制：

1. 上方白車身留邊。
2. 罩體在正面／俯視的寬度、上下長度、圓角與下側收窄。
3. 真正玻璃的位置及薄緣。
4. 下方燈區的分布與間距。
5. 雨刷及支點；只有在主形成立後才加。

用參數面 P(u,v) 跟隨鼻面產生罩體，沿表面法線做小偏移與實體厚度。不要把平面黑色 billboard 壓在曲面上，也不要整塊下移到車身裡。

如果殼面有後續變形，玻璃與設備必須跟著最後的殼面更新，再驗證背板距離與穿模；不能只依據最初的未變形殼。

### 7.3 輪組、裙板與車頂

- 輪徑、軸數、軸距、轉向架中心、前後懸分別核對。
- 輪胎截面要包含真正最低點；只看 bounds 的 Z=0，不能證明每個輪子都貼軌。
- 裙板要在正面遮住合理的上部輪架，在側面保留真實開口與輪組淨空。
- 不能把整個底盤加厚，來掩飾車殼與輪組不協調。
- 集電設備、空調、冷卻箱、絕緣支承要有安裝結構；不要只放幾根浮空桿件。
- 看不到的車底管線可簡化，但必須標為補全／資料不足。

公車另核對車門側、軸數、輪距／軸距、前後懸、風擋與大型車頂設備；不能直接把列車縮短當公車。

## 8. 配色不是最後隨手填色

先採用專案既有色票，通常以車身底色、主帶、深色玻璃／裙板、少量燈色建立層級。用色數量不是固定規則，重點是大色塊不互搶。

在相同光線下問：

- 第一眼看到的是車體輪廓，還是一大片過大的色帶／黑罩？
- 色帶在正面中央應是窄邊，還是寬板？兩側是否不同？
- 從側面接回直車身時，線條是否突然上升再下降？
- 俯視會不會因色帶過寬，讓鼻尖看起來變胖或變尖？
- 灰階／小圖下，白身、玻璃、裙板和設備還分得開嗎？

新的顏色組合按專案規則計算對比，記錄「未打光基礎色」與實際渲染條件，不能把基礎 sRGB 對比說成所有打光像素或真機都達標。

### 8.1 曲面色帶直接切殼面

本案用頂點色／單面色，不貼照片。可定義分色場：

    d(P) = P.height - boundary(P.forward, P.lateral)
    白區：d >= stripeWidth
    細線：0 <= d <= stripeWidth
    主帶：d <= 0，另受下裙板色界限制

邊界需要隨鼻與肩部包覆，不能只沿全車畫一條水平裁切線。相同顏色也必須核對面積；「選對綠色」不代表「綠色大小正確」。

**穩定切分原則：**

1. 對原始三角的三個頂點計算一次分色值。
2. 在線性三角內，用這些值切出色區；切點 t=(level−dA)/(dB−dA)。
3. 新交點保存精確的 level，供下一次切細線使用。
4. 共享邊用一致的端點排序與運算，避免兩邊算出不同交點。
5. 等於色界的頂點、平行邊、極短邊、近零面積都要明確處理。
6. 不在新交點重新計算原本的非線性場，否則可能把同一色界又切一次。
7. 完成後檢查封閉有向邊、退化面、共面覆蓋與原殼面積。

700T 個案用 1 微米級分色值近界處理；這是該 Float32／公尺管線的實作選擇，不是通用建模精度。別把它當成模型具工程級精度的證明。

只改色帶時，應能用實際三角證明新面仍在原殼面上、覆蓋一致。不要為了顏色把殼一起改胖，也不要用貼近殼面的重疊色片造成閃爍。

## 9. 列車編組要當獨立結構核對

先列單元表，再生成完整編組：

| 欄位 | 例子／要求 |
|---|---|
| 單元 ID／種類 | 頭車、中車、集電車、尾車；依來源細分 |
| 長度與基準 | 單元殼長、連結器範圍、共同軌面／車身中心 |
| 次序／朝向 | 哪一端向前、尾車是否已旋轉 |
| 變換 | 每節實際平移與旋轉，不能只寫「排成十二節」 |
| 間距／接點 | 殼隙、風琴、連結器與相鄰設備淨空 |
| 差異與假設 | 中車不同門窗／設備是否有完整資料？ |

中間單元不得殘留駕駛窗或頭燈。尾車若已在原生旋轉 180°，組裝不要再轉一次。獨立單元、完整編組、GLB、viewer 都用同一份最終單元及變換表。

完整編組超過單檔原生限制時，用引擎支援的組裝格式或多實例契約；不能把檔頭的三角上限改大，卻宣稱遊戲能載入。

## 10. 每一輪都看實際原生模型

~~~mermaid
flowchart LR
    A[實際看參考並填特徵表] --> B[比例與主曲面]
    B --> C[原生配色／白模／剪影四向]
    C --> D{有主要偏差}
    D -->|有| B
    D -->|無| E[門窗輪組設備與分色]
    E --> F[同相機真前後與遊戲尺度]
    F --> G{仍有可見問題}
    G -->|有| E
    G -->|無| H[匯出與獨立驗證]
    H --> I[來源／SHA／ZIP／交接]
~~~

渲染一定來自實際原生頂點。概念圖、另一套手工簡化 mesh、用 PNG 拼出來的車頭，不能代替模型預覽。

固定做：

| 模式 | 側面／正面／俯視／代表性斜視要抓的問題 |
|---|---|
| 配色 | 色塊比例、門窗、設備可讀性、色界接點 |
| 白模 | 真正曲面、厚度、接觸、台階、穿模與外掛盒感 |
| 剪影 | 長寬高、鼻形、肩部、輪廓辨識 |
| 遊戲尺度／灰階 | 縮小後是否仍清楚、細框是否變成雜訊 |

不要只看英雄斜視。不能用「渲染成功」代替「自己看過渲染」。

每輪外觀紀錄至少三欄：

    已符合：本輪已修對的部分，附視角／檔案
    仍不符合：可見但尚未解決的問題
    資料不足：不能靠目前來源確認的部分

發現主要偏差就回到對應層修正，再重新渲染。把問題寫成「待優化」卻照常批次交付，並沒有通過外觀驗收。

## 11. 真前後對照與局部修訂

同時固定：模型單位、相機朝向、相機中心、投影／焦距、取景範圍或公尺／像素、燈光、材質、底色。兩張各自 auto-fit 的圖不能比較長短與胖瘦。

保存真正前版，不准事後重捏一個更差的「前版」。如果需要鼻部特寫，選取兩版相同空間範圍的完整三角並保留原座標，清楚標「局部」；不要拿截斷模型當完整單元。

使用者只說綠色太大時：

1. 重看參考與真前版。
2. 列出要動的白／綠／黑分色，以及要鎖住的殼、罩、燈、門窗、輪架。
3. 調色界與面積，保留同一實體殼面。
4. 重新出固定相機前後；看中央窄邊、左右肩部、車側銜接三處。
5. 用實際三角範圍、共面交疊／面積、bounds 與受保護單元 bytes 證明改動範圍。

使用者說某段形狀不對時，則要改幾何，不得拿換色充當修形。兩種修訂必須分清，所跑的稽核也不同。

## 12. 驗證要能抓到可見缺陷

驗證分開記三條線：

| 線 | 記錄內容 |
|---|---|
| 外觀 | 已符合／仍不符合／資料不足；誰看過哪些原生圖；是否有使用者認可 |
| 本機技術 | VERIFIED／UNVERIFIED、工具／版本／平台、實際輸出與限制 |
| CI／裝置 | 最新 head 的實際 CI、Simulator、真機 Metal／效能／動畫各自結果 |

### 12.1 最低技術覆蓋

- 原生讀回：位置、顏色、發光標記、法線／頂點數與預期一致。
- 幾何：有限數值、退化面、封閉有向邊、外向法線、正體積及實際 bounds。
- 接觸：玻璃背板、設備底座；輪胎實際連通件逐個貼軌，輪頂與裙板淨空。
- 組裝：獨立單元重建完整編組，與直接組裝結果核對；檢查尾車與設備朝向。
- 共存：新模型不破壞既有資產、ID、近遠景或註冊。
- GLB：用另一個 importer 讀取，核對三角、bounds、軸向、頂點色與霧面材質。
- PNG：完整解碼、透明、非空、留白、不裁邊，不只驗檔頭。
- viewer：真載入、旋轉、縮放、切方向、下載檔案並比對 hash；檢查缺件／外部請求。
- ZIP：完整解壓、CRC、檔案集合與每檔 bytes，比對最終 live 輸出。

### 12.2 加會失敗的反例

| 人為缺陷 | 檢查應抓到 |
|---|---|
| 刪一片面／反轉一片面 | 開邊、朝向或體積不對 |
| 玻璃往外移一段明顯距離 | 背板距離／實體支承不符 |
| 一節編組平移錯位 | 組裝 payload、接點或實際位置不符 |
| 輪子抬離軌面 | 該連通件最低點不是軌面 |
| 只改塗裝卻移動殼面 | 原生新舊共面覆蓋或保護範圍不符 |
| 圖片被截斷／透明丟失 | 完整解碼／alpha／邊界檢查不符 |
| viewer 下載另一版檔案 | 實際下載 SHA 與 manifest 不符 |

不要只斷言「配方裡輪半徑等於某常數」。直接檢查輸出幾何，才有機會抓到轉換、裝配與匯出造成的錯誤。

抽樣射線不是全表面碰撞證明；有向邊平衡與正體積也不能證明沒有所有自交／重疊。Linux WebGL、Blender 匯入、Xcode 編譯、Simulator 截圖都不是 Metal 真機效能驗收。

## 13. 匯出、來源與封包保持同版

建議每次修訂輸出到新資料夾：

    recipe / tools / focused tests
    models/        獨立單元原生、GLB、組裝描述
    views/         上下左右前後立體透明 PNG
    previews/      配色／白模／剪影、單元與編組、真前後、風格比較
    history/       真前版與其 manifest／來源／配方
    manifest.json  模型列表、實際 bounds、三角數、軸向、變換、SHA
    reference-review.json / source-record.json
    verification / visual-review
    index.html / offline viewer
    SHA256SUMS / 完整 ZIP

配方獨立檔案，入口只做必要註冊，重建工具放自己的目錄；不要把一整台車塞進中央入口。

程式碼與原生／預覽要有真實 producer commit。做法是先穩定生成流程、完成必要驗證並提交會影響輸出的來源，再用該 commit 重建／核對來源 bytes 與 metadata；如果有任何輸出來源變更，就重新驗證，不把未提交工作區冒充該 commit 的結果。

封包常見的最後一個陷阱：

1. manifest 寫入 producer。
2. viewer 若內嵌 manifest／模型，重新產生。
3. 跑實際 viewer 下載檢查。
4. 打 ZIP 並完整解壓逐檔比對。
5. 再測最終 ZIP 按鈕。
6. 確認下載測試沒有改到 ZIP 裡的 verification／log；若改了，要重包並再次比對。

不必追求把 ZIP 自己的 hash 塞進自己，造成遞迴依賴。可把最終 ZIP hash 放在 ZIP 外的驗證紀錄／PR。

本案公開庫只放配方、工具、必要測試、文件和一張總覽；完整模型、七向圖、viewer、比較、來源與 ZIP 放私庫。其他專案依其政策配置，但私有來源、個資、真實商標不得意外公開；不得把私有素材送外部生成服務。

## 14. 手機遊戲接入是下一道驗收

「素材註冊」只代表模型可被找到；「營運映射」才決定遊戲中哪列車使用它；「接入」後還要驗證：

- 單節長度、共同地面／軌面、朝向與縮放。
- 台車中心對齊裙板開口，轉彎、坡度與編組間隙。
- 前後燈色、夜間發光、集電設備與動畫。
- LOD、近景距離、遠景替代、同時多列車的記憶體／CPU／GPU。
- Simulator 與真機 Metal；實際遊戲鏡頭下的顏色與辨識。

不要為了讓漂亮素材立刻出現，就順手改 GameCore、編組資料、存檔或 fixtures。把素材契約交給已認領整合的人，讓整合依專案規格完成。

700T 個案的素材交付與後續接入時間、來源與限制，見 [實例文件](CASE_STUDY_700T.md)；不要把歷史「當時仍為靜態」當成永久未接入，也不要把之後有人接入當成之前已做過真機驗證。

## 15. 常見問題該改哪一層

| 看見的問題 | 先查 | 優先修法 |
|---|---|---|
| 車頭像尖錐／鉛筆 | 俯視 W(x)、中央罩與下肩寬度 | 分開收中央罩與保留下肩 |
| 鼻子像鏟子／厚板 | 側面鼻長、前唇上下厚度 | 修整鼻尖曲率；別整車往前拉 |
| 黑色方框太高 | 正面罩高、上方白邊；俯視罩長 | 沿鼻面重映射罩輪廓，不整塊塞入車身 |
| 主色帶忽上忽下 | 正交側面色界與斜率 | 以連續色界切原殼，保持接點方向 |
| 綠色很大、車頭笨重 | 正面中央厚度、俯視白區、肩部 | 擴白／縮綠，保留窄邊與肩部，先不要改殼 |
| 中央色界冒小突點 | 小端面局部寬度正規化、切分交點 | 平順調整色界的尺度；保存精確切值，重新看正／俯視 |
| 門像貼上去的箱子 | 門厚、外推距離、側面曲率 | 薄門葉、細框、沿殼面定位 |
| 輪架從車頭整片露出 | 正面裙板包覆與輪組高度 | 修真實下殼與開口，同時重驗輪頂淨空 |
| 窗在空中／穿進殼 | 最終變形殼與玻璃取樣面不同 | 更新貼合面與背板，再做射線／接觸檢查 |
| 小圖很髒 | 細節尺寸、框線、材質與對比 | 刪低價值細節，保留主輪廓與大設備 |
| GLB 好看、原生不一樣 | 軸向、法線、材質、是否兩套幾何 | 從同一最終原生轉出並逐項核對 |
| 技術全綠但看起來不像 | 參考是否真看過、驗收相機、主輪廓 | 回到特徵表和白模，不加更多容易通過的測試 |

## 17. 在本專案怎麼實際執行

### 17.1 程式與工具各負責哪一層

### 17.2 既有 700T 工具鏈的執行順序

以下是**已具備這批來源紀錄與合法工具環境時**的操作順序，不是任意新車的一鍵指令。先依工具 README 確認 Chromium／Playwright、Python 套件、Blender 與 Swift 路徑；輸出放公開庫外。本機路徑請換成自己的目錄。

新車需另寫 export／manifest／單元表／相機與來源欄位；不能直接沿用這支工具的固定 ID、十二節排列、參考 SHA 或歷史回歸門檻。尤其 bundle.py 會讀本批的 reference-review.json 與 reference-study，這些內容必須是實際已查看、可核對的資料。

在已完成並提交會影響輸出的最終來源版本、repository 根目錄執行：

~~~sh
export PATH="<你的 Swift 6.4 安裝目錄>/usr/bin:$PATH"
model_out="/工作目錄/公開庫外/本輪新輸出"
model_prior="/工作目錄/真正前版輸出"
model_producer="$(git rev-parse HEAD)"

swift build --build-tests -Xswiftc -warnings-as-errors -j 4
swift test --skip-build --filter 'Map3DTrainShapeRefreshTests|Map3DModelFileTests|Map3DModelTests'
tools/train-shape-refresh/export.sh "$model_out"
node tools/train-shape-refresh/review.mjs "$model_out"
~~~

**此時實際開圖，看側正俯斜配色／白模／剪影。** 有主要問題就回去修、提交新來源並重做，不直接往下批次出圖。

~~~sh
node tools/train-shape-refresh/verify.mjs "$model_out"
python3 tools/train-shape-refresh/wheel-audit.py "$model_out"

# 只有第十版這種「保持原殼、只改鼻部分色」且有正確前版時才跑：
python3 tools/train-shape-refresh/livery-audit.py "$model_out" "$model_prior"

node tools/train-shape-refresh/render.mjs "$model_out"
node tools/train-shape-refresh/feedback-compare.mjs "$model_out" "$model_prior" nose
node tools/train-shape-refresh/feedback-compare.mjs "$model_out" "$model_prior" cab
node tools/train-shape-refresh/feedback-compare.mjs "$model_out" "$model_prior" formation
blender --background --python tools/train-shape-refresh/glb-audit.py -- "$model_out"
python3 tools/train-shape-refresh/verify-png.py "$model_out"
~~~

再實際查看完整圖、單元／編組、真前後與風格比較。更新外觀紀錄、真前版保存、來源與必要證據；這些檔案不能在最後 ZIP 後悄悄修改。

~~~sh
python3 tools/train-shape-refresh/bundle.py "$model_out" "$model_producer"
node tools/train-shape-refresh/standalone.mjs "$model_out"
node tools/train-shape-refresh/browser-check.mjs "$model_out" --standalone
node tools/train-shape-refresh/browser-check.mjs "$model_out"
python3 tools/train-shape-refresh/bundle.py "$model_out" "$model_producer"
node tools/train-shape-refresh/browser-check.mjs "$model_out"
~~~

第一輪 bundle 使 viewer 能驗真 ZIP；第二輪把內嵌 producer 的 viewer 與下載驗證紀錄納入最終包。最後還要逐一確認 ZIP member 仍等於 live bytes，因為 browser-check 可能重寫 verification；若不同就重包，不能只靠命令 exit 0。

前後兩次 bundle 的 ZIP hash 不必一樣，因封包時間與內容可能已更新；要核對的是**最終交付 ZIP**的內容與實際 hash。原生／GLB／PNG 的資料、producer 與實際來源則必須一致。
