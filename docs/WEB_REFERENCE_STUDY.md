# 網頁參考研究

專案作者提供了一份自製網頁版交通經營遊戲的快照，這份文件記錄從中學到什麼、打算吸收哪些想法，以及它們各自屬於 [ROADMAP](ROADMAP.md) 的哪個 Stage。這個網頁遊戲有地鐵、高鐵、航空三種模式。

作者的參考資料有兩個網站，要分開判斷，不能把一個的結論套到另一個：

- `Ci/`：這份文件研究的交通經營遊戲（地鐵、高鐵、航空）。
- `Railway/`：台灣鐵道的班表與 3D 股道網站（`rail-3d/`）。Stage T–W 對照的是它的實體層，見 [RAILWAY_REFERENCE_MAPPING.md](RAILWAY_REFERENCE_MAPPING.md)。

## 結論

1. **參考的地鐵模式沒有時刻表。**
   - 玩家設定每條線在高峰、平峰、低峰的上線列車數。
   - 班距由「往返一圈的時間 ÷ 列車數」推導，最短班距限制能加幾台車。
   - 只有高鐵模式用逐班的時刻表，而且可以「每方向自動產生 N 班」，並配對回程。
   - 我們的 Stage O、P 已經是逐班時刻表的執行層。Stage Q 的服務模式會把「時段 × 列車數」展開成具體的班次，交給 Stage P 執行。這樣兩種玩法共用同一個執行核心。
2. **子系統分得很清楚。** 服務規劃、列車移動、客流、經濟、事件與呈現各自獨立。我們要守住同樣的邊界：基礎設施不是服務，服務不是交通控制，交通控制不是乘客需求，乘客需求不是城市成長，UI 不是權威狀態。
3. **乘客以群組儲存，不是一人一個物件。** 需求以整數釋出並保留餘數，玩家還看得到守恆稽核。Phase 5 採用群組（cohort）與精確的整數守恆。
4. **效能被當成產品功能。** 參考遊戲有這些做法：
   - 客流派發分片，並設有預算；
   - 依縮放層級決定顯示多少細節；
   - 拖曳時隱藏覆蓋層；
   - 把重的計算交給背景 worker。

   但它的分片預算會依裝置的畫格時間改變，所以模擬結果取決於裝置。我們只讓**呈現**隨效能調整，模擬結果永遠與裝置無關。
5. **分析就是玩法。** 參考遊戲讓玩家看到滿載率、候車人數、月台使用率、未滿足的需求、守恆稽核與帳本對帳，所以玩家能找出網路差在哪裡，而不是只看到一個分數。
6. **這個遊戲（`Ci/`）沒有實體鐵路層。** 它沒有車廠、號誌、閉塞或待避站；快車與慢車互相「看不見」，而不是真的待避。2026-09 對私有 repo 的快照重新確認過：UI 字串與作者的程式裡沒有待避、越行、閉塞或號誌。舊研究推論的「同線同向防撞」（見下面的地鐵服務規劃），在目前的快照裡只剩常數定義（`MIN_TRAIN_GAP`、`SLOW_FACTOR` 等），找不到使用的地方，無法再確認。
   - 這個結論只適用 `Ci/`。作者的 `Railway/` 網站有同向待避、單線交會、排定的等待與股道指派，Phase 4.6、4.7 對照它（[RAILWAY_REFERENCE_MAPPING.md](RAILWAY_REFERENCE_MAPPING.md)）。

## 各子系統

下面各節的「採用」與「不採用」是 faithful-port 規則之前做的決定，Stage Q–S5 已經照它們實作。之後的新 Stage 照上面「來源與使用方式」的規則。若要把已實作的部分改回參考的做法（例如以秒計的停留、寫死的時段），另開 PR，並逐項說明 golden 與 property digest 的變化。

### 1. 地鐵的服務規劃

**觀察**

- 每條線在高峰、平峰、低峰各有上線列車數（`metro.service.peak_trains`、`metro.service.off_peak_trains`）。FAQ 說明「設定高峰、平峰和低峰的上線列車數」（`guide.metro.faq.3.desc`）。
- 平日與週末的列車數分開設定（`metro.service.weekday_trains`、`metro.service.weekend_trains`）。
- 每條線有營運時間，也可以 24 小時營運（`metro.line.opening_hour`、`metro.line.closing_hour`、`metro.line.service_24h`）。收班最晚可以到次日 06:00。
- 加車會被「發車間隔或共線容量限制」擋下（`metro.edit.cap.increase_blocked`）。
- 交路（短程折返）：
  - 一條線可以有多個交路，每個交路有起訖站和自己的列車數；
  - 所有交路必須連續覆蓋整條線，不能留下沒覆蓋的區段（`metro.routing.coverage_gap`）。
- 快車：
  - 從整條線依序挑出停靠站，至少 2 站，有自己的列車數；
  - 說明文字是「擁有獨立路權，與慢車分開計算發車間隔」（`metro.express.help`）；
  - 同一條線裡，快慢車之間的換乘不算作轉乘。
- 支線與主線直通、環線的內外環。
- 車型（A、B、C 等）、編組輛數與每列車容量。改變編組會消耗「輛」的配額。
- 列車資訊顯示它的交路、目前區間、滿載率，並標出「長時間停站（>45 秒）」。
- 參考沒有車廠、號誌、閉塞或待避站的介面。

**推論**（信心：高）

- 時段是固定的：
  - 07–10 時與 16–20 時是高峰；
  - 00–07 時與 21–24 時是低峰；
  - 其他時間是平峰；
  - 營運時間以外沒有列車。
- 派車以**目標列車數**為準，而不是時刻表：
  - 每個模擬分鐘判定目前的時段。
  - 時段改變而需要增車時，把新車插進最大的空檔，並放在列車較少的方向。新車直接出現在線上，不是從車廠開出。
  - 需要減車時，把多出的列車標記為「到終點站後退出」，讓它們跑完這一趟。
- 班距 = 往返時間 ÷ 列車數：
  - 往返時間是各區間的行駛時間，加上中間站的固定停留（36 秒）與終點站的停留（42 秒），來回各算一次。
  - 最多能放的列車數，是讓班距仍 ≥ 1.5 分鐘的最大值（以二分搜尋求出）。
- 交路或支線重疊的區段，把各自的頻率相加後，再檢查同一個最短班距。
- 防撞只在同線、同方向、同種類（快或慢）的列車之間生效：
  - 只有前車在同一個站間區間、或正停在下一站時，後車才看得到它；
  - 距離太近時停車，較近時等比例減速；
  - 快車與慢車彼此看不見，這就是「獨立路權」的實作方式；
  - 共線區段另外以時間預約保留空間。

**採用**

- 玩家編輯的對象是**服務模式**：時段 × 列車數，以及營運時間。班距由系統推導並顯示，不要求玩家自己算。（Q2、R）
- 班距推導、最短班距上限、交路必須覆蓋整條線、重疊區段的頻率檢查，全部改用整數分鐘。（Q2、Q3）
- 減車時讓多出的列車跑完這一趟、在終點退出，而不是瞬間消失。（Q2）
- 交路以時刻表車站的**索引區間**表示，快車以停靠站的子集合表示。（Q3）

**歷史上未採用（目前可依需要直接移植／整合）**

- 列車憑空出現在線上。我們的列車必須實體放在鐵軌上（決策 14），所以增車只能從已放置的列車，或之後的車廠開始。
- 以連續距離減速的防撞，以及快慢車「互相看不見」。這些改由 Phase 4.5、4.6 的佔用、進路與 dispatcher 決定。
- 以秒為單位的固定停留與加減速曲線。我們用整數分鐘與 rate（決策 15）。
- 寫死在核心裡的時段。時段由玩家設定，或由可以修改的預設值決定。

### 2. 高鐵的服務規劃

**觀察**

- 每一班車都有明確的時刻表，包含停靠站、停留與出發時間。
- 可以「每方向自動產生 N 班」（`hsr.auto_generate`），而且每班配對回程（`hsr.detail.return`）。
- 報告顯示月台使用率（已用的月台分鐘 ÷ 可用的月台分鐘），以及每條路線沒有被滿足的需求。

**採用**

這是最接近我們 Stage O、P 的模式。Q1 的折返與重複運行、Q2 由服務模式自動產生班次，對應的就是「自動產生班次」與「配對回程」。月台使用率會成為 Stage S2 之後的分析指標。

### 3. 乘客流

**觀察**

- 需求來源：
  - 真實的人口網格、普查資料，以及每小時的出行需求；
  - OD 圖層，線條越粗越紅表示通勤的人越多；
  - 這些客流模型由伺服器計算。
- 每個車站有 24 根每小時進出站的長條，玩家可以拖曳調整。也可以套用辦公、住宅、景點、商場四種預設，套用後維持該站原本的全日總量（`metro.station.custom_ridership_help`）。
- 可以開關「模擬地鐵週客流變化」（`menu.settings.metro_weekly_demand`）。
- 車站會顯示候車人數，太擁擠時發出通知。車站可以切換成限流或關閉。
- 轉乘的種類：
  - 同月台或跨月台；
  - 經由通道步行；
  - 距離太遠的轉乘連結會被自動移除。
- 行程估計包含候車與轉乘時間。
- 票價可以是單一票價、依距離分段（1–64 段），或票價表。改變票價會影響「新收入與之後的需求」（`metro.fare.help`）。
- 守恆稽核直接顯示給玩家看：「進站 = 上車 + 候車 + 出站 + 浮動」（`notice.audit.171`）。

**推論**（信心：高）

- 航空的乘客以**群組**儲存：
  - 每組只記人數、起訖、建立時間、到期時間、狀態與航段，不存個人；
  - 資料以欄位陣列（每個欄位一個陣列）配置成固定大小的區塊；
  - 人數歸零的群組被回收；
  - 個別的乘客（姓名、座位）只在畫面上生成。
- 候車佇列：
  - 每個 OD 各有一條先進先出的佇列，同一小時到達的人併入同一組；
  - 上車時先上最早的組，以 (小時, ID) 決定先後；
  - 存檔時做差值編碼並加上 checksum，讀檔時嚴格驗證。
- 需求釋出：
  - 每個 OD 有一週的總量，乘上「星期 × 小時」的權重後，做成一條累積曲線；
  - 每次釋出「目前累積量 − 已釋出量」，取整數，小數部分保留並寫進存檔；
  - 同時發生的事件依 (時間, 起點, 迄點) 排序，順序是固定的。
- 地鐵的路徑選擇不在每個 tick 計算，而是由伺服器預先算好每個 OD 的幾個選項，每個選項都有選擇機率、時間與轉乘次數。
  - 把乘客依機率分配到各選項時，有一處用最大餘數法並以索引決定平手，是 deterministic 的；
  - 另一處分配餘數時使用系統亂數，**不是** deterministic。
- 車站佇列依方向與目標分開，有收容上限，超過的人只計入溢出計數。
- 列車只記錄「在哪一站下車」的人數分組。
- 容量 = 每輛定員 × 輛數，允許小幅超載。
- 高峰係數與星期係數會把需求在一天和一週內重新分配，但維持總量。
- 票價彈性用浮點公式，網路超過 300 站時暫停。
- 守恆稽核有容差：差距在 5% 以內算通過，超過 10% 只記錄警告。

**採用**

- 用群組代替個人，例如 `PassengerGroup { 起點, 迄點, 時段, 人數 }`。個別乘客只存在畫面上。（5B–5E）
- 以整數釋出需求並保留餘數，讓一天的總量完全精確。同時發生的事件依 (tick, 起點, 迄點) 排序。（5B）
- 在沒有城市模擬之前，用車站類型的每小時需求曲線作為需求來源（住宅、辦公、商業、景點），權重用千分比整數。（5A）
- 路徑選項在網路或服務改變時預先計算，比較成本時用整數分鐘：候車、乘車、轉乘懲罰。分配人數一律用最大餘數法並以索引決定平手。（5C）
- 車站佇列依方向與目標分開，有收容上限，被拒絕的人記入溢出計數。列車記錄「在哪一站下車」的人數。（5D、5E）
- 容量 = 輛數 × 每輛定員。依距離把轉乘分成同月台與步行通道等等級。同一條線裡快慢車之間的換乘不算轉乘。（5E、5F）
- 單一票價與距離分段票價，以 `Money` 整數計算。（5G）
- 守恆稽核：產生的人數 = 出站 + 候車 + 車上 + 到期 + 被拒，**精確相等**，並寫成 property 測試。（5B 起）

**歷史上未採用（目前可依需要直接移植／整合）**

- 真實人口資料與伺服器計算的 OD。我們離線運作、以格子地圖為基礎，而且這類資料有授權問題。需求改由 5A 的車站類型曲線提供，之後由 Phase 6 的城市提供。
- 用系統亂數分配餘數，以及浮點係數與浮點彈性公式。如果需要，改用千分比整數或查表。
- 有容差的守恆稽核。

### 4. 效能

**觀察**

- 有「性能模式」：開啟後把客流派發的分片預算降低，以減輕高峰時的 CPU 負載（`menu.settings.performance_help`）。
- 大型網路有保護措施：超過 300 站時暫停票價彈性；也可能暫停編輯，直到改用輕量的客流模型。
- 說明建議拖曳地圖太慢時，先縮小到車站與列車變少再拖曳。

**推論**（信心：高）

- 分片預算依平滑後的畫格時間自動降低。處理順序用一個與總列數互質的步長交錯走訪，所以即使某一片中途被截斷，涵蓋範圍仍然平均。
- 每一幀能推進的真實時間有上限，超過的部分直接丟棄，不補跑。
- 顯示的細節依縮放層級分成幾級：
  - 縮到很小時隱藏車站；
  - 中間的層級只顯示轉乘站；
  - 放大後才畫出月台；
  - 曲線的精細度也分低、中、高。
- 拖曳時完全不畫列車、標籤與候車人數的覆蓋層，拖曳結束有防抖動與逾時保護。重繪有頻率上限，畫面外的物件不畫。
- 航空計算在 Web Worker 執行，資料分塊傳送並限制同時在途的數量。每個結果帶有世代計數，過期的結果直接丟棄。

**採用**

- 依縮放層級的細節分級、拖曳時隱藏覆蓋層、只畫畫面內的物件，以及以（世界版本, 縮放層級）為 key 的路徑快取。（R、Phase 8）
- 重的計算（路徑選項、需求）對不可變的 `Sendable` 世界快照在背景執行，帶世代計數，過期結果丟棄。結果仍由唯一的權威擁有者套用。（5C 起）
- 限制每幀補跑的時間：已經做到。`GameSession` 單次最多換算 500 ms，背景時停止、回來不補跑（決策 12），和參考的上限是同一個想法。

**歷史上未採用（目前可依需要直接移植／整合）**

- 依裝置的畫格時間改變模擬的工作量。分片可以，但同一個 tick 的**結果必須與分片方式和裝置無關**。性能模式只能影響呈現。
- 網路變大時暫停遊戲規則。改為量測後調整資料結構。

### 5. 分析

**觀察**

- 客流儀表板：
  - OD 弦圖；
  - 昨日每小時的進出站；
  - 線路強度；
  - 高峰上線列車數與轉乘量；
  - 可以排序的車站表。
- 列車面板：滿載率、定員、目前乘客與長時間停站。
- 車站面板：候車人數與營運狀態（正常、限流、關閉）。
- 月台使用率、未滿足的需求、需求滿足率、七日平均載客率。
- 「列車已滿」「月台擁擠」的通知，以及擁擠程度與載客量的地圖圖層。

**採用**

- 指標優先由狀態**推導**，不另存：上線列車數、班距、滿載率、候車人數、月台使用率與未滿足的需求。要看歷史時，才存每日壓縮的彙總（例如每站 24 個整數）。
- 通知有冷卻時間，不洗版。
- 各指標在需要它的 Stage 才加入：R（服務）、S（資源）、5D、5E（候車與滿載）、Phase 7（帳本）。

### 6. 經濟

**觀察**

- 有「經營」與「創造」兩種模式，切換到創造模式後不能回頭。會破產。
- 建設用**配額**（車站數、路線公里、車輛、月台等），而不是直接扣現金。沒用完的配額可以退，配額不足時不能復原。
- 帳本分類：
  - 每小時的淨收入；
  - 每日的能源與人事成本；
  - 擁擠退款與賠償；
  - 路網費用與補貼。
- 帳本明細會標示「已對帳」，或列出差額。
- 高鐵以每公里或每百公里定價，並提供建議價。
- 沒有看到貸款。

**推論**

- 結算是事件形式，每一期有唯一的 key，重複結算會被拒絕。（信心：中）
- 分攤成本時用最大餘數法，讓各項加總剛好等於總額。（信心：高）

**採用**（Phase 7）

- 帳本的各類別加總必須精確等於總額，全部用 `Money` 整數。
- 每一期只結算一次（idempotent），成本分類包含人事、能源與車輛。

**歷史上未採用（目前可依需要直接移植／整合）**

- 配額制。我們維持《A列車》式的現金經濟，是否加入配額留到 Phase 7 再決定。
- 以曲線擬合的收益模型。

### 7. 事件與中斷

**觀察**

- 地鐵：客流激增、展覽。事先預告「{n} 天後開始、持續 {m} 天」，期間提高某一站的需求。
- 航空：天候關閉、油價漲跌、節慶等事件。設施過度擁擠時取消班次，並退款、賠償。
- 設定裡可以關閉事件。

**推論**（信心：高）

- 亂數以「種子 + 用途」的雜湊產生，最久沒被選中的地點優先。
- 事件狀態有版本與 migration，另有待確認的通知佇列。
- 但種子在第一次建立時混入了系統亂數。

**採用**（Phase 6、7）

- 事件是獨立的一層，不寫進基本的移動或服務規則。
- 亂數一律由世界裡存檔的種子，以（種子, 用途, 序號）的雜湊產生。事件事先預告。

**歷史上未採用（目前可依需要直接移植／整合）**

- 在執行期間從不確定的來源取得種子。

### 8. 存檔

**觀察**

- 下載存檔時可以選擇是否包含客流資料。
- 有分享碼、雲端存檔欄位與衝突偵測，存檔自動加密，而且有大小上限。

**推論**（信心：高）

- 每個子系統有自己的 schema 版本。
- OD 矩陣以對數尺度量化成一個位元組後壓縮。
- 存檔前會做一次來回的一致性檢查。

**採用**

- 存檔版本與 migration（已列在跨階段議題）。
- 可以重算的衍生資料不存檔，高流量的資料只在量測後才考慮壓縮格式。
- 來回檢查已經由 `PersistenceAndDeterminismTests` 與 `SaveMutationTests` 負責。

**歷史上未採用（目前可依需要直接移植／整合）**

- 把權威狀態量化成有損格式。
- 目前也不需要加密。

### 9. 城市

**觀察**

- 真實的人口圖層。
- 車站的服務範圍以半徑或距離分帶顯示。
- 每站的每小時需求預設（辦公、住宅、景點、商場）。
- 另有一張約 25 × 40 km 的虛構島嶼地圖。

**採用**（Phase 6）

- 車站的服務範圍以格子距離計算。
- 城市的土地使用取代 5A 的車站類型曲線，成為需求來源。
