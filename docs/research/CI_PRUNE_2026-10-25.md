## 4. main 每次 push 都跑「不縮減」的完整 campaign

**它守什麼**：每次合併以後，在 main 的 commit 上把整個 package 再跑一次：18 個 campaign 分片、`rest`、gate。這次的結果也是發版的前提（CLAUDE.md：發版的 commit 要有綠的完整 `ci.yml` run）。PR 已經照它的 tier 跑過（GameCore 的 PR 跑 full tier），所以 main push 多抓到的，是「PR 各自綠、合在一起才紅」的情況，加上 PR 只跑部分 tier 時漏掉的東西。

**每週**（7 天合併了 406 次，平均一天 58 次）：
- `ci.yml` 的 push run 406 個：98 個被後面的合併取代（cancelled，concurrency 的設計），304 個綠，1 個紅，3 個重跑。
- 有 Swift job 的 304 個裡，208 個跑了 full tier（另外約 100 個只改 docs 或 App，Swift job 跳過）。
- 一個 full tier 約 234 Linux 分：campaign 16.2 個 job × 13.5 分 = 219 分，`rest` 15 分。
- 合計 **48,775 Linux 分**：campaign 45,492、`rest` 3,147、changes＋gate 137。**占全部 Linux 時間的 50%**，比所有 PR 的 Swift job（46,712）還多。
- 每個 full tier 一次占 20 個 job（帳號上限 40）。一天約 30 次，每次 17–20 分，所以白天 main 幾乎一直占著 20 個 Linux runner，PR 的 full tier 只能用剩下的一半。

**合併改到什麼**：7 天的 406 次合併，用 `swift-shards.sh plan`（PR 選 tier 的同一支）逐一看每次合併改的檔：
- 最近 218 次（腳本跑太久，跑到這裡停下）：full 24 次（11%）、presentation 99 次（45%）、none 95 次（44%）。
- 全部 406 次改用路徑粗分（改到 `Sources/GameCore/`、`Package.swift`、`Tests/GameCoreTests/` 算 GameCore，會多算）：GameCore 57、GamePresentation 或資料 203、其他 146。

也就是說，**main 上 push 跑 full tier 的那 208 次裡，大多數只改了 GamePresentation**。照 PR 的規則，它們只要跑 5 個 `selected` job（GamePresentation 的測試，一個約 12.4 分），不用跑 18 個 campaign。

**選項**：
- A 維持：每次 push 都跑 full tier。
- B push 照 PR 的規則選 tier：和 push-base（上一次綠的 push run 的 commit）比，用 `swift-shards.sh plan` 決定。改到 GameCore 才跑 full，只改 GamePresentation 就只跑 presentation。每次 push 測的東西，和合併前 PR 測過的同一套規則一樣；同一個 push 包含好幾次合併時，取最大的 tier。

- D 每次 push 只跑輕的一組，完整的 campaign 每晚跑一次。
- E 給每個 campaign 做一個「縮減版」（少跑幾個種子或步數），push 跑縮減版，每晚跑完整版。現在沒有這種模式：要改約 100 個 campaign 類別的測試程式，campaign 的 digest 也要分成兩套。
