- 查閱日期：2026-10-10

- 範圍：只寫文件，不改遊戲。產出是給作者選的玩法方案（第 8 節），不是已決定的設計；沒有保留任何存檔版本、決策編號或 golden schema。

## 0. 摘要

**問題**：目前的事件全是好事（展覽、大量人潮、天燈節，決策 69、90）。中期容易變成「蓋好就自動賺錢」，玩家沒有需要應變的決定。ROADMAP 把中斷與國定假日列為缺口（Phase 5 段落、`REFERENCE_PORT_INVENTORY` 的 O4）。

**查到的重點**：

1. **參考庫能直接搬的是「事件骨架」與「資料」，不是故障模型。** 事件的亂數、節奏與提前公布，決策 69 已經從 `aviation_disruptions` 搬過來了；它還有沒搬的部分：假日表、區域天候封閉（含颱風）、燃油指數、避免同區域連續中招的規則。故障、車齡、維修、事故、地震、誤點傳播，**六個來源都沒有**（第 5 節列出搜尋範圍）。
2. **誤點傳播不用另外做。** `Railway/` 的參考只把誤點當每班車的時間位移，沒有連鎖規則（`dispatch.json` 的 `officialDelaySec` 全是 0）。但本專案的交通控制（Stage T、U、V）已經會讓後車等前車：只要有東西能讓一班車停住，後面的誤點就自己出現，`lateness(of:)` 直接量得到。
3. **故障、車齡的設計只能讀概念**：OpenTTD、OpenRCT2 是 GPL，Simutrans 是 Artistic License 1.0，都只讀概念、不複製程式碼（第 6 節）。本專案的車輛已有購入時間（`AssetRecord.acquired`）與 10 年折舊，車齡幾乎不用新存檔欄位就能推導。
4. **決定論可行，而且比 OpenTTD 容易**：事件由（種子、用途、序號）雜湊決定，和推進方式無關；故障也能做成「午夜時就決定今天哪台車、幾點壞」，不必每分鐘抽籤（第 3 節）。
5. **Q4（彈性發車）要先做**，除了「天候與國定假日的需求變化」以外的方案都依賴它（第 4 節）。

**三個方案**（第 7 節）與建議（第 8.4 節）：

| 方案 | 玩家要做的決定 | 依賴 Q4 | 規模 |
| --- | --- | --- | --- |
| **A. 車齡、故障與檢修** | 檢修多久一次、備不備車、何時汰舊 | 是（檢修會讓車離開路線） | 3 個 PR |
| **B. 天候與國定假日** | 連假和颱風前加不加班車、調不調票價 | 否 | 2 個 PR |
| **C. 颱風、地震停駛與復駛** | 預先停駛或硬開、搶修順序、要不要接駁 | 是（列車停在半路） | 4–5 個 PR |

**建議**：**B → Q4 → A**，C 留給史實劇本用「固定事件」先試，之後再決定要不要做隨機版。理由和替代路線在第 8.4 節。

### 2.3 校準用的實際誤點分布

我自己重算 `delay-stats.json`（`python3 -I` 讀 `trains`）：929 班、平均最終誤點 **1.89 分**、中位數 1.2 分、平均準點率（≤5 分）**91.7%**。調查員另統計（我沒有逐項複核）：單日最大誤點 `m` 的中位數 12 分、第 90 百分位 39 分、第 99 百分位 119 分、最大 200 分；平均最終誤點超過 10 分的只有 18 班。

用法：遊戲的準點率若以相同口徑（終點站晚 5 分內）量，離峰沒有干擾的路線應該在 90% 以上；每次干擾讓部分班次晚 10–40 分是合理的量級，100 分以上要留給嚴重事件。

## 3. 對照現有 GameCore：決定論、存檔、golden、replay

### 3.1 決定論契約（必要條件）

事件必須由「種子＋世界狀態」決定，存檔與 replay 能重現。沿用決策 69 已證明可行的做法：

1. **亂數**：`SeedDraw(seed).roll("disruption.<序號>.<用途>", in:)`，即 FNV-1a 對 `seed|key`。鍵含序號與用途，所以：加新用途不會改變舊用途的結果；批量、逐分鐘、存檔續玩都相同。**不要用會被消耗的亂數序列**（OpenTTD 就是靠固定的每 tick 呼叫順序保持同步，我們不需要那種脆弱的約束）。
2. **以「日」為抽籤單位**：在午夜（和 `startDemandEventDay` 同一個掛點）決定當天會發生什麼。分鐘級的發生時間也在那時由雜湊決定（例如「第 3 台車今天 14:07:20 故障」），之後只是一個已排好的時間點。
3. **狀態決定是否生效**：排好的故障若到時那台車不在運行（已經被拆、在檢修），就取消，不順延、不重抽。這個判斷只看世界狀態，所以可重現。
4. **整數**：機率用千分比、天數用整數；不使用浮點（跨階段議題）。
5. **批次推進的捷徑**：`advance(ticks:)` 在沒有變化時會跳到下一個有事的時刻（`nextServiceEvent`、`nextRunChange`）。**每個新的、會在非午夜時刻發生的事（故障開始、復原）都必須提供「下一個時刻」**，否則批次與逐秒會不同。這是最容易漏、也最容易被 CI 的批次＝逐秒比對抓到的地方。
6. **權威狀態**：事件排程和「正在發生的故障」放在 `GameWorld`，是權威狀態；GamePresentation 只畫、只提示。不要讓畫面自己決定「颱風來了」。

### 3.2 存檔

- 事件排程比照 `demandEvents`：**只在開啟時寫**，舊存檔與預設關閉的世界讀起來和以前一樣。
- 但只讀得到 35 的舊 build 會丟掉新欄位，所以仍要升 `SavedGame.currentVersion`（目前 35，`SavedGame.swift:184`），加 migration 與新版本的 fixture（`SaveFixtures/README.md` 的規則）。實作的 PR 照工作登記 #231 取「最大值加一」。
- 方案 A 要多存的：每台車的上次檢修時間；進行中的故障（哪台車、到何時為止）。車齡不用存（`AssetRecord.acquired` 推導）。
- 方案 B 幾乎只多存排程本身。
- 方案 C 要存受損的軌道邊與修復進度。

### 3.3 golden 與 replay

- **預設關閉**時，既有的 golden、`SaveFixtures/`、`ReplayFixtures/` 都不變（決策 69、87 同樣的做法）。`ReplayState` 的校驗和只在有干擾時才納入新欄位，才不會移動既有校驗和。
- 新增：每個方案一份短 golden（schema 取最大值加一，手算時刻與餘額）、一份新版本存檔 fixture。
- 獨立參考模型（`ReferenceWorld`）：沿用決策 133 的先例（班次、土地不在參考模型上重播），由專屬測試驗證，並做「一次推進 N 分鐘＝逐分鐘」的比對（`LineRunsTests` 的 3,000 分鐘做法）。
- 新指令（檢修、拖吊、搶修順序）要加進 `ReplayCommand`，並在新的 replay fixture 錄製；**不重錄舊檔**。
- CI 時間：ROADMAP 記錄過 `campaigns-9`、`-12` 超過 20 分鐘被取消。新的差分 campaign 要先量測再放進分片，不要拉 timeout。

遊戲沒有真實日期，第 0 天是星期一，一年 360 天。所以假日要用「每年第幾天」，和天燈節（每年第 45 天起 3 天）同樣做法：

| 元旦、清明、勞動、端午、中秋、國慶 | 各 1–4 天 | 清明 2026 年是 4 天（4/3–4/6），可取 4 |

## 4. 和 Q4（彈性發車與折返）的先後關係

Q4（ROADMAP「Q4 — 彈性發車與折返」）要解的是：**停在路線中間、或第一站不是它停下那一站的列車，現在不會被派出，整條線無聲停擺**。干擾事件會大量製造這種列車。

| 方案 | 會不會讓車停在「不是第一站」 | 結論 |
| --- | --- | --- |
| A 故障：車在路上壞掉，修好後繼續原服務 | 否（續跑同一個服務） | 單純的故障可以不等 Q4 |
| A 檢修：車必須到站、離開服務去檢修，檢修完在那一站 | **是**，除非限定在第一站檢修 | 要等 Q4，或第一版限定「只在起站檢修」 |
| A 拖吊：把壞車拖走 | 是 | 等 Q4 |
| B 需求變化 | 否 | 不依賴 Q4 |
| C 停駛：列車停在災區之間的站 | **是**（很多台） | 一定要 Q4 |
| C 復駛：恢復時要「就近發車／空車回送」 | 是 | Q4 要定的玩法正是這個 |

**所以：Q4 先於 A 的檢修與 C。** B 可以與 Q4 平行，也可以更早。

另一個理由是工程上的：Q4 要動的 `readyTrain`、`nextRunChange`、`LineRuns`，和干擾事件要掛的 `advance(ticks:)` 批次捷徑是同一組函式，同時改容易衝突，也讓逐秒＝批次的比對難以判斷是誰造成的差異。

Q4 的「空車回送算不算成本」也直接影響干擾的玩法：如果回送免費，停駛的代價就只剩收入損失；若回送要錢，停駛就更痛。這是作者在 Q4 要定的事，本研究不代為決定，但方案 C 的難度會因此改變。

## 5. 現有機制能直接提供的東西

- **誤點傳播免費**：停住的車持有進路（`Train.reservation`），後車依 U1／U2 等待，V1 會試著繞路、V2 只解「互相等待」。一台壞車不是死結（別的車等它，它不等別的車），所以不會觸發 V2 的送進待避站，**這需要一個實測確認**（建議在方案 A 的第一個 PR 先寫場景測試）。
- **取消班次**：固定班次的路線已有「晚 30 分鐘就取消」。
- **封站**：已有，並且乘客處理（候車的人離開、不再往封站產生旅次）已完成。缺的是「自動封站，而且和玩家手動設的封站不互相覆蓋」：現在 `operationMode` 是單一欄位，自動封站結束時不知道要還原成什麼。需要「有效模式＝手動模式與災害模式取較嚴」（GameCore 的 `PassengerRoutes`、`Boarding`、`PassengerDemand`、`GameWorld`、`LandDemand`、`LandValue` 六個檔案，加上 GamePresentation 三個檔案讀 `operationMode`）。
- **準點率**：沒有；但可以由 `lateness(of:)` 在列車到終點時累計（官方口徑：終點站晚 5 分內算準點）。歷史彙總才存檔，其餘由狀態推導（跨階段議題）。

### 6.1 OpenTTD（`vehicle.cpp` 的 `CheckVehicleBreakdown`，概念）

- 每台車有「目前可靠度」、「可靠度衰減速率」與「故障機率累加器」。每次檢查可靠度下降（夾在 0 與車型最大值之間），再抽一次籤；可靠度越低、距上次故障越久，故障越容易發生。
- 故障分階段：先是倒數、然後「開始」（車停下、冒煙、音效）、最後「已壞」並倒數到恢復；飛機只減速，不停。
- **檢修**把可靠度恢復到車型最大值，並把累加器壓低。觸發有兩種：每隔多少天，或可靠度降到最大值的某個百分比；訂單可以含「去車廠，需要時才檢修」。
- **車齡**：到了最大車齡之後，衰減速率逐年加倍；舊車型的最大可靠度也會下降。
- 全局難度三級：無／減少／一般（預設「減少」）。災害預設關閉，且依年代出現。
- 玩家得到的：「這輛車老了」的新聞、冒煙與音效；能選的是難度、檢修間隔、訂單、自動更新。
- 可借用的概念：**可靠度＋衰減＋檢修歸零＋車型上限**；**「距上次故障越久越容易壞」的累加器**；**車齡讓衰減階梯式加速**；**三級難度**。
- 未驗證：表格數值、停車時間長短、鐵路故障後的速限、平交道事故。

### 6.2 OpenRCT2（`Ride.cpp`，概念）

- 兩段式：先是「待處理的故障」，維修員被派出或抵達後才轉為真正的故障，並產生通知。維修員是**有限的資源**，派最近的一位。
- 檢修間隔由玩家設定：間隔短需要更多維修員、間隔長可靠度下降。
- 可借用的概念：**「預警→發生」的兩段式（給玩家反應時間）**；**有限的搶修人力與玩家設的檢修頻率**。

### 6.3 Simutrans（Extended 論壇，概念）

- 核心遊戲是否有隨機故障沒有驗證（**未驗證**）。車型有「上市日」與「退役日」，退役日只是不能再買新車；Extended 另有「過時日」，之後維修費上升。
- 可借用：**沒有亂數的老化**——車型過時後維修費爬升，把汰舊變成純財務決定。這和本專案「10 年折舊」自然相接。

### 6.4 商業遊戲（只談設計教訓，二手資料）

- Mini Metro：隨機事件讓玩家沮喪，是因為玩家**沒有能回應的手段**。
- Railway Empire 2：機車有狀況百分比與兩種故障，低於約 60% 自動送修，維修廠是車站延伸（粉絲資料，數值可能不準）。
- Cities: Skylines〈Natural Disasters〉：有預警、有應變單位、有疏散，評論稱讚「有組織的應變」的緊張感，但有些災害（雷、火）太無力。
- 共通教訓（也是方案設計的準則）：**有預警、有有限資源可以選擇如何回應、能靠平時投資降低損失。只有懲罰沒有手段就會惹人厭。**

5. 準點率若要顯示，建議兩個口徑並陳（官方的終點站口徑與乘客感受的每站口徑；消基會算出的誤點發生率約 18.66%，與官方差很多，需複核）。

## 8. 方案

下面三個方案共用同一個骨架（第 8.0 節），差別在「發生什麼」與「玩家能怎麼回應」。

### 8.0 共同骨架

- **`DisruptionSchedule`**：仿 `DemandEventSchedule`（種子、事件、下次抽籤日、抽籤次數），只在開啟時存檔；上限 64 筆。
- **難度**：`off`／`light`（偏少、偏輕）／`standard`。比照 OpenTTD 的三級，影響頻率與嚴重度的千分比，不影響規則本身。存在世界裡（它是規則的一部分，要隨存檔走）。
- **預設**：教學關閉；空白與實景的新遊戲建議預設 `light`，但**挑戰與每週挑戰先關閉**（挑戰目標是 `CHALLENGE_REPORT` 量過的；決策 145 要求改平衡就重跑報告；而且同一個週挑戰所有人事件相同，是日後的賣點，但要先有一輪實機平衡）。
- **提示**（三級）：
  1. 預警：站長一句話（排在「煩惱」最前）與地圖泡泡，例如「颱風預計 2 天後登陸，北部沿海的站會受影響」。
  2. 發生：泡泡＋音效（`GameFeedback`）；嚴重事件沿用決策 99 的做法自動暫停一次。
  3. 事後：結算一行字（「連假運量 +38%，有 4,200 人沒上到車」）。
- **第一次發生**時彈出一張說明卡（不是教學步驟），說明這是什麼、能做什麼；之後不再彈。
- **新手保護**：開局前 30 天不抽；`light` 下只抽預警類事件。

### 8.1 方案 A：車齡、故障與檢修

**玩家要做的決定**

1. **檢修頻率**（每條路線或全公司一個設定）：勤檢修花錢、車不容易壞；少檢修省錢、車會壞。
2. **備不備車**：壞車佔著進路時，後面一串車等；備用車能先頂替（需要 Q4 的彈性發車）。
3. **何時汰舊換新**：車齡越大越容易壞、維修費越高；換新要買車，也有折舊。10 年折舊本來就存在，現在才有理由提前汰換。
4. **故障當下**：等它自己修好（免費、久）／拖吊（付費、較快、需 Q4）／把車清出去讓別的車過。

**怎麼運作（概念，不是規格）**

- 每台車有「可靠度」（千分比），由兩個量推導：距上次檢修的天數、車齡（由 `acquired` 推導）。不存可靠度，只存「上次檢修時間」。
- 午夜時，對每台運行中的車以雜湊決定「今天會不會壞、幾點壞」：機率隨可靠度降低而升高，並加上「距上次故障越久越容易壞」的累加（OpenTTD 的概念）。
- 故障分兩段：**預警**（車速降低、泡泡冒出，給玩家幾分鐘）→ **故障**（車停住、仍持有進路、乘客留在車上）→ 修好後原地繼續原服務。
- **檢修**指令：車必須在車站（站內不阻塞），離開服務數小時，花錢，可靠度恢復。因為沒有車庫，第一版不引入新建物：檢修發生在站內。
- 嚴重度的量級參考第 2.3 節：多數故障讓該班晚 10–40 分，少數嚴重故障 100 分以上。
- 財報加「準點率」一行（由 `lateness(of:)` 在終點站累計）。

**難度與開關**：`off`／`light`／`standard` 影響每日故障機率（建議 `light` 約 `standard` 的一半）；另有「自動檢修」選項（預設開，幫新手：車自己在閒時檢修，成本略高）。

**對新手與教學**：教學關閉；`light` 預設只有自動檢修的車、不會有嚴重故障。第一次故障時的說明卡引導「去看看哪台車壞了」。

**GameCore 影響**：`Train` 新欄位（上次檢修、故障到何時）、`Disruptions.swift`、`Operations.swift`（維修費隨車齡）、新指令（`serviceTrain`）、新批次捷徑（下一個故障或修復時刻）、新錯誤種類。存檔升版、新 golden、新 save fixture、新 replay 指令。

**PR 分法**（建議）

1. **A1 骨架＋單台故障**：`DisruptionSchedule`、難度、午夜抽籤、列車停住與復原、批次＝逐秒測試、站長與泡泡提示、場景測試（確認壞車不被誤判為死結）。**不含檢修與車齡。**（M，規模約決策 69 的兩倍）
2. **A2 車齡與檢修**：推導可靠度、`serviceTrain`、維修費、自動檢修、準點率一行。（M）
3. **A3 畫面**：路線／列車面板的狀況條、檢修按鈕、財報。（S–M）

A2 的檢修在 Q4 完成前，只允許在「路線第一站」進行，才不會產生靜默停擺的列車。

**主要風險**

- 壞車擋住單線，後面整串等，玩家覺得被懲罰卻無事可做 → 要有預警、拖吊、備用車三個手段，並在 `light` 下降低頻率。
- 批次推進的新捷徑漏了某個時刻 → 逐秒＝批次的測試一定要先寫。
- 與固定班次的互動：壞車讓班次被取消，可能與 Q4 的新規則衝突 → 排在 Q4 之後可避免。

**規模**：3 個 PR，約 2–4 個 session。

### 8.2 方案 B：天候與國定假日（需求面）

**玩家要做的決定**

1. **連假前加不加班車**：連假有預告（7 天前公布），需求大增。玩家用既有的指令（調整班距、加車、加掛車廂、調整票價）準備。沒準備好，車站會滿、乘客被拒載（`abandoned`），事後有結算。
2. **票價**：連假加價賺更多，但需求彈性（`FareRules`）會讓人變少；現有票價指令就能操作。
3. **颱風預警**（1–3 天前）：預先把站設成 `flowControl` 或 `closed`（現有指令）可以避免「颱風天空車跑」的營運成本，但封站會損失收入、也要記得開回來。如果不處理，颱風天的需求會掉到很低，列車空跑照樣付成本。
4. **燃油／電價指數**（可選）：指數升高時，每日能源費用變貴；玩家可以縮班或忍受。

這個方案的決定是「**事前規劃**」，不是「臨場應變」。它的好處是安全，壞處是決定的深度有限。

**怎麼運作（概念）**

- 假日：第 3.5 節的固定日表，觸發全公司（或全網）的需求倍數；假日當天用週末形狀（`weekendShape`），固定班次路線用週末班表（可選：`LineRun.days` 增加「假日」位元）。
- 天候：狀態機（晴／雨／雷雨／颱風）。季節由月份決定（遊戲月 7–10 是颱風季，這是遊戲設定，不是氣象統計）。颱風是有預警的事件，雨與雷雨沒有預警、影響較輕。效果是**區域需求倍數**（下雨 −10%～−20%、颱風 −60%～−90%；數值是本專案的，需實機調整）。
- 實作上重用 `demandMultiplier(at:)` 與每日計畫重建。現有 `DemandEvent.boost` 限 1…2000，所以要新種類或新型別來表示「減少」與「全網」，不要去放寬舊型別的檢查（舊存檔的 `isValid` 會被影響）。
- 燃油指數：乘在每日 `routeEnergy`／`trainEnergy`（來源：`fuelIndex` 0.88–1.32、持續 7–14 天）。

**難度與開關**：沿用共同骨架。可以分開關：假日、天候、燃油各一個開關（假日預設開，因為幾乎沒有懲罰）。

**對新手與教學**：假日是正面的（需求變多）、風險最低；教學照舊關閉。颱風預警是第一次「需要反應」的時刻，說明卡會指向「路線面板的班距」與「車站的封站」。

**GameCore 影響**：`Disruptions.swift`（假日、天候）、`DemandEvents.swift`（倍數可為負或全網）、`Operations.swift`（燃油，可選）。**不動列車、軌道、預約、乘客路徑。** 存檔升版（排程）、golden 一份、save fixture 一份、replay 校驗和不變（預設關閉）。

**PR 分法**

1. **B1 事件骨架＋國定假日**：`DisruptionSchedule`、難度、假日表、需求倍數、預警提示、事後結算一行。（S–M）
2. **B2 天候（含颱風預警）與燃油指數**：狀態機、區域倍數、颱風預警提示、站長建議、颱風天的路線面板狀態列。（M）

**主要風險**

- 決定的深度不夠：玩家加了班車就沒事了 → 這是它「安全」的代價；用 B2 的颱風把「封不封站」變成真的取捨。
- 平衡：假日需求倍數若太高，所有車站都滿，玩家會覺得是 bug → 先用小的倍數（+20%～+50%，和展覽同量級），看實機。
- 挑戰的平衡：全網需求倍數會動到 `CHALLENGE_REPORT` 的結果 → 挑戰預設關閉。

**規模**：2 個 PR，約 1–2 個 session。

### 8.3 方案 C：颱風、地震停駛與復駛

**玩家要做的決定**

1. **颱風預警期間（2–3 天）**：預先停駛（封站、停止發車）還是硬開？硬開有收入，但受損機率高；預先停駛損失收入但保護車與軌道。
2. **事後的搶修順序**：災後會有數個受損的軌道段，搶修人力有限（比照 OpenRCT2 的有限維修員），玩家要決定先修哪一段：先修賺錢的幹線，還是先修能接回孤立城鎮的支線？
3. **接駁**：受阻的路段要不要花錢叫接駁車（讓部分乘客仍能到達，付一筆每日費用；真實的花蓮＝宜蘭海運接駁是例子）。
4. **投資**：平時的投資能降低受損（例如給軌道「防災補強」，花錢降低機率）；沒有就等於賭。
5. **地震**：沒有預警；震度大時所有列車自動停車（遊戲的「地震限速」），再逐級放寬（參考臺鐵的 30 → 60 km/h、高鐵的逐級提速）。

**怎麼運作（概念）**

- 事件有一個**中心點與半徑**（世界單位）以及強度。颱風從東向西，中心每天移動；地震在隨機點。受影響的站與軌道邊由幾何決定（整數運算）。
- 受損軌道：每條邊有「受損、修復所需天數」，不能進入（等同被占用，但不是被車占用），列車停在受阻前的站。
- 乘客：路徑要重算（既有的 `PassengerRoutes` 已處理封站）；孤立的站候車乘客離開。
- 修復：有限的搶修隊，玩家排順序；每段有成本與工期（工期可能延後 ×1.0–×1.5，參考真實案例）。
- 嚴重度三級：預防停駛（0.5–2 天）、搶通（1–3 天）、結構性（遊戲裡縮短為 10–30 天）。同一路段修好後一段時間內二次受災機率升高。

**難度與開關**：同共同骨架；另外 `standard` 才有結構性中斷，`light` 只有預防停駛與搶通。

**對新手與教學**：影響最大；新手第一次看到整條線停擺的感受可能是「遊戲壞了」。必須有：兩天的預警、站長明確說明、一鍵「全部預先停駛」、事後一鍵「自動搶修（依收入排序）」。教學關閉；新手保護期內不發生。

**GameCore 影響**（最大）：軌道的「受損」狀態（`TrackResources`、進路取得要考慮不可通行）、列車停在半路（Q4）、乘客路徑在邊的受損與修復時重算（plan cache 失效的代價要量測）、自動封站與手動封站要能並存（有效模式＝取較嚴）、新指令（搶修順序、接駁）、新批次捷徑、存檔升版、golden 數份、新 campaign（`traffic.*` 差分模型要認識受損邊，CI 時間要量）。

**PR 分法**（建議）

1. **C1 事件與災區幾何**：颱風／地震事件、預警、中心與半徑、自動封站（有效模式）。（M）
2. **C2 受損軌道與停駛**：邊的受損、進路不可通行、列車停住與路徑重算、孤立站處理。（L）
3. **C3 搶修與復駛**：有限搶修隊、順序指令、工期延後、二次受災。（M）
4. **C4 接駁與投資**：接駁費用、防災補強、財報科目。（M）
5. **C5 畫面與難度**：災區圖層、搶修面板、說明卡、一鍵動作。（M）

**主要風險**

- 與交通控制（T、U、V）和差分 campaign 的交互作用最複雜；CI 分片時間已吃緊。
- 玩家「被動挨打」的感受，失敗的處理要細緻。
- Q4 沒做好之前，不可能做出體面的復駛。
- 史實性：真實案例的工期以月計，遊戲縮短後是否失去重量？需要實機判斷。

**規模**：4–5 個 PR，約 5–8 個 session，且必須在 Q4 之後。

### 8.4 比較與建議

| | A 車齡、故障、檢修 | B 天候、國定假日 | C 颱風、地震停駛 |
| --- | --- | --- | --- |
| 決定的性質 | 持續的小決定（中期穩態） | 事前規劃 | 少見但重大的臨場決定 |
| 解決「蓋好就自動賺錢」 | 最直接（每台車都要照顧） | 部分（要在事件前準備） | 強烈但不常發生 |
| 依賴 Q4 | 檢修與拖吊要 | 否 | 是 |
| 動到的 GameCore | 列車、財報 | 需求、財報 | 軌道、預約、乘客路徑 |
| 決定論風險 | 中（新批次捷徑） | 低 | 高 |
| CI 風險 | 中 | 低 | 高 |
| 台灣特色 | 弱（通用） | 中（連假、颱風季） | 強（颱風、地震、花蓮、平溪） |
| 新手風險 | 中 | 低 | 高 |
| PR 數 | 3 | 2 | 4–5 |

**建議：B → Q4 → A，C 先由史實劇本用固定事件試水。**

1. **先做 B**（2 個 PR）：成本最低、沒有 Q4 依賴、可立即做出台灣味的連假與颱風預警；更重要的是它把「事件骨架、難度開關、預警提示、事後結算」一次建好，A 與 C 都重用它。這是風險最低、能先給作者看感覺的一步。
2. **Q4**（作者已排入）。
3. **再做 A**：它直接針對「中期穩態沒有決定」；OpenTTD 證明這類機制長期有效，而且本專案已有車齡與折舊的基礎，汰舊換新是自然的決定。
4. **C 暫緩，改用史實劇本試水**：史實劇本（劉銘傳鐵路）與平溪線（真實的 2025 年豪雨停駛約 3 個月）可以用**固定事件**（寫死「第 N 天路基掏空，第 M 天復駛」，不抽籤）示範受損與復駛，使用 B 的骨架但不需要邊的受損機制（先以封站＋取消班次呈現）。等實機回饋再決定要不要做隨機版與完整的受損軌道。這個安排的理由是：C 是風險與工作量最大的一項，動到 T、U、V 與差分 campaign，且 Q4 的玩法（空車回送算不算成本）尚未定。

**如果作者只想做一個**：選 A，但要等 Q4；若不想等，選 B。

**替代方案**：如果作者更看重「台灣特色與戲劇性」，也可以 B → Q4 → C → A；代價是更晚才有穩態中的小決定。
