> 每次換寫作 session 之前，開一個只改這份的文件 PR，把第 5 節補到最新一版。草稿本身照樣不 commit。

## 1. 這個 session 做什麼

寫作 session 用繁體中文寫《沿線》的 Threads 貼文。

每次 TestFlight 發新版，就幫作者寫 Threads 貼文：
- 一篇主文，下面幾則留言：🔧 修好的、✨ 介面和新功能、🚧 正在做、💬 常見問題。
- 主文和每則留言都不超過 500 字。
- 另外附 3 則短版。
- 寫什麼時候發，還有要在實機上拍哪些圖、哪些影片。
- 草稿寫成暫存資料夾裡的檔案，用 SendUserFile 交給作者。

## 2. 規則

- 貼文不寫程式或函式庫的名稱，不寫內部編號、決策號，也不寫「AI」寫了什麼程式。
- 照作者原本的語氣寫。
- 草稿不 commit、不開 PR、不發布。唯一的例外是換手前更新這份交接（見最上面）。
- 不動排程：「每日 Threads 開發日誌」維持暫停。
- 不跑 testflight.yml，不寫 `@claude`（會啟動 `claude.yml`）。
- 想知道開發進度，用 send_message 問規劃 session。它的 session ID 在 #1041。

## 3. 內容從哪裡查（都看 origin/main，先 git fetch）

- 這一版的 What to Test：`.github/testflight-whats-new.md`。
- 每一版的紀錄，還有作者和測試者的回報：`docs/research/PLAYER_FEEDBACK.md` 裡的「0.5.0 (N.1)」。
- 做到哪裡、留給誰做：`docs/HANDOFF.md` §2.0。
- 待辦：`docs/research/NEXT_PRIORITIES_2026-10-12.md`。
- 合併了哪些 PR：`git log origin/main --first-parent`。
- 某個 PR 有沒有進某一版：`git log <那一版的 commit> --merges`。
- 按鈕和畫面上的字，先在 Swift 的字串裡確認寫法再用，例如「放空模式」「怎麼搭」「打開道路與公車」「列車包」「3D 畫質」。

## 4. 作者教過的事

- 功能要寫成玩家怎麼按、會看到什麼。
  - ✗「車站卡點一班車，3D 直接飛到它停的月台」：作者說看不懂。
  - ✓「想看哪班車進站：點車站，在『即將進站』點那班車，3D 就帶你到它的月台」
- 前幾版已經有的東西，不要寫成這一版的新功能。例如拿掉 3D 的 12×12 公里限制是 83.1 的事。
- 不寫演示模式：它是藏起來的開關，只有測試版有。
- 列車包也只有測試版有，要寫就放在常見問題，說是「測試版的設定」。
- 3D 只有實景地圖會邊開邊載入街景；高鐵示範地圖也算在內。
- 一天出好幾版，或有一版沒給測試者，就合成一篇發：
  - 已經這樣合過：81/82、83/84、85–87。
  - 89.1 沒給測試者，併進 90 一起寫。
- 時間建議：給測試者之後發，最好在 20:00–22:30。過了 23:30 就改到隔天早上 8:00–9:00。

## 7. 留言格式範本

```
🔧 上次回報、這版修好的
・推拉式自強號的車頭還是舊的方塊：換成 E500 了
・舊存檔找不到公車：公車工具裡按「打開道路與公車」就有了
```

```
💬 常見問題
Q：舊存檔的公車在哪？
A：選公車工具，按「打開道路與公車」，道路會長出來，就能畫公車路線

Q：舊存檔還能玩嗎？
A：照常讀

以上謝謝各位測試者
```

- 「✨ 介面和新功能」：一行一項，前面加「・」。一天出好幾版時，一版一則。
- 「🚧 正在做」：只寫交接文件或規劃 session 確定在做的事，不確定就不寫。
