### 2.2 每條線的真實班次

- 新工具 `tools/real-timetables/extract_metro_runs.py`：讀 App 已打包的 `<系統>_times.json`。
  - 每條線取一個平日、一個週六、一個週日，排成 `LineRun`。
  - 照 `extract_branch_runs.py` 的 `overnight` 檢查：每天開始和結束時，每組車都要在同一站。
  - 需要時加回送。
  - 輸出 `RealRailways/metro_runs.json`。
- 推算出來的時刻（文湖、三鶯、台中綠線）在收購卡上寫「照官方班距排的班次」。鐵道迷看得出那不是公告的時刻表。
- 支線（含新北投、小碧潭）班次獨立；中和新蘆線的兩條支線各自一條路線，共用的主線鋪一次（決策 351 是各自鋪一次，收購要改成共用）。
- 大小：
  - 台北捷運一個平日約 3,000 多班（全系統、兩個方向），但 `LineRun` 只存每班的出發時刻與停站序。
  - 粗估三種日子、所有線約 1–2 MB（JSON），和現在的 `trtc_times.json` 同一級。
  - 實際大小在第一個 PR 量。

### 2.3 價格

- 公式照決策 315，不改：建造 + 列車 + 營運價值。
- 捷運沿線的旅客多：`trtc_ridership.json`（2025 年，進出站 ÷ 2）的台北車站一站 149,891 人次。沿線各站相加（轉乘站每條線都算一次）：
  - 板南 787,944、淡水信義 676,126、松山新店 471,906、中和新蘆迴龍 379,903、蘆洲 362,728、文湖 304,649、環狀 94,463。
  - 照 $10,000／人，板南線光營運價值就是 $79 億，比任何玩家賺得到的都多；
  - 也超過 `maximumDailyRiders` 200,000。
- 選項：
  1. **每個系統等級各一個值**（支線 $10,000；輕軌、捷運另量）：GameCore 的 `valuePerDailyRider` 變成一張小表，`recordLineAcquisition` 多一個 `tier` 參數，`maximumDailyRiders` 提高到 2,000,000。
  2. 營運價值設上限：好懂，但所有捷運線變成同一價。
  3. GamePresentation 把運量縮小再傳：GameCore 存的數字就不是真的旅客數，不採用。
- 目標照決策 315「後來」的新目標（÷ 自己蓋 1.5–5、回本 3–12 個月、÷ 一般玩家第 180 天利益 1–2 個月），再加一條：**捷運是後期的大目標**，價格 ÷ 一般玩家第 360 天的利益約 2–6 個月。

### 2.4 開局的錢與第一條線

- 標準開局 $300 萬，買不起任何一條線，所以只收購的開局要另外給第一條線。
- 選項：

| 選項 | 怎麼做 | 問題 |
| --- | --- | --- |
| A 開局選一條，接手時不收錢 | 新遊戲畫面選地圖框之後，列出框裡可收購的線，選一條。開局資金加上那條線的建造＋列車費，鋪好後剩下的仍是標準的 $300 萬；營運價值以 0 記（`dailyRiders` 0）。 | 要確保接手後剩的錢和自己蓋的開局差不多 |
| B 開局資金夠買最便宜的一條 | 資金 = 框裡最便宜一條的價格 + $300 萬 | 玩家可以不買、拿去蓋，就變成有錢的普通開局 |
| C 開局貸款買第一條 | 照決策 46 的貸款 | 新手一開始就背債，對「最不用做」的玩法太重 |
| D 先自己賺錢再買 | 不給 | 開局沒有線、沒有收入，玩家什麼都不能做 |

- 不升存檔：
  - A 的「接手」完全用現有的指令：`GameWorld.newGame` 的起始資金，加上 `acquireRealLine` 的 `dailyRiders` 0。
  - 要確認 `acquireAsset` 收不收 0 元的資產，第一個 PR 寫測試。
- 地圖框裡沒有任何一條可收購的線時，「只收購」這個選項變灰，並寫原因（照決策 336 的 `realLinesForSaleNote`）。

### 2.5 和簡單規則（決策 258）怎麼搭

- 只收購的開局**固定用簡單規則**。決策 315 的收購量測都在簡單規則下：寫實規則有區間閉塞，真實班次的交會可能卡住（決策 133 的瑞芳死結），沒有量過。新遊戲畫面選了只收購，規則那排變灰。
- 簡單規則留下的「行車控制」「彈性派車」不關。
- 建造工具照樣在：玩家隨時可以自己鋪軌、蓋站、開線，接到買來的線。只收購是開局的方式，不是另一種遊戲。
- 列車數與效能：
  - 板南線 4–6 分一班，全天要幾十組車；
  - HANDOFF 第 3 節「先優化再加新功能」的效能線（2D 高鐵 6000× 只有 3 fps）還沒過。
  - 第 3 批（捷運）PR 要先量一條大線的每秒模擬步數，過不了就先開短的線（三鶯、台中綠線、安坑、淡海）。
- 開局時送的那條線不算成就裡「自己蓋的」：只要照現有的收購紀錄判斷，不用新欄位。

### 2.6 玩家看到的

- 新遊戲：實景地圖的選項多一排「開局：自己蓋／只收購」。選只收購，下面列出框裡可以接手的線（線名、站數、公里、每天幾班），選一條。
- 遊戲中：路線面板的「可收購的真實路線」（決策 336）照舊；地圖上未收購的真實路線可以點，點了打開同一張收購卡。
- 說明頁多一則「只收購怎麼玩」。

## 3. 10i：道路與公車

### 3.1 真實公車：資料從哪來

**參考庫 `Railway/geo-scene-reference-clean/`**（`source/public/bus/`，44 MB）：
- 20 個縣市的市區公車**路線形狀**：每個路線方向一條座標串；5,213 個路線方向，共 1,933,587 個點。
- **沒有台北市**：`types/index.ts` 指向的 `taipei_bus_routes_v2.json` 沒有收進來。公路客運 `intercity_bus_routes_v2.json`、台灣好行也沒有。
- 沒有站牌與班次。
- `BusEngine.ts` 其實**不是照時刻跑**：檔頭寫「鐵路靠時刻表插值，公車靠 GPS 位置 snap 到路線上」。它讀即時 GPS（`fetchBusIntercityCurrent` 打後端的 RPC），兩次讀取之間沿路線推進。
- 能搬的是幾何的部分：
  - `snapToRoute`（點投影到折線，回傳 0–1 的進度）；
  - `cumDist`（每點的累計距離）；
  - 沿線插值。
- GPS 的部分（異常濾除、趟次切分）用不到。

**參考庫 `Railway/taiwan-rail-reference-clean/source/data/`**（這次新找到的，比 geo-scene 有用）：
- `bus_stops_index.tsv`（4.7 MB）：全台 43,363 個**站牌**，有站名、縣市、座標、經過的路線名、各家業者的站牌代碼。台北市 5,367、新北 8,717、台中 6,763、高雄 5,272、台南 4,973；**桃園只有 46**，是部分資料。
- `bus-transfer/*.json`（542 個火車站各一檔，12 MB，壓縮後 0.76 MB）：
  - 每個鐵路車站 600 m 內的站牌，含步行距離估計（直線 × 1.25、每分 75 m）；
  - 每個站牌經過的路線與**站序**（`routeKey` 加上 `stopSequence`）。
  - 共 6,115 個路線方向：公路客運 1,530、台北 1,044、新北 982、台中 562、高雄 445、桃園 368、台南 348……
- `bus_providers.json`：取得即時到站的策略。寫明 TDX 的 `Bus/Station` 只收 21 個縣市，連江縣不在其中。
- 這幾個檔的資料都來自 TDX（`THIRD_PARTY_NOTICES.md`：「交通部 TDX 運輸資料流通服務：臺灣路網、班表、站點及相關運輸資料；依資料發布條款標示來源」）。
- **沒有班次**：沒有一個檔有公車的時刻或班距。

**TDX（交通部運輸資料流通服務）**：
- 有的 API：
  - `/v2/Bus/Shape/City/{City}`：路線形狀；
  - `/v2/Bus/StopOfRoute/City/{City}`：站序；
  - `/v2/Bus/Schedule/City/{City}`：班表，有逐班時刻，也有只給班距的；
  - 公路客運把 `City/{City}` 換成 `InterCity`。
- **授權**：TDX 的常見問題寫，介接的資料依「政府資料開放授權條款第 1 版」，應用服務要揭露資料來源「交通部 TDX 平臺」。這個條款允許重製、改作、散布，也允許商業用途，只要標示出處。所以**打包進 App 是可以的**，`DataSourceCredits` 加一行。
- **要帳號與金鑰**：
  - 要用程式抓，得先註冊會員、申請 API 金鑰（Client ID 與 Client Secret），換一天有效的 access token；
  - 2024 年起，沒有訂閱方案的基礎會員每把金鑰約每分鐘 5 次；
  - 不註冊只能用瀏覽器，每個 IP 每天 50 次，不能用程式讀。
- 結論：抓班次是**作者要決定的事**。帳號與金鑰是作者的；金鑰只能放在 GitHub 的 secret 或作者自己的電腦，不能進 repository。見決策 400 的「要作者決定的」。
- 打包多大（粗估，第一個資料 PR 量實數）：
  - 只收「經過某個火車站 600 m 內」的路線：6,115 個方向，約全部的一半。
  - 形狀：
    - 原始約 190 萬點；
    - 簡化到 5 m 誤差、存成相對前一點的整數公尺，估計 3–6 MB；
    - 只收經過火車站的路線，估計 2–3 MB。
  - 站牌與站序：約 1 MB。
  - 班次：
    - 只存每個方向每種日子的發車時刻與站間分鐘，估計 2–5 MB；
    - 只給班距的路線只存時段與班距，很小。
  - 合計 5–10 MB。App 現在打包的 `RealRailways/` 約 5 MB，`taiwan.pmtiles` 更大，所以是可以接受的量級。按縣市分檔、跟著地圖框懶讀（像 `LandBlocks`）。

### 3.2 道路怎麼長

**參考庫 `Railway/island_city_reference_clean/`**（`g10.js`、`g11.js`）：
- **沒有「路自己長」**：路是玩家一格一格鋪的，每格 10 金，可以按住拖曳。
- 跟道路有關的規則：
  - 旁邊有路的建築才算「接上道路」：住戶幸福 +5、農田商店產出 +20%；
  - 公車站（80 金）要蓋在路旁，附近 3 格的住戶幸福 +4，每天收車資 `2 × 產出倍率 − 1`；
  - 捷運站（400 金）附近 4 格幸福 +6，車資 `(2 + 0.12 × 人口) × 倍率 − 1`；
  - 住戶開心時會買機車、技能高時換汽車，用 `Math.random()`：每天 1.2% 買機車、0.4% 換汽車；
  - 機車每台每天收稅 0.3、汽車 0.6；
  - 停車位不夠就塞車，`jamLevel = 汽車 − 車位 − 4`。
- 能搬的只有數值的比例：
  - 路：公車站：捷運站的價格 = 1 : 8 : 40；
  - 公車服務圈 3 格、捷運 4 格。
- 它的方格狀態與隨機數不搬（CLAUDE.md）。

**本專案已有的**：
- 城市格子 64 m（`Land`）；
- 空白地圖開局三個城鎮（`Land.towns(seed:in:)`）；
- 實景地圖的路在底圖圖磚裡，有路名與等級；
- 3D 已經能從城市格子推出 64 m 的街道（決策 259）。

**設計的方向**（細節在決策 400）：
- GameCore 多一張**道路格子**：
  - 一格就是土地的 64 m 格，記這一格有沒有路；
  - 存在世界裡，跟著存檔。
- 實景地圖：GamePresentation 讀進一塊土地時（`LandBlocks`），順便從底圖圖磚算出哪些格子有路，交給 GameCore，和 `setLand` 的做法一樣。GameCore 不讀真實資料，只存結果。
- 空白地圖：開局每個城鎮中心有一小塊「種子道路」。
- 每個月長一次，決定性、沒有隨機：
  - 每個城鎮朝最近的車站長，每個月最多長一格；
  - 只長進有人住或有工作的格子，或長進朝車站方向的下一格；
  - 照 OpenTTD 城鎮「從市中心往外長路」的想法自己寫，不抄它的程式。
- 站前路：
  - 從車站拉到最近一格有路的地方，照長度付錢，最長 512 m（8 格）；
  - 站離路更遠時，等路自己長過來，或是先蓋近一點的站。

**站前路的價格**：
- 遊戲的軌道是每 16 m $1,600（每公尺 $100，`ConstructionCosts.newGame`），車站 $20 萬。
- 照島城「路：公車站 = 1 : 8」與台灣的實情（平面道路比鐵路便宜），站前路先定**每公尺 $50**，8 格滿也只要 $25,600，約車站的八分之一。
- 公車站牌 $1 萬（約車站的 1/20：一個站牌加一座候車亭）。
- 公車一輛 $5 萬（遊戲的列車第一節 $15 萬、加一節 $4 萬）。
- 以上都是起點，第一個 PR 用 economy-balance 量。

### 3.3 公車和 `ModeShift` 怎麼分客

- 第一版的公車只做**接駁**：載人去火車站，不做只坐公車、不搭火車的旅程。
  - 和 10i 的「接駁到自己的火車站」一致；
  - GameCore 的旅客還是以車站對車站計算（決策 139），不用新的旅程模型。
- **服務圈**：
  - 一個公車站牌 400 m 內的格子，算進它所在路線接到的那個火車站的腹地；
  - 那個站本來的 800 m 腹地照舊；
  - 同一格同時在兩個站的腹地時，照現有的規則只算一次。
- **門到門時間**：從一格經公車到火車站的分鐘 = 走到站牌（直線 × 1.3 ÷ 每分 75 m）+ 半個班距 + 公車上的分鐘（路線長度 ÷ 時速 18 km，台灣市區公車的平均）。
- 這個分鐘取代 `ModeShift.accessMinutes`（6 分）那一端，所以 `ModeShift` 照舊比較「鐵路＋公車」和機車、汽車：
  - 公車很慢、班距很長時，那一格的旅客大多騎車，和真實的台灣一樣；
  - 公車密、路線短時，接駁才搶得到客人。
- 簡單規則的上限 20%、寫實規則的地區分擔率都不變。
- **公車的收入**：
  - 每位接駁旅客收一段票（台灣市區公車一段票多半 NT$15）；
  - 照遊戲票價表的比例換算，第一個公車 PR 量；
  - 記在那條公車路線的損益（決策 179 的路線帳）。
- 真實的台灣：`ModeShift` 用的交通部 2024 年調查（表 4）裡，汽機車佔全國旅次 72%，公共運輸只佔一小部分。公車的分擔率要在第一個公車 PR 從同一份表查出來寫進決策（這次沒有查表）。
  - 所以接駁不該讓鐵路的旅客暴增：量測目標先訂「有公車接駁的站比沒有的多 5–25% 旅客」，第一個公車 PR 量。
