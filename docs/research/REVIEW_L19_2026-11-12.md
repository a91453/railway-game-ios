## 派工單的五個重點

### 1. #2086 TICK-L0 的索引：沒有發現問題

- **失效**：`TrainLineIndex`（`Sources/GameCore/Railway/TrainLineIndex.swift:32-51`）自己留著算出索引時的那份 `lines`，
  每次查都先比 `self.lines != lines`，不一樣就重算。所以不靠任何命令去通知它：不管哪條命令改了列車、路線、班表，
  下一次查一定是對現在的 `lines` 算的。沒有「漏掉某條命令」這種失敗方式。
- **failure atomicity**：索引不是世界狀態。它在 `PathMemo.trainLines`（`ServicePath.swift:154`），
  `PathMemo` 由 `RouteMemo` 跨 `advance` 保留（`ServiceDirections.swift:196、286`），而 `RouteMemo` 的 `==` 永遠是 true、不進存檔。
  命令失敗時世界照舊回復，索引就算留著舊的，下次查也會比對出來。
- **Codable**：不編碼；讀檔後 `RouteMemo` 是空的，第一次查就建。
- **確定性**：`indices`、`first` 兩個字典只用來查，沒有走訪；`ring` 只問 `contains`。建索引照 `lines` 的順序、
  「第一條有這列車的線」先佔（`:43`），和原本 `assignedLine(of:)`＋`line(id:)` 的「第一條」同義；
  同 ID 的線取第一條（`:40`），也和原本一樣。環狀線判斷（`line.isRing && line.trains.contains`）等價。
- **`planTrafficOvertakes` 的 `prefers` 預先算**（`ScheduledTraffic.swift:629`）：兩層迴圈裡 `plan.services` 的列車沒有被改
  （`overtakeTrackFree`、`timetabledOvertake` 只寫 `plan.moves／sidings／opposite／nominal`），所以先算一次與每對各問一次同值。
- **`trainPosition(of:)`**（`Depot.swift:428`）：二分找不到會退回線性找，列車不照 ID 排也不會答錯。
  `runningTrains` 從「走訪所有列車」改成「走訪這個 stream 的 ID」，列車 ID 不重複，計數相同。
- **`serviceLevel(of line:)`**（`LineJourney.swift:219`）假設線的 ID 不重複；世界的檢查在 `GameWorld.swift:6028` 一帶。
- 成本：索引多持有一份 `lines`（共用儲存）。`RouteMemo.Key` 本來就留一份 `lines`，所以沒有新增 copy-on-write；
  `lines` 在一次 `advance` 裡被改（例如記發車時間）後，下一次查會重建，O(線＋列車)，可忽略。
- 旁證：完整 tier（golden、SaveFixtures、ReplayFixtures）在 #2086 上是綠的，三套 fixture 沒有動。

只有兩條 P3（見下面 P3-1、P3-2），都是留下的效能，不是錯。
