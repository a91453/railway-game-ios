## 結論

**沒有找到確定的正確性 bug**（沒有一條能寫出在舊程式上紅的觸發情境），所以這個 PR 只有這份報告，沒有程式修改。下面是逐項看過的重點與留下的疑點。

### GameCore（決定性、存檔相容）

- **#1967**（`planHeadwayOvertakes` 與 `trafficOvertakeTracks` 的快取）：
  - `trafficOppositeCounts` 取代「其他每一班的反向集合」：同一個 plan 裡每列車只有一個 service（`trafficPlan` 對 `trains` 各取一次），所以「排除同一列車」等於「排除自己」，計數減去自己後 > 0 與舊的聯集相同。
  - `TrafficParts.Kept` 以列車與 `Shape`（長度、時刻表的站與折返、點的站／停／berth／距離）共用。被快取的四個函式另外只讀路網、路線（`routePreference` 經 `runOrder`／`routeOrder`，只看時刻表的站與 `dispatchStream`）與 `keepLeft`；這些都在 `ServiceKey` 裡，變了 `TrafficParts` 就不借給下一次。第一點、列車站在該 berth 時，查詢鍵帶 `trailEdges`，和 `trafficTrack` 判斷 `bodyStretches` 的條件相同。
  - 字典只在算 plan 時查，結果照 `plan.services` 的順序用，沒有拿字典的順序決定結果；不影響決定性。
  - 結論：等價，沒有疑點。
- **#1961**（`standsAgainstTheLine`）：`lines.first(where:)` 依陣列順序，決定性；`memo.paths.against` 鍵含線與車長。只在 `!blockSections` 時作用。`PlayerCommand` 新增 `rebuildRealLine`，舊的命令紀錄不含它，讀得回。沒有疑點。

### #1971 車站點擊（作者回報點車站會當機）

- 新的 `stationDemandPairs(of:days:)` 和舊的（經 `stationRidership`）逐項相同：同樣的 `guard stationDemand(of:)`、同樣照 `stations` 的順序、同樣「去或回 > 0」才列。只用字典查詢，沒有索引、強制解包、除法或整數運算，**不會因這個 PR 當機**。
- 當機本身仍沒有紀錄（決策 644「缺口與下一步」1）；決策 644 的第 3 點（換站時舊的 `Task.detached` 不停）還成立，是 App 層，Linux 測不到。

### #1972 軌道高度改成拖曳

- `stepsUp`／`stepsDown` 與 `raiseNetworkEnd(by:)` 的夾住範圍用同一個 `heightRange`，拖曳的步數先被 `clamped` 夾住，放開時才 `onRaise`，命令一次。沒有溢位（Int64 公尺單位、`Int(Double)` 只吃有限的拖曳位移）。
- **疑點 R122-1（P3，UNVERIFIED，只有 Simulator 能答）**：`slidSteps` 與 `isHeld` 是 `MapConstructionHUD` 的 `@State`，只在 `onEnded` 歸零。手勢被系統取消（第二根手指、跳出的 sheet、高度格在按住時變成不可拖的那種）時 SwiftUI 不叫 `onEnded`，格子會停在亮底，讀數多算沒套用的步數，直到下一次按。改用 `@GestureState`（取消時自動回 0）就不會。沒有找到 Linux 能重現的觸發情境，所以沒改。

### #1962 3D 時鐘、夜窗、開啟位置

- `Map3DClock` 只讀 `world.clock`，沒有自己的狀態。
- `openingDistance` 取 `min(整個場景, 2D 的距離)`，`Map3DCamera.init` 再夾在 `nearest...farthest`；viewport 高度為 0 時 `distance(referenceSize:viewportHeight:)` 用 `max(…, 1)`，不會除以零。
- 夜窗的 `fwidth` 在分支前取，符合 Metal 的導數規則。
- **疑點 R122-2（P3，效能，未量）**：`Map3DHandoff.nearestTrack` 在主執行緒掃全部節點、每條邊的幾何點與車站，只在 2D 拉到比一個 3D 場景還遠、又沒選站或車時才跑。收購多條真實路線的局沒量過；若卡，可改用格子索引或只看畫面附近的邊。

### #1974 可收購路線清單

- 背景檢查（`landCheckOnly`）在土地檢查通過時就停，被拒的判斷用同一句 `landProblem` 文字比對，兩處文字一致（`refusedForLand` 與 `RealLineRing`）。
- **疑點 R122-3（P3）**：完整收購時，取樣點之間碰到的格子還會再加買（`RealLineAcquisition.swift` 約 1552 行），那裡也可能回「土地不相連」；只做土地檢查的清單看不到這一步，所以極少數的線會在清單上可點、點了才被拒。被拒時仍有說明，不會壞。
- **疑點 R122-4（P3）**：清單只在面板出現時（`onAppear`）重算；面板開著時擴建地圖，灰掉的線要關掉再開才更新。重算期間顯示的是上一次的結果（可能把已經相連的線暫時灰掉）。

### 其他

- #1964 `crossings`：`guard` 先排除完全在畫面外的線段，所以 `x0...x1`、`y0...y1` 不會倒過來；NaN 座標也被 `guard` 擋掉。
- #1959 `NewTrainArrival.together` 的 `arrivals[0]`：唯一的呼叫端先 `guard !new.isEmpty`。`StationLabels` 的排序比較是嚴格弱序。`LineReport` 用第一次收購的日子排除收購當天（同一條線賣掉再買時用最早那天，P3，只影響報表從哪天算起）。
- #1973 `followableTrain` 讀 `tappedTrainID`，和原本卡片的列車相同。
