## 5. 小型驗證方案

### V1（短期線）：幀時間紀錄，跟問題回報走

一張 PR，只動 GamePresentation 與 App，**不動 GameCore、存檔、golden、replay，不加依賴**（只用 Apple 自帶的 Metal、QuartzCore、MetricKit、Foundation）。

- 量（App 只交樣本，統計與文字在 GamePresentation，Linux 測）：
  - **3D 上螢幕的間隔**：drawable 的 `addPresentedHandler`／`presentedTime`（系統回報的實際呈現時間；`presentedTime` 為 0 的是沒上螢幕的幀，另外計數）。
  - **2D 的主執行緒節拍**：`CADisplayLink` 回呼之間的時間差（`timestamp` 與 `targetTimestamp`）。**這不是完整的實際呈現時間**：它量到主執行緒有沒有準時醒來，量不到之後 SwiftUI 與 Core Animation 提交、系統合成到上螢幕的那段。報告裡一律寫「2D 節拍」，不寫「2D 幀時間」或「呈現時間」；決策 328 的各部分 ms 一起附上，補看主執行緒在忙什麼。
  - 分布：中位數、p95、p99，與 **50–100、100–250、250 ms 以上** 的停頓次數；**250 ms 以上記為嚴重停頓**（和 418 的門檻對得起來），另記**最長的一次停頓**（多長、什麼時候、當時的情境與 2D 各部分 ms）。
  - 3D 每幀 CPU ms 與 GPU ms（已有，改成記分布）、三角形、draw call、可見的場景塊數。
  - 2D 每幀各部分（已有的 `FrameCostMeter` 部分，記最長的幾次是哪一部分）。
  - 記憶體：`phys_footprint` 的高點與 `os_proc_available_memory` 的低點、收到記憶體警告的次數。
  - 發燙：`ProcessInfo.thermalState` 的變化。
  - 情境：2D／3D／跟車、倍速、車站數、線數、417 的畫質與那一格。
- 存：裝置上一個小檔（最近幾段，每段一個畫面一個情境），像 418 一樣有大小上限，只在玩家送出問題回報時附上。
- 不做：上傳、第三方分析服務、每幀寫檔。
- 驗收：
  - Linux 測試：用寫死的樣本序列，證明中位數、p95、p99、各段停頓次數、**嚴重停頓次數、最長停頓**與它的情境都算對；邊界（剛好 50／100／250 ms、沒上螢幕的幀、空的紀錄、超過大小上限時丟最舊的）各有一例。
  - macOS 建置與既有 UI 測試綠。
  - 實機（作者）開一次問題回報，看得到 3D 與 2D 兩段，2D 那段標明是「節拍」。

### V2（短期線）：固定的測試場景

一張 PR（可和 V1 合成一張），同樣不動 GameCore。

- 固定的存檔（台北實景；1、5、10、20 條線）、固定的鏡頭路徑（2D 平移縮放、3D 環繞、3D 跟車），每段 60 秒、固定種子。
- 從 Debug／TestFlight 的隱藏入口開，跑完用 V1 的格式出結果（可複製或附在問題回報）。
- **重複測試**：每台機型、每個情境連跑 **3 次**（App 冷啟動後各一次），報告每次的中位數、p95、嚴重停頓次數、最長停頓，再列三次的中位數與最大最小差。三次的 p95 差超過 20%，或嚴重停頓次數不一致，該情境標「不穩定」，不拿來校準或比較，要先查原因（發燙、背景下載、第一次載入）。
- 作者手邊的機型都跑，至少一台舊的（iPhone 12–13 級）、一台新的。模擬器只當 CPU 端的回歸參考，**不當 GPU 數字**。
- 驗收：
  - Linux 測試：固定的情境清單、鏡頭路徑與種子產生的序列逐次相同；重複測試的彙整（中位數、差、「不穩定」的判斷）算對。
  - 實機（作者）：至少一台機型的完整三次結果貼得出來。
- 結果用來：校準 417 的三級上限（250,000／600,000／1,000,000）、判斷 419、420 有沒有效、找出 2D 該修的地方。

### V3（長期線）：顯示層對照實驗，不進正式 App

**暫不開工**（作者 2026-10-26）。以下只是之後的範圍，開工前再定。

- **RealityKit**：在實驗用的 target 或分支，用同一份 3D 邏輯產生的網格，畫 V2 的同一個場景，量同樣的數字；記下要寫多少行、哪些功能做不到（自訂 shader、陰影、上千個會動的實例）。
- **Unity／Godot**：不裝進 App。只做兩件：
  1. 在 Linux 用 Swift 靜態庫加 C 的小程式，量「每幀把 1,000 列車的位置經 C 介面讀出來」要多少時間。**這只是介面的微型測試**：它說明這個介面本身會不會太慢，不代表接進 Unity／Godot 的整體成本（引擎端的處理、建置、除錯、記憶體搬移都不在裡面）；
  2. 從官方文件查證：現行授權條款、SwiftGodot 的 iOS 支援、GLB 匯入、CI 建置要什麼。
- 結果寫成表：同場景的 GPU ms／幀間隔 p95／嚴重停頓／記憶體高點／App 大小，加上 §4 每格的實際答案，與下面的製作與維護成本。

### 長期比較要看的（看結果前先定）

長期的引擎比較**不以單一效能門檻決定**（作者 2026-10-26：不以快 30% 作唯一門檻）。每個選項都要有下面四類的實際數字或紀錄，一起比：

1. **效能**：同場景、同畫面的 GPU ms、幀間隔 p95、嚴重停頓次數、最長停頓、記憶體高點、App 大小（V2 的量法、各跑 3 次）。
2. **製作成本**：在 V3 的實驗裡實際記錄做出同一個場景花的工（session 數或小時）、碰到的阻礙；加一款新車、一種新街景各要經過幾步、哪些步要人工。
3. **維護成本**：
   - 工具：35 個模型工具要不要改、改多少；程式產生的車型配方能不能照用。
   - 測試：現有 Linux 測試能照用的比例；搬走的邏輯要不要另寫測試、能不能在 Linux 跑。
   - CI：建置要什麼環境、授權啟用、每次建置多久。
   - 升級：引擎或系統框架每年升級要跟著改什麼（看該引擎近兩年的升級紀錄）。
   - 學習：美術與實作 session 要學什麼新工具。
4. **功能缺口**：作者列出想要的畫面功能（光影、天氣、粒子、後製等），每個選項做得到與否、要自己寫還是現成。

判讀：

- **繼續自研**：V1、V2 照數字修完後，舊機（iPhone 12–13 級）3D 的幀間隔 p95 在目標內（60 Hz 時 20 ms 內、30 Hz 時 40 ms 內）、嚴重停頓接近 0，而且功能缺口用自研補的成本沒有明顯高過換掉。
- **寫遷移方案**：某個選項在四類加總後明顯較好：效能較好是條件之一（例如 GPU ms 或 p95 好 30% 以上可當參考），但製作與維護成本若明顯較高，效能好也不換。
- 判讀由遊戲規劃依四類的數字寫成決策，附每類的依據；作者可以推翻。
