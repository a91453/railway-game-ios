# 台灣地理資料包（`geo-scene-reference-clean`）：能用在哪、和遊戲的資料誰比較好

日期：2026-10-20。基準是遊戲 `main` 91fdce4，參考庫 `b3af6d8`（commit「mapp」）。
讀者：作者，以及之後開工的 session。

作者 2026-10-20：「我在隱私資料夾建立了台灣地理資料，幫我看一下有哪些可以使用到遊戲，並且跟現有優先順序比較」，接著「順便看遊戲內資料跟這份資料誰的比較好，還是需要各取優點融合」。

> **怎麼做出來的**
> - 讀了資料包的說明檔（`00_READ_ME_FIRST.md`、`SANITIZATION_REPORT.md`、`THIRD_PARTY_NOTICES.md`、`DATA_USE_NOTICES.json`），盤點 `source/public/` 的資料與 `source/src/` 的程式，並對照遊戲 App 已打包的資料（`RailwayGameApp/Resources/RealWorld/`、`RealRailways/`、`tools/`）。
> - 同類的資料，在 Linux 雲端容器用暫時的 Python 腳本實際比對（沒有提交；用到 shapely、pyproj、h3、pmtiles、mapbox-vector-tile、scipy、pyosmium，只裝在 scratchpad）。需要第三方評判時，用 osmtoday.com 2026-10-20 的台灣 OSM 整包檔。
> - **VERIFIED**：文中的數字都是這樣跑出來的。**UNVERIFIED**：沒有改遊戲程式，也沒有在 App 裡試。

## 1. 結論

- **優先順序不變**（§16、§17）。這包裡沒有一項比甲線的 M3，或乙線的「建議站點」更該先做。它的用處是讓已經排好的項目變便宜。
- **遊戲比較好的，不用融合**：鐵路線形、車站位置、地形高度、居民人口。
- **要融合的**：
  1. 新車站命名用的地名：加上內政部的聚落；
  2. 旗津區的鄉鎮外框：用官方的；
  3. 21 個「approx」景點：用官方點位校正其中幾個；
  4. 日夜人口：拿白天與夜間的比例，補上「只算居民」的限制。這項要先查出處，跟乙線的 R1 一起做。
- **只有這包有、遊戲沒有的**：廟（內政部登記＋OSM，有主神）、百大宗教活動、古蹟、溫泉、地方文化館、公有市場。給 3D 生活感那條線與 §16 第 5.5 項（節慶、景點新種類）用。

## 2. 這包是什麼

一個台灣地理儀表板網站的去敏版本：634 MB、2,084 個檔；約 690 份 GeoJSON／JSON、42 份 PMTiles、20 個 Three.js 程序化場景（沒有 GLB）。帳號、追蹤、後端與部署都已拿掉，程式不能直接建置。

大半內容和鐵路經營無關：醫療、犯罪、毒品防制、垃圾車、殯葬、漁業、環境監測、氣候、航班、衛星、船、日本資料。

**授權**：
- 每份資料各自標了來源與授權，多數是政府資料開放授權 1.0，或 OSM 的 ODbL。
- **Ookla 網速圖（4 份）是 CC BY-NC-SA 4.0，不能商用。遊戲要上 App Store，不用。**
- 標成 HOLD、DISPLAY_ONLY 或待確認的資料，照原狀態，不當成已授權。
- `religion/temples.pmtiles` 的 metadata 沒有出處欄，但每一筆有 `source`：`moi_temple_xml` 12,394 筆、`osm_overpass` 6,702 筆、`boch_heritage` 105 筆。用之前照這三種來源各自署名。

## 4. 融合的做法與排在哪

都不動 GameCore 規則，只改資料工具與 GamePresentation；第 4 項例外，它會跟 R1 一起動。

| # | 做什麼 | 改哪裡 | 排在哪 |
| --: | --- | --- | --- |
| 1 | 地名：`tools/place-names/` 多讀內政部的聚落（`place_names_moi.pmtiles` 的 `category=settlement`），和 OSM 同名而且在 500 m 內的算同一個；帶「?」的跳過。`DataSourceCredits` 加「內政部地政司 臺灣地區地名資料（政府資料開放授權 1.0）」 | `tools/place-names/build_place_names.py`、`taiwan_place_names.json`、`DataSourceCredits.swift`、`PlaceNamesTests` | 修正 lane 的小 PR，隨時可以做。和乙線的「建議站點」不同檔：那是真實車站，這是附近沒有車站時的地名 |
| 2 | 旗津區的外框：從官方的鄉鎮界取，和 1 同一個 PR | 同上 | 同 1 |
| 3 | 21 個 `approx` 景點：這包、OSM 與官方網站三方核對，位置確定的才改，`source` 寫來源 | `tools/tourism-spots/taiwan_attractions.json` 與 App 讀的資料 | 併進 §16 第 5.5 項（景點新種類），同一個 PR |
| 4 | 白天人口：先查 `taiwan_daynight_population` 是怎麼算的（原專案的上游文件不在這包）。查不到，就只當「白天比夜間多幾倍」的參考，用 economy-balance skill 量過再決定要不要用。可能的用法：車站周邊白天多出來的人，算成上班、上學的旅次；或用來判斷車站類型（辦公、商業） | `tools/real-world-population/`（新的格網檔）、`PopulationGrid` | 和 §17 的 R1 轉乘站一起評估；一樣改運量，一起量平衡，只動一次 |
| 5 | 廟：3D 的「廟埕與牌樓」改放在真實的廟址；大廟（百大、古蹟）用比較大的模型 | `tools/` 新的小工具（抽出地圖範圍內的廟）、3D 的資料 | **可以現在做**，由 3D 生活感那條線做（決策 259），和 2D 不搶檔案 |
| 6 | 節慶與景點新種類：百大宗教活動（鷄籠中元祭、頭城搶孤、平溪天燈節、大甲鎮瀾宮媽祖遶境進香、白沙屯媽祖徒步進香…）、古蹟、地方文化館、公有市場 | `DemandEvents`、`Holidays`、景點資料 | §16 第 5.5 項，位置不變。§17.2 的條件（甲線的 M2 之後）已經滿足（#842），照 §16 第 5 項的順序，排在放空模式、「這版新增」卡之後。節慶日期要換算農曆（`tools/holiday-calendar`）。這包沒有夜市，夜市照舊從 OSM 找 |
| 7 | 電腦的車照時刻表跑：`source/src/engines/RailEngine.ts`、`TraTrainEngine.ts`（由站的時刻找出所在區間、沿線內插），以及 `BusEngine.ts`（狀態是路線上的進度，不是位置；頭尾 60 秒淡入淡出） | R2 的畫面層 | R2 開工時當移植來源，寫進對照表。不提前 |

**四方**（第 1–5 項）：
- **玩家**：新車站更常叫得出真實的村名；景點與廟在對的位置，「在廟旁邊蓋站」的人看得到廟。不增加要做的決定。
- **開發**：1–3 只改資料工具與一個資料檔，Linux 測得到，GameCore 不動。4 會改運量，所以跟 R1 一起量，平衡只動一次。5 只在 3D 那條線。
- **美術**：廟的位置與大小對了，3D 的台灣味更足；不畫新圖。
- **音樂**：無。節慶（第 6 項）之後可以接節慶配樂。

**沒選的**：
- 整包換成這包的鐵路與車站：比遊戲的粗，系統也比較少。
- 用戶籍人口取代 WorldPop：格子太粗、數值複製，離島是戶籍不是常住。
- 等全部項目排到再一起做：1、2 很小，又能馬上讓新車站的名字變好，晚做沒有好處。

## 6. 不只鐵路：公車、渡輪、航空的參考（之後的方向）

作者 2026-10-20：「如果之後因為叫沿線，所以想不侷限在鐵路，公路也有線、航運、船運也有線，能參考嗎」。

**參考庫裡有的**：

| 種類 | 有的 | 沒有的 |
| --- | --- | --- |
| 公車、客運 | 這包：20 個縣市的公車路線形狀（`bus/`）、公車沿路線進度移動與淡入淡出（`src/engines/BusEngine.ts`、`src/three/BusScene.ts`）。`taiwan-rail-reference-clean`：43,363 個公車站牌的索引（`source/data/bus_stops_index.json`）、542 個鐵道車站各自 600 m 內的站牌與路線（`source/data/bus-transfer/`）。競品研究 #832（City Transport Manager 是公車經營遊戲）。`OpenWorld` 的環島公路路線與交通規則（`play/src/world/taiwan-route-data.js`、`play/src/game/traffic-rules.js`） | 路線沒有台北市，也沒有站序與班次；即時到站要 TDX 金鑰（`bus_providers.json`），不用 |
| 公路 | 這包：國道交流道 207、服務區 22、省道里程與號誌（`geo/`） | 車流量；遊戲的貨運只走鐵路（決策 155） |
| 航空 | 這包：16 座機場範圍，有 ICAO／IATA（`geo/airports.geojson`）、`FlightScene.ts`、歷史航跡的畫法（`docs/features/historical-flight-trails/`） | 航線與班次；歷史航跡的資料不在包裡，原專案標 `license_status=unverified`；載客量要接 API |
| 船運 | 這包：277 個港區範圍（多數是漁港，`geo/port_polygons.geojson`）、`ShipScene.ts`、AIS 船位的程式 | 渡輪航線與班次：整個參考庫都沒有（`world-rail-reference-clean` 的 12 個城市也沒有）；AIS 是即時資料、沒有附檔 |

**和現在的排序**：公車接駁（抽象化）在 §13、§14 是 2.30–2.55 分；機場樞紐、纜車與渡輪、航空競爭、汽機車競爭在 §15.2 是 3.0 分以下、不排。作者 2026-10-16 說遊戲「太複雜」（決策 254），多一種交通工具就多一套要管的事，所以**不插隊**：排在 §17 的甲、乙兩線做完、上過 TestFlight 之後。三種都要動 GameCore、升存檔版本。

**要擴時的順序**：
1. **公車接駁**：參考最多。先做成從車站伸出去的線，不用道路路網：用 542 站的轉乘資料決定接得到哪裡，客人轉進鐵路；和 R1 轉乘站同一個方向，排在 R1 之後。
2. **離島渡輪**：一條水上的線只要兩個港口與班次，不用鋪軌，大半可以沿用路線與時刻表；也解鎖景點工具因為「鐵路到不了」略過的 6 個（澎湖七美、馬祖、蘭嶼、小琉球、綠島、金門水頭，`tools/tourism-spots/build_tourism_spots.py`）。航線與班次要另找資料（例如航港局的公開資料），先查授權。
3. **航空**：最後。國內線少、和高鐵重疊，比較像「機場樞紐」的轉乘站，不是玩家經營的線。

**四方**：
- **玩家**：「沿線」不只鐵路，離島景點也到得了；但先做成自動的接駁，不讓玩家一台一台派公車。
- **開發**：公車接駁可以不做道路路網；渡輪重用路線與時刻表；航空的資料最缺。三種都要升存檔版本。
- **美術**：公車、渡輪要新的圖示與 3D 模型；船、飛機的 3D 程式只參考動態，外型照 art-style 重畫。
- **音樂**：渡輪可以有出港的汽笛；公車不用。

**沒選的**：
- 現在就加公車：核心玩法還在收尾，第二套系統會讓「太複雜」更重。
- 先做航空：資料最缺，和高鐵重疊。
- 做完整的道路路網讓公車在路上跑：要道路的建造、路口與塞車，等於另一個遊戲；先用抽象的接駁看玩家要不要。
