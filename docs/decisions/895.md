### 895. 地標也自己註冊，一棟一檔；地標的匯入工具合成一支（LANDMARK-REGISTRY）

2026-11-20，雲端工作串「地標改成跟列車一樣逐棟登錄」（協調者派工），分支 `claude/project-thread-82y9rb`。作者先問「遊戲建築要改跟地標一樣拆分放嗎」，確認是「改跟列車」；評估後作者同意（「都行」），並補一條：「那列車舊的不強搬 現在有更新計劃了 記得用新格式」。號碼依 #2118 登記。

不動 GameCore、存檔版本、golden schema、golden、replay；畫面一個頂點都不變（§3）。

## 1. 問題

列車從決策 782 起一款車一組檔，兩款車同時做也不會衝突。地標還沒有這樣：

- 香港十棟、福岡三棟和海外地標共用一個 enum（`Map3DHongKongLandmark`），每加一棟要改 case、經緯度、高程好幾個 switch，還有共用的材質表（11 月這個檔被改了 7 次，福岡三棟就是一棟一張 PR 輪流改）。
- 網格擠在共用的大檔裡（`Map3DHongKongLandmarkMeshes.swift` 1.08 MB、`Map3DFukuokaStudioMeshes.swift`、`Map3DOverseasLandmarkMeshes.swift`）。
- 匯入工具有三支：`tools/hk-landmarks/glb_to_swift.py`、`tools/sunmoon-landmarks/glb_to_swift.py`、`tools/tpe-mrt-stations/glb_to_swift.py`，讀 GLB、併點、編碼的程式各抄一份，只差座標軸、z 有沒有號、要不要套節點的變換。

評估（同一串）也查過：建築與地標本來就是鏡頭走到哪個區塊才建、地標只在它所在的區塊解碼，模型包約 314 MB 是列車、車輛與路邊道具，所以拆檔**不省記憶體**，好處是並行不衝突與交件、審查一致。一般城市建築（照 OSM 輪廓生成）與 kit 配方不拆。

## 2. 做了什麼

1. **`Map3DLandmarkRegistration`**（`Map3DLandmarkRegistry.swift`）：一棟地標的 `id`、所在地圖、經緯度、腳的高程、自己的色票（`Map3DPalette` 的色，順序與 `--materials` 相同，像列車的 `meshPalette`）、哪幾格是玻璃（窗格線）與樓層線玻璃、編碼的近景與遠景、和真的一樣的長寬高。解碼搬成共用的 `LandmarkMesh.decodedLandmark`，香港 enum 的 `decoded` 也改呼叫它（同一套程式，香港的色由它自己的材質表給）。
2. **`Map3DLandmarkRegistryList.swift`**：一行一棟的清單，`.gitattributes` 設 `merge=union`，和列車的清單一樣。
3. **場景**：`addHongKongLandmarks` 先放香港 enum 的十棟，再放註冊的地標，做法不變（在場景裡、不壓到地面軌道、近景遠景、腳下的地不重畫）；回傳改成放了哪些的名字（enum 的 raw value、註冊的 id）。
4. **福岡三棟搬進新格式**：`Map3DFukuokaTower.swift`、`Map3DFukuokaDome.swift`、`Map3DHakataStation.swift` 各放 registration，`…Mesh.swift` 由工具寫。`Map3DFukuokaStudioMeshes.swift`、`Map3DOverseasLandmarkMeshes.swift` 刪掉；香港 enum 拿掉福岡三個 case，材質表拿掉只有福岡用的七色（香港的網格只用前十二色，重寫出來逐位元組相同）。
5. **一支工具** `tools/landmarks/glb_to_swift.py`：新地標寫自己的 mesh 檔（`--enum`、`--materials`、`--centre`、`--source`）；`--legacy hongkong|sunmoon|tpe-mrt` 寫還沒搬的三個共用檔。舊的三支刪掉；三個共用檔用新工具重寫，**除了開頭說是誰產生的那三行，一個位元組都沒變**（PR 裡記比對）。`tools/fukuoka-map/fukuoka_tower.py` 改用它的讀檔與寫檔，寫 `Map3DFukuokaTowerMesh.swift`。
6. **測試**：新 `Map3DLandmarkRegistryTests`（清單與原始碼裡的 registration 一致、每棟有鎖檔、近遠景尺寸與置中、遠景面數 ≤ 近景一半、色票每色都用到、每張地圖合計 ≤ 60,000 面、壞掉的編碼不收、每棟的網格雜湊照 `tools/landmarks/locks/<id>.json`）；福岡三棟放在地圖上的測試搬到 `Map3DFukuokaLandmarksTests`；`Map3DPaletteGuardTests` 加查註冊地標的色票。加一棟新地標不用改任何測試。

## 3. 為什麼畫面不變

福岡三棟換成自己的色票後，編碼裡的材質號碼變了，但每個三角形解出來的位置、顏色、玻璃層都和以前一樣；放的順序也一樣（香港十棟之後，塔、巨蛋、博多站）。用 `Map3DMapLoadReportTests` 的場景摘要比：福岡（天神、博多，買全部路線）與香港的每個場景、四種預建區塊的摘要，改之前與改之後相同（PR 裡記數字）。

## 4. 舊的不強搬

作者 2026-11-20：「那列車舊的不強搬 現在有更新計劃了 記得用新格式」。

- 註冊表之前的列車（手寫的台鐵、高鐵、捷運車）與地標（香港十棟、日月潭、北市捷運站、台北的廟）**不為了換格式專程搬**。
- 照更新計畫重做、改外形或改塗裝時，**同一張 PR 順便搬進註冊表**：列車照決策 782，地標照這個決策。派工單與接回的 PR 寫明「這次一起搬」。
- 這條也寫進素材庫 `a91453/railway-assets-private-2` 的 `docs/studio/studio-brief.md` §4（接回遊戲）第 5、6 條。

## 5. 五方

| 角度 | 理由 | 分 |

| 玩家 | 畫面不變；之後的地標可以並行做，來得快 | 2 |

| 美術 | 交件與審查和列車同一套；每棟自己的色票直接寫 `Map3DPalette` 的名字 | 2 |
| 音樂 | 無 | 1 |

加權（§19 的尺）2.45。

其他選項（沒選）：

- 一般城市建築與 kit 配方也拆：一般建築是程式照 OSM 輪廓生成的上千棟，沒有「一棟一檔」可拆；kit 配方本來就按 kit 分檔。
- 改用 `.m3dmodel` 資源檔（台北的廟那樣）：App 小不到 0.5 MB，但要動 Xcode 專案與 `makeModels` 的載入路徑，雲端驗不到；之後若把地標搬進地圖包再一起考慮。
- 香港十棟這次一起搬：作者說舊的不強搬，等重做時再搬。
- 色票沿用共用的材質表：每加一個新色還是要改同一張表，又是衝突點。
