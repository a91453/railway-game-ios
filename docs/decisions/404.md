### 404. Swift 分片快到 20 分上限時，CI 先警告；每片用 swift test --parallel

2026-10-24，遊戲規劃 session_013dJ7tvDYJnhe7XjXCE5cNi 派工，實作 session_016VsuVC61edGEaS3rfsHJkS。號碼依 #1041：決策 404；存檔版本、golden schema 不動；SaveFixtures、ReplayFixtures 不動；GameCore 不動。

## 問題

`ci.yml` 每個 Swift 分片的 job 上限是 20 分鐘（`timeout-minutes: 20`）。測試一直在加、在變慢，分片的時間就跟著慢慢變長。到現在都是**撞到上限、main 變紅之後**才重新分配：`swift-shards.sh` 開頭的歷次紀錄裡，2026-10-13、10-14、10-21、10-23（兩次）、10-24 都是這樣，最近一次（main 82fffc7，run 40081281220）擋住了 87 版的發版。

為什麼每次都在事後才發現：

- 被取消的 job 不會印出「Slowest classes」的摘要。要知道各類別花了多久，得下載整份 job log 自己算。
- 新加的類別沒人點名，就落進 `rest`（10-24 的 `Map3DPlatformClearanceTests`，113 s）。
- `CLASS_WEIGHTS` 裡的權重沒人核對（`Map3DSceneMemoryTests` 寫 57，實際 274 s）。

## 做法

都在 `.github/scripts/swift-shards.sh` 的 `run` 裡，只有**警告**（`::warning::`），不會讓分片變紅：

1. **job 時間**：`ci.yml` 的 Swift job 第一步把開始時間寫進 `JOB_STARTED`。測試跑完時，job 已經用了 `SHARD_WARN_SECONDS`（900 s，15 分）以上，就印一則警告，列出最慢的三個類別，叫人改 `classes_of`。這則警告也寫進 run 的摘要。PR 的 checks 頁面、main 的 run 頁面都看得到。
2. **快被取消時**：背景的 watchdog 在 job 用到 `SHARD_WATCHDOG_SECONDS`（1110 s，18 分 30 秒）時，印出到那時為止最慢的三個類別。之後 job 就算被上限取消，log 裡也有這一則，不用再下載整份 log 自己算。測試先跑完的話，watchdog 會被停掉。
3. **權重**：一個類別跑了 `CLASS_WARN_SECONDS`（60 s）以上，`CLASS_WEIGHTS` 裡卻沒有它，或實際時間超過權重的兩倍，就印警告。`selected` 的分組是照權重分的，權重錯了，某一組就會特別長。

沒有設 `JOB_STARTED`（例如在本機跑）時，只做第 3 項。

自我測試（`swift-shards-selftest.sh`）多了 8 項：job 用到 1000 s 會警告；剛開始的 job 不會；沒有 `JOB_STARTED` 時不會；沒權重的慢類別會警告；超過權重兩倍會警告；權重以內不會；watchdog 在上限前會警告；測試先跑完時 watchdog 會被停掉（不會留下 `sleep`）。

**門檻為什麼這樣定**：build 在慢的 runner 上要 4.5 分（10-24 的 rest 跑了 4m17s），開 container 約 40 秒。15 分就警告，是因為測試時間在不同 runner 上會差到 1.3–1.9 倍（swift-shards.sh 10-21、10-23 的紀錄）。在快的 runner 上跑到 15 分的分片，換到慢的 runner 就會超過 20 分。18 分 30 秒的 watchdog 留 1 分半，讓這則警告在取消前印出來。

## 五方

- 玩家：分片不會突然逾時讓 main 變紅、卡住 TestFlight（87 版就被擋過一次），修正和新功能能照時發。
- 鐵道迷：無。
- 開發：還沒逾時就看得到哪個分片、哪個類別在變長，在 PR 上就看得到，不用等到 main 變紅、再下載整份 log 自己算。沒有加依賴、沒有多一個 job，也不用多一份 API token。

## 沒採用的做法

| 做法 | 為什麼沒採用 |
| --- | --- |
| A. `plan` 或 changes job 用 GitHub API 讀最近幾個 main run 的各分片時間，超過 15 分就警告 | 要多一次 API 呼叫，`gh` 也要在 changes job 拿到 Actions 的讀取權限；main run 裡被取消的 job 讀不到類別時間；而且只看得到過去，看不到這個 PR 加的測試。分片自己量自己，比較準也比較簡單。 |
| B. 在 changes job 加總每個分片的 `CLASS_WEIGHTS`，超過一個預算就警告 | 權重取的是歷次最慢的那一次，現在好幾個分片加起來就超過 700 s，門檻定低了每次都會警告，定高了又抓不到。沒有權重的新類別（10-24 的問題）也加不進去。 |
| C. 警告改成讓分片變紅 | 測試全部通過，只是慢，就讓 PR 紅，會擋住跟這件事無關的 PR。慢不慢是規劃巡查時要看的，不是那個 PR 的錯。 |
| D. 照實測時間自動重新分配 `classes_of` | 分片每次跑的時間不一樣，自動分配的結果會一直變。pr_plan 又靠 campaign 分片點名的類別來決定 tier（GameCore 類別一搬就改變 PR 的 tier），所以還是要人看過再改。 |
| E. 把 timeout 拉長 | 派工單不准；拉長只是讓問題晚一點出現。 |
| F. 自動在 #1041 留言（像 full-lane-watch） | 第一版先只印警告；規劃巡查本來就看 main 的 run。之後如果警告常常沒人看到，再加。 |

## 容量

#1184 的 full-ci run（40083863654）全綠，但那批 runner 偏慢：job 最長的是 campaigns-12 19m31s、-8 19m09s、-11 19m04s。重新分配只能攤平，總量不會變少。三個方向：

| 做法 | 實測 | 代價 |
| --- | --- | --- |
| G. 再多分片，每片約 7 分 | #1186 加了第 18 個分片（campaigns-17）。run 40091661566（db54381）全綠，測試時間 6m32s（-5）到 14m18s（-11，job 19m33s，離上限 27 秒） | 每多一片多一次 build（約 4 分）與一個 runner；兩個 GameCore PR 同時跑已是 2 × 21 = 42 個 job，碰到帳號 40 的上限。要到 7 分得再加十片左右，做不到 |
| H. `swift test --parallel`（每個 batch 用 runner 全部的核心） | 本機 4 核：舊 campaigns-10（4 類 13 個測試）序列 839 s，`--num-workers 4` 423 s；新 campaigns-10（3 類）經 `swift-shards.sh run` 337 s。最長的單一測試（PassengerPlanKey 的 203 s）決定下限 | 不加 job、不加依賴；最慢的單一測試仍是瓶頸；CI runner 上的實測待做（下一步） |
| I. 讓最慢的測試變快 | BoardingPropertyTests 421–624 s、Map3DSceneMemoryTests 274 s、PassengerPlanKeyTests 343 s | 每個都是獨立的工作，也會改到測試本身 |

**選 H**（遊戲規劃 2026-10-24 的方向），G 已在 #1186 做了一次；H 在 CI 上撐不住時退回 G（把最長的分片拆開），I 留給個別的慢測試。

H 的做法（`swift-shards.sh`）：`SWIFT_TEST_WORKERS`（預設 1；`auto` 是 `nproc`）大於 1 時，每個 batch 加 `--parallel --num-workers N --verbose`。`ci.yml` 的測試步驟設 `auto`。

- **決定性與共享狀態**：`--parallel` 的每個測試在自己的 process 裡跑，全域狀態不共享。寫檔的測試都寫進帶 UUID 的暫存資料夾；寫固定路徑的只有重產 fixture 的測試，而且要設環境變數才寫，CI 不設。GameCore 本身是決定性的，跟執行順序無關。
- **「每個 job 剛好跑到它的類別」的檢查**：沒有 `-v` 時 log 只有「[k/N] Testing X」。加了 `--verbose`，每個測試結束時會印出完整的 XCTest 輸出（started、passed／failed 與秒數），原本比對「Test Case started」的檢查與類別計時照用。`--xunit-output` 的時間不能用（同時跑的測試時間一樣），所以沒用。
- **失敗 log**：失敗的測試印出完整輸出，一次一個，不會交錯；一個測試 crash 只讓它自己失敗（rc 1），其他繼續。watchdog 在 parallel 時另外列出「still running」：還沒開始印的測試，最多 4 個。
- **自我測試**多了：workers=3 會傳 `--parallel --num-workers 3 --verbose`；序列不傳；`auto` 可以；「many」會失敗並說明；parallel 下漏跑與失敗行的檢查；watchdog 列出還在跑的測試。
