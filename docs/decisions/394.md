### 394. 隧道裡的駕駛視角不畫地面上的東西

2026-10-24，作者原話：「如果在隧道或是地下能不能不要算地面上的建築物等切換視角的時候再計算會省gpu嗎」。遊戲規劃 session_01XsVqbA1A5wGtJbuAa881oT 派工，session_01AdAQTbXs639m7Yd3ZoxLE7 實作。存檔版本、golden schema、SaveFixtures、ReplayFixtures、GameCore 都不動；改的是 GamePresentation（新的 `Map3DUnderground`、`Map3DTrackCover.openings`）和 App 的 3D 畫圖（`Map3DMetalView.draw`、`Map3DPreviewScreen` 的雨）。

**規則**

1. **什麼時候算「在地下」**：同時符合才算。
   - 3D 地圖跟著列車，視角是駕駛室（`Map3DFollow.View.cab`）。
   - 鏡頭沒有在飛（切進、切出駕駛視角的 1.2 秒照舊全部畫）。
   - 列車車頭在隧道裡（`Map3DTrains.Head.inTunnel`）。
   - 每個洞口（`Map3DTrackCover.openings`，就是畫洞口牆的 `portalEnds`）都離眼睛超過 `near`（300 m），而且離眼睛畫得到的距離內（`depthRange.far`），洞口四周 12 m 的盒子都不在視野裡（`Map3DCamera.sees`，和 chunk 用同一個判斷）。
2. **不閃的方法（hysteresis）**：從「全部畫」進到「在地下」，距離和盒子都要再放大 1.25 倍（375 m、15 m）仍然看不到才算；已經在地下時，進到 300 m 或盒子一碰到視野，當幀就恢復全部畫。在 300–375 m 之間來回，答案不會變。
3. **在地下時畫的**：每個 chunk 的前 `baseIndexCount` 個索引（地面、軌道、道路、玩家的建物；隧道的 bore、燈、洞口牆、地下車站的月台都在這裡），列車（盒子與模型）和列車的影子。
4. **在地下時不畫的**：城市的完整建物（mesh 的其餘部分）、`far`、`close`、街具（props）、招牌（signs）、街景的人與車（連 CPU 的 `streetLife` 都不算）、日影的 shadow map pass（`sunDrawing`）、地面的柔影（chunk 的 shadows）、天空、雨（SwiftUI 的雨層）。
5. **不丟掉**：所有 Metal buffer 都照樣留著；chunk 的遠近細節狀態（`detailed`、`closeUp`）每幀照算，所以恢復那一幀就畫得完整。日影的 shadow map 在地下時不重畫，恢復時若已過時，當幀重畫一次。
6. 統計（3D 地圖右上角的 fps，點開的細節）在地下時多一行 `underground`。

**量到的**

- VERIFIED（Linux，`MAP3D_FRAME_REPORT=1 swift test --filter Map3DFrameCostReportTests.testTheCabUnderTaipei`）：台北市中心地下 15 m、駕駛視角、整個台北的實景場景，視野裡的 chunk：
  | 面向 | 全部畫 | 在地下 |
  | --- | --: | --: |
  | 東 | 316,285 三角形、120 draw | 59,058 三角形、36 draw |
  | 北 | 292,989 三角形、109 draw | 41,729 三角形、30 draw |

  另外少一個 shadow map pass（它自己會再畫一次附近的城市）。
- UNVERIFIED（需要實機）：GPU 毫秒數。Linux 沒有 Metal，`gpuMilliseconds` 只在 iPhone／iPad 上量得到。

**怎麼在實機上看**（TestFlight）

1. 開實景地圖，在台北地下段（例如台北車站到松山的地下化路段，或玩家自己蓋的隧道）找一列車，打開 3D 地圖、跟著它、選「駕駛室」。
2. 點右上角的 fps，打開細節：看 `GPU … ms`、`draws`、`triangles`，以及有沒有 `underground` 那一行。
3. 比較同一列車在隧道深處（有 `underground`）和剛出洞口（沒有）時的數字。山線的隧道（例如三義一帶）也可以看同樣的事。
4. 看洞口：列車接近洞口時，城市要在洞口看得到之前就已經在；看到「城市突然冒出來」，就是 `near` 不夠，回報給遊戲規劃。

**參考與先例**

- 作者的參考庫：`Railway/taiwan-rail-reference-clean/source/rail-3d/integration/map3d.js` 把地下的列車放在另一層透視著畫（`isUnderground`、`undergroundMaterial`），沒有在隧道裡不畫地面的做法；`tunnel-apertures.js`、`portal-clearance.js` 只管洞口的形狀；`OpenWorld/reference_snapshot/play/src/game/city-metro*.js` 也沒有。沒有可以搬的程式。
- 開源：portal culling（Teller & Séquin 1991 的 cell-and-portal 可見性；Godot 3 的 Rooms and Portals，MIT）。只取它的想法：「格子（隧道）裡只看得到格子本身，和從入口（洞口）看出去的東西」。這裡的隧道只有一種格子、入口就是洞口，所以不用建格子圖，直接看洞口近不近、在不在視野裡；沒有複製任何程式碼。
- 程式是這個專案自己的。

**五個角度**

- 玩家：在隧道裡跑久一點的駕駛視角，手機比較不燙、比較不掉幀；看出去一樣是隧道，接近洞口時城市已經在了，看不出差別。
- 鐵道迷：隧道裡本來就看不到外面；台北的地下化路段、山線隧道這些真實路段跑起來更順。不改任何路線資料。
- 開發：判斷放在 GamePresentation、用 Linux 測試鎖住（深處、近洞口、洞口在視野、其他視角、飛行中、邊界不閃）；App 只照一個布林略過工作，不丟 buffer、不重建 mesh。洞口用畫洞口牆的同一份 `portalEnds`，不會兩邊不一致。
- 美術：在地下時天空不畫，bore 外的縫看到的是清除色（天空的底色），和原本差不多；彎曲的隧道裡洞口在視野內但被牆擋住時照樣全部畫（保守，不會少畫）。
- 音樂：無。

**沒有選的**

- 沿著軌道算「前方幾公尺有洞口」：要走軌道圖、處理道岔和車站，判斷比較準但程式多；直線距離加視野的判斷比較保守（多畫，不會少畫），而且和洞口的形狀無關。
- 看 bore 能不能直視洞口（射線檢查牆）：彎道裡能更早不畫，但每幀要對 bore 的牆做檢查，成本和省下來的差不多。
- 在地下時把 chunk 的 base 也只畫 bore 附近的：要拆 mesh、多一份 buffer；base 本來就只佔約兩成的三角形。
- 在地下時把 mesh 放掉、出隧道再建：作者要的是切換時立刻有東西，重建要幾百毫秒，看得到。
