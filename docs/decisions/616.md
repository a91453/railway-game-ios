### 616. TestFlight 版號第一次執行不帶「.1」：119，重跑才是 119.2

2026-11-07，派工單 BUILDNUM（遊戲規劃第 53 任派），session_01YGNNukjT21RbsADWN6DuNi，分支 `claude/build-number-plain`。作者：TestFlight 版號不要「.1」，119 就顯示 119，不是 119.1。存檔版本、golden schema、GoldenScenarios、ReplayFixtures、SaveFixtures、GameCore 都不動；`testflight.yml` 的觸發條件與 secrets 不動。

## 做了什麼

1. **`testflight-preflight.sh`**：CFBundleVersion 原本是 `<offset + run number>.<attempt>`（118.1）。改成第一次執行（`GITHUB_RUN_ATTEMPT` = 1）只用 `<offset + run number>`（119）；按「Re-run failed jobs」重跑時（attempt ≥ 2）才是 `<n>.<attempt>`（119.2、119.3）。下一次新執行是 120。4 位／2 位的上限檢查照舊。
2. **`testflight-changes.py`**（What to Test 的「Changes since build …」）：上一版的號碼由 `build_label()` 照同樣的規則寫；run 118 以前第一次執行也帶 `.1`，所以加 `LAST_DOTTED_RUN = 118`，那些 run 仍寫成 `118.1`。上傳的是哪一次 attempt 照舊從 upload job 讀（只重跑 processing job 時 run 的 attempt 會變，build 不變）。
3. **處理檢查與 IPA 檢查**：`testflight-processing.py` 用 `BUILD_NUMBER` 原樣向 App Store Connect 查（`filter[version]`），`testflight-verify-ipa.sh` 原樣比對 Info.plist，兩者都不解析格式，只改了註解的例子。
4. **測試**：`testflight-selftest.sh` 的期待值改成 7、7.2、7.3、8、107、9999（9999.99 不變），排序檢查改成 `7 < 7.2 < 7.3 < 8 < 107`；`testflight-selftest-processing.py` 加 run 119 第一次（「build 119」）、重跑（「build 119.2」）、加 offset（「build 219」）與 `build_label` 對照表（118.1、118.2、119、119.2、119.3、120）；macOS dry run（`testflight-selftest-macos.sh ipa`）加一個 build 為 `7` 的 IPA 要通過，與期待 `7` 卻是舊式 `7.1` 要擋下。
5. **文件**：`docs/TESTFLIGHT_GITHUB_ACTIONS.md`〈Build number〉與驗證表、`docs/HANDOFF.md` 兩處「run 編號.1」。`.github/testflight-whats-new.md` 的標題在 #1914 合併後改成 `0.5.0 (119)`。App 裡 `WhatsNew` 的 id（如 `2026-11-07-119-1`）玩家看不到，不改。

## 為什麼不會重複、會遞增（根據）

- Apple TN2420〈Version Numbers and Build Numbers〉：build number「must consist only of '.'s and numbers and must begin and end with a number」、「may have up to three components separated by periods」，同一版本內「must be in ascending sequential order」；合法例子有 `1`（一段）與 `1.1.1`。所以 `119` 與 `119.2` 都合法。
- 比較方式：App Store Connect 的拒絕訊息（TN2420 引的 `'1.6095'` 不比 `'1.6096'` 高）與 CFBundleVersion 的說明都把它當以點分開的整數一段一段比。TN2420 沒寫缺的段怎麼算；兩種讀法——缺的段當 0，或段數少且前段相同的較小——都得到 `118.1 < 119 < 119.2 < 119.3 < 120`。兩種讀法只在 `119` 對 `119.0` 有差別，而這個規則從不產生 `.0` 或 `.1`，所以不受影響。
- GitHub：run number 每次新執行加一、重跑不變；run attempt 每次重跑加一。第一次是 `n`、之後是 `n.2`、`n.3`…，同一個 run 內不會重複，下一個 run 的 `n+1` 比它們都大。
- 舊號碼：run 118 以前的 build 第一段都 ≤ 118，新的第一段從 119 起，不會撞到。
- UNVERIFIED：還沒有一次真的重跑上傳 `<n>.2` 給 App Store Connect；第一次執行的 `119` 會在 119 發版時驗到。

## 五個角度

- 玩家：TestFlight 與 App 裡看到的是「0.5.0 (119)」，和作者、遊戲規劃平常說的版號一樣，不用記多出來的「.1」。
- 鐵道迷：none。
- 開發：只改 preflight 一行規則與 What to Test 找上一版的寫法；重跑仍拿到沒用過、比較大的號碼，舊 run 的號碼照實寫（`LAST_DOTTED_RUN`）。
- 美術：none。
- 音樂：none。

## 沒選的

- 一律只用 run number、重跑也不加 attempt：重跑失敗的 release job 會再上傳同一個號碼，App Store Connect 會拒絕（組合必須不重複）。
- 重跑從 `n.1` 起（第二次執行叫 `.1`）：號碼和 GitHub 的 attempt 差一，對 log 時容易弄錯；用 `.<attempt>` 第幾次執行一看就知道。
