### 775. iOS 建置開 Xcode 26 編譯快取（CAS 跨 run 存）

2026-11-15，雲端 thread session XCODE-CAS（「試 Xcode 編譯快取縮短 CI」工作串，`claude/project-thread-mssk9n`）。主規劃派工，`CI_SPEED_ANALYSIS_2026-11-15` 第 3 項（五方 2.05）；決策 754「沒有選的」裡的「Xcode 26 的編譯快取另案評估」。號碼依 #2118 登記；存檔版本、golden schema、fixture、GameCore 不動。只改 `.github/workflows/ios-build.yml`。

## 1. 問題

iOS 的 PR job 約 26 分，其中建置 9–18 分（11-15 的 4 個 PR run：11.1、9.2、17.6、10.3 分）。每個 run 從零編：跨 run 存 DerivedData 沒用，因為 checkout 每次都換新檔案時間，Xcode 照時間判斷全部重編（決策 754）。

## 2. 做法

- Xcode 26 的編譯快取（swift-build 的 `COMPILATION_CACHE_ENABLE_CACHING`）：每次編譯以「輸入內容＋參數」的雜湊查 CAS，查到就直接放回結果，不看檔案時間。CAS 預設在 `$(DERIVED_DATA_DIR)/CompilationCache.noindex`（swift-build `Settings.swift`），這裡就是 `$RUNNER_TEMP/DerivedData/CompilationCache.noindex`。
- 三個 Xcode build（build job、full lane 的 second／lessons、iPad）都加 `COMPILATION_CACHE_ENABLE_CACHING=YES`、`COMPILATION_CACHE_LIMIT_SIZE=3G`，並都加 `SWIFT_EMIT_LOC_STRINGS=YES`（原本只有 build job 有）：編譯參數一樣，快取才共用。
- **誰存、誰讀**：每個 job 在建置前用 `actions/cache/restore` 拿同一 Xcode＋模擬器 SDK 的最新一份（key 前綴 `xcode-cas-v1-<雜湊>-`）。只有 build job、而且不是 pull request 的 run（main 的 nightly full lane、手動 run）建置成功後存一份（`<前綴><run_id>-<attempt>`）。PR 讀得到 main 的快取；PR 自己存的只有它以後的 run 讀得到，又佔 10 GB 的空間，所以不存。
- **只留一份**：新的 job `prune-compilation-cache`（`actions: write`）在存好之後刪掉同一分支其他 `xcode-cas-` 開頭的快取。存檔沒列出來就什麼都不刪。
- **失敗不擋**：讀、存、刪都 `continue-on-error`；沒快取就是從零編，和以前一樣。
- **會不會編出舊的東西**：key 是編譯器算的輸入內容雜湊，內容或參數一變就是另一個 key；actions/cache 的 key 只挑哪一份 CAS，不決定哪些檔重編。

## 3. 量到什麼

Xcode 26.6、iPhone 模擬器 SDK 26.5、macos-26 runner，「Build for iOS Simulator」這一步：

| run | 快取 | 建置 | Cache hit／miss | 說明 |
| --- | --- | ---: | ---: | --- |
| 11-15 前 4 個 PR run（43679047717、43677614581、43674974385、43673104165） | 沒開 | 11.1、9.2、17.6、10.3 分 | — | 基準 |
| PR #2247 run 43681652307 | 開，沒有可讀的 | 11.6 分（iPad job 12.9 分） | 0／160 | 開快取本身不拖慢；CAS 591 MB |
| 本分支手動 43683983030 | 開，沒有可讀的 | 13.1 分 | 0／160 | 存快取 5 秒（壓縮後 168 MB） |
| 本分支手動 43686001541 | 讀上一個 | **1.25 分** | 161／0 | 讀快取 6 秒；翻譯檢查照樣過（`.stringsdata` 也從快取放回）；UI 測試照跑照過 |

- 全部命中時建置從約 11–13 分降到 1.25 分。這是最好的情形（同一份程式碼）。
- 一般 PR 讀的是 main 前一晚 full lane 存的那份：沒改的模組（多半是 GameCore、App 以外的套件）命中，改過的模組照樣重編。GamePresentation 是整模組 -O，改到它就整個重編，所以只改 GamePresentation 的 PR 省的是 GameCore 那段；這部分沒量（推論約 2–4 分，`CI_SPEED_ANALYSIS_2026-11-15`）。合併後頭幾個 PR 的建置時間要回頭看。
- main 第一次有快取是合併後的第一個 nightly full lane（或手動 run）。

## 4. 五方

- 玩家：PR 早一點綠、版本出得快一點（2）。
- 鐵道迷：無（1）。
- 開發：iOS 建置少等；改動只在 workflow，壞了就是退回從零編（4）。
- 美術：無（1）。
- 音樂：無（1）。

## 5. 沒有選的

- PR 也存快取：每個 PR 一份、各數 GB，會把 Linux 的 `.build` 快取（決策 545）擠出 10 GB；而 PR 的快取只有它自己以後的 run 讀得到。
- 遠端快取服務（Tuist、Bitrise 的 plugin）：要外部帳號與新相依，作者沒同意加相依。
- release-archive.yml 的 Release 建置：參數不同、一天最多一次，不在這次。
