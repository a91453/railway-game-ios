### 878. 真實全買世界的 tick：一分鐘裡重算好幾次的答案改成借用（TICK-REAL）

2026-11-18，雲端工作串「優化模擬 tick 並清查死結」（TICK-REAL，協調者派工；作者：「進量做 難度高一點的才值得 看要優化3d或是tick 死結 等」）。
只動 GameCore 的備忘（memo）與量測用的兩個報告測試；規則一條都沒改：存檔版本、golden schema、`GoldenScenarios/`、`SaveFixtures/`、`ReplayFixtures/` 都不動。
死結清查是同一張派工的第二部分，交給另一條工作串（DEADLOCK-SWEEP，決策 877）。

**問題。** tick 以前量的都是為量測做的地圖（決策 703、TICK-L1、TICK-2）。玩家最重的局是真實地圖把在售路線全部買下（共線綁賣決策 862、地下站決策 867 之後），
這種世界在 GamePresentation 的 debug build 裡鋪一次要幾分鐘，所以沒人量過。這次先做出量的工具，再量、再改。

**量的工具（留在 repo，只在要求時跑）。**

- `BoughtWorldSaveTests`（GamePresentationTests）：`BOUGHT_WORLDS=<目錄>` 把香港、羅瓦涅米、整個台灣「在售路線全部買下」的世界各存成一個 `SavedGame`（簡單、寫實兩種規則，共六個）。
- `SavedWorldTickReportTests`（GameCoreTests，改 GameCore 後一分鐘建好）：`SAVED_WORLD=<存檔>` 一個 tick 一個 tick 跑，印每 tick 的時間（平均、中位數、p95、最久、最貴的八個時刻、每小時）、
  死結數，與每 60 tick 一次的世界雜湊（世界的 JSON、鍵排序、FNV-1a，和 `DEPOT_RETURN_CHECKSUM` 同一種，決策 805）。**兩個 build 的雜湊逐一相同＝這次改動沒有改到世界的任何一個位元。**
  `SAVED_WORLD_AUDIT=1` 時每個借用的答案都重算一次比對，不同就當場 trap。

**在 main 量到什麼**（雲端 Linux、4 核、同時有別的程序在跑；`normal` 速度一 tick 一分鐘，一天 1,440 tick）：

- 香港全買（22 站、6 線、36 列車）：平均每 tick 208 ms（尖峰小時平均 430–480 ms、最久 1.2 秒）。也就是遊戲的一分鐘要算 0.2 秒，60× 以上的倍速跟不上。
- 台灣全買（161 站、15 線、149 列車）：平均每 tick 約 3 秒（中位數 2.1 秒、p95 9–10 秒、最久 26–31 秒），一天要跑 69–74 分鐘：遊戲的一分鐘比真實的一秒還久，1× 都跟不上。
- 取樣（`perf`，香港一天）：有跟車時一步是一秒，一分鐘 60 步；每一步都重問的東西裡，
  `runDepotEntryCandidates` 12.3 %（其中 `trainsInTheWay` 9.7 %、`heldRunDepartures` 8.0 %）、`preferredPath` 8.2 %、`opposingParts` 5.7 %、`runTrip` 4.2 %、`plannedDirections` 3.9 %
  是「同一分鐘裡、世界沒變卻重算」的；其餘（`cover(of:)` 16 %、`authority(of:reserved:)` 9.2 %、`settleClaims` 6.8 %、`pathAhead` 5.1 %、`foulingNodes` 4.8 %……）是逐秒真的在變的那一層。
- 根因之一：`RouteMemo` 把路徑與曲線借給下一次 `advance` 的鍵是「整條 `ServiceLine`」，而每發一班車 `runDays`／`lastDispatch` 就變，所以**每次發車整份路徑備忘都丟掉**。真實時刻表的線幾乎每分鐘都在發車。

**做了什麼（五項，全部是「同樣的問題、同樣的世界就給同樣的答案」）。**

1. **路徑備忘的鍵去掉發車時刻。** `RouteMemo.Key.lines` 改存 `withoutDispatchTimes`（`ServiceKey` 本來就這樣）。路徑與曲線只讀線的停靠站、指定路徑與側別，從不讀哪一班發過。
2. **班次行程備忘。** `runTrip(of:_:for:memo:)`：鍵是（線、這一班停哪些站、起站、環狀方向、列車停在哪）。它只讀這些，以及路網、線的站與性能、號誌開關，一份備忘裡都不變。
   `dueRun`、`dueRunDeparture`、`dueRunHasStarted`、`dueRunPreferredDeparture`、`readyRunTrain` 都多一個帶備忘的版本，調度、機廠、死結判斷改用它。
3. **一條線的計畫備忘。** `linePlans(of:service:length:memo:)`：`workedOutOpposingParts` 裡每條線、每種車長的計畫方向與發車點，鍵是（線、服務、車長）。
4. **派車共用一份備忘，但 holders 自己一份。** `dispatchTrains` 以前每問一列車就開一份全新的備忘（holders、計畫方向、路徑、行程全部重算）。
   現在整輪派車共用步進的備忘，唯獨 holders 換成自己那一份（`DirectionMemo.HolderStore`、`exchangeHolders(with:)`），見下面「一個沒改的發現」。
5. **「擋路的車」與「該走卻走不了的班次」的答案備忘。** `GameWorld.WorldAnswers`：`trainsInTheWay(memo:)`、`heldRunDepartures(memo:)` 的答案，
   鍵是（全部列車、去掉發車時刻的線、現在時刻、這一步有沒有 `stepTraffic`），再加 holders 的變動戳記（`holderChanges`）：列車、線、時刻都沒變，而且那份備忘的 holders 也沒被動過，才借用。

**為什麼結果一樣。**

- 每一項的鍵都是那個函式讀到的全部輸入（上面逐項寫了讀什麼）。一份備忘活在一次 `advance` 裡，或由 `RouteMemo` 在鍵（路網、線、號誌開關……）相同時借給下一次；路網或線一變就整份丟。
- 假設世界（`secondsUntilARouteFrees` 的 `var moved = self`、死結排解的 `replacing(_:)`）會和真世界共用備忘，所以 5 的鍵含全部列車與時刻，而不是只看「這一步」。
- 測試裡的檢查（遊戲不付這個成本）：`GameWorld.answerAudit` 開著時，每個借用的答案都當場重算、`precondition` 相等。`AnswerAuditTests` 在全部錄好的指令串上跑這個檢查，重播的雜湊照舊相等。
- 六個全買世界各跑一天，新舊 build 的 24 個整點雜湊逐一比對（見下表）。

**一個沒改的發現（已交給死結清查）。** `settleClaims` 會讀現在時刻（空車跟車的 `isDueToLeave`、`leavingCover`），但 holders 的備忘只用列車當鍵，
所以同一份備忘裡「列車沒變、時刻變了」會拿到舊時刻算的 holders。這是既有行為；改它會改到世界，不屬於「不改行為的加速」，所以這裡刻意**照原樣保留**：
步進那份 holders 照舊可能是舊的，派車那份照舊每秒新算（第 4 項分開的原因），也因此沒有預先把 holders 算熱。DEADLOCK-SWEEP 回報已用小場景證實它是 bug（逐秒、一分鐘一步、十分鐘一步三種走法世界不相等），修法在決策 877。

**五個角度。**

- 玩家：買很多線之後開高倍速比較跟得上（香港全買每分鐘的計算少一成六到一成七）；世界一個位元都沒變，所以不會有「更新後班次不一樣」。台灣全買少四成（平均每 tick 3 秒 → 1.7 秒），但遊戲的一分鐘仍要算 1.7 秒，還是跟不上，要等第二批。
- 鐵道迷：無（時刻、調度、號誌規則都沒動）。
- 開發：以後量真實世界的 tick 有固定工具（存檔一次、GameCore 一分鐘重建、雜湊對位元），改動的對錯不靠猜；備忘的鍵與稽核寫在同一處。
- 美術：無。
- 音樂：無。

**找過什麼。** 熱點全在本專案自己的進路保留、調度與機廠規則裡，這次是替這些函式的答案補備忘與鍵值，沒有可以搬的對象，所以沒有去參考庫或開源專案找，也沒有新增相依。程式都是本專案自己的。

**後來（2026-11-18，雲端工作串「加快台灣全買的模擬 tick」，派工單 TICK-TAIWAN）：台灣全買的待避推論與找路少找幾次。**
台灣全買一個 tick 仍要 1.7 秒，比香港慢的倍數遠超過列車數的比例。先在 main 的台灣簡單晨峰（08:00–08:40，平均每 tick 5.4 秒）取樣：
`trafficPlan` 45 %（其中 `planTrafficOvertakes` 30 %：`preferredTrafficSharesCorridor` 9.1 %、`overtakeTrackFree` 7.7 %、`preferredTrafficCommon` 7.6 %；`planHeadwayOvertakes` 6.2 %），
以及每次找路都問的 `sidings(except:)` 24 %（其中 `station(id:)` 18.5 %：每個月台都在 161 個車站裡從頭找一次）。香港的取樣看不到這些，因為它只有 22 站、36 列車。
規則一條都沒改；五項都是「同樣的問題給同樣的答案，只是少找幾次」：

1. **`sidings(except:)` 先查一次哪些站是機廠。** 照 `station(id:)` 的意思（同 ID 的第一個車站）建一次表，再看每個月台。結果一樣。
2. **`planTrafficOvertakes` 只看共用兩站以上的列車對**（`trafficPartners`），依原來的列車對順序。共用不到兩站的一對，`a` 的每一站只對到一個點（各站的第一個點），
   一串共同點要嚴格遞增才算，所以一定是空的、什麼都不提；以前它照樣逐點比對完才發現。共同點改用「各站第一個點」查表，和 `firstIndex(where:)` 是同一個點。
3. **`preferredTrafficCommon` 的分段與各段各站的第一個點，一份計畫算一次**（`TrafficRuns`）。以前每一對列車都把兩邊再切一次、再逐點找。和 `x.first { 同站 }` 是同一個點。
4. **`preferredTrafficSharesCorridor` 的軌道段在一份計畫裡借用**（`TrafficPlan.corridors`，鍵是列車與兩個點）。它讀列車與點的車站、停靠、側別，不讀時刻；
   錨定（`applyTrafficAnchor`）只動時刻，所以整份計畫裡不變。以前同一條線的一列車和每一列對手比一次，就找一次路。
5. **`planHeadwayOvertakes` 不問快車沒經過慢車所在站的對**（`headwayOvertake` 第一個會看的條件就是快車在那一站有點，沒有就回 `nil`，之前沒有任何副作用）；
   **`trafficOppositeCounts` 在同樣的班次組合下借上一份計畫的**（`TrafficParts.opposite`，鍵是各列車的 `Run` 依序）。反向計數只讀各班次的名目方向，名目方向由 `Run` 決定（點由 `TrafficParts.points` 依 `Run` 借用）。

**為什麼結果一樣**：上面逐項寫了。測試 `TrafficPairsTests` 比對 `trafficPartners` 與暴力法、`preferredTrafficCommon` 與舊的逐點掃描；`TrafficPlanKeptTests`（借來的計畫和從頭算的相同）也涵蓋第 5 項的借用。
