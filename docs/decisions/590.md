### 590. 試算指令的預覽不在畫面更新裡算：新路線的價格與開線卡片的預覽等主執行緒下一輪

2026-11-05，派工單 CRASH112（session_01YGNNuoNBB6PagaAcLNEY8h，遊戲規劃第 48 任派），分支 `claude/crash112-stack`。存檔版本、golden schema、GoldenScenarios、ReplayFixtures、SaveFixtures 都不動；GameCore 不動。

## 為什麼

作者回報 TestFlight 0.5.0 (112.1)，iPhone17,1、iOS 26.7.2，「在新增路線車站時當機跳掉」：`EXC_BAD_ACCESS (SIGSEGV)`，Thread stack size exceeded，主執行緒，約 89 層、沒有遞迴。堆疊（112.1 的 `bef26cae`，main `72f8b46` 上同一條路沒變）：

```
0  ___chkstk_darwin
1  specialized static GameSession.addTrains(...)           LineStaffing.swift
2  GameSession.apply(_:to:)                                 AutoService.swift
3  GameSession.feasible(_:on:)                              AutoService.swift
4  GameSession.lineOpeningPreview.getter                    AutoService.swift
5  GameSession.workOutLineDraftSummary(stops:)              LineDraftSummary.swift
6  GameSession.lineDraftSummary.getter
7  GameSession.mapLineDraft.getter                          MapLineDraft.swift
8  BuildConfirmation.init(_:linesPanelOpen:openLines:)      MapBuildConfirm.swift
9  … MapView.timedBody.getter（巨大的 closure）→ GeometryReader → SwiftUI …
```

選第二站時，地圖上的 ✓（`BuildConfirmation`）在 MapView 的 body 裡讀 `mapLineDraft`，它要新路線的價格（`lineOpeningPreview`，決策 264），價格是把「開這條線」真的在世界的副本上跑一次：建線、補越行站、買車、放車（`autoServicePlan` → `feasible` → `apply` → `addTrains`）。快取（`LineOpeningMemo`）只省掉重算，第一次還是在 body 裡算。

**量到的**（Linux，Swift 6.4.0，**VERIFIED**）：

- `MemoryLayout<GameWorld>.size` = **2032 bytes**：GameWorld 是 struct，每個副本整塊在堆疊上；2 KB 分散在六十多個欄位（最大的是 `CompanyAccounts` 176、`ScenarioState?` 113、`FreightState?` 112），沒有一個值得單獨搬到堆上。
- 每個函式一進來就保留整個堆疊框（不管走哪條路）。`swift build -c release`（-O，x86_64；arm64 相近）後反組譯每個函式開頭的 `subq $N, %rsp`：

  | 函式 | 堆疊框 |
  | --- | --: |
  | `GameSession.apply(_:to:)`（AutoService） | 61,440 |
  | `addTrains(...)`（specialized） | 29,680 |
  | `feasible(_:on:)` | 17,800 |
  | `lineOpeningPreview.getter` | 14,664 |
  | `autoServicePlan(creating:...)` | 13,288 |
  | `passingLoopsNeeded(...)` | 13,080 |
  | `mapLineDraft.getter` | 6,520 |
  | `workOutLineDraftSummary(stops:)` | 4,168 |

  當機那條路上光 GamePresentation 就約 **145 KB**，疊在 SwiftUI 的 view 更新與 MapView `timedBody` 那個巨大 closure（偏移 +34524，它自己的框 Linux 量不到）上，用完 iPhone 主執行緒的堆疊。
- 在 Linux 測試裡直接量主執行緒用掉的堆疊（`StackProbe`：先在呼叫者下方 2 MB 塗滿標記，呼叫後找最深被改的字；-Onone）：選好兩站後讀一次 `mapLineDraft`，**當場算 260–272 KB**。

## 規則

- **app 的 session 裡，試算指令的預覽不在畫面問它的那一刻算**：`lineOpeningPreview`（新路線的價格，地圖 ✓、路線面板、草稿那一行）與 `lineConfirmationPreview`（決策 303 的開線卡片）在快取不是目前這份草稿與世界的時候回 `nil`（「還沒好」），並排一個主執行緒的 `Task` 在下一輪算（`GameSession.waits(for:workOut:)`，`WaitingPreview.swift`）。那個 Task 從主執行緒的事件迴圈開始跑，堆疊很淺；算好後 `previewsWorkedOutLater` 加一，問過它的畫面（讀過這個被觀察的值）再看一次，拿到快取的值。同一個預覽等著時再問幾次都只排一次。
- **按下去的動作不等**：開線卡片的「確認」（`confirmLine()`）用 `lineConfirmationPreview(now: true)` 當場算，和以前一樣；按 ✓（`confirmLineDraft()`）本來就不讀價格。
- **算的部分搬到自己的函式、不內聯**（`workOutLineOpeningPreview(stops:)`、`workOutLineConfirmationPreview`，`@inline(never)`）：堆疊框是函式一進來就整塊保留的，原本讀快取的那一刻也要先付 14.6 KB；拆開後讀快取的 `lineOpeningPreview(now:)` 只剩 40 bytes。
- **草稿那一行（`lineDraftSummary`）價格還沒好時不存快取**，價格到了再算一次，才會補上價格。
- **只有 app 打開**：`GameLauncher.worksOutPreviewsOnTheNextTurn`（app 的 `makeLauncher` 設 true）交給它開的每一局；測試、`HeadlessGame`、GameSim 預設 false，照舊當場算，所以現有的測試與 golden 都不用改。
- 玩家看到的：選好第二站時，✓ 旁的「約 N 分 · NT$…」與「附 1 列車」晚一個主執行緒輪（一個畫格之內）出現；開線卡片的價格同樣。

**改後量到的**（**VERIFIED**，Linux）：

- -O 反組譯：`lineOpeningPreview(now:)` 40 bytes、`lineConfirmationPreview(now:)` 4,632；✓ 等待時整條路（`mapLineDraft` 6,520 + `lineDraftSummary` 408 + `workOutLineDraftSummary` 4,168 + `GameWorld.lineDraftRun` 4,584 + 40）約 **16 KB**，改前約 145 KB。
- `StackProbe`（-Onone）：同一個 `mapLineDraft`，**等待 24–32 KB**（其中 16 KB 是探針自己留的邊），當場算 260–272 KB。
- 測試 `WaitingPreviewTests`：
  - `testTheLinePriceComesOnTheNextTurn`：app 模式下讀 `mapLineDraft` 沒有價格、沒有快取、草稿那一行不存快取；`await` 下一輪後和當場算的 session 完全相同，而且只算了一次。
  - `testTheCardPreviewWaitsButConfirmDoesNot`：卡片的預覽等下一輪，「確認」不等，線照樣開出。
  - `testTheMapCheckTakesLittleStackWhileTheScreenAsks`（只在 Linux）：當場算 > 128 KB、等待 < 48 KB。
  - **修前紅、修後綠**（**VERIFIED**）：把 `lineOpeningPreview(now:)` 裡等待的那一行拿掉（等於改前的行為）重跑 `--filter WaitingPreviewTests`，6 個斷言紅，其中堆疊那支量到「等待」也是 260 KB（267,208 > 49,152）；放回後 3 支全綠。
- 實機有沒有不再當機：**UNVERIFIED**，要 113.1 請作者在同一個動作（新增路線、選第二站）上試。

## 五方

- 玩家：選站時不再閃退；價格晚一個畫格出現，看不出差別。
- 鐵道迷：無。
- 開發：改動只在 GamePresentation 的兩個預覽與 launcher 一個旗標，GameCore、存檔、golden、replay 都不動；其他方案（把 GameWorld 整個包成堆上的 COW box、在大堆疊的執行緒上算）要改 GameCore 的六十多個欄位或把 session 的格網拆成值，113.1 來不及也風險大。同樣的機制（`WaitingPreview` 加一個 case）之後可以套到其他預覽。
- 美術：無（✓ 的版面不變，只是價格那行晚一格）。
- 音樂：無。

其他考慮過的：

| 選項 | 為什麼沒選 |
| --- | --- |
| A. GameWorld 改成堆上的 COW box | 每個框都變小，但要改 GameCore 全部欄位的存取，完整 tier、效能要重量；2 KB 沒有單一大欄位可搬 |
| B. 在 16 MB 堆疊的執行緒上同步算 | 這條路讀 session 的人口、地形、水、覆蓋等格網與 `self`，`GameSession` 是 `@MainActor`，搬到別的執行緒要先拆成值 |
| C. 只縮這幾個框（`inout` 取代副本、拆函式） | 61 KB 的 `apply` 是幾十個副本與內聯的結果，一個一個拆效果不確定，arm64 上也量不到 |
| **D. 不在 view 更新裡算（選這個）** | 只在 app、只改兩個預覽；確定把模擬移出 SwiftUI 的深堆疊 |
| E. 拆小 MapView `timedBody` 的 closure | 該做，但它的框只有 macOS／iOS 才量得到；放進下一步 |

## ViewThatFits 裡的 ForEach（CRASH101 同型，順查）

`main` 上掃了 `RailwayGameApp/Views` 所有 `ViewThatFits`（含它裡面呼叫的同檔 helper，往下三層）：放在裡面的 `ForEach` 都已經是 `@Sendable` 的 row closure（CRASH101、CRASHSWEEP 修過：`Map3DPreviewScreen.choices`、`FollowBar.speeds`、`YearEndReport` 兩個 grid、`LinesPanel.lineFilterPicker`、`FinanceCompositionChart.rows`、`NetworkControls.modePicker`），`LinesPanel.lineRow` 那個已經改成不用 `ForEach`。剩下兩個不是 `@Sendable` 的在 `Menu` 的內容裡（`LinesPanel.lineFilterMenu`、`lineSortMenu`）：選單內容在選單打開時才建，`ViewThatFits` 量版面時只量選單的 label，這次不改，寫進下一步。
