### 627. 暫停、繼續、換速度不再丟掉站長記住的答案：整點不再停一下

2026-11-07，派工單 HOUR-STALL（遊戲規劃第 54 任的 side session 派），分支 `claude/hourly-stall`。號碼依 #1579 的登記：決策 627。存檔版本、golden schema、GoldenScenarios、SaveFixtures、ReplayFixtures、GameCore 都不動；只改 GamePresentation 的 `GameSession`（`logging`）與 `LineLossFixes.swift` 的兩個備忘，加一支只在要求時跑的報告測試 `HourTickReportTests`，和 `AutoServiceTests` 的一段回歸檢查。

## 問題

另一個 session 在 iPhone 18 Pro Simulator 驗證 main `dc48fd10`（Debug 版，橫拿，沒帶 `-ui-testing`）：高鐵示範 07:00 開局、切到 10× 之後跑到 11:00，畫面上的時鐘停在 10:59:59 約 3.3–3.5 s，再停在 11:00:01 約 1 s；同一段時間 `hud.lag` 寫著「The game really runs 2.7 times real time」。主執行緒有回應，卡的是模擬的 tick。同一份程式的 Release 版看不到。

## 原因

每個遊戲整點（:59:59 → :00:00 那個 tick），遊戲迴圈在主執行緒外算站長的建議（決策 330）。建議裡最貴的兩項有備忘：

- 「哪條線賠最多」：`LineLossLeaderMemo`（決策 194）；
- 「哪條線沒有地方交會」：`PlaceToPassMemo`（決策 597）；高鐵示範在全 -Onone（`dc48fd10` 的 Debug）下一次要約 0.6 s（Mac）。

兩個備忘和這個小時的建議（`hourAdvice`，決策 459）都以 `commandRevision` 為鍵，而 `commandRevision` 在 `world` 每次被 tick 以外的東西改到時加一。**暫停、繼續、換速度也是這種改動**（`logging(.setSpeed)`、`.pause`、`.resume`），所以玩家一暫停或繼續，三個記住的答案就都不算數，下一個整點全部重算。10× 一個 tick 是 1 遊戲秒、每 100 ms 一個，時鐘就停在 10:59:59 直到那個 tick 算完。

驗證的 session 在 10:59 前按了暫停再繼續（它的 `run-debug-2`：600× → 1× → 10× → 暫停 → 繼續），所以停了。換速度不一定會：tick 正在算的時候選的速度先記著（`heldSpeed`），等 tick 收尾（`finish`，`isApplyingTick` 為真）時才套上，那時 `commandRevision` 不加；tick 之間選的才會加。暫停與繼續每次都加。

這三項讀的是軌道、路線、各線的列車和結算到哪一天（`lineLossSettledDay`），沒有一項讀時鐘的速度或是否暫停。

## 做法

`GameSession.logging(_:_:)`：動作是 `.setSpeed`、`.pause` 或 `.resume`（只改時鐘速度的指令）時，把兩個備忘與 `hourAdvice` 從改之前的 `commandRevision` 搬到改之後的（`keepStationMasterWork(from:)`；`LineLossLeaderMemo.keep(from:to:)`、`PlaceToPassMemo.keep(from:to:)`）。只搬原本就在舊版本上的；別的指令照舊丟掉重算。所有暫停、繼續、換速度（速度選單、暫停鍵、事件暫停、跳過夜晚、3D 跟車的速度上限、tick 收尾時套上的 `heldSpeed`）都經過 `logging`；收尾時套上的本來就不加 `commandRevision`，`keepStationMasterWork` 什麼都不做。

其他以 `commandRevision` 為鍵的備忘（地圖泡泡、路線預覽、軌道檢視）不動：它們在主執行緒外重算或很便宜，不會讓時鐘停。

站長說的話、說的時機都不變：搬過去的答案就是重算會得到的答案（`AutoServiceTests.testTheLoopKeepsTheLineWithoutAPlaceToPassBetweenCommands` 暫停、繼續、換兩次速度之後再跑 30 個 tick：備忘一次都沒重算，每小時的建議仍等於重算的）。拿掉修正，這段檢查會紅（三個斷言失敗，**VERIFIED**，Mac）。行車結果逐位元相同：GameCore 沒動，改的只是 GamePresentation 什麼時候重算一個不影響世界的答案。

## 量到的

`HourTickReportTests`（`HOUR_TICK_REPORT=<小時>`，預設 11）：高鐵示範由 `GameSession.LoopTick.work()` 與 `finish` 從 07:00 用一般速度（600×）跑，10:58 切到 10×（一個指令，像玩家那樣），整點前後的 tick 一個一個量，慢的 tick 在副本上拆開量。`HOUR_TICK_FROM_START=1` 則 07:00 就切 10×、之後沒有指令。

Mac（Apple Silicon，12 核，Swift 6.4.2，`swift test`；**VERIFIED**）：

| 10:59:59 → 11:00:00 那個 tick | 全 -Onone（等於 `dc48fd10` 的 Debug App） | 全 -O（`-Xswiftc -O`，接近決策 624 之後的 Debug App） |
| --- | ---: | ---: |
| 改前，10:58 換過速度 | 601 ms（站長建議 592，其中「沒有地方交會」重算） | 47 ms（站長建議 45） |
| 改前，07:00 之後沒有指令 | 9 ms | 2 ms |
| 改後，10:58 換過速度 | 9 ms | 2 ms |

Simulator（iPhone 18 Pro，iOS 27.2，Debug，`-ui-testing`，Mac 本機 Xcode；**VERIFIED**）：一支只在本機用、沒有提交的 UI 測試照驗證 session 的做法跑：開高鐵示範，600× → 60× → 1×（10:5x）→ 10× → 10:59:2x 按暫停、8 s 後按繼續，接著每約 0.3 s 讀一次 `hud.time`（一次讀取本身約 0.3 s）跨過 11:00，記時鐘停最久的一段。

| 版本 | 時鐘停最久 | 那時的 `hud.lag` |
| --- | --- | --- |
| `dc48fd10`（全 -Onone，回報的那版） | 10:59:59 停 **3.23 s**，再 11:00:01 停 0.94 s | 「3.3 times real time」 |
| `dc48fd10` 加這個修正 | 0.37 s（等於讀取間隔，整點前後每次讀都在走） | 無 |
| main `ff153451`（決策 624 之後，-O） | 0.32 s | 無 |
| 這個分支（main 加修正） | 0.33 s | 無 |

`dc48fd10` 那一列和回報的一樣（3.3–3.5 s 加約 1 s）。11:00:01 那約 1 s 也是同一件事：修正之後兩段都沒了。main 在決策 624 之後重算只要幾十 ms，0.3 s 的讀法看不出來；這個修正讓它連那幾十 ms 都不用算（Mac -O：47 → 2 ms）。只有換速度、沒有暫停的跑法（600× → 60× → 10×）在 `dc48fd10` 也沒停（0.36 s），原因見上面的 `heldSpeed`。

## 沒修、留給下一步的

- 開局第一個 tick（07:00）照舊要算一次「沒有地方交會」與全部乘客路徑：全 -Onone 約 0.95 s、全 -O 約 0.11 s（Mac）。決策 624 的「下一步」已記。
- 10:00:00 那個 tick 全 -Onone 約 0.35 s、全 -O 約 0.07 s：乘客路徑先算（`PassengerRoutesAhead`）約一半、推進約一半，是服務等級在 10:00 換的時候（決策 597「下一步」第二點）。不是這次的 4 s，-O 之後也低於 0.1 s。
- 真的改了路網、路線或列車的指令之後，下一個整點仍要重算一次「沒有地方交會」（決策 597 的設計）；全 -O 在 Mac 上約 45 ms。

## 五面向

- 玩家：換速度、暫停之後的第一個整點不再停一下；站長說的話不變。
- 鐵道迷：無（行車結果逐位元相同）。
- 開發：照現成備忘的做法，只多一個「從舊版本搬到新版本」的方法，只在三種只改時鐘的指令上用；另一個選項是讓換速度不加 `commandRevision`，但很多別的備忘與測試依賴它，改動面大，沒選。
- 美術：無。
- 音樂：無。
