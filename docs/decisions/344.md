### 344. 簡單規則下，列車可以進線的第一站的另一股

2026-10-22，遊戲規劃 session_014rYHMtmqA5bEMkBBuKu6PV 派工（NEXT_PRIORITIES §22.2 第 12 名，HANDOFF §5 的重現），實作 session_018gQPWzopcCfuR9gTAApKTj。號碼依 #231：決策 344；存檔版本、golden schema 不動。改的是 GameCore 的行車調度（決策 57 的方向保護），存檔格式不變。

**問題**：簡單規則（決策 258）沒有閉塞區間。在這個規則下，線的第一站有 2 股以上時，後到的列車可能整天等不到月台。

- 前一列照班次停在第一站，正好停在後到列車的路線所指的那一股。
- 後到列車改走別股（決策 57 的 `alternativeRoute`）時，空的那股被方向保護擋下。
- 原因：線的計畫從第一站的**每一股**出發（`plannedDirections`），所以每一股的進站路都算有列車要反方向走。
- 終點站的豁免（決策 278 的 `terminusTraversals`）只在有閉塞區間時才有。
- 結果：那一列和後面的列車一直等。這不算死結，也沒有警告，第 30 天起 0 人次。收購的平溪、集集、內灣線都是這樣，所以決策 315 的「後來」把站序反過來繞開。

**怎麼查的**（`diagnosing-bugs`）：

- **會紅的測試**：新的 `FirstStopBerthTests.testATrainTakesAnotherBerthOfALinesFirstStopWithoutBlockSections`，在舊程式上是紅的。
  - 場景：第一站 A 有正線 P1 和待避線 P2，終點是 B。
  - 線的列車 X 停在 P1，Y 從 B 開往 A。
  - 舊程式：Y 一直停在 B，`trainHoldingRoute` 指向 X。
- **證實的假說**：擋住 Y 的是線的計畫從 P2 出發的那一段。
  - 同一個場景打開閉塞區間時是綠的：A 的西邊是盡頭，所以決策 278 的豁免適用。
  - 把 X 從線上拿掉（線就沒有計畫）時也是綠的。
- **推翻的假說**：P2 本來就找不到路。沒有計畫時 Y 會進 P2，所以不是。
- **縮小時碰到、與這個 bug 無關的兩件事**：
  - 待避線兩端的道岔角度太大，軌道不相連。測試改用較緩的角度。
  - X 朝 B 停著時，它的保留延伸到 B 那側的道岔。測試讓 X 朝西停，和從 B 開進來停下的列車一樣。

**修法**（`ServiceDirections.swift`、`RouteReservation.swift`）：

- 線的計畫分開算第一段：從第一站每一股出發的那一段，記下哪些行經只有那一股出發的列車會走。
  - 判斷：別股出發的第一段沒走過、計畫之後各段也沒走過的，就是只有那一股出發才走的（`DirectionMemo.Planned.departures`）。
- 往這一站的列車，路上逆著這些行經走時不算違反方向保護（`firstCallTraversals`）。
  - 條件：別的列車與別的計畫都沒有反方向走同一段。
- 為什麼安全：列車要從那一股出發，一定先停在那一股；往那一股的路要那一股空著才走得，走了就整段占住。所以兩者不會相遇，和決策 278 終點站的道理一樣。
- 為什麼沒有閉塞區間也可以：決策 278 不在無閉塞時豁免，是因為跟車的列車會停在咽喉裡。沒有閉塞時，`alternativeRoute` 找到的路是整段占住才走（`reservingDeparture` 的第一個分支，`reserving` 不跟車），不會停在半路。跟車走別股的分支只在有閉塞區間時才用，那時跟車只停在閉塞的邊界（決策 278）。
- 只用在 `alternativeRoute`（出發時改走別股，與死結判斷的 `couldGo`）。`berthChange`、待避（`passingPlace`）、照班次的待避線（`ScheduledOvertakeTracks`）照舊。
- 不記住結果：計畫本來就記在 `DirectionMemo.plans`，同一次推進裡只算一次。
