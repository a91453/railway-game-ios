## 熱點

開路線（93 ms）：

- 73% 是 `createLineFromDraft` 的 `feasible(autoServicePlan(...))`。這是在副本上把自動排班整個試一遍。但它只在「替玩家排路線的遊戲」（`runsLinesForThePlayer`：簡易規則的經營模式）才用得到。寫實規則下，算完就丟。
- 其餘幾乎都在指令本身的 `abandonUnservedPassengers` → `servedWaitingLegs` → `isScheduled`。

蓋車站（255–343 ms，而且越按越慢）：

- 59% 是 `networkPlatformDraft` 試並排月台。它在 `pricingCopy()` 上把指令整個跑一遍，包括 `abandonUnservedPassengers`。但它只要知道 GameCore 拒不拒絕這一對月台，以及並排月台的渡線要畫在哪裡。
- 其餘是真的指令，同樣是 `servedWaitingLegs` → `isScheduled`。這裡的 `lineHeadway` 對每個服務等級都呼叫 `serviceRoundTrips`。後者把這條線的第 0…n 個服務重開一次行程（`journey` → `drive`，每一段都在全網找路）：同一條線的同一個服務，一次指令裡開了「等級數 × 服務數」次。

## 規則

1. **GameCore：一條線的服務共用行程**（`PassengerDemand.swift`）。
   - `isScheduled(_:pattern:journeys:)` 先開那個服務自己的行程，再開它之前的服務，然後用同一組行程算每個服務等級的班距。開過的行程記在 `journeys` 裡（線 → 服務 → 行程，開不出來也記）。
   - `servedWaitingLegs` 在一次呼叫裡共用這份記錄。
   - 同一個世界、同一條線、同一個服務，行程是同一個值：`journey(of:service:)` 只讀世界，不改世界。所以結果和每次重開一樣。
   - 每個 tick 的 `isServed(_:memo:)` 照舊每次自己記，不共用 `DispatchMemo`。這次只動建設那條路，風險最小。
2. **GamePresentation：寫實規則下不試自動排班**（`GameSession.createLineFromDraft`）。只有 `runsLinesForThePlayer` 的遊戲，才先在副本上試那份排班；其他遊戲本來就不用它的結果。
3. **GamePresentation：並排月台用預覽副本試**（`NetworkSession.networkPlatformDraft`）。
   - `pricingCopy()` 改成 `trackPreviewCopy()`（決策 521）：那個副本不去走每一群等車的乘客。
   - GameCore 拒不拒絕、價錢、軌道的幾何，都不看乘客（決策 521 寫過）；渡線也是在那個副本的軌道上規劃。所以結果不變。
   - 真的指令照舊在 `performCommand` 裡跑完整的 `abandonUnservedPassengers`。
