### 413. main 的 push 照 PR 的 tier 跑，每晚跑一輪完整的 `ci.yml`

2026-10-25，遊戲規劃 session_01KvN8GrLosqRswrXMQgVQir 從 CI 瘦身稽核（`docs/research/CI_PRUNE_2026-10-25.md` 第 4 項）選了 D，實作 session_01P66bY6nFU891b1C3sYwkRU。號碼依 #1041：決策 413；存檔版本、golden schema 不動；GoldenScenarios、SaveFixtures、ReplayFixtures 與讀它們的測試不動；`Swift CI (gate)` 的名字不動；`testflight.yml` 不動。這是決策 185（PR 的 tier）的後續。

## 問題

決策 185 讓 PR 只跑它改的檔案需要的 tier，但 main 的 push 一律跑全部 19 個分片。10-18 到 10-25 這一週 main 合了 406 個 PR，`ci.yml` 的 push run 有 208 輪跑了完整 tier，每輪約 234 分 runner 時間：一週 48,775 分，是全部 Linux 用量（96,713 分）的一半。同一個改動在 PR 上已經照它的 tier 跑過，合進 main 再跑一次全部，多出來的大多是 PR 沒選的 campaign，而 30 天裡 push run 抓到的真的 bug（10-11 HolidayTests、TutorialSessionTests，10-06 NetworkBuildingSessionTests）都在 `rest`，沒有一個是只有完整 campaign 才抓得到的。

## 決定

- **push**：`swift-shards.sh decide` 對 push 也用 `plan`，跟 PR 一樣分 full、presentation、fixtures、tests-only、none；不看 label（`full-ci` 只對 PR）。比的還是「上一輪成功的 push run 的 head」（`push-base`），所以一輪被取代或紅了，下一輪的檔案清單包含它們，選的 tier 至少跟它們合起來一樣大，沒有改動會沒被測。找不到 base（沒有成功的 run、API 失敗、不是祖先）就跟以前一樣跑全部。
- **每晚**：`ci.yml` 加 `schedule`，台灣 01:37（UTC 17:37）。跑全部分片，但 `main` 最新的 commit 已經有一輪成功、而且 `rest` 分片成功的 `ci.yml`（只有完整 tier 有 `rest`；手動跑的、tier 剛好是 full 的 push、或前一晚的同一個 commit）就跳過（`swift-shards.sh head-full-run`）。查不到（API 失敗）就照跑。
- **發版**：要發的 commit 要有一輪綠的完整 `ci.yml`：每晚那輪，或手動 `workflow_dispatch`（手動一律全部跑）。push run 不再算（CLAUDE.md、`docs/HANDOFF.md` §1.2）。

## 不會漏測的理由

- PR 的 tier 規則本來就是「這些檔案可能影響的測試」：GameCore、Package、CI 腳本、共用的測試檔都是 full；GamePresentation 只影響 GamePresentationTests（GameCore 的測試看不到它）。push 用同一條規則，main 上每個改動至少跑過它 PR 那時的測試，再加上合併後的那一輪。
- PR 的 base 舊、合進去之後跟別的 PR 交互：兩個都改 GameCore 就都是 full；一個 GamePresentation、一個 GameCore 的組合，GameCore 那個是 full。剩下抓不到的是「只有完整 campaign 才會露出來、而 tier 沒選到」的交互，最多晚一天由每晚那輪抓到。
- `full-lane-watch.yml` 只看 iOS App Build 的 full lane（`workflow_run` 的 iOS App Build），不讀 `ci.yml`，不受影響；`ios-full-lane.yml` 也不讀 `ci.yml`。
- `push-base` 的「上一輪成功」現在指那一輪的 tier 過了。下一輪從那裡比，選的是之後的檔案；之前的檔案已經照它們的 tier 測過。每晚那輪補完整。

## 量與估計

- 稽核用 `plan` 算了最近 218 個合併：full 24、presentation 99、none 95。push 會把被取代的幾個合併一起算，tier 會往上靠，估計 push 的完整 tier 從每週 208 輪降到約 60 輪，presentation 約 100 輪（5 個 job），加上每晚 7 輪：一週約 22,000 分，省約 25,000 分（Linux 的四分之一）。一週後照稽核的方法再量一次。
- 每晚那輪約 234 分；`main` 當晚沒有新的合併（或最後一個合併的 push 剛好是 full）就跳過。

## 五方

權重照 `docs/HANDOFF.md` §1（玩家 .30、開發 .25、美術 .15、鐵道迷 .15、音樂 .15），選項與分數在稽核第 4 項；選 D（2.10）是規劃的決定，稽核推薦的 B（2.95）要另外設一組每次 push 跑的輕分片，D 不用新的分片定義。

- 玩家：PR 那時已照 tier 測過，push 只少了「沒選到的 campaign」；發版的 commit 一定有一輪完整的，玩家拿到的版本跟以前一樣全部測過。
- 開發：PR 等 runner 的時間變短（push 不再一次佔 21 個 job）；campaign 的 bug 最多晚一天才看到，那天合的東西要二分。
- 美術：無。
- 鐵道迷：無（golden、存檔、replay 的測試照舊，fixtures 一改就跑讀它們的類別）。
- 音樂：無。
