### 418. 問題回報帶上裝置記下的卡住與 App 結束原因（MetricKit）

2026-10-26，遊戲規劃 session_01TS89hbaHPJiFJycqrKiK5z 派工，實作 session_01KWqgRo5LR2pwGzb34wNEeC。號碼依 #1041：決策 418；存檔版本（74）、golden schema 不動。GameCore 不動。

**為什麼**：TestFlight 87.1 的 iPhone 17 測試者回報「會頻繁當機」，作者確認是卡頓；App Store Connect 沒有當機報告，作者不想聯絡測試者（`docs/research/PLAYER_FEEDBACK.md` 0.5.0 (87.1)）。卡在哪裡只能猜。iOS 內建的 MetricKit（Apple 的框架，不是新依賴）在主執行緒卡住約 250 ms 以上時記下當時的呼叫堆疊（`MXHangDiagnostic`），也統計 App 在畫面上與背景結束的原因（`MXAppExitMetric`）。這個決策讓下一次有人回報卡頓時，一份問題回報就帶著卡在哪裡。

**做了什麼**：

- **收**（App，`RailwayGameApp/App/DeviceDiagnosticsRecorder.swift`）：一個 `MXMetricManagerSubscriber`，App 一啟動就註冊（`RailwayGameApp.init`），並讀一次 `pastDiagnosticPayloads`／`pastPayloads`。系統在自己的佇列上交來的每份 payload 取 `jsonRepresentation()`，交給 GamePresentation 整理後寫進 `Application Support/Diagnostics/device-diagnostics.json`（加鎖，原子寫入）。不進存檔、不上傳、不送任何地方。
- **整理**（GamePresentation，`DeviceDiagnostics.swift`，Linux 測試 `DeviceDiagnosticsTests`）：
  - 從 `MXDiagnosticPayload` 取卡住（hang）、當機（crash）、處理器用量過高（CPU exception）、寫入過多（disk write exception）、啟動很慢（app launch）：時間（payload 的 `timeStampEnd`）、長度、App 版本與系統、當機的 exception／signal／原因，與被歸屬那條執行緒（`threadAttributed`）的堆疊。MetricKit 的堆疊樹根是最外層（執行緒開始的地方），每層的 `subFrames` 是它呼叫的；這裡從根往裡，每層跟著樣本數最多的那個（同數取第一個），走到最內層，再倒過來由內往外列，最多留 48 層，更外面的只記還有幾層。核心的位址（`0xffff…` 起）沒有 binary 可以換名字，不留。
  - 從 `MXMetricPayload` 只取兩項：`applicationExitMetrics`（畫面上／背景各種結束原因的次數，只留大於 0 的）與 `applicationResponsivenessMetrics.histogrammedAppHangTime`（那天的卡住依長度分幾格）。其他（電量、網路、GPU、記憶體峰值…）不取。
  - 上限：事件最多 12 筆（最新的），日資料最多 3 天，檔案最多 256 KB（超過就從最舊的事件丟）。同一筆不重複收（App 每次啟動都會再讀一次過去的 payload）；同一天（begin、end 相同）的日資料用新的取代。
  - 每個欄位都可有可無；讀不懂的欄位跳過，不會因此丟掉整份。不是 payload 的資料什麼都不加。
- **送**（`SettingsView.swift` 的 `ProblemReportRows`，設定的「關於」與遊戲選單的回報都用它）：「回報問題」的訊息最後多一段（有紀錄時才有）：最新 5 筆事件，每筆一行標題（什麼事、何時、多久、版本與系統）加堆疊；更早的只寫還有幾筆；接著最新一天的結束原因次數與卡住長度分布。訊息照舊由玩家在分享表單選 App、按下傳送才送出。底下的說明多一句「最近遊戲卡住或意外關閉的時間與位置（只記在這台裝置上）」。沒動 `ProblemReport` 本身與 `ProblemReport.current`（決策 417 的 #1271 也改它們，避開衝突）。
- **隱私**：MetricKit 的資料是 App 自己的效能與堆疊位址，不含個人資料、帳號或裝置識別碼；它只存在 App 自己的檔案裡，只有玩家自己分享時才離開裝置，與決策 127 的回報（版本、機型）一樣。`PrivacyInfo.xcprivacy` 的收集資料型別維持空的：Apple 的「收集」指 App 把資料傳出裝置，這裡沒有；MetricKit 也不是 required-reason API。只在檔案的註解補一句。

**怎麼讀一份回報**（給作者與遊戲規劃）：

回報最後一段長這樣（數字是範例）：

```
這台裝置記下的卡住與結束：
2026-10-25 21:03:00 UTC 卡住 1.50 s (0.5.0 (87.1), iPhone OS 26.0 (23A341))
  0 libsystem_kernel.dylib 0x1e8801ce4 +0xce4 8E8E…
  1 RailwayGame 0x105a1c64c +0x138a4b 1C2B3D4E-0000-1111-2222-333344445555
  2 SwiftUI 0x19a998a28 +0x100a27 9F9F…
  3 RailwayGame 0x1058eaaa8 +0x6ea7 1C2B3D4E-0000-1111-2222-333344445555
  4 dyld 0x1be42df08 +0x3ef07 D1D1…
結束 2026-10-24 21:00:00 UTC – 2026-10-25 20:59:00 UTC：畫面上：正常 3、超過記憶體上限 1、卡太久被系統結束 2；背景：被系統收回記憶體 5。
那天的卡住，依長度：250 ms–500 ms ×4、500 ms–1000 ms ×1。
```

1. **卡在哪個函式**：堆疊每行是「層數、binary、位址、+offset、binary 的 UUID」，第 0 層最內層（卡住時最常停在的地方），越往下越外層，最後通常是 `dyld`（App 的起點）。最內幾層多半是系統函式庫（`libsystem_kernel.dylib`、`Metal`、`CoreFoundation`…）在等或在做事；往下找**第一個 binary 是 `RailwayGame` 的層**，那就是遊戲自己叫了這件花時間的事的地方；再往下的 `RailwayGame` 層是誰呼叫它。卡住的堆疊是取樣合起來的：每層選樣本最多的那支，所以是「最常卡在這裡」，不一定是每一次。binary 寫 `?` 的層 MetricKit 沒給名字，多半也是 App 自己的（對 UUID）。
2. **把位址換成函式名**（在 Mac 上）：
   - 要那個 build 的 dSYM。`testflight-archive.sh` 匯出時 `uploadSymbols` 是 true，符號在 App Store Connect；`testflight.yml` 目前沒有把 archive 或 dSYM 存成 artifact（見「下一步」）。拿到 `RailwayGame.app.dSYM` 後先對 UUID：`dwarfdump --uuid RailwayGame.app.dSYM`，要和回報那層的 UUID 一樣（`arm64` 那個），不一樣就是別的 build，換不出正確的名字。
   - 載入位址是「位址 − offset」（`+` 後面那個就是 offset）：上面第 1 層是 `0x105a1c64c − 0x138a4b = 0x1058e3c01`，第 3 層 `0x1058eaaa8 − 0x6ea7` 也是 `0x1058e3c01`；用十六進位算，例如 `printf '%x\n' $((0x105a1c64c - 0x138a4b))`。同一個 binary 每層算出來的應該一樣。所以範例就是 `atos … -l 0x1058e3c01 0x105a1c64c 0x1058eaaa8`。
   - `atos -arch arm64 -o RailwayGame.app.dSYM/Contents/Resources/DWARF/RailwayGame -l <載入位址> <位址>`，一次可以給好幾個位址。
3. **記憶體被殺還是背景被收回**（結束那一行）：
   - **背景：被系統收回記憶體**（`cumulativeMemoryPressureExitCount`）：App 在背景時系統要記憶體給別的 App，正常現象，不是 bug；玩家回來時從頭開，看起來像「被關掉」。
   - **畫面上：超過記憶體上限**（`cumulativeMemoryResourceLimitExitCount`）：App 在畫面上時自己用的記憶體超過這台裝置的上限，被系統結束，玩家看到的就是閃退。這是要修的（先看 3D、資料載入，決策 417）；沒有堆疊，要配合玩家當時在做什麼。
   - **背景：超過記憶體上限**：背景時還佔太多記憶體，也該查。
   - **卡太久被系統結束**（watchdog，`cumulativeAppWatchdogExitCount`）：主執行緒卡太久（通常是啟動、回到前景時幾秒以上），系統直接結束 App；玩家感覺「卡住然後閃退」。看同一段時間的卡住事件堆疊。
   - **記憶體存取錯誤**、**非法指令**、**異常**：真的當機，通常同時有一筆「意外關閉」事件，帶 exception、signal 與堆疊，照第 1、2 點讀。
   - **正常**：玩家自己滑掉或系統正常關閉。
4. **時間**：一律 UTC。事件的時間是系統交 payload 那一段的結束時間（iOS 15 起，卡住與當機在發生後的下一次啟動就交），不是精確到秒的發生時刻；日資料大約每 24 小時交一次。

**五方**：
- 玩家：不用做任何事，也不用聯絡誰；按「回報問題」就帶著，說明寫了只記在這台裝置上、按傳送才送出。
- 鐵道迷：無。
- 開發：卡頓有了堆疊與時間，不再只靠猜；整理全在 GamePresentation 用 Linux 測，App 那層只收與存；不加依賴、不碰 GameCore 與存檔。
- 美術：無（只多一段文字，沒有新畫面）。
- 音樂：無。

**沒選的**：
- 把紀錄做成另一個附件檔（像 `command-log.json`）：要再多一個開關與說明；文字放在訊息裡，郵件與訊息 App 都看得到，也能直接貼進 issue。
- 上傳到伺服器或第三方當機服務（Crashlytics、Sentry）：要新依賴、要隱私說明，作者也沒有要。
- 記下全部 `MXMetricPayload`：多數項目和卡頓無關，回報會變得很長。
