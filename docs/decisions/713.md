### 713. 開 3D 的第一格不再等機場鋪好：機場在背景鋪、登機橋端點每座機場只算一次、區塊的頂點緩衝在背景上傳

2026-11-13，派工單 PERF-OPEN3D（Mac 本機 session，遊戲規劃第 63 任派），分支 `claude/perf-open3d`。接 [FPS_DEVICE_2026-11-12](../research/FPS_DEVICE_2026-11-12.md) 第 7、8 節的「每次開 3D 第一格停 270 ms–1.8 秒」與 L19 P2-4「其中多少是機場重鋪」。`Sources/GameCore/`、存檔版本、golden schema、SaveFixtures、ReplayFixtures、GoldenScenarios 都不動：只動 GamePresentation 的機場鋪設與 App 的 3D 畫面檔。

## 1. 量法（先有能重現的）

照 `.claude/skills/diagnosing-bugs/SKILL.md`：先重現，再一次改一個。

- main `cfc051d` 的 Release 組態跑在 iPhone 17 Pro 模擬器（Mac 上），讀作者「整個臺灣」的存檔（16 站、3 線、35 列車、13 座機場），暫停，按 3D、回 2D、再按 3D。
- 數字讀 App 自己的 `Diagnostics/frame-times.json`：每段的 `cpu.longest`（`Map3DMetalView.draw()` 裡花的時間）與 `intervals.longest`（兩格之間最長隔多久）。
- 主執行緒在做什麼：macOS 的 `sample <pid> 6 1`，在取樣期間按 3D（`xctrace --attach` 接不上模擬器的行程）。

每次開 3D 都重現，不是只有第一次：

| 第幾次開 3D（main，模擬器） | 那一格 CPU 最長 | 格距最長 | 三角形 | 區塊 |
| --- | ---: | ---: | ---: | ---: |
| 第 1 次 | 1,075 ms | 1,291 ms | 150 萬 | 98 |
| 第 2 次 | 1,048 ms | 66 ms | 326 萬 | 307 |
| 第 3 次 | 1,049 ms | 83 ms | 421 萬 | 347 |

（第 2、3 次的格距沒有記到那一秒：格距從畫面開始出格才算，停住的那一格是第一格。CPU 那一欄才是每次都有的。）

## 2. 主執行緒在做什麼

取樣（1 ms 一次）裡開 3D 那一段主執行緒的時間：

| 在做什麼 | 時間 | 在哪 |
| --- | ---: | --- |
| 把機場鋪進場景（`Map3DTrainFeed.laidAircraft` → `Map3DAircraft.Laid.init`） | 882 ms | 畫第一格的路上 |
| 　其中：每個機位去找登機橋 | 621 ms | 每個機位把同一座機場的每座登機橋重新換算位置、查一次地面高度 |
| 　其中：滑行道的點與走法 | 157 ms | |
| 　其中：跑道沿線的地面高度 | 82 ms | |
| 建立 Metal 畫面（`Map3DView.makeUIView`：第一次編譯著色器等） | 207 ms | 第一格之前 |
| 把區塊的頂點複製進 GPU 緩衝（`Map3DMetalView.show`） | 153 ms | 第一格之前 |

結論：

- **畫第一格時的那一秒幾乎全是機場重鋪**（L19 P2-4 的答案）。它每次開 3D 都重做，因為場景每次都是新的。存檔 B 只有 1 座機場，所以報告裡它開 3D 沒有這個尖峰。
- 報告裡「格距比 CPU 多出的 120–300 ms」是建立畫面加上傳區塊，發生在第一格之前。
- 假設「是場景本身在主執行緒建」不成立：場景原本就在背景建（決策 424 之後）。

## 3. 改了什麼

1. **登機橋端點每座機場只算一次**（`Map3DAircraft.Laid.init`）。機位有沒有登機橋，原本是每個機位把每座登機橋的端點重新換算並查地面高度，再看水平距離是否小於 35 m；現在端點先算好（只要水平位置，不查高度），判斷式不變。結果逐機位相同（`testAStandsBridgeIsFoundAsBefore`）。
2. **機場在背景鋪**（新檔 `Map3DAircraftLayer.swift`，`Map3DAircraft.Layer`）。照公車的做法（`Map3DBuses.Layer`，決策 424）：畫格來問，鋪好了就給、還在鋪就給「還沒有」，不等。場景位置或機場數變了就重鋪，被取代的那次鋪完不留。`Map3DTrainFeed` 改用它；鋪的期間問「跟著的那架飛機在哪」回答的是「還不知道」，不是「飛走了」，所以跟著飛機時開 3D 不會被踢出跟隨。
3. **區塊的頂點緩衝在背景上傳**（`Map3DMetalView.upload`、`Uploaded`）。場景建好後接著在同一個背景工作裡把緩衝做好，畫面拿現成的；分塊重建（鏡頭往前蓋）也一樣。拿不到或對不上時照舊在主執行緒做（做法同 `Map3DUploadedModels`，決策 608）。

沒有動：`makeUIView`（建立 Metal 畫面）。模擬器上 207 ms，大半是第一次編譯著色器；實機有著色器快取，要看實機的 Time Profiler 才知道還剩多少，見「下一步」。

## 5. 五個角度

- 玩家：按 3D 不再整個畫面停一秒；代價是飛機晚一點點出現、天空底色可能多露出一瞬間。停住比晚出現難受得多。
- 鐵道迷（交通迷）：無。機位、登機橋、滑行道的資料與判斷都沒變。
- 開發：沿用已有的兩個做法（公車的背景鋪、列車模型的背景上傳），沒有新的機制；鋪設邏輯能在 Linux 測。和 #2098、#2105 改同一個檔（`Map3DMetalView.swift`、`Map3DPreviewScreen.swift`），避開它們改的那幾行，後合的併 main。
- 美術：畫面結果不變（同一批頂點、同一批飛機），只有出現的時刻差幾格。
- 音樂：無。

## 7. 已知限制

- 飛機在場景出現後才出現（模擬器約 0.25 秒）。這段時間停機坪是空的。
- 鋪機場本身仍要約 250 ms（13 座機場），只是不擋畫面；滑行道走法與跑道高度還能再省，沒有做。
- 背景上傳用 `MTLCreateSystemDefaultDevice()` 拿裝置，和畫面的裝置對不上時退回主執行緒上傳（iPhone 只有一個 GPU，不會發生）。
- 取樣時順便看到、但不是第一格的熱點：每格的 `Map3DTrains.frame` 裡 `Map3DModelPack.index(of:)`／`layout`／`farModel` 的查找。沒有動。

## 8. 沒選的做法

| 做法 | 為什麼沒選 |
| --- | --- |
| 機場鋪好的結果跨場景留著 | 鋪的結果用的是場景自己的座標與畫出來的地面高度，場景換了就不對 |
| 把鋪機場分幾格做 | 仍在主執行緒，每格還是要讓出時間；背景做一次就好，公車已經這樣做 |
| 在建場景的背景工作裡順便鋪機場 | 要動 `Map3DSceneCache` 與場景的型別，#2105 正在改那一帶 |
| 只修登機橋那 621 ms | 剩下的 260 ms 仍超過 100 ms 的目標 |
