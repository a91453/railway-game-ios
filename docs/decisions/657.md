### 657. 量過 swift-collections 的 Heap：GameCore 沒有變快，不加這個依賴

2026-11-08，派工單 PERF-COLLECTIONS（session_01YGNNuntRZN1n5tCnnE6ajf，遊戲規劃第 56 任 session_01YGNNuqMnQwhbSmiaZzhLsX 派），分支 `claude/perf-collections`。號碼由規劃預留。只改文件：程式、`Package.swift`、存檔版本、golden schema、GoldenScenarios、SaveFixtures、ReplayFixtures 都不動。

## 背景

作者 2026-11-08 同意加 `apple/swift-collections`（Apache-2.0，只有這一個依賴），條件是先量：Linux release 至少快 20%，或記憶體明顯少，才加；沒有就不加，寫進這裡。

## 量了什麼

**先剖析**。用 callgrind 量 main（`4ad1374`）的 AQ 那局（91.1，高雄 78 站，私庫 branch `bug-reports/clock-stuck-2026-10-27`），從 05:59:57 跑 120 秒，跨過 06:00。整段 176 億道指令，乘客計畫（`makeNetworkPassengerPlan`）佔 65%，路線搜尋（`PassengerRouteSearch.run`）佔 36%。heap 本身（下表前三列）合計約 14%：

| 函式 | 佔整段（self） |
| --- | --: |
| `PassengerRouteSearch.siftDown` | 6.7% |
| `PassengerRouteSearch.precedes`（heap 的比較） | 6.1% |
| `PassengerRouteSearch.push` | 1.6% |
| `memcpy`（分岔時複製標籤） | 7.5% |
| `swift_retain`／`swift_release` | 7.9% |
| `Hasher`（`Set<PassengerRideEdge>` 當字典鍵） | 5.8% |
| 列車找路的 `SearchQueue`、公車找路的 `BusSearchHeap` | 不到 0.1%，不在前幾名 |

所以就算 heap 完全不花時間，也最多快 14%，到不了 20%。比 heap 大的負擔是複製、ARC 和雜湊，換資料結構解決不了。

**再實測**。在本地的另一個 worktree 把 swift-collections 1.7.4 換上去（`HeapModule`，`Heap` 是 min-max heap），試了三處：

- 列車找路 `SearchQueue`（`Sources/GameCore/Railway/TrainRoute.swift`）：元素是（距離、推入順序），嚴格全序，結果逐位元相同。
- 公車找路 `BusSearchHeap`（`Sources/GameCore/Passenger/BusRoute.swift`）：元素是（公尺、列、欄），同樣逐位元相同。
- 乘客路線搜尋的待展開標籤（`PassengerRouteSearch.open`）：`Heap` 的元素要自己 `Comparable`。但現在的比較在分鐘、轉乘、秒數都同分時，會沿著搜尋自己的 `orders` 樹比較路線順序，元素本身不帶這個資料。為了只量時間的上限，實驗版跳過這一層比較，直接比停靠點與標籤編號，所以不保證逐位元相同。

**結果**：Linux release（Swift 6.4.0，4 核；main 和實驗版交替跑，各三次，取中位數）。

- 列車、公車的 heap 換掉之後沒有變快，差距在跑與跑的誤差裡，中位數還慢一點。
- 乘客的 heap 換掉之後，即使跳過最貴的那層比較，AQ 那局也只快 0.6%，合成 200 站快 1%，記憶體反而多 7–9%。要做到逐位元相同，元素得帶著路線順序，或每次比較都去找那棵樹，只會更慢。
- 其他看過的地方：
  - `Deque`：GameCore 當佇列用的陣列都已經用索引往前走（例如 `TrackResources` 的最大流），沒有 `removeFirst` 的熱點。唯一的 `removeFirst` 是纜車、公車、渡輪每天的紀錄，只有幾筆。
  - `OrderedDictionary`／`OrderedSet`：GameCore 的 `keys.sorted()` 要的是排序後的順序，`OrderedDictionary` 給的是插入順序，換了會改行為。這些地方也都不在剖析的前幾名。

## 決定

不加 swift-collections。`Package.swift`、`Package.resolved`、`project.yml` 都不動。條件（快 20% 或記憶體明顯少）沒有達到：

- 最好的情況只快約 1%；
- 乘客那一處還做不到逐位元相同；
- 記憶體反而多。

**五方**：
- 玩家：無。量過的換法都沒有讓 06:00 的停頓變短，不加就沒有改變。
- 鐵道迷：無。選路的規則與結果不變。
- 開發：少一個依賴，也少一個要跟著 Swift 版本、XcodeGen 與 Xcode 專案一起維護的套件（1.7.x 要 swift-tools-version 6.4）。現有手寫的二元 heap 已經是嚴格全序，同分的順序由程式自己定，不必另外鎖測試。
- 美術：無。
- 音樂：無。
