### 329. CI 流程：新決策一個檔一個、取消的 PR run 不判紅、swift-build 崩潰重試一次、main 的 full lane 紅了自動留言

2026-10-21。遊戲規劃 session_014rYHMtmqA5bEMkBBuKu6PV 派工（作者 2026-10-21：「還需要一個session優化ci流程」），CI 流程優化 session_01E8oiGWPQZ2a8wAE8tNvFKk。號碼依 #231：決策 329（遊戲規劃保留）；存檔版本、golden schema 不動。量到的數字：`docs/research/CI_MEASURE_2026-10-21.md`。

**派工時的四個痛點與量到的**：

1. **GameCore PR 的完整 tier 要 20–40 分**。一輪 CI 其實是 17–21 分：Linux 不排隊（p90 0.1 分），最慢的分片 job 約 16 分，其中建置只有 2.7 分；分片之間最慢的兩個只差 0.1 分。會改到 App 的 PR，gate 由 iOS App Build（約 21 分）決定。多出來的時間是**同一個 PR 跑好幾輪**（#934 五輪）。
2. **合併衝突**：10-19 起 49 個 merge main 的 PR run（PR run 的 19%）用了 PR 的 Linux 用量的 40%；49 個全部解了衝突，41 個在 ARCHITECTURE 或 OVERVIEW。預約一節（10-21 起）也擋不住：預約的幾節相鄰，git 還是當同一處。
3. **main 的 full lane 紅了沒人知道**：10-20 14:19 起連續 10 次紅。
4. **取消的 PR run 判紅**：被新 push 取消、有 gate 的 36 個 run 有 33 個 gate 紅。**swift-build 崩潰**：2,320 個分片 job 裡 1 次（signal 11，libdispatch，一個檔都還沒編）。

**做法**（一次一個 PR）：

1. **新決策一個檔一個**（第 1 個 PR）：
   - 329 起每個決策是 `docs/decisions/<N>.md`，第一個標題 `### N. 標題`（`docs/decisions/README.md`）。並行的 PR 加的是不同的檔，不會再改到同一行。
   - 不用在 main 先放預約的節：#231 的登記就是預約。撞號時兩個檔同名，第二個合併的衝突，照登記先後改號。
   - OVERVIEW §9 只列到 328；329 起這個目錄就是索引，`doc_numbers.py --index` 印出整份。合併後不用再開 PR 補索引列（#911、#924 那種）。
   - 1–328 的「後來」照舊改 ARCHITECTURE 裡那一節：那些分散在 15,000 行裡，很少兩個 PR 同時改同一節。
   - `doc_numbers.py --check` 加三項差異：檔名和標題的號碼不一致、一個檔有兩個決策、同一號同時在 ARCHITECTURE 和 `docs/decisions/`。
2. **取消的 PR run 不判紅；swift-build 崩潰重試一次**（第 2 個 PR，`ci.yml`、`swift-shards.sh`）：
   - **被新 push 取代的 PR run，gate 顯示 skipped（灰），不是紅**：新的 job `superseded`（`Superseded by a newer push?`）只在取消的 PR run 跑，用 API 讀 PR 現在的 head；不是這個 run 的 commit，就輸出 `superseded=true`，gate 的 `if` 就跳過。skipped 的必要檢查算通過，但它在舊的 commit 上，branch rule 只看 head，所以不會讓沒測完的東西合併。
   - **還是紅的情形**：在 head 上手動取消的 run，或讀不到 head（API 失敗）。這時 gate 照舊紅，擋住合併。另外，gate 已經在等 iOS 時才被取消（三天 33 次裡 7 次），job 已經開始，跳不過；這時訊息改寫成「被新的 push 取代，不是測試失敗」。
   - **建置崩潰重試一次**：`swift-shards.sh build` 取代 `ci.yml` 裡直接呼叫的 `swift build`。exit code 大於 128（被 signal 殺掉，139 是 SIGSEGV）就再建一次；編譯錯誤是 exit 1，不重試；第二次再崩潰就紅。
   - **測試步驟**：只有在一個 batch 的 `swift test` 被 signal 殺掉、而且還沒有任何 `Test Case … started` 時，才重跑那個 batch 一次。有測試開始過，崩潰可能是測試本身造成的，照舊紅。測試失敗（exit 1）永遠不重跑。
   - **自測**（`swift-shards-selftest.sh`，假的 `swift` 與 `gh`）：新增 22 項，包括崩潰一次會重建、編譯錯誤不重建、崩潰兩次會紅、測試開始後的崩潰不重跑、取代與沒取代的判斷、讀不到 head 時不跳過。
3. **main 的 full lane 紅了自動留言**（第 3 個 PR）。

**等太久那一項，沒有改的**（量過，省不到）：

- **再分配分片**：最慢的 `campaigns-8` 和 `rest` 只差 0.1 分，第三慢差 0.4 分；而且會改 App 的 PR 是 iOS 比較慢。
- **多開分片**：完整 tier 已是 19 個 job（上限 40，同時最多 2 個 GameCore PR 加 main 的 push 就 57 個要排），多開只會排隊（決策 187）。
- **快取 `.build`、建置一次再分給各分片**：建置每個 job 2.7 分，三個 job 平行，所以牆鐘最多省 2 分左右；`.build` 有 977 MB（本機 Linux，Swift 6.4，`swift build --build-tests` 3.2 分），每個 job 要下載這麼大一份，改到 GameCore 時大部分還是要重編；分片之間傳 `.build` 也要上傳下載，加上 Actions 的快取上限 10 GB，省下的可能比花掉的少。也會多一種「快取壞了」的失敗。
- **iOS 那邊可以再看的**（`ios-build.yml`，macOS 上才驗得到，留給之後）：Simulator 開機（2.0 分）和建置（2.6 分）並行；翻譯匯出（2.9 分）是 UI 測試之後才做，PR 等它跑完才綠。

**沒選的**：

- **`.gitattributes` 的 `merge=union`**：只在本機的 `git merge` 有用。GitHub 判斷 PR 能不能合併時不跑 `.gitattributes` 的 merge driver，PR 頁面照樣顯示衝突、照樣要 merge main 再跑一輪；union 還會把兩個 PR 改同一段的文字交錯合在一起，不報錯。
- **工具產生 OVERVIEW §9，把產生的結果 commit 進去**：產生的那幾行還是每個 PR 都改，照樣衝突。
- **把 1–328 也搬成一個檔一個**：15,000 行的搬移，所有指到 `ARCHITECTURE.md#…` 的連結都要改，衝突又不在舊決策。
- **每個 PR 自己的 golden／存檔號碼也拆開**：存檔版本（`SavedGame.currentVersion`、`SaveFixtures/README.md` 的最後一列）本來就要一個接一個做（第二個要接在第一個的遷移後面），衝突是對的；照 HANDOFF 一次只派一件。

**五方**：

- **玩家**：修正和新功能少等一輪 CI 就能合併、進 TestFlight；full lane 紅了有人很快接手，發版前不會才發現。
- **鐵道迷**：無。
- **開發**：每合一個 PR，其他開著的 PR 不再因為 ARCHITECTURE、OVERVIEW 衝突而重跑（三天約 4,900 分鐘 Linux，其中 18 次是完整 tier）；遊戲規劃不用再開補索引的 PR。代價是決策分在兩個地方，`grep -rn '^### N\.' docs/` 或 `doc_numbers.py --index` 一次找兩邊。
- **美術**：無。
- **音樂**：無。

**驗證**（第 2 個 PR）：`.github/scripts/swift-shards-selftest.sh` 在 Linux 跑過，全部通過，VERIFIED。取消時 job 怎麼跑（`superseded` 在取消的 run 裡跑、gate 被跳過）只有 GitHub 上看得到，UNVERIFIED，要等這個 PR 自己有一次被新 push 取消的 run。

**驗證**（第 1 個 PR）：`python3 -I tools/golden-checks/doc_numbers.py --selftest`（16 個情境）與 `--check`（main 加上這個 PR：差異 0）在 Linux 跑過，VERIFIED。這個 PR 只改文件與 `tools/golden-checks/`，Swift CI 跳過。
