### 749. 3D 區塊緩衝上限降到 600／500 MB；火車模型上 GPU 時一個一個放掉 CPU 的頂點

2026-11-14，Mac 本機 session（MEM3D，由 PERF-DEVICE 雲端串派），分支 `claude/project-thread-r9xb1y`（從 `perf/map3d-memory` 切）。接 `docs/handoff/PERF-DEVICE-2026-11-14.md` 排名第 1：作者最重的存檔（176 站、184 列車）開 3D 時 iPhone 17 Pro 用到 2.65–2.76 GB、收到 3 次記憶體警告。

不動 GameCore、存檔版本、golden、SaveFixtures、ReplayFixtures；不碰模擬相關程式，所以不必比 20 tick 的 SHA-256。

## 1. 查到什麼

在 iPhone 17 Pro 模擬器（Debug，同一局，`-screenshot-3d-at 25.0478,121.5170`、`-screenshot-3d-view 1500,0,45`：台北車站上空 1,500 m）上，用 `footprint`、`vmmap`、`heap -s` 看 App 程序，再加一行暫時的紀錄印出 Metal 畫面持有的區塊緩衝（`heldBytes`，沒進 repo）：

| | 2D（讀檔後 70 秒） | 3D 近景（台北車站 1,500 m） | 3D 拉到最遠 2 分鐘後 |
| --- | ---: | ---: | ---: |
| footprint | 約 800 MB | 1,430–1,600 MB | 1,890 MB，還在漲 |
| GPU（模擬器裡算 Untagged） | 約 60 MB | 750–830 MB | 1,030 MB |
| 區塊緩衝 `heldBytes` | 0 | 360–450 MB（約 700 塊） | 631 MB（1,151 塊），往上限 1,000 MB 漲 |
| malloc | 約 700 MB | 約 730 MB | 約 820 MB |

`heap -s` 分出最大的幾項：

1. **火車與街上車輛的模型包，約 287 MB**（`Map3DVertex` 陣列；標準包 889 個模型、658 萬個頂點、每個 40 bytes 共 251 MB，再加公車、垃圾車、街道擺設、香港車輛）。決策 546 讓它在讀檔 8 秒後就先做好，所以 **2D 就一直拿著**；開 3D 時整包上 GPU（`Map3DUploadedModels.make(from:)`），整包上完才放掉 CPU 那份，所以開 3D 那一刻 CPU、GPU 各一份，約 290 MB 疊在一起。
2. **3D 場景的區塊緩衝**：近景 360–450 MB；拉遠以後，決策 714 讓鏡頭看得到的都建起來，一分鐘多 100 MB 一直漲，直到 `Map3DSceneBudget.bytes` 的上限。iPhone 17 Pro 是 `.ample`，上限 1,000 MB。
3. 場景本體 CPU 那一份網格約 276 MB（`Map3DVertex` 243 MB＋索引 33 MB），開著 3D 時和 GPU 那份並存（決策 711 第 7 節已列）。
4. 世界本身（`WorldCoordinate` 80 MB、`LandCell` 67 MB、`CellPosition` 30 MB、`CitySkyline.Lot` 25–50 MB 等）是 2D 就有的。

疊起來：2D 約 1.2 GB（手機的 frame-times.json 量到 1,087–1,311 MB）＋開 3D 時模型包多一份 0.29 GB＋場景 CPU 0.28 GB＋區塊緩衝最多 1.0 GB，約 2.7 GB，和手機量到的 2.65–2.76 GB 對得上。

另外查過、不是原因的：模擬器裡 GPU 那欄比 `heldBytes` 多 300 多 MB，但在 Mac 自己的 Apple GPU 上量 `makeBuffer`（`storageModeShared`）：4 KB 以下的緩衝共用一塊，以上的對齊到 16 KB，7,600 個緩衝多出約 60 MB；多出來的那 300 MB 是模擬器自己的做法，手機上不會有。模型包改成用索引（去掉重複頂點）只少 30%（658 萬 → 462 萬），不值得改畫法。

## 2. 改了什麼

1. **區塊緩衝上限**（`Map3DSceneBudget.bytes(memory:)`）：`.ample` 1,000 → 600 MB、`.roomy` 700 → 500 MB（低於 `.ample` 才合理）、`.tight` 400 MB 不變。近景與中景（360–460 MB）照舊全建；拉遠時到 600 MB 就不再多建看得到的區塊，超過就照決策 711 卸掉比鏡頭看得到還遠的區塊（模擬器上從 599 MB 卸回 500 MB）。
2. **模型包逐個上 GPU、逐個放掉**（`Map3DUploadedModels.make(from:)`、新的 `Map3DModelPack.letGoOfVertices(at:)`）：先放掉 `Map3DModelPack.standard` 那份參考，先讀完貼圖、玻璃、發光這些要讀頂點的東西，再一個模型一個模型做緩衝，做完就放掉那個模型的頂點。工作交給背景工作時用一個 `Handed` 盒子交出去，背景工作的閉包不再抓著整包。最後留下的包和以前一樣（`withoutVertices()`），畫面不變。

## 3. 量到的數字

iPhone 17 Pro 模擬器（iOS 27.2，Debug；模擬器的 GPU 數字不能當手機的，`heldBytes` 與 malloc 可以比）。同一局、同一個地點、同樣的動作：讀檔 → 2D 70 秒 → 開 3D 90 秒 → 兩次 0.25 倍捏合拉遠 → 等 120 秒。每 5 秒讀一次 `footprint`：

| | 改前 | 改後 |
| --- | ---: | ---: |
| 2D footprint（這次的改動不碰 2D） | 782–786 MB | 760 MB |
| 3D 近景 footprint | 1,424–1,600 MB | 1,353–1,698 MB |
| 拉遠 2 分鐘後 `heldBytes` | 631 MB，1,151 塊，還在漲 | 599 MB 後卸回 500 MB，654 塊 |
| 結束時 footprint／峰值 | 1,894／1,929 MB | 1,740／1,863 MB |

模型包那一項在 5 秒取一次的 footprint 裡看不出來（開 3D 時同時在建場景、上傳區塊）；單元測試證明逐個放掉後留下的包和一次放掉的一樣。

截圖（`/Users/chienlinyeh/Developer/mem3d-shots/`，作者的 Mac，不在 repo）：`before-2d／3d／far.jpeg` 與 `after-…`。2D 與 3D 近景一樣；拉到最遠時，改後畫面邊上有 3 個區塊是空的（左上、右緣、右下，露出底色），改前只有左上 1 塊（還沒建好）。

## 4. 五個角度

- 玩家：重的存檔開 3D、拉遠玩久了不會一路吃記憶體到被系統警告或關掉；代價是拉到最遠時畫面最外圈偶爾少一兩塊。
- 鐵道迷：無（軌道、車站、列車都不變）。
- 開發者：一個數字和一段上傳迴圈；上限仍是 `Map3DSceneBudget` 的純函式，Linux 測得到。
- 美術：近景不變；最遠時外圈可能缺塊，這是保命用的。
- 音樂：無。

## 5. 查了什麼

- 參考庫：`Railway/tw3d-reference-clean` 的區塊總量上限（決策 711 已取用過），這次沒有新東西可拿。
- 外部專案：沒有再找；用的是 Apple 的工具（`footprint`、`vmmap`、`heap`）。

## 6. 沒選的

- **開著 3D 時放掉場景 CPU 那份網格**（約 276 MB）：重開 3D（決策 269 保留場景）、只重建改到的區塊（決策 517 續）、渡輪碼頭找水面都讀它，要改的地方多，留給下一步。
- **模型包只上傳這局用得到的車**：可以少 200 MB 以上，但買新車時要補傳、模型索引全程式共用，留給下一步。
- **2D 不先做模型包**（決策 546）：2D 少 287 MB，但開 3D 要多等，而且 3D 的峰值不變。
- **上限再低（400 MB）**：近景就要卸，鏡頭一動就重建。

## 7. 已知限制、下一步

- **UNVERIFIED：手機實機。** 作者 2026-11-14 晚上要用手機，改前改後都沒在手機上量到 3D（只量到 2D 1,087–1,311 MB）。請在手機上照 `docs/handoff/PERF-DEVICE-2026-11-14.md` 的量法量一次：同一局、台北車站、拉遠等 2 分鐘，看 frame-times.json 的 `memoryPeak` 與 `memoryWarnings`。
- `.roomy` 500 MB 是推的，沒有 6 GB 的裝置量過。
- 卸掉後鏡頭往回移會重建（決策 711），CPU 要再做一次；沒有量重建的時間。
- 上面「沒選的」前兩項是下一步最大的兩項。
