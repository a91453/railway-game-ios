## 做法

`Package.swift` 在 `#if os(Linux)` 時給 `GameCore` 與 `GameCoreTests` 加 `swiftSettings: [.unsafeFlags(["-O"])]`，其他目標照舊。debug 組態其餘不變（`-enable-testing`、`-g`、`@testable import` 都照常），所以 CI 的指令、分片腳本、本機的快速檢查指令都不用改，本機和 CI 跑的是同一種建置。

- **測試的意義不變**：沒有跳過、停用、隔離任何測試，沒有放寬斷言，沒有改 GoldenScenarios／SaveFixtures／ReplayFixtures。`-O` 保留 `precondition`、整數溢位檢查與 XCTest 的斷言；套件裡沒有 `assert`、`assertionFailure` 或 `#if DEBUG`（`grep` 過，只有 App 有）。GameCore 全用整數，唯一的浮點（`RunSpacing` 的比較）是 IEEE 運算，Swift 不開 fast-math，`-O` 不改結果。golden、存檔與重播測試在 `-O` 下照樣要全過，這次 CI 就是驗證。
- **App 不變**：Xcode 在 macOS 建置，`#if os(Linux)` 不成立。發出去的 App（Release）本來就是最佳化的 GameCore，所以 CI 現在測的反而更接近玩家跑的。
- **build job 逾時 20 → 30 分**：建置約多 1.5 倍（本機 193 → 291 s，CI 估 5.5 → 8 分），被 signal 殺掉重建一次（決策 329）時 20 分不夠。
- **分片不動**：權重是相對的，先看這次 CI 量到的新秒數；片數要不要減（每片只剩幾分鐘時，容器、下載、`swift test list` 的固定成本變大）留給下一步，見下面。

### build 是瓶頸：之後可以做的（這次沒做）

改後每片約 7 分，build 8–10 分（其中編譯 410 s，容器與 checkout 約 50 s，打包上傳約 25 s），佔牆鐘一半以上。

- **A. 快取 `.build`（建議先做）**：`actions/cache` 以 Swift 版本＋`Package.swift`／`Package.resolved` 為 key，main 的 push run 存、PR run 讀，SwiftPM 只重編改過的目標。只動 GamePresentation 的 PR 就不必重編 -O 的 GameCore 與 GameCoreTests（最貴的兩個），估 build 從約 8 分降到 3–4 分，GP tier 牆鐘約 −4 分。要處理的：checkout 會把每個檔案的 mtime 設成現在，SwiftPM 會以為全部改過，所以要先把檔案的 mtime 設成它最後一次 commit 的時間（`git log` 幾行 shell 即可，不加依賴）；快取每份約 450 MB（壓縮後），帳號快取上限 10 GB，只存 main 的最新幾份；增量編譯出錯時要能退回乾淨建置（例如 key 加日期每天換一次）。
- **B. 拆 build**：Linux 上所有測試目標連成一個測試執行檔，拆成兩個 job 編譯後很難合回一個 `.build`；不建議。
- **C. GP tier 少一點 build**：GP tier 只跑 GamePresentation 的測試，但 `swift build --build-tests` 仍編 GameCoreTests（-O，最慢的目標）。若 SwiftPM 能只建需要的測試目標，可省 2–3 分；目前 SwiftPM 的 `--build-tests` 沒有選目標的參數，要另找做法（例如 GP tier 用環境變數讓 `Package.swift` 對 GameCoreTests 不加 -O）。要動 `Package.swift`，留給下一輪。

### 五面向

- 玩家：無（App 不變）。
- 鐵道迷：無。
- 開發：完整 tier 少 6 個 job、測試那一段實測快 1 分、runner 分鐘少 22%；GP PR tier 估快約 2 分；兩個完整 tier 同時跑時多出 12 個名額給其他 PR，等 runner 的時間少。權重與分片照實測，自我檢查與每片的覆蓋檢查不變。
- 美術：無。
- 音樂：無。

### 不選的

- **照舊 20 片只換權重**：和 14 片一樣快（rest 是下限），多用 6 個 job。
- **10–12 片**：再省 2–4 個 job，但每少 2 片慢約 0.8 分；完整 tier 不常跑，少的名額不如快的牆鐘。
