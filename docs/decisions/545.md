## 問題

決策 544 之後，完整 tier 的測試片約 7 分，build job 8–11 分（編譯 410–580 s），佔牆鐘一半以上。每個 run 都從零編，連只改 GamePresentation 的 PR 也重編 -O 的 GameCore 與 GameCoreTests。

## 做法

### 1. 快取 `.build`（`actions/cache`）

- **誰存、誰讀**：main 的 push run、nightly、手動 run（只在 `refs/heads/main`）建置成功後存（`actions/cache/save`）；pull request 與 main 的 push run 讀（`actions/cache/restore`）。**nightly 與手動 run 不讀快取**，一律從零編：發版要的完整 run（決策 413）永遠不靠快取。
- **key**：`swift-build-v1-<swift --version 的雜湊>-<hashFiles('Package.swift')>-<sha>-<run_id>-<attempt>`；讀的時候用前綴 `swift-build-v1-<swift>-<Package.swift>-` 拿最新的一份。key 只用來挑最近的一份，**不決定哪些檔要重編**。沒有 `Package.resolved`（套件沒有外部依賴）。
- **哪些檔重編：照內容，不照時間（`swift-shards.sh stamp`）**。SwiftPM 的編譯器驅動程式（swift-driver）看每個來源檔的修改時間是否等於 build record 記的時間；checkout 會把每個檔的時間設成現在，等於全部改過。所以 build 前先把每個 git 追蹤的檔的時間照 `.build/ci-source-stamps`（上一次建置時每個檔的「時間、blob、路徑」）設定：
  - blob（git 對內容的雜湊）相同的檔：設成清單記的時間，也就是 build record 記的時間，不重編。
  - 改過或新增的檔：設成清單裡最大的時間再加 1 秒，**一定不等於任何 record 記的時間**，所以一定重編，相依它的檔由 driver 自己的相依追蹤一起重編。
  - 沒有清單（沒快取、或從零編）：全部設成 2000-01-01。
  - 新清單寫進 `.build`，跟著快取存起來，所以快取裡的清單與 build record 永遠是同一次建置。
  - 不需要 git 歷史（`fetch-depth` 照舊 1）：比的是內容雜湊，不是 commit 時間。外面常見的作法 git-restore-mtime（把時間設成最後一次 commit 的時間）要完整歷史，而且同一個檔在兩個分支上 commit 時間不同、內容相同時會白白重編；這裡照內容，沒有這兩個問題。
- **改到 GameCore 或 `Package.swift` 時不用快取**：比對時發現 `Sources/GameCore/` 或 `Package.swift` 和快取不同（含刪掉的檔），就刪掉還原的 `.build`、從零編（本機量到改 GameCore 時在快取上編比從零還慢，見下表）。改 GameCoreTests 照樣用快取（只改測試檔 92 s）。
- **快取上編壞了就從零再編一次**：`stamp` 用了快取時在 `.build` 放一個記號；`build` 看到記號、建置失敗（編譯錯誤，或被 signal 殺掉兩次）時刪掉 `.build`、重新蓋時間、從零編一次。所以**舊快取不可能讓一個 PR 變紅**；真的編譯錯誤會再錯一次，照舊報。
- **舊快取會不會讓結果變綠（該重編的沒重編）**：
  1. 內容不同的檔一定拿到 record 裡沒有的時間（上面），driver 一定重編它；
  2. 編譯器版本或參數不同時 driver 自己整個重編（build record 記了這兩樣），而且 key 已含 `swift --version` 與 `Package.swift`；
  3. GameCore 改了就整個從零編；
  4. 每天 nightly 從零編一次，完整 run 不碰快取；
  5. 本機實驗（下面）改過 GamePresentation 的函式內容後，測試讀到的是新的行為。
- **分片不變**：分片照舊下載 build job 打包的 `.build`、`swift test --skip-build`；`swift-shards.sh run` 的「每片恰好跑了它的測試」自我證明一字未動，沒有測試少跑。`Swift CI (gate)` 名稱不動。
- **容量**：每份快取約 1.5 GB（未壓縮，zstd 後估 400 MB 上下），每次 main push 存一份。帳號快取上限 10 GB，GitHub 依最近使用時間淘汰；iOS 的「這個改動過了」記號也在同一個空間，可能被擠掉，被擠掉只是那個 PR 的 iOS job 重跑一次。

### 2. 方案 C（GP tier 不建 -O 的 GameCoreTests）：不做

- 有了快取，只改 GamePresentation 的 PR 本來就不重編 GameCoreTests（它沒改），C 能省的只剩沒命中快取的時候。
- C 要讓 GP tier 用不同的編譯參數建 GameCoreTests，參數一不同，main 存的快取那一份就不能用，GP tier 每次都要從零編 -Onone 的 GameCoreTests，反而比 A 慢；兩者互斥，選 A。

### 3. L5-1：計時測試重新量得到比例（只改這兩個測試的量法）

- `HolidayTests.testAPlanAsksForTodaysHolidayOnce`：每次取樣做 10 個乘客計畫（原本 1 個），-O 下每次取樣約 90 ms，斷言 `taiwan < china * 1.5 + 0.01` 不變，10 ms 寬限只佔一小部分（原本台灣慢到 2.5 倍還綠）。
- `TrainTripLogTests.testCreditingATripDoesNotWalkTheLog`：開始計時前先記一次帳，讓第一次寫入的 copy-on-write（複製 21,000 筆紀錄）不算進時間；計時的次數 2,000 → 400,000，-O 下幾十 ms。斷言 `long < short * 5 + 0.01` 不變。
- 兩個測試驗證的東西（台灣的假日查一次、記帳不走整個紀錄）都不變。本機量到的時間見下面。

## 五面向

- 玩家：無（App 不變）；CI 快了，修正早一點進 TestFlight。
- 鐵道迷：無。
- 開發：只動 GamePresentation、測試或資料的 PR 與 main push，build 估從 8–11 分降到約 4–5 分；改 GameCore 的照舊從零編，不會更慢。快取上編壞了自動從零再編，發版用的完整 run 從不靠快取。L5-1 兩個計時測試重新量得到中等的退步。
- 美術：無。
- 音樂：無。

## 不選的

- **git-restore-mtime（照最後 commit 時間設時間）**：要 `fetch-depth: 0`（Changes 以外的 job 現在是淺 clone），而且內容相同、commit 不同的檔會白白重編。該工具（MestreLion/git-tools）是 GPL-3.0，本來也只能參考作法。
- **快取 key 加日期、每天換**：nightly 已經每天從零編並存一份，正確性靠內容比對，不靠換 key。
- **改 GameCore 也用快取**：本機量到比從零慢（349／468 s 對 265 s）。
- **PR run 也存快取**：只有同一個 PR 之後的 run 讀得到，每次 push 多存 400 MB，擠掉 main 的快取；不做。
- **方案 C**：見上。
