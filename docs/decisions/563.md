## 做法

1. **自我檢查變成自己的 job（`selftest`）**：原本是 Changes job 的最後一步，build 要等它（26–38 s）。現在 `needs: changes`，和 build 同時開始；gate 加一個條件 `SELFTEST`（要測時必須 success，不測時必須 skipped），所以自我檢查失敗照樣紅。`superseded` 也等它。代價：每個要測的 run 多一個約 1 分的 job（完整 tier 17 → 18 個），自我檢查失敗時 build 照跑（原本會跳過）。
2. **存快取變成自己的 job（`swift-build-cache`）**：只在 main 的 push、手動、夜間 run 跑（和原本存快取的條件一樣）。build job 輸出 key（和原本同一個字串），這個 job 在同一個容器、同一個路徑下載 build、解開、`actions/cache/save`，和測試片同時跑；gate 不等它，失敗不影響結果（`continue-on-error`）。main 的 run 每次少約 1 分。
3. **`CLASS_WEIGHTS` 照實測重算**：上面四個 GamePresentation PR tier 與完整 run 41646134590，每個 2 s 以上的類別取這五次裡最慢的那次（決策 544 續的做法），其他類別照舊；新增 18 個、更新的見 diff（212 個類別有權重）。用同樣的五次逐類別秒數模擬 8 份的分法：舊權重算出的份和 CI 實際的份完全一樣（所以模擬可信），新權重下：

   | run | 舊權重：最慢／最快一份（s） | 新權重：最慢／最快一份（s） |
   | --- | --- | --- |
   | 41623817021 | 496／245 | 374／289 |
   | 41638327376 | 510／176 | 353／258 |
   | 41646101866 | 459／188 | 341／243 |
   | 41650455897 | 469／257 | 375／302 |

   最慢一份少約 2 分（這是樣本內的估計，下一個 GP tier 的 PR 補實測）。完整 tier 的分片名單是固定的，不受權重影響。

4. **一個運算式型別檢查 213 s**（本機用 `-warn-long-expression-type-checking=400` 找到）：`Map3DModelTests.testEveryStyleHasACabAndAMiddleCarOfTheRightSize` 的 `XCTAssertEqual(Map3DModelPack.studies.models.count, …)` 是 30 項的加法（每加一款研究車就多一項，`Int` 與字面值混在一起，型別檢查的組合是指數長），最近幾天加的 EMU700、機場捷運、文湖線研究車把它推到 213 s。改成 `let studyModels: [Int] = [ … ]`、`reduce(0, +)`：一樣的項、一樣的總數、一樣的斷言。本機（4 核，Swift 6.4.0，只改這一個檔、增量建置）：**改前 222 s → 改後 31 s**。從零建置與每個讓 GamePresentationTests 整個重編的 PR（決策 545：GamePresentation 的介面改了就是）都要編它，而且同一個檔在一個編譯工作裡單線程跑，所以這 3 分鐘大多直接加在 build 的牆鐘上；這也是 PR 的建置步驟從基準的 51 s 變成 105–208 s、從零建置從 410–580 s 變成 572–675 s 的主要原因之一。第二慢的是產生的 `Map3DStationKitCatalog.swift`（28 s，一個大陣列字面值，由 `tools/station-kit/catalog.py` 產生），要改產生器，留給下一步。其餘都在 7 s 以下（`Boarding.swift` 6 s）。

測試沒有一個跳過、斷言沒有放寬、完整 tier 測的東西一樣（14 片、`rest`、每片的覆蓋檢查都不動）。

## 等 macOS（只寫方案，沒做）

GamePresentation PR 的牆鐘有 8–11 分是 gate 等 `ios-build.yml`。macOS runner 帳號只有 5 台，full lane 佔 4 台時 PR 的 iOS 檢查只剩 1 台。可以做的：

- **A. gate 不等 iOS，改由 `ios-build.yml` 自己成為 main 的必要檢查**：`Swift CI (gate)` 在 Swift 部分跑完就綠，PR 看起來快 8–11 分，但合併照樣要等 iOS（branch rule 要兩個 check）。要改 branch rule，是作者的事；而且 `ios-build.yml` 對文件等改動不跑（paths-ignore），必要檢查不回報時 PR 會卡住，要像 gate 一樣永遠回報。
- **B. 縮短 PR 的 iOS gate list**（決策 199、265）：看哪些 UI 測試最久，移到 full lane。要看 `ios-build.yml` 的 job 時間，下一輪做。
- **C. full lane 少佔一台**（4 → 3 個 job）：PR 的 iOS 檢查多一台，full lane 慢一些；full lane 不擋 PR，可能划算。

這三個都不在這張派工單「讓測試變快或重排分片」的範圍，也都要動 macOS 的排程，留給遊戲規劃決定。

## 五面向

- 玩家：無（App 不變）。
- 鐵道迷：無。
- 開發：從零建置與重編 GamePresentationTests 的 PR 少約 3 分（一個運算式 222 → 31 s），每個要測的 run 少約 30 s（自我檢查不再擋 build），main 的 push 與完整 run 再少約 1 分（存快取不擋測試片），GamePresentation PR 的最慢一份估少約 2 分；代價是每個 run 多一個小 job（main 多兩個）。等 macOS 的 8–11 分寫成方案給規劃決定。
- 美術：無。
- 音樂：無。

## 不選的

- **完整 run 也用快取**：快 5–8 分，但發版要的完整 run 會建在別的 run 的產物上（決策 545 特意避開）。
- **GP tier 加到 9–10 份**：權重準了以後最慢一份約 350 s，`Map3DSceneMemoryTests` 一個就 221 s；加份數只多用 runner。
- **把自我檢查放進 build job 背景跑**：build 在 `swift:6.4-noble` 容器裡，自我檢查用到的工具沒有確認都在；分開的 job 最單純。
