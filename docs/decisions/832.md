### 832. 優先清單的新列一項一檔（docs/priorities/）

2026-11-17，PRIO-FILES（NEXT_PRIORITIES §29.29 第 3 列，2.00）。只動文件與 `tools/golden-checks/doc_numbers.py`；GameCore、GamePresentation、CI 設定、存檔版本、golden schema 都不動。交接：`docs/handoff/PRIO-FILES.md`。

**為什麼。** 2026-11-17 一天 #2355、#2365、#2367、#2371、#2375 都把評分寫成 NEXT_PRIORITIES 最後一節的下一個小節（§29.28–§29.31），號碼互撞、改同幾行，先合一張其餘就衝突，各自再併 main、再跑 CI；#2367 因此卡著沒人發現（§29.29）。決策 329 把決策改成一號一檔、`docs/handoff/` 把交接改成一件一檔之後都沒再撞。

**做法。**

1. PR 評出的新項目寫成 `docs/priorities/<工作名>.md`，第一行 `# <工作名>（YYYY-MM-DD，來源 PR）`，一張至少有「項目、玩家、開發、美術、鐵道迷、音樂、加權」欄的表（`docs/priorities/README.md`）。檔名用工作名而不是號碼：工作名在 #2118 登記時就定了、不會撞，也不用預約。
2. `doc_numbers.py --check` 檢查這些檔：檔名、第一行、日期是真的日子、欄位齊、分數 1–5 的整數、加權照 §19（30／25／15／15／15）算得出來。錯了是差異；來源沒有 PR 號只是附註（開 PR 前寫的檔還不知道號碼）。`--selftest` 加了 11 個情境（先在 `main` 上寫好、確認會失敗，再實作）。CI 的 `doc-numbers` 工作（決策 830）在改到 `docs/` 時已經會跑，不用改 CI。
3. 規劃併回：`doc_numbers.py --priorities` 列出還沒併回（檔裡沒有「併回：」那一行）的所有列，bug 在前，再照加權、玩家、開發、鐵道迷排（§19 的同分規則），附來源連結，可以直接貼進清單；`--mark "<貼到哪>"` 在那些檔寫「併回：<貼到哪>（日期）」。
4. 規則改在 CLAUDE.md（Workflow 的 Decisions 段）、`docs/HANDOFF.md` §1.3「先評分再排、再派」、`docs/handoff/README.md`。現有 §29 不搬。

**五方。**
- 玩家：無直接影響；卡住的 PR 少了，新東西早一點到手上。
- 鐵道迷：無。
- 開發：評分的 PR 不再互撞，格式與加權在 PR 上就驗；規劃一個指令收齊所有新列。
- 美術：無。
- 音樂：無。

**沒選的。**
- 照決策 329 用號碼當檔名（`docs/priorities/<N>.md`）：又要在 #2118 預約號碼，多一個會撞的東西；工作名本來就唯一。
- 另寫 `tools/priorities/merge.py`（派工單的例子）：新目錄要加進 `swift-shards.sh doc_paths` 才會在 CI 跑到它的測試，而改 CI 腳本會讓這張 PR 跑完整 19 個工作；放進 `doc_numbers.py` 的 `--priorities`，和 `--index` 同一種用法，selftest 一起跑。
- 併回時刪檔而不是標記：決策與交接裡指向它的連結會斷；整理時規劃仍可以刪。
- 檢查 NEXT_PRIORITIES 有沒有人又新加小節：只有規劃改那份，不值得做成紅燈。

**下一步。** 規劃第一次併回時（有檔之後）照 `docs/priorities/README.md` 跑一次，確認貼上的表順手。
