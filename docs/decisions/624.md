### 624. Xcode 的 Debug 組態也用 -O 編 GameCore 與 GamePresentation（修訂決策 544）

2026-11-07，派工單 DEBUG-O（session_01YGNNukhF4UAsQZeoWZqjo4，遊戲規劃第 54 任 session_01YGNNupJUx5viUadNmXs45j 派），分支 `claude/debug-optimized`。號碼依 #1579 的登記：決策 624。存檔版本、golden schema、GoldenScenarios、SaveFixtures、ReplayFixtures、GameCore 與 GamePresentation 的程式都不動。改的是 `Package.swift`，加一支只在要求時跑的報告測試 `FirstTickReportTests`。

## 問題

作者在 Mac 的 Simulator 上跑 Debug 版 App 非常卡：開了遊戲，早上的時鐘就不走；同一份程式改用 Release 組態編的 Simulator 版，模擬一天快很多。決策 544 只在 Linux 給 GameCore 加了 `-O`（`#if os(Linux)`），寫明「Xcode builds on macOS are unchanged」：Xcode 的 Debug 組態下 GameCore 與 GamePresentation 都還是 `-Onone`。CI 的 UI 測試（`ios-build.yml`）與網站截圖（`website-screenshots.yml`）都用 Debug 組態；2026-11-07 一次網站截圖在「Take the screenshots」那步跑到 45 分鐘被停掉（run 42359762168）。

## 量到的（Linux 雲端容器、Swift 6.4.0，main 621746f）

`FirstTickReportTests`（`FIRST_TICK_REPORT=<ticks>`）照遊戲迴圈的做法跑一局剛開的頭幾個 tick（`GameSession.LoopTick.work()`：先在每個核心上算乘客路徑、推進、讀交通、站長的建議、地圖泡泡），再把每一段在副本上分開量。三種組態：

- **A：兩個都 -Onone**，等於今天 Xcode 的 Debug App。
- **B：只有 GameCore -O**，等於今天 Linux 的 `swift test`。
- **C：兩個都 -O**，等於這個決策之後 Xcode 的 Debug App（也接近 Release）。

每個 tick 是遊戲的一分鐘；一般速度（600×）下迴圈每 100 ms 要一個 tick。A 組態下開局先停約 2.7 s，之後每個 tick 20–80 ms 再加上主執行緒同樣是 -Onone 的畫面工作，已經接近或超過 100 ms，所以時鐘幾乎不走；Mac 上的絕對時間會不同（UNVERIFIED）。Linux 量的是 tick 的成本，不含 SwiftUI 與地圖的畫面。

**時鐘不走的原因**：高鐵示範與宜蘭線示範都從早上 07:00 開始。開局的第一個 tick 要先把全部乘客路徑算一次（決策 470），還要算站長的建議（決策 330），其中「哪條線沒有地方交會」（`firstLineWithoutPlaceToPass()`，決策 597）幾乎全在 GamePresentation 裡算。A 組態下第一個 tick 要 2.7–2.9 s，其中這一項約 1.6–1.7 s（B 組態也還要約 1 s）。第一個 tick 算完之前畫面上的時鐘停在 07:00。之後每個 tick 只要幾 ms，到下一個整點站長再看一次（交會那一項有快取，車沒變就不重算）。

**-O 之後還會不會卡好幾秒**：不會。C 組態下第一個 tick 是 0.27–0.48 s，之後每個 tick 幾 ms，沒有另一個卡住好幾秒的 bug。剩下的最大一項仍是 `firstLineWithoutPlaceToPass()`：全線雙軌的高鐵也要約 0.14 s，因為它先替每條線把整條路走一次才看有沒有單線。這個小、不影響時鐘，寫在下一步。

示範的建立（載入畫面）在 B 是高鐵 14.3 s、宜蘭線 4.8 s，C 是 7.2 s、3.6 s：GamePresentation 的 -O 也讓載入快一倍。

建置時間（Linux，`swift build --build-tests`，4 核）：B 7 分 15 秒，C 10 分 43 秒。所以 Linux 上 GamePresentation 照決策 544 維持 -Onone；Xcode 的 Debug 才加。

## 做法

`Package.swift`：

- GameCore：`-O` 在 Linux 與 iOS（`.when(platforms: [.linux, .iOS])`）。Linux 和以前一樣；iOS 的 Debug 與 Release 都是 -O（Release 本來就是）。
- GamePresentation：`-O` 只在 iOS（`.when(platforms: [.iOS])`）。Linux 的 `swift test` 不變。
- GameCoreTests：`-O` 只在 Linux，照舊。
- App 用 `project.yml` 的本機路徑套件引用整個 repository，本機套件可以用 `unsafeFlags`。App 自己的程式（`RailwayGameApp/`）不加，Debug 仍是 -Onone，除錯時 App 的畫面程式照樣能逐行看。
- `-O` 保留 GameCore 與 GamePresentation 的 precondition 與溢位檢查；兩個目標都沒有 `assert` 也沒有 `#if DEBUG`（Xcode Debug 的 `DEBUG` 條件照樣定義），所以 Debug 版的行為和以前一樣，只是快。
- macOS 上的 `swift build`／`swift test`（作者在 Mac 跑 GameSim）不變。

決策 544 的「Xcode builds on macOS are unchanged」由這個決策取代：Xcode 給 iOS 建的兩個套件目標都是 -O。

## 五面向

- 玩家：無直接影響（Release 本來就是 -O）；作者與測試在 Simulator 上看到的 Debug 版和玩家拿到的速度接近，卡頓回報不再被 Debug 的慢蓋過。
- 鐵道迷：無（行車結果不變）。
- 開發：Simulator 上的 Debug App、UI 測試與網站截圖不再慢好幾倍，開局不再停在 07:00；GameCore 與 GamePresentation 在除錯器裡看變數會比較難（-O 會省略變數），要逐行看時在本機暫時拿掉那一行就好。
- 美術：無。
- 音樂：無。

## 不選的

- **只換 CI 的組態（UI 測試、截圖改用別的組態）**：作者自己的 Mac 上 Debug 版還是一樣卡，而卡的正是作者要看的；CI 與作者也會用到不同的程式。
- **放棄 Debug 版**：UI 測試靠 Debug 才有的啟動參數（`DebugLaunch`，Release 驗證不能有），截圖與除錯也要它。
- **UI 測試改用 Release 組態**：Release 沒有 Debug 專用的啟動參數，UI 測試開不到指定的畫面；而且 Release 的 App 本身也是 -O、整個模組最佳化，建置比只加兩個套件目標慢得多。
- **Linux 上 GamePresentation 也加 -O**：建置多 3.5 分鐘（7:15 → 10:43），測試省下的少於這個（決策 544 的實驗）。
