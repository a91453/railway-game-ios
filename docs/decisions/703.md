### 703. 列車的路線用查的，不要每次從頭找：行車控制開、100 列車的一個 tick 快約 20 倍

2026-11-12，派工單 TICK-L0（遊戲規劃第 62 任 session_01YGNNupmJExcmCK1xgu6s5A 派），session_01YGNNunMtn9WFV5v3P2Xscx，分支 `claude/tick-l0`。來源：`docs/research/TICK_SCALE_CLOUD_2026-11-12.md` 第 3.1 節的 L0（第 1.7 節的 A1、A2、A3、A5、A7）。存檔版本、golden schema、`GoldenScenarios/`、`SaveFixtures/`、`ReplayFixtures/` 都不動；**沒有改任何規則或順序**，只是同樣的答案少算。

## 看到的

TICK-SCALE 量到：行車控制開、100 列車（每列一條線）一個 tick 618 ms（預算 100 ms），大約是列車數的 3 次方；取樣 25 次有 20 次在 `planTrafficOvertakes` → `hasRoutePreferences` → `assignedLine(of:)`／`line(id:)`。`planTrafficOvertakes` 對**每一對**服務問兩次「這列車的路線有沒有指定路徑」，每問一次都把所有路線的列車清單掃一遍、再把路線掃一遍。

## 決定

1. **`planTrafficOvertakes` 每個服務只問一次** `hasRoutePreferences`，放進陣列，逐對時讀陣列。
2. **「列車 → 路線」做成對照**（`GameWorld.TrainLineIndex`，`Sources/GameCore/Railway/TrainLineIndex.swift`）：一次把所有路線走過，記下每列車在 `lines` 的第幾條。
   - 放在 `PathMemo` 裡（`DirectionMemo.paths`、`DispatchMemo.directions.paths`）：已有的、不進存檔、不進 `Codable` 的暫存，一次 `advance` 或一次發問一份，路網與路線沒變時由 `RouteMemo` 借給下一次。**沒有動 `GameWorld` 的欄位與記憶體配置**（決策 590）。
   - **鍵是它建的時候的那份 `lines`**：每次查都先比 `lines`，不同就重建。Swift 的陣列共用同一塊儲存時一比就知道相等，平常（路線沒變）不花時間；發車會改路線的「上次發車時間」，那時重建一次（走一遍路線，線性）。所以不管誰把這份暫存帶到哪個世界、中間下了什麼指令，查到的都和從頭找的一樣，不靠「`advance` 裡不會有指令」這個前提。
   - 查到的是「第一條有這列車的路線的 ID，在 `lines` 裡第一條有那個 ID 的」，和 `lines.first(where: { assignedLine(of: id) == $0.id })`、`line(id: assignedLine(of: id))` 逐字相同。
   - 用它的地方：`hasRoutePreferences`、`routePreference`（發車、交通計畫各點、`workedOutServiceDirections`）、死結搜尋裡十一處 `lines.first(where: { assignedLine… })`（`Deadlock.swift`、`GameWorld.swift` 的讓路幾招）。
   - 沒有暫存可用的呼叫（指令、畫面的發問）照舊用 `assignedLine(of:)`，沒有動。
3. **`closingStart`（A1）**：「這列車是不是環狀線的」同一份對照順便記（環狀線自己的列車的集合），`stepDwell` 與 `nextServiceEvent` 用它。
4. **`runningTrains`（A5）**：數一條線某個方向在跑的列車，改成只看那條線自己的列車，每列用 ID 在 `trains` 裡二分找（`trainPosition(of:)`；`trains` 照 ID 遞增，讀檔時驗過；二分沒找到時退回從頭找，所以順序不對也不會答錯）。原本每條線每個方向每分鐘把全世界的列車看一遍。
5. **`serviceLevel`（A7）**：`lines.map { serviceLevel(of: $0.id, …) }` 六處改成 `serviceLevels(at:)`，直接讀那條線，不再用 ID 回頭找一次（路線 ID 不重複，讀檔時驗過）。

## 沒選的做法

- **把對照放進 `GameWorld` 當欄位**：會改 `GameWorld` 的大小與每個指令的維護點（決策 590 的教訓），而且要每個改路線的指令都記得更新；現在這樣一個指令都不用改。
- **以「一次 `advance` 內路線的列車不會變」當前提、不比鍵**：`DispatchMemo` 的其他欄位是這樣做的，但那樣對不對要靠每個帶著暫存的呼叫者都守這個前提；比 `lines` 幾乎不花時間，所以選不靠前提的做法。
- **記住每列車 `hasRoutePreferences` 的結果**：它還讀時刻表，鍵要多帶時刻表；每個服務問一次之後它已經不在取樣裡，不值得。
- **把 `assignedLine(of:)` 本身改成查表**：它是 `public`、沒有暫存可帶，四十處呼叫多半在指令裡（一次指令一次），不是熱路徑。
- **L1、L2、L3、多核心、雲端**：派工單明說不做。
