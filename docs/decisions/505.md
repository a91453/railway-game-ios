**假說與結果**（照排序）：

1. **tick 之後主執行緒的收尾**（`finish`：新聞、站長建議、泡泡、地圖提示、午夜）：**推翻**。最長 80 ms，而且 App 把它計為「推進後」，不是「其他」。

3. **畫面每次更新對新世界做的比較與小計算**（`onChange`／`task(id:)` 的 key：`land`、`buildings`、`network`、`trains`、`lines`、`stations`、`passengers`、`roads` 的 `==`，`MapLayers.waitingPassengerCounts`、`LineBadge.codes`、`depotRuns`、`forecast`、`MapWeather`、`RealWorldFrame`、`roadCellCount`）：**推翻**。每個 tick 最長 1.3 ms（`waitingPassengerCounts`；這局車站上有 51,414 群、64,144 人在等，存檔裡 `passengers` 佔 11 MB，見 WAIT1、決策 504）。

所以 1–3.6 秒不在 GamePresentation 的主執行緒工作裡（Linux 上整整 60 個遊戲小時沒有一次超過 80 ms），而在 App 層。回報分不出是哪一種：2D 節拍的紀錄（決策 421）只在畫面上的讀數打開時才量「畫面更新」（決策 379 的 run loop observer），各畫面的 body（`mapBody`、`hudBody`、`stationMasterBody`、`screenBody`）與地圖跟著推進的幾段雖然有量，卻因為是「畫面更新」的一部分而不列出。

**做了什麼**（只動 GamePresentation 的紀錄與 App 的紀錄器，不改遊戲）：

1. `FrameCostMeter.frameParts`：最長停頓列出主執行緒上量到的每一段，包括「畫面更新」與它裡面的各畫面、「推進後」裡面的新聞等。「其他」照舊是扣掉不含別段的那些之後剩下的，所以「畫面更新」與各畫面的時間仍在「其他」裡；看「畫面更新」佔「其他」多少，就知道是畫面還是別的。列出的段數 3 → 5（`FrameTimeMeter.shownParts`）。
2. `FrameTimeRecorder`（App）：2D 節拍開著時，自己加上決策 379 那兩個 run loop observer，量「畫面更新」；畫面上的讀數開著時不量（讀數已經在量，免得算兩次）。
3. 最長停頓記下當時的遊戲時刻（`FrameTimeStall.game`，舊紀錄沒有，讀成 `nil`），回報寫成「最長 3600.0 ms（第 4.8 秒，遊戲第 38 日 06:47）」，分得出是 06:00 換計畫、午夜、整點，還是隨時。

測試：`FrameTimeRecordTests.testThe2DLongestStallTellsTheViewUpdateAndTheGameClock`（在 origin/main 上編不過：沒有 `game`，也不列畫面更新與各畫面）；`testThe2DLongestStallCarriesItsParts` 改成也列出「推進後」裡的新聞。
