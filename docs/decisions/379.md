### 379. 高鐵 6000× 的推進：每列車的判斷不再複製整個世界，午夜的城市成長沿用前一天的乘客計畫

2026-10-23，遊戲規劃派工（NEXT_PRIORITIES §22.2 第 41 名、`docs/HANDOFF.md` §7.1，決策 330、377 的下一步），session_01MhQXufQK6jhjrKXY6iUTDB，`claude/tick-advance-hotspots`。存檔版本、golden schema、SaveFixtures、ReplayFixtures 都不動；GameCore 只改寫法與快取，結果逐位元相同。

**作者的實機讀數**（TestFlight 85.1，iPhone 17 Pro，高鐵示範，2D，6000×）：幀數表的「推進」（背景執行緒上的 `GameWorld.advance(ticks:)` 與交通讀取）500–690 ms/s、每秒 ×8–12、max 194–305 ms，白天比深夜高。背景執行緒一秒忙半秒以上：發熱、耗電，單次 300 ms 時高倍速的遊戲時間跟不上。

**1. 怎麼量**：`TickCostReportTests` 加了高鐵示範 6000× 的報告（`MapFrameCostReportTests.highSpeedSession()`，15 站、3 線、35 列車、交通控制關），逐 tick 計時 `advance(ticks: 1)` 與 `TrafficReading`，印出平均、最長、每小時的平均與最貴的 8 個 tick：

```sh
TICK_REPORT_HSR=432 swift test -c release -Xswiftc -enable-testing --filter TickCostReportTests/testWhatATickCostsOnTheHighSpeedRail
```

432 個 tick 是 6000× 的三天（一個 tick 10 分鐘）。哪裡花時間用 valgrind 的 callgrind 量（Linux 沒有 perf），只收被量的那段 closure（`--toggle-collect`），再用 `callgrind_annotate --inclusive` 與 `--tree=caller` 看呼叫者；懷疑是複製時，看 release 的 `.o` 反組譯（`objdump -dr`）裡呼叫 `GameWorld` 的 outlined copy（`$s8GameCore0A5WorldVWOc`）的地方。

**2. 改前白天一個 tick 的錢花在哪**（callgrind，白天 36 個 tick，98 億指令）：

| 哪裡 | 佔 |
| --- | --: |
| 複製與釋放整個 `GameWorld`（約 40 萬次） | 約 19 % |
| `assessSpacing`（間隔判斷；`heldUp` 9 %、`spacingIndex` 3 %、`way` 5 %） | 21 % |
| `TrainRoute.shortest`（找停車位） | 12.7 % |
| `routeStretches`（`secondsUntilARouteEnds`、`dropRunsHeldUp` 經 `pathAhead`） | 11 % |
| `dispatchTrains` | 10.6 % |
| `departService` | 8.9 % |
| 乘客計畫重算 | 5.3 % |

交通讀取（`TrafficReading`）每次 0.01 ms，可以不管。乘客產生、收入結算在白天都不到 1 %。

**3. 第一個熱點：每列車的判斷複製整個世界**。在 `mutating` 的方法裡把 `trains[index]` 直接當引數傳給不改世界的方法（例如 `isStopped(trains[index], at: …)`），Swift 會先把整個 `GameWorld` 複製一份再讀，讀完釋放；世界有路網、車站、時刻、帳本，一次複製就是幾百個參照計數。高鐵示範一個 tick 有幾千次。改法是先把列車放進區域常數（`let train = trains[index]`）再傳，反組譯確認那些地方不再呼叫 outlined copy。改了的地方：`goOn`、`extendAuthorities`、`moveTrains`、`releasePassedTrack`、`recordArrivals`、`dropRunsHeldUp`、`departService`、`stepDwell`、`runServices` 的 `freePlatformOnTheWay`；`clearOfBlocked` 的兩個 closure 原本各自抓整個世界，改成只抓路網。都只是寫法，算的東西一樣。

**4. 第二個熱點：午夜重算一整份乘客計畫**。6000× 的呼叫都從整 10 分鐘開始，所以有一次剛好從 00:00 開始。那次呼叫開頭先替新的一天算計畫（示範的線用新線預設的營運時段 06:00–24:00（`ServiceWindow.standard`），00:00 收班，班次等級變了，計畫要重算，乘客找路的 memo 也跟著換掉），接著城市成長要「前一天最後一秒」的計畫，`reachedStations` 就把快取清掉、用白天的路網再算一整份（callgrind：一次約 7 億指令，第一個午夜 6.5 秒裡最大的一塊）。其實開頭重算之前留著的那份計畫就是前一天的：改成在 `advance` 裡記住最後一次重算前的計畫（`endedPlan`），`reachedStations` 先看它或目前的計畫在 23:59:59 的 `passengerPlanKey()` 是否相同，相同就直接用（`PassengerPlanKeyTests`：鍵相同時留著的計畫就是重算出的那份），不同才照舊重算。直接找路模式照舊重算。`TownGrowthTests.testMidnightReadsTheEndedDaysNetworkPlanHoweverTheCallsFall` 釘住這件事：網路找路、午夜收班的線，跨午夜一次呼叫、從午夜開始的呼叫、午夜讀檔，三種的成長都等於「兩站互相到得了」的成長（故意改成沿用新一天的計畫時這個測試會紅）。

**6. 沒有做的，與下一步**：
- `assessSpacing` 仍是白天最大的一塊（約兩成）：每列車問每一列別的車時，別的車的「車尾＋車頭＋前方」邊集合每次重算。可以每次 `assessSpacing` 先替每列車算一次（`bodyStretches` 也一樣），`heldUp` 只做集合交集。
- `routeStretches` 每次重走 `pathAhead`：可以依列車與它的進路記住。
- 午夜與 06:00 仍要替新的一天各算一次計畫（班次等級真的變了）。可以讓乘客找路的 memo 依班次等級各留一份，06:00 與 00:00 換來換去時不必從頭找路。
- `RouteMemo.Key(self)`、`resolveDeadlock`、`dispatchRuns` 的 `readyRunTrain`、`runPullOut` 的 lazy closure 仍會複製世界，但一個 tick 只有幾次到一百多次，不在熱點裡。
- 乘客佇列照路線分組（§22.2 第 41 名原本的寫法）沒有做：量出來乘客產生與上下車在白天都不到 1 %，不是這個示範的熱點。

**請作者重量**：TestFlight 86.1 以後，高鐵示範、2D、6000×，開「設定 → 地圖 → 幀數」，記下「推進」那一行的 ms/s、×幾、max，白天與深夜各看幾秒。85.1 是 500–690 ms/s、max 194–305 ms；Linux 平均少了約 27 %、最長少了約 35 %，實機的 ms/s 應該跟著降，max 在午夜與早上六點。

**參考與搜尋**：
- 參考庫 `Simulator/reference_snapshot/` 的模擬頁是軌道配置與 3D 行駛（Next.js 打包後的 JavaScript），沒有間隔判斷或乘客計畫，沒有可搬的。
