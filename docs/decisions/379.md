### 379. 2D 高鐵 6000× 主執行緒：音效在自己的佇列播放，幀數表拆開「其他」

2026-10-23，遊戲規劃派工（session_01H5RHAwnA69n8EfAUSUrH52；`docs/HANDOFF.md` §7.1，決策 377、371、367 的下一步），session_019RS5qZNMdEtyEF7MkVyR4c。存檔版本、golden schema、SaveFixtures、ReplayFixtures、GameCore 都不動；只動 App 與 GamePresentation。背景的推進（500–690 ms/s）是另一個 session 的（§22.2 第 41 名），這裡沒有動。

**作者的實機讀數**（TestFlight 85.1，含 #1098；iPhone 17 Pro，高鐵示範，2D，6000×，站名與候車數打開，站長泡泡開著，第 1 年 1/5–1/6 六張截圖）：26–41 fps（84.1 是 3 fps）；地面、軌道與路線、交通與車站、站名都接近 0；**最長一幀 173–200 ms，其中「其他」165–200 ms**（每張都有）；推進後 · 音效：白天 25–28 ms/s ×8–11、max 28.9–29.8 ms，深夜 0；推進後 · 收入：10–21 ms/s、max 10.4–21.9 ms。

**1. 音效與收入：時間在 `AVAudioPlayer.play()`，改在自己的佇列播放**。

- 讀數的 ms/s 和 max 幾乎一樣，表示一秒裡只有一次花了 29 ms（或 22 ms），其他 tick 幾乎是 0。
- 「音效」這一段在 GamePresentation 裡只做：比到站時間（在背景的 tick 已經算好 `step.arrived`）、`SoundCue.arrivalCue`（沒有看著的車就直接回 `.arrival(watched: false)`）、`updateFollowSounds()`（沒有跟車時只比一個數）。Linux 上都量不到。一秒一次的貴的那次只能是 App 的 `GameAudio.play(_:)` 真的放出聲音的那次：`player.play()` 會同步等音訊輸出開起來，開發者論壇常見它卡主執行緒幾十毫秒的回報；Linux 量不到，要靠作者重量確認（下面「播放音效」那一行）。深夜 0 也對得上：高鐵深夜不開車，沒有到站聲。
- 「收入」這一段（`noteIncome`、`retireCoveredShortfall`、`noteDayLoss`）只加總最後幾筆帳（`entries.lastIndex(of:)` 從尾端找，通常一兩筆就找到）、找一天的帳，然後 `playSound?(.income)`：每遊戲小時結一次票款，6000× 約 0.6 秒一次，硬幣聲至多每 3 秒一次。同樣是 `play()`。
- 改法：`GameAudio` 照舊在主執行緒決定放不放（間隔、震動、音量、開關都不變），播放交給 `CuePlayers`：一個自己的序列佇列（`DispatchQueue`，`.userInitiated`），提示音的 `AVAudioPlayer` 只在那裡建立與播放。音樂、跟車的行駛聲、天氣與雷聲不是每個 tick 的事，沒有動。
- 聲音一樣：同一個檔、同一個音量、同樣的間隔（到站 6 秒、看著的車 0.5／1.5 秒、硬幣 3 秒），只是晚不到 1 毫秒才開始。
- 幀數表多一行「播放音效」（`FrameCostPart.soundPlayback`，背景，不算進主執行緒），作者重量時可以直接看到 `play()` 花多少、而且不在主執行緒了。若重量後「推進後 · 音效」「收入」還是 20–30 ms，就表示不是 `play()`，下一步寫在下面。

**2. 「其他」190 ms：幀數表把它拆開**（像決策 377 拆軌道）。

Linux release（`FAST_FORWARD_READS=50 FAST_FORWARD_SPEED=6000 swift test -c release -Xswiftc -enable-testing --filter FastForwardReadsReportTests`，15 站、35 列車、3 線）：每個 tick 後畫面第一次讀 session 的東西加起來只要 **3.1 ms**，最多的是 `TrainMotion(world:)` 2.8 ms，其他都在 0.1 ms 以下。所以 190 ms 不是畫面讀模型的值，而是 SwiftUI 重算 view、排版與 Core Animation 送出這一段，Linux 量不到。幀數表加了：

- 「**畫面更新**」（`FrameCostPart.viewUpdate`）：App 在主執行緒 run loop 等待之前的那一段（`CFRunLoopObserver`，`beforeWaiting`，最早與最晚兩個 observer 之間），SwiftUI 的更新與 Core Animation 的 commit 都在這裡，畫布的繪製也在裡面。因為包含畫布，它不從「其他」扣掉，改成第一行寫「最長一幀 200 ms · 其他 190 ms（畫面更新 180 ms）」：最長那一幀裡畫面更新佔多少。
- 它底下的分項，各 view 自己的 body（子 view 的 body 算子 view 自己的）：「地圖」（`MapView` 的 body 與 `GeometryReader` 裡的內容，含 modifier 比較的各種 key）、「地圖列車滑行」（`MapView` 在 tick 換世界時拿的 `TrainMotion`）、「地圖車流」（同時拿的交通控制讀數）、「地圖跟著推進」（其餘：真實列車的時鐘、天氣、跟車置中；第 4 段的第一次量測時滑行與車流也算在這裡）、「畫面框架」（`ContentView` 與它的路線提示）、「狀態列」（`HUDView` 與錢、時間、天氣預報、觀看速度）、「站長」（`StationMasterCorner`）。
- 讀法：「畫面更新」大、分項都小 → 時間在排版或 Core Animation（例如地圖上很多 view 的 diff、`ViewThatFits` 量四個版本、陰影與材質）；某個分項大 → 就是那個 view 的 body。「畫面更新」也小、「其他」還是大 → 時間在 run loop 的事件處理（例如我們沒有計時的 `Task` 接續），不在畫面。

改法（照決策 330 把站長建議移到背景的做法）：
- 遊戲迴圈的 tick（`LoopTick.work()`，背景）多帶「地圖上一次顯示的滑行」（`GameSession.shownGlide`），算完世界就順便算出到新世界的滑行，放在 `TickStep.glide`，`finish` 時記在 `glideMemo`（和 `trafficMemo` 一樣綁世界的版本）。
- 地圖的 `onChange(of: world.trains)` 改叫 `session.trainMotion(after:at:)`：同一個世界、同一個上一次滑行時，用背景算好的，只補上顯示的時間與長度（`TrainMotion.seen(at:after:speed:)`，和 `init(world:previous:time:)` 算時間的式子同一個）；不然（中間有指令、兩個 tick 合成一次顯示、1×）照舊在主執行緒算。結果和地圖自己算的一樣（Linux 測試逐 tick 比 200 個 tick）。
- 1× 不在背景算：1× 的滑行可能整秒沿用上一次（`init` 直接回傳 `previous`），補時間會把它重新開始。
- 地圖關掉（`onDisappear`）就停（`mapStoppedGliding()`），tick 不再白算。
- 另外 `covered` 多一個上限：經過的軌道超過一次滑行的最遠距離（40 km）就不組點，直接當成跳過去（本來組完量了長度才丟）。這個示範的滑行剛好都在 40 km 內，所以這次省不到；更快的車、更大的 tick 才用得到。結果一樣（測試：上限內的點相同，超過的回 `nil`）。

背景的推進因此每 tick 多做這段（Linux debug 約 0.5 秒，release 估約二十幾 ms；原本就在主執行緒做，總量沒有變多，只是換到背景）。推進是另一個 session 在量的，若它說推進變成瓶頸，下一步是把滑行的點照螢幕容許誤差簡化（決策 377 的 `PolylineDetail` 做法），或讓滑行與下一個 tick 平行。

### 379（續）. 高鐵 6000× 的推進：每列車的判斷不再複製整個世界，午夜的城市成長沿用前一天的乘客計畫

2026-10-23，遊戲規劃派工（NEXT_PRIORITIES §22.2 第 41 名、`docs/HANDOFF.md` §7.1，決策 330、377 的下一步），session_01MhQXufQK6jhjrKXY6iUTDB，`claude/tick-advance-hotspots`。存檔版本、golden schema、SaveFixtures、ReplayFixtures 都不動；GameCore 只改寫法與快取，結果逐位元相同。

**作者的實機讀數**（TestFlight 85.1，iPhone 17 Pro，高鐵示範，2D，6000×）：幀數表的「推進」（背景執行緒上的 `GameWorld.advance(ticks:)` 與交通讀取）500–690 ms/s、每秒 ×8–12、max 194–305 ms，白天比深夜高。背景執行緒一秒忙半秒以上：發熱、耗電，單次 300 ms 時高倍速的遊戲時間跟不上。

**3. 第一個熱點：每列車的判斷複製整個世界**。在 `mutating` 的方法裡把 `trains[index]` 直接當引數傳給不改世界的方法（例如 `isStopped(trains[index], at: …)`），Swift 會先把整個 `GameWorld` 複製一份再讀，讀完釋放；世界有路網、車站、時刻、帳本，一次複製就是幾百個參照計數。高鐵示範一個 tick 有幾千次。改法是先把列車放進區域常數（`let train = trains[index]`）再傳，反組譯確認那些地方不再呼叫 outlined copy。改了的地方：`goOn`、`extendAuthorities`、`moveTrains`、`releasePassedTrack`、`recordArrivals`、`dropRunsHeldUp`、`departService`、`stepDwell`、`runServices` 的 `freePlatformOnTheWay`；`clearOfBlocked` 的兩個 closure 原本各自抓整個世界，改成只抓路網。都只是寫法，算的東西一樣。

**4. 第二個熱點：午夜重算一整份乘客計畫**。6000× 的呼叫都從整 10 分鐘開始，所以有一次剛好從 00:00 開始。那次呼叫開頭先替新的一天算計畫（示範的線用新線預設的營運時段 06:00–24:00（`ServiceWindow.standard`），00:00 收班，班次等級變了，計畫要重算，乘客找路的 memo 也跟著換掉），接著城市成長要「前一天最後一秒」的計畫，`reachedStations` 就把快取清掉、用白天的路網再算一整份（callgrind：一次約 7 億指令，第一個午夜 6.5 秒裡最大的一塊）。其實開頭重算之前留著的那份計畫就是前一天的：改成在 `advance` 裡記住最後一次重算前的計畫（`endedPlan`），`reachedStations` 先看它或目前的計畫在 23:59:59 的 `passengerPlanKey()` 是否相同，相同就直接用（`PassengerPlanKeyTests`：鍵相同時留著的計畫就是重算出的那份），不同才照舊重算。直接找路模式照舊重算。`TownGrowthTests.testMidnightReadsTheEndedDaysNetworkPlanHoweverTheCallsFall` 釘住這件事：網路找路、午夜收班的線，跨午夜一次呼叫、從午夜開始的呼叫、午夜讀檔，三種的成長都等於「兩站互相到得了」的成長（故意改成沿用新一天的計畫時這個測試會紅）。
