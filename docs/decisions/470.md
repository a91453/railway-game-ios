**先試、推翻的**：HANDOFF §5 的 (1)「圖沒變的部分跨天沿用」。`PassengerRouteMemo` 改成依連通的部分（路徑去掉 `dailyCapacity`、步行、關閉的站）記路線：一個部分的路線只讀那個部分，所以別處改了，這部分照用，逐位元相同（`testRoutesKeptThroughEditsElsewhereGiveTheSameWorld`）。最多記 4 張圖前用過的部分（原本是目前與前一張圖），夜裡的空圖和早晚不同班距的圖不會把白天的換掉。但 BK 那局的路線圖一直是**一整塊**（78–81 站，路徑 10→44 條），改任何一條線整塊都變，所以這一步在那局一點都沒快；時間跟著路徑數長。它留下來，給有好幾塊互不相連路網的局用。

**做了什麼**：

1. GameCore（`Sources/GameCore/Passenger/PassengerRouteCache.swift`）多三個公開的進入點，都不改遊戲狀態：
   - `passengerRoutesToWorkOut(forTicks:)`：下一個 tick 的計畫要重搜哪些起點、在哪一刻的圖上。計畫不是最新的（沒有、`passengerPlanKey()` 變了、換了一天）就是現在這一刻；否則看這個 tick 內（不含終點，終點是下一個 tick 的開頭）第一個班距變了的整分（06:00 開始有車）。記憶裡已有的起點不算。
   - `workingOutPassengerRoutes(_:origins:)`：在那一刻的圖上，從給的起點到每個有乘客的站，照計畫問的方式算路線。只讀世界，所以可以同時算好幾份。
   - `takePassengerRoutes(_:)`：把算好的路線放進世界的 `PassengerRouteMemo`。
   `PassengerRouteGraph(world:at:)` 可以給時刻（班距照那一刻）。
2. 表現層（`Sources/GamePresentation/PassengerRoutesAhead.swift`）：`GameSession` 每個 tick 在背景推進世界的複本之前，先問有沒有要重搜的起點；有 8 個以上，就把起點分成核心數 4 倍的份，用 TaskGroup 同時算，收齊後交給那份複本，再照舊 `GameSession.advanced`。

**為什麼結果不變**：`PassengerRouteMemo` 不是遊戲狀態（`==` 永遠相等、不存檔）；一組起訖的路線只由路線圖決定（同一張圖、同一個搜尋，tie-break 照路徑與標籤的順序，和誰算、哪個執行緒、算的順序都無關）。tick 拿到的是它自己本來就會算出的同一份，所以只是不用再算。換上的時機不看裝置速度：一定是在這個 tick 開始之前算完、收齊（沒算完 tick 就等），不是「算好了才在某個 tick 換上」，所以快慢不同的裝置在同一串指令下得到同一個世界。驗證：
   - `PassengerRoutesAheadTests`（GamePresentation）、`PassengerPlanKeyTests` 的三個新測試：先給路線與不給路線，tick 之後世界、乘客、乘車都相同，tick 不再自己算任何一組（記憶的組數不變）。
   - BK 重播：慢的 tick 各自用一核、全部核心預先算，再推進，世界和沒預先算的相同（`same world: true`）。
   - 整份 command log（1,154 個 tick）重播的結尾存檔，SHA-256 三份都是 `f7e615c8…3b293137`：main 的 binary；這個 branch 照舊推進；同一個 branch binary 每個 tick 都先算好路線再交給它（`COMMAND_LOG_GIVE=1`，經過遊戲迴圈的 `beginLoopTick`／`finish`）。結尾也和裝置的相同。

#### 續（2026-11-01）：第二層禁用邊從第一層分岔、標籤的順序共用前綴

遊戲規劃 #39（session_01YGNNupwLVxuPiWcrdA6NPs）派工單 PLANDAY，實作 session_01YGNNuqEZL9bfYRQGsEEG44（`planday-route-search`）。號碼依 #1579：決策號沿用 470（預留的 530 釋出），存檔版本、golden schema 不動；GoldenScenarios、SaveFixtures、ReplayFixtures 的值都不動。做的是上面「下一步」的 D，和 HANDOFF §5 的 (2)、(3)。

**問題**：上面的預先計算靠多核心分擔，單核心的工作量沒變。BK 那局（92.1，實景、81 站、22 線）載入後第一天的 06:00，GameCore 自己算一次計畫在 Linux release 仍要約 13 秒（`PassengerRouteSaveReportTests`，不經表現層的預先計算）。數 pop 的結果：

| --- | --: |
| 不禁用 | 75,899 |
| 禁一條邊時重播檢查點 | 497,446 |
| 禁一條邊 | 2,558,461 |
| 禁兩條邊 | 7,997,897 |

這一天的計畫開了 7,402 個禁一條邊的搜尋、18,581 個禁兩條邊的搜尋。禁兩條邊的搜尋每次都從不禁用搜尋的檢查點起跑，幾乎把整張圖再走一遍，佔了七成。

**做了什麼**（`Sources/GameCore/Passenger/PassengerRoutes.swift`）：

1. **搜尋記下自己的經過**：`PassengerRouteSearch` 記錄以下時間，時間是已展開的標籤數：
   - 每個標籤何時產生、何時 pop、何時被支配而移出前緣；
   - 每個站的槽第一次抵達的時間；
   - 每個停靠點第一次展開的時間，和展開的是哪個標籤。

   `paused(before:)` 用這些紀錄，把搜尋還原成「第一次展開某停靠點之前」的樣子，不用重搜：
   - 標籤照產生順序編號，所以那時已有的標籤就是前面那一段；
   - 其中還在前緣的，照編號組回前緣；
   - 還沒 pop 的，用 heapify 組回 heap。

   heap 依嚴格全序 `precedes` pop，最後的 tie-break 是標籤編號，所以 heap 怎麼排列不影響 pop 的順序。原本的 16 個檢查點和重播一起拿掉了。
2. **第二層也分岔**（§5 的 (2)）：禁 {x, y} 的搜尋，取 x、y 中不禁用搜尋較晚展開其停靠點的那條，假設是 y（同時或都沒展開時照 `PassengerRideEdge.precedes`），從禁 {x} 的搜尋在第一次展開 y 的停靠點之前分岔。禁 {x} 的搜尋沒走到那裡就先接著跑，再放回記憶。禁一條邊的搜尋照舊從不禁用的搜尋分岔，不禁用的搜尋也改成原地暫停，不先複製。
3. **順序共用前綴**（§5 的 (3)）：標籤的 `order`（同分時比的腿序）原本每個標籤一個 `[PassengerRouteOrderLeg]` 陣列，改成指向搜尋裡 `orders` 的一個節點（腿、父節點、深度）。比較時較深的一端先往上走到同深度，再兩端一起往上找最前面不同的腿，結果和 `passengerRouteOrderPrecedes` 比陣列相同。
4. **記憶照最近使用**：`PassengerRouteSearches` 的最近使用改用時間戳與字典，不再用陣列 `firstIndex`；標籤總數也改成增量記帳。上限照舊是 512 個搜尋、合計 40 萬個標籤。`init(graph:searchLimit:labelBudget:)` 少了 `checkpointLimit`。

**為什麼逐位元相同**：禁 B∪{y} 的搜尋和禁 B 的搜尋，在第一次展開 y 的停靠點之前做的事完全相同，因為禁用只影響那個停靠點的展開（`expand` 不從被禁的停靠點搭下一段）。所以從禁 B 的搜尋在那一刻的狀態接著跑，結果和從頭跑一樣。那一刻的狀態，是從紀錄還原出來的：
- 已產生的標籤；
- 仍在前緣的標籤；
- 未 pop 的標籤；
- 已抵達的站；
- 已展開的停靠點；
- 暫停在手上的標籤。
