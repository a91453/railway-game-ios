#### 續（2026-11-01）：第二層禁用邊從第一層分岔、標籤的順序共用前綴

這一天的計畫開了 7,402 個禁一條邊的搜尋、18,581 個禁兩條邊的搜尋。禁兩條邊的搜尋每次都從不禁用搜尋的檢查點起跑，幾乎把整張圖再走一遍，佔了七成。

**做了什麼**（`Sources/GameCore/Passenger/PassengerRoutes.swift`）：

1. **搜尋記下自己的經過**：`PassengerRouteSearch` 記錄以下時間，時間是已展開的標籤數：
   - 每個標籤何時產生、何時 pop、何時被支配而移出前緣；
   - 每個站的槽第一次抵達的時間；
   - 每個停靠點第一次展開的時間，和展開的是哪個標籤。

   `paused(before:)` 用這些紀錄，把搜尋還原成「第一次展開某停靠點之前」的樣子，不用重搜：
   - 標籤照產生順序編號，所以那時已有的標籤就是前面那一段；
   - 其中還在前緣的，照編號組回前緣；
   - 還沒 pop 的，用 heapify 組回 heap。

   heap 依嚴格全序 `precedes` pop，最後的 tie-break 是標籤編號，所以 heap 怎麼排列不影響 pop 的順序。原本的 16 個檢查點和重播一起拿掉了。
2. **第二層也分岔**（§5 的 (2)）：禁 {x, y} 的搜尋，取 x、y 中不禁用搜尋較晚展開其停靠點的那條，假設是 y（同時或都沒展開時照 `PassengerRideEdge.precedes`），從禁 {x} 的搜尋在第一次展開 y 的停靠點之前分岔。禁 {x} 的搜尋沒走到那裡就先接著跑，再放回記憶。禁一條邊的搜尋照舊從不禁用的搜尋分岔，不禁用的搜尋也改成原地暫停，不先複製。
3. **順序共用前綴**（§5 的 (3)）：標籤的 `order`（同分時比的腿序）原本每個標籤一個 `[PassengerRouteOrderLeg]` 陣列，改成指向搜尋裡 `orders` 的一個節點（腿、父節點、深度）。比較時較深的一端先往上走到同深度，再兩端一起往上找最前面不同的腿，結果和 `passengerRouteOrderPrecedes` 比陣列相同。
4. **記憶照最近使用**：`PassengerRouteSearches` 的最近使用改用時間戳與字典，不再用陣列 `firstIndex`；標籤總數也改成增量記帳。上限仍是 512 個搜尋；標籤的上限從 40 萬個降到 **20 萬個**，因為每個標籤多記了經過與順序節點（父、深度用 32 位元），照原上限 92 那局尖峰多約 50 MB。上限只影響要不要重算，不影響答案。`init(graph:searchLimit:labelBudget:)` 少了 `checkpointLimit`。

**為什麼逐位元相同**：禁 B∪{y} 的搜尋和禁 B 的搜尋，在第一次展開 y 的停靠點之前做的事完全相同，因為禁用只影響那個停靠點的展開（`expand` 不從被禁的停靠點搭下一段）。所以從禁 B 的搜尋在那一刻的狀態接著跑，結果和從頭跑一樣。那一刻的狀態，是從紀錄還原出來的：

- 仍在前緣的標籤；
- 未 pop 的標籤；
- 已抵達的站；
- 已展開的停靠點；
- 暫停在手上的標籤。

#### 續二（2026-11-01）：試了以目的地為界的 A*，推翻；改成把搜尋的前緣攤平

遊戲規劃 #40（session_01YGNNuoSiXAJiUsqe53Fe24）派工單 PLANDAY-2，實作 session_01YGNNupKp56159yj4t686J8（`claude/passenger-route-astar`）。號碼依 #1579：決策號沿用 470，存檔版本、golden schema 不動；GoldenScenarios、SaveFixtures、ReplayFixtures 的值都不動。做的是「續」的下一步第一條。

**先試、推翻的：以目的地為界提早停（A*）**。做法：
- 每個目的地先從終點倒著做一次單一準則的最短路，得到每個狀態到終點的最少秒數。禁用只會拿掉邊，所以這個下界不會高估，也滿足一致性。
- 禁兩條邊的搜尋先用 A* 求出最少秒數，再丟掉「秒數加下界後的整分，超過最佳路線整分」的標籤。

這樣的答案逐位元相同，證明寫在當時的程式註解：
- 支配別人的標籤秒數不比對方多，所以被丟的標籤只會支配也被丟的標籤；
- 留下的標籤產生與 pop 的順序不變，連最後用產生順序比的 tie-break 也一樣。

驗證方式：
- 兩份存檔的世界 SHA-256 和 main 相同；
- 隨機路網測試對照不設界的搜尋，把界故意少 1 分鐘時測試會紅。

**但沒有變快**：AQ 那局 06:00 從 3.3 秒變成 4.3 秒，92 那局持平。原因是禁兩條邊的搜尋大多被很多目的地共用。AQ 那局一天問了 77,883 次禁兩條邊，其中 65,795 次（84%）接著用別的目的地留下的搜尋，只開了約 1.2 萬個新的。以單一目的地為界之後，搜尋不能再給下一個目的地用：
- 分岔從 17,796 次變成 7.3 萬次（只在找得到現成路線時才設界的版本是 4.7 萬次）；
- 要複製的標籤從 550 萬個變成 1,500–2,400 萬個；
- 展開的 pop 只從約 142 萬降到約 98 萬–127 萬；
- 先求最佳秒數的 A* 本身又多了 819 萬次（較便宜的）pop。

**做了什麼：攤平搜尋的前緣**（`Sources/GameCore/Passenger/PassengerRoutes.swift`）。用 callgrind 量 main 的 AQ 那局 06:00（計畫共 163 億道指令），時間花在：

| 部分 | 佔計畫 |
| --- | --: |
| 搜尋本身（`run`） | 48% |
| 分岔（`start`／`paused(before:)`） | 19% |
| 銷毀搜尋（`destroy for PassengerRouteSearch`） | 12% |
| `malloc`／`free`、retain／release（散在上面幾項） | 約 25% |

原因是前緣 `frontier: [[Int]]`：每個狀態（停靠點的兩倍，約 1,200 個）一個小陣列。複製搜尋時每個都要 retain；分岔時每個都重新配置；銷毀時每個都要 release；每次 `offer` 也會重新配置那個狀態的陣列。

改成一條串在標籤上的鏈：
- `frontierHead` 記每個狀態第一個標籤；
- `frontierNext` 記每個標籤的下一個，-1 是結尾。

兩個都是 `Int32` 的平面陣列，複製就是整塊記憶體。

**為什麼逐位元相同**：前緣只用來判斷新標籤是否被支配、移出它支配的標籤。「有沒有一個支配它」與「哪些被它支配」都和前緣的排列順序無關，所以結果只在排列順序上不同。分岔時照標籤編號重建，原本是依序附加，現在是插到鏈頭；heap 的 pop 順序照舊由嚴格全序決定。搜尋的步驟沒有變，所以 pop 次數和 main 相同。

驗證：
- 兩份存檔推進 2 分鐘（跨 06:00），世界 SHA-256 和 main 相同：
  - 92 那局：`69bfe17c…46e024`；
  - AQ 那局：`397d1565…38b536b4`。
- 92 那局推進兩天（`fast`，174,000 秒，290 個 tick）：`5bb4ad57…acfed4d`，和 main 相同。這和「續」的 `c83e614a…` 不同，是因為 main 在這之間改過，例如 #1654。
- 新測試 `PassengerRouteSearchTests.testTheSecondBanFindsTheSameWhenRoutesTie`：在很多路線同分、有些車程是 0 秒的隨機路網上，最後的 tie-break 也要分出勝負。每一組禁一條、兩條邊的答案，都和單獨從頭搜尋的相同。
- 原有五個測試照舊通過。

**結果**（Linux release，同一台機器，main 與這個 branch 交替各跑兩次；這台機器比「續」量的那台慢，而且跑之間的差距大）：

約快 4 成，pop 次數不變。

量法：`PASSENGER_ROUTE_SAVE=<存檔> PASSENGER_ROUTE_DUMP=<輸出> swift test -c release -Xswiftc -enable-testing --filter PassengerRouteSaveReportTests`。存檔在私庫：
