**這一批做了什麼**（派工說太大就分 PR，先做玩法最多的一兩種）：

1. **公園**（`PlacedBuildingKind.park`，24 m、1 層、用途 `park`）：
   - 不住人也沒有工作（容量 0），不收租。
   - 中心算進地價的「附近有公園」（決策 91 的 P：中心 400 m 內的格加 600 c/m²），和城市自己的公園格一樣（`landValueParks()`）。所以周圍玩家建物的租金與賣價、收購城市建物的價錢、城市長大時選的用途，都照既有的地價規則跟著變；沒有另外的新係數。
   - 造價照所有自有建物的規則：576 m² × 每 m² 造價＋占地 × 地價，每天付維護與地價稅。
2. **廟**（`PlacedBuildingKind.temple`，32 m、2 層、用途 `leisure`）：
   - 子公司（決策 173），客人是香客：每座廟是一個 2★ 的「城鎮」景點（`Tourism.templeStars` = 200），用景點既有的人數規則（星等、星期、季節、天氣、颱風）算當天的香客。800 m 內有幾座玩家的廟，就平分幾份（`templeSights()` 的 `sharing`）。
   - 香客照觀光的規則搭玩家的車到廟旁的車站（`touristFlows` 把廟當景點），半夜算到的人數存在建物上（`PlacedBuilding.visitors`）。前一天的客人就是這個數；其他日子是預計的人數。蓋好或賣掉一座廟，當下就重算乘客計畫（`PassengerPlanCache.temples`），和讀檔後的遊戲走得一樣（`testATempleBuiltOrSoldMidDayRunsAsIfLoaded`；第一版沒有，`NewGameSavePropertyTests` 抓到存檔後走得不一樣）。
   - 每位香客留下 $30（`SubsidiaryRules.templeSpend` = 3,000 分：香油錢、光明燈、香與廟口小吃），香火、燈與祭典花掉其中 40%（`templeVariableCostPercent`），另付子公司共用的人事費（造價的萬分之 4 一天）。
   - 廟的景點 ID 是建物 ID 的負數，所以永遠不會存進 `tourism.attractions`，也不算一日券的景點、不能開紀念品店。飯店的星等與客人仍只看真正的景點。
   - 沒有觀光（`tourism == nil`：示範地圖、劇本、關閉觀光的世界）時，廟沒有香客，只有支出。新遊戲預設有觀光（決策 174）。
3. **外觀**（`PlacedBuilding.look`，`PlacedBuildingKind.looks`）：
   - 只決定畫成什麼樣子，不影響規則。公園三種：社區花園、兒童遊戲場、池畔涼亭；廟兩種：廟埕、大廟。其他種類一種。

   - 存檔：`"look"` 不是 0 才寫，`"visitors"` 只有廟、不是 0 才寫。舊存檔沒有這兩個鍵，讀成第一種外觀、0 位香客。
   - `PlayerCommand.Edit.placeBuilding` 多一個選填的 `look`，第一種外觀時不寫，舊的編輯紀錄照樣讀。
4. **畫面**：
   - 建造選單（`ControlPanel`）多兩張卡（`BuildingPark`、`BuildingTemple`）。有外觀的種類多一排分段選擇器（`building.look`），並用一句話說明這種建物帶來什麼（`building.effect`）。`GameSession.buildingLook` 每一種各記自己的。
   - 2D 地圖圖示 `MapGlyphPark`（兩棵樹）、`MapGlyphTemple`（兩層翹脊屋頂）。照 art-style 畫，看過 16 pt、模糊、灰階。

**還沒解決**：400 m 內多長，但全圖第 200 天反而少 1.1%／0.9%。一個車站的成長在分到格子時已經不會少（下面的 P2），所以少的地方在別處，還沒查到；猜是車站之間怎麼分城市的成長（`LandDemand.shares`，照空間分）或收購拆掉的 72 人之後的連鎖，沒有驗證。交給接手的 session 查（`docs/HANDOFF.md` §7.2）。

**獨立審查（遊戲規劃 session_0138XhXTjToUd3fpKV7kebeH，#1232 head 281ac10）之後改的**：

- P1 蓋了馬上賣會賺錢：賣價的地價含有這棟自己帶來的加成（學校 +900、醫院 +500、公園 +600），而不住人的建物照帳面價全額退建物，所以同一分鐘蓋了又賣，學校每次賺 $18,547、醫院 $4,352、公園（main 上已有）$2,995。改成：不住人的建物（公園、廟、學校、醫院、夜市）賣地時，用沒有它自己時的地價（`saleQuote(of:)`，`BuildingSale.swift`）。回歸測試 `testBuildingAndSellingAtOnceNeverPays`：每一種內陸的建物同一分鐘蓋了又賣都不賺。
- P2 學校旁的格子住滿時，車站反而長得少（滿的格子分到更大一份，那份丟掉）：西邊滿 400 人、東邊 100 人、長 290 人，沒蓋 558、蓋學校 534、蓋醫院 541。改成兩步（`homeGrowth`，`LandDemand.swift`；`grow` 與 `growSteered` 都用）：
  1. 只有還有空間的格子才乘學校、醫院的倍數（`civicGrowthWeights`），三者都是 558（`testAFullHomeNearASchoolTakesNoLargerShare`）。
  2. 加權後一格分到的超過「它的空間」與「沒加權時它本來分到的」兩者較大的，超過的部分再照沒加權的比例分給還有空間的格子，一輪一輪分到分完或沒有格子有空間為止（每一輪不是分完，就是至少再滿一格，所以最多格數那麼多輪）。西邊 380、東邊 100、長 290：三者都是 400／160（`testWhatAHomeNearASchoolCannotTakeGoesElsewhere`）。
  - 總數：分出去的加起來等於要長的人數，除非所有有空間的格子都滿了；每一格最後長得進去的，加起來不少於沒蓋時（`testASchoolOrAHospitalNeverLosesGrowth`：西邊 20 到 400 每 20 一檔、長 1／7／50／290／700 人，學校與醫院都不少於沒蓋，同一輸入兩次結果一樣）。
  - 決定性：只用陣列順序與整數；分配是最大餘數法（`GameWorld.apportion`），餘數一樣時照格子的順序，沒有用到集合的走訪順序。
  - 沒有學校也沒有醫院時：`civicGrowthWeights` 回傳原來的權重，`homeGrowth` 直接走原來的 `apportion`，所以沒蓋的世界、golden 與重播不動（GoldenScenarioTests 24、ReplayFixtureTests、SavedGameTests 在本機都過）。
  - 溢位：權重是「格子居民 × 車站權重 × (10+9+5)」，居民一格最多 `Land.maximumPerCell` = 100,000，車站權重最多 3，所以一個權重不到 10⁷；`apportion` 算 `total × w / sum`，`total` 是一天一站長的人數（幾百到幾千），乘起來遠小於 Int64 的 9.2×10¹⁸。
  - 在 origin/main 上：這幾個測試用到 main 沒有的 `.school`／`.hospital`，在 main 上編不過；改動前（head 281ac10）`testAFullHomeNearASchoolTakesNoLargerShare` 紅（534／541）、`testBuildingAndSellingAtOnceNeverPays` 紅（公園、學校、醫院賺），本機驗過。

**五方**：

- 玩家：學校與醫院「附近長得快、地價變高」，夜市「帶人搭車來、賺攤位錢」，一句話就懂，和公園、廟的用處不重複。
