**為什麼**：決策 418 只記主執行緒卡住約 250 ms 以上；50–250 ms 的停頓、GPU、幀的分布、記憶體與發燙都沒有記，決策 328 的 2D 讀數與 3D 除錯數字列只在螢幕上、只有平均，看不出偶爾一次的停頓（規格 §2）。玩家說卡，卡在 2D 還是 3D、CPU 還是 GPU、哪個情境，都不知道。

**做了什麼（V1，這一張 PR）**：

- **量**（App，`RailwayGameApp/App/FrameTimeRecorder.swift`，只交樣本）：
  - 3D：每一格 drawable 的 `addPresentedHandler` 回報的 `presentedTime`（系統說這格真正上螢幕的時間）之間的間隔；`presentedTime` 為 0 的是沒上螢幕的格，另外計數，不算進間隔。每格的 CPU ms（不含等 drawable，和除錯數字列同一個量法）、GPU ms（`gpuEndTime − gpuStartTime`）、三角形、draw call、看得到的場景塊（`Map3DMetalView.swift` 的 `draw` 裡加幾行）。
  - 2D：一個 `CADisplayLink` 的 `timestamp` 之間的間隔，**一律叫「2D 節拍」**：它量到主執行緒有沒有準時醒來準備下一格，量不到之後 SwiftUI 與 Core Animation 的提交、系統合成到上螢幕那段，報告裡寫明「不是上螢幕的時間」。只在 2D 地圖在畫面上、3D 沒蓋住它時跑（`MapView` 的 `onAppear`／`onDisappear`，`Map3DPreviewScreen` 的 `onAppear`／`onDisappear` 各加一行）。
  - 2D 停頓的各部分：決策 328 的 `FrameCostMeter` 多一個 `keepsFrameParts`，2D 節拍跑的時候打開（讀數面板沒開也一樣），每格把主執行緒上各部分的 ms 加進一個固定大小的陣列，下一格歸零。只有出現比這段裡之前都長的停頓時，才取出最長的 3 部分與「其他」（沒有任何部分計時的那段，和讀數的「其他」同算法）。
  - 每秒一次：情境（2D／3D／跟車、倍速、車站數、線數、決策 417 的畫質與那一格）、記憶體（`task_info` 的 `phys_footprint`、`os_proc_available_memory`）、發燙（`ProcessInfo.thermalState`）；收到記憶體警告就計一次。
- **統計**（GamePresentation，`FrameTimeRecord.swift`，Linux 測 `FrameTimeRecordTests`）：
  - 一段（`FrameTimeSegment`）＝一個畫面、一個倍速：畫面或倍速一變、App 離開前景、或滿 300 秒就結束一段、開下一段；車站數、線數、畫質取最新的。少於 10 個間隔的段不留。
  - 分布用固定的計數格（`FrameTimeDistribution`）：100 ms 以下每 0.1 ms 一格、2 秒以下每 1 ms 一格、更長的放一格並記最長值；每格只加一，不配置記憶體。中位數、p95、p99 用 nearest rank（至少該比例的樣本不比它長的最小值），精度就是格寬。
  - 停頓：50 ≤ 間隔 < 100、100 ≤ 間隔 < 250、間隔 ≥ 250 ms 三段，**250 ms 以上是嚴重停頓**（和決策 418 的門檻對得上）；剛好 50、100、250 ms 算進較長的那段。**最長停頓**記長度、在這段的第幾秒、這段的情境，2D 另記上面的各部分 ms。
  - 時間差先四捨五入到微秒再比，免得浮點相加把剛好 50 ms 算成 49.999…。
  - 記憶體記高點與「最少剩」，MB；發燙記第一個狀態與每次變化（最多 6 個）。
- **存**（`FrameTimeLog`）：`Application Support/Diagnostics/frame-times.json`，和決策 418 的檔放一起；最多 24 段、64 KB，超過丟最舊的。只在一段結束時寫（在自己的佇列上，原子寫入），不每格寫檔。不進存檔、不上傳、不加第三方服務。
- **送**（`SettingsView.swift` 的 `ProblemReportRows`）：「回報問題」的訊息在決策 418 那段之後多一段「這台裝置最近的畫面節奏」：正在跑的那段（還沒存檔的，先列）與最新的幾段共 6 段，每段四到五行；更早的只寫還有幾段、共幾次嚴重停頓、最長多久。底下的說明加半句「並附上最近地圖畫面是否順暢」。

- 3D 的 p95 在 60 Hz 時該在 20 ms 內、30 Hz（省電）時 40 ms 內（規格 §5 判讀）；CPU 或 GPU 的 p95 接近間隔的 p95，就是那一邊在拖。
- 「沒上螢幕」多，是 GPU 來不及或系統丟格。
- 2D 的最長停頓後面的部分是決策 328 讀數的名字；「其他」大，多半是 SwiftUI 的版面與 Core Animation 提交（讀數面板開著時會多一個「畫面更新」）。
- 溫度出現偏高、過熱，或記憶體警告，那一段的數字不拿來比較。

**沒選的**：
- 每格的原始時間全存下來再算：一分鐘 3,600 筆，存檔與記憶體都大；固定計數格的精度（100 ms 以下 0.1 ms）已夠分辨 60／120 Hz。
- 2D 也想量「上螢幕」：SwiftUI 沒有 drawable 可掛 presented handler；要量就得把 2D 改成 Metal 或 `CAMetalLayer`，那是改架構，作者說不改。
- 只在設定裡開了才記：玩家卡的時候不會先想到去開；量測夠便宜，就一直記。
- 用 MetricKit 的 `MXAnimationMetric`（scroll hitch）：只量捲動，每天交一次，沒有情境。
