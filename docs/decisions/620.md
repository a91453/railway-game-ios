## 為什麼

規劃量到的牆鐘：#1924（完整 tier）的 PR run 33 分，每晚的完整 `ci.yml` 32 分（11-04 18 分、11-05 21 分），上一輪 CIOPT 記的是 27 分。

- **不是排隊**：這幾個 run 裡，每個 job 等 runner 最多 7 s。
- **變慢的只有 `rest` 這一片**：測試秒數 470 s（11-04）→ 707 → 982 → 1,268 s（11-06 夜間，run 42303936063），job 跑了 22.6 分，上限 30 分。13 個 campaign 片都在 3–7 分。
- 多出來的時間，一半以上是 11-06 新加的 `KaohsiungLightRailDayTests`：一個類別 428 s。它跑高雄環狀輕軌兩天：交通管制開著時，簡單、擬實各約 200 s；交通管制關掉只要 23 s。其餘是 `rest` 本來就在長：沒有被 campaign 點名的新類別都落進 `rest`（`Map3DSceneRebuildTests` 84 s、`SingleTrackLengthTests` 59 s，`TaoyuanAirportLineTests` 從 45 s 變 105 s 等）。
- GamePresentation 的 PR tier 裡，`KaohsiungLightRailDayTests` 沒有權重（算 1），和別的重類別分到同一份：#1925 的 selected-3 跑了 956 s，其他份 270–550 s。

## 決定

1. **GameCore：交通計畫的每段路只找一次路徑，找過的存進 memo**（`ScheduledTraffic.swift`，`trafficPoints(of:cycle:paths:)`）。
   - 用 gdb 對跑著的測試取樣 42 次，有 28 次在 `trafficPlan`，其中 17 次在 `trafficPoints`；這 17 次一半在第 256 行的 `plannedPath`，一半在第 257 行。
   - 第 257 行為了算「是不是線的指定路徑」（`matched`），用同樣的參數把 `preferredPath` 又找了一次。
   - 兩次都沒有用世界已經留著的 `PathMemo`（`DirectionMemo.paths`）。
   - 改成：`preferredPath` 只找一次；沒有指定路徑時用 `path(from:toStation:length:memo:)`；`matched` 看指定路徑找不找得到。
   - 兩個路徑函式都只讀路網（`PathMemo` 的說明），和原本逐位元相同。memo 就是 `advance` 與問答本來在用的那一份，`RouteMemo` 照決策 138 續（TRAFFIC-READ，#1924）的規則借出、收回；這裡沒有另外再存一份。
   - 本機（4 核，Swift 6.4.0，同一台機器、同一個指令）：`KaohsiungLightRailDayTests` **364 → 255 s**。簡單 148.9 → 97.6 s，擬實 173.9 → 116.5 s，交通管制關掉 29.4 → 28.6 s。兩天的結果每一項都一樣：290 班 0 班沒發、擬實 168 趟 5 趟誤點、3,744 km、空車 40 km、最多誤點 5 分。
   - 玩家也受益：遊戲迴圈每一步的交通計畫就是這段（3D 跟車、高倍速的大路網）。
2. **`rest` 分成 `rest-1`、`rest-2` 兩片**（`swift-shards.sh`）：`rest` 的類別照 `CLASS_WEIGHTS` 從重到輕，每個放進目前最輕的那一片，和 `selected_part` 分 GamePresentation 那幾份的做法一樣（抽成共用的 `deal_part`）。
   - `run rest` 照舊跑整個 `rest`，本機用。
   - `head-full-run` 認 `rest-1`，也認舊 run 的 `rest`。
   - 完整 tier 從 18 個 job 變 19 個。
   - 用 11-06 兩個完整 run 的逐類別秒數模擬（`KaohsiungLightRailDayTests` 照本機比例算成 300 s）：兩片 548／467 s、555／467 s，原本一片 1,015–1,022 s。
3. **權重**：`rest` 裡 2 s 以上、沒有權重或權重比實測低的類別，取上面五個完整 run 與 #1924 那個 PR run 裡最慢的一次（決策 563 的做法；這次只補、只往上調，沒有往下調）。`KaohsiungLightRailDayTests` 照改後的比例取 300。

沒有跳過任何測試、沒有放寬斷言，每晚的完整 run 跑的測試和原本一樣：`check_partition` 與每片的覆蓋檢查照舊證明每個測試只跑一次；自我測試加了 `rest` 兩片正好分完 `rest` 的檢查。

## 五面向

- 玩家：環狀線與大路網開著交通管制時，遊戲迴圈每一步少約三成的計畫時間，3D 跟車與高倍速比較順。畫面不變，結果不變。
- 鐵道迷：無（行車結果逐位元相同）。
- 開發：
  - 完整 tier 估從約 32 分降到約 20–21 分：build 約 9 分，最慢的片約 11 分。
  - GamePresentation 的 PR tier 不會再把環狀線和別的重類別放進同一份。
  - `rest` 離 30 分的上限有一半的餘裕。
  - 代價是完整 tier 多一個 job（帳號 40 個裡用 19 個）。
- 美術：無。
- 音樂：無。

## 不選的

- **把 `KaohsiungLightRailDayTests` 列進某個 campaign 片**：照決策 563，GamePresentation 的類別一旦被 `classes_of` 點名，改它的 GamePresentation PR 就會照「一個 campaign 加上 GamePresentation」跑完整 tier。它 11-06 一天就被改了 4 次。而且這只解這一個類別，`rest` 下次還會再長。
- **把簡單、擬實拆成兩個類別**：CPU 時間一樣，只是能分到兩片。`rest` 分片以後，這樣做省不到東西。
- **環狀線的交通計畫改成跨週期共用點列**：`TrafficParts.points` 照 run（車次、週期、時刻表）存。真實時刻表的每一班是不同的時刻表，要改的是快取的鍵，風險比這次大。等下一輪取樣，看剩下的熱點再說（見「下一步」）。
