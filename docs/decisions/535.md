## 設計：環線班次

#### 1. 資料：`LineRun` 多一個 `way`

- `LineRun.way: RingDirection?`。不是環線的線一律是 `nil`，和現在完全一樣。
- 環線的班次一定要有 `way`，不是環線的一定不能有。
- **車站順序**：從 `from` 出發，照 `way` 每次加一或減一，數到最後再從頭接（取 n 的餘數，n 是站數），共走 `times.count - 1` 段，最後停在 `to`。
  - 段數是 `((to - from) × 方向) mod n`；算出來是 0 時當成 n，也就是**繞一整圈，`from == to`**。高雄輕軌 154/168 班是這種：籬仔內出發，再回到籬仔內。
  - 一班最多繞一圈（n 段），真實資料沒有超過一圈的。
- **檢查**（`isValid(stopCount:ring:)`）：
  - 環線：`times.count == 段數 + 1`，而且 2 ≤ `times.count` ≤ n + 1。
  - 不是環線：照現在的規則，`from != to`。
  - 其他檢查（時間不倒退、星期幾）不變。
- `canHave(_:)` 拿掉 `!isRing`。環線本來就不准第一站等於最後一站、也不准有服務模式；`Set(stops).count == stops.count` 照舊要求。
- 換方向的算法：`isOutbound` 在環線上改成 `way == .inner`。`runsServe` 和 `runStretches` 在環線上改用環上的弧，見下面第 5 點。
- 為什麼不另開一個「環線班次」的型別：派車、機廠（決策 221）、時刻表、存檔都直接沿用 `LineRun`，多一個欄位改動最小。這也和參考庫的做法一樣：`close_metro_loops.mjs` 只在原本的站序後面接回第一站，並標上 `loop: true`。

#### 2. 時刻表與派車

- **派車沿用決策 133**：`dueRuns`、`readyRunTrain`、`dispatchRuns` 都不用改。班次的第一站有一列沒有任務的車，就派它出去。
- **`runTrip` 在環線上不先掉頭**：只有照列車現在面對的方向開不過去時，才掉頭再開（`turnsFirst`）。
  - 現在的規則是「掉頭比較近就掉頭」，在環線上可能讓車逆著它那個方向的軌道開。複線環線靠左行駛（決策 202），一個方向一條軌道，逆著開就會在單線上和對向車卡死。
- **第一站停多久**：沒有掉頭時照 `ServiceDwell.minimum`（36 秒，和決策 49 一樣），掉頭時照 `terminalMinimum`。
  - 現在 `RunTrip.timetable` 一律用 `terminalMinimum`。真實的籬仔內接下一圈只有 25 秒以上，用 36 秒最接近。
- **一圈接下一圈**：列車跑完一圈停在籬仔內，面向它繞過來的方向，等下一班從籬仔內同方向出發的班次。所以每列車一直留在同一個方向，不用掉頭。
  - 「列車連續繞圈」是決策 49 留下來沒做的（參考的時間相位）。有班次以後由時刻表自然做到，不用另外寫。
- **班距**：`runHeadway` 在環線上照兩個方向中班次比較多的那個方向算，和現在的算法一樣。高雄輕軌平日每個方向 84 班，算出來約 13 分，真實是尖峰 10 分、離峰 15 分。
- **照班距跑的環線完全不變**：`isDispatchDue` 本來就排除有班次的線（`!line.hasRuns`）。

#### 3. 進出機廠

- 沿用決策 221，`RunDepot.swift` 不用改規則：
  - 車在某一站等，接下來兩小時（`runDepotLookahead`）沒有班次從那站出發，就空車回機廠。
  - 有班次要從某站出發、那站卻沒有車時，從最近的機廠空車開過去。
- **高雄輕軌早上的頭班車不是都從籬仔內出發**：平日有 7 組、假日有 5 組從環線中間的站出發（例如軟體園區、哈瑪星、鼓山）。這幾班照決策 221 從機廠空車開過去。
- **要守住的一點：出庫的空車要停在班次方向那一側的月台**（`emptyRun` 的目的地加上方向）。不然它停進對向的月台，`runTrip` 就只能掉頭開。PR 1 寫一個測試守住這一點。
- **收車**：每班都在籬仔內結束。最後一班之後，列車照決策 221 回機廠。輕軌機廠就在籬仔內和輕軌機廠站（C37）之間。

#### 4. 閉塞與號誌

- 複線環線，一個方向一條軌道（決策 49 的示範地圖就是內外兩圈），靠左行駛讓兩個方向不會擠進同一條軌道。所以**不會有對撞的死結**。
- 單方向的環線，只有在**每一個閉塞區間都有車**時才會互相等到卡死。所以規則是：一個方向同時在線上的車，要比那個方向的閉塞區間少。
  - 照班距跑的環線，`LineCapacity` 的環線分支已經這樣限制。
  - 有班次的線，車數由時刻表決定。高雄輕軌每個方向最多 10 組，22 km、38 站，閉塞區間遠多於 10。
  - 收購工具要多一項檢查：照鋪法的閉塞區間數算，每個方向的組數超過時不賣。
- 進路預約、接近鎖閉（`RouteReservation`、`ApproachLocking`）是以軌道上的路為單位，不是以線為單位，所以接縫那一段不用特別處理。
- 待避（決策 526）：環線上的站照一般的站處理。高雄輕軌沒有越行，所以用不到。

#### 5. 乘客路線搜尋（環線上兩個方向的最短路）

- 現在照班距跑的環線，每個方向一條 `ServicePath`，`isRing` 是 `true`；路線搜尋（`PassengerRoutes.search`）會自己比較兩個方向，挑比較快的。**這一點有班次的環線直接沿用。**
- 有班次的環線怎麼建路線（`PassengerRouteGraph.init`）：
  - 每個方向，把該方向所有班次走過的弧合起來。
  - 合起來**整圈都有車**，就建一條 `isRing: true` 的路線，從**最多班次出發的那一站**開始繞一圈。高雄輕軌是籬仔內，兩個方向都是。
  - **沒有整圈都有車**，就把合起來的弧拆成幾段，每段一條 `isRing: false` 的路線。這和現在一般線的 `runStretches` 一樣，只是弧可以跨過接縫。
- **接縫**照決策 49：一圈在籬仔內結束，要繼續坐就得在籬仔內重新等車。真實也是這樣：每班都開到籬仔內為止，月台看板寫「往籬仔內」（參考庫 `docs/klrt-board-directions-20260928.md`）。
- 每段的秒數：沿用 `lineJourney` 一圈的各段秒數。外環用 `journey(of:service:direction: .outer)`，和照班距跑的環線一樣。
- **上車**（`Boarding.boardingPlan`）：有班次的環線，方向照班次的 `way` 判斷，不再照 `here < next`；判斷環線方向的那段程式要排在「有班次」那段前面。
- 乘客計畫的快取（決策 470，PLANDAY-2 正在改 `PassengerRoutes.swift`）：只是多建幾條路線，不改搜尋本身。**PR 1 要等 PLANDAY-2 合併後再開工**，免得衝突。

#### 6. 存檔、golden、replay

- **存檔：要升一版。**
  - 環線班次多存一個 `"way": "inner"|"outer"` 鍵；`nil` 不寫，所以舊存檔不用轉換就能讀。
  - 但舊版的 build 會把有 `way` 的班次當成直線的班次讀，`canHave` 再整條拒絕，只會說存檔壞了。照決策 49 的先例升一版，讓舊版的 build 說「這是較新版本的存檔」。
  - 用哪一版：PR 1 開工時取 main 和 #1579 裡還沒釋出的登記中最大的加一。今天 main 是 79，80 已經被 STATIONEXP-2 釋出，所以那時多半是 80。
  - 加一個 `SaveFixtures/v<N>-ring-runs.json`：一條有兩個方向班次的小環線，加一座機廠。
  - 讀檔要拒絕的情形：環線的班次沒有 `way`、不是環線的班次有 `way`、`times` 的數量和段數對不上、一班超過一圈。
- **golden：現有的值不動，加一個新的 fixture。**

## 五方

- **玩家**：高雄開局終於有一條買得起的線，38 站繞市區一圈，和自己的線接轉乘；兩個方向都有車，乘客自己挑近的那個方向，和真的搭輕軌一樣。
- **鐵道迷**：照 TDX 的真實時刻表，兩個方向各約 84 班，每班從籬仔內繞一圈回籬仔內，清晨有幾班從中間站出發，晚上回輕軌機廠，都和真實一樣；派工單原本的「單向繞」是錯的，這裡改正。出處：TDX（政府資料開放授權條款第 1 版）；OSM（ODbL）。
- **開發**：只在 `LineRun` 加一個欄位，派車、機廠、存檔都沿用；GameCore 只有一個 PR，現有的 golden 和 replay 不動；收購的工具、鋪法放在 GamePresentation 和 `tools/`，不佔 GameCore 名額。
- **美術**：`kaohsiungLightRail` 的 CAF／Citadis 3D 模型已經有了，只要讓收購來的車也用它；接縫那一段要連續，車身不能跳。
- **音樂**：無。
