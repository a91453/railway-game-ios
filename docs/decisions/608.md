### 608. 模型包的頂點只放 GPU：背景上傳一次、App 期間共用，CPU 不再留一份

2026-11-05，實作 session MAP3D-MEM-1（`session_01YGNNupPFCZfR6rbV8asP6U`，遊戲規劃第 50 任派），分支 `claude/map3d-mem-1`。研究 `docs/research/MAP3D_STATE_CHECK_2026-11-05.md` §12 的候選 A、`docs/research/NEXT_PRIORITIES_2026-10-12.md` §24.6 的 6a，接決策 546「下一步」的第二、三條。號碼依 #1579 的登記：決策 608；存檔版本、golden schema、GoldenScenarios、SaveFixtures、ReplayFixtures、GameCore 都不動；模型的頂點與 `tools/train-models/hashes.lock.json` 不動。

## 問題

3D 地圖的模型包（列車、公車、垃圾車、街道設施、樹；main `99b9e44` 量到 846 個模型、6,330,858 個頂點、40 B 一個，約 253 MB）：

1. **CPU 一直留一份**：`Map3DModelPack.standard` 與 `Map3DView.models` 是 `static let`，做好就留到 App 結束；GPU 緩衝又是一份。
2. **上傳在主執行緒**：`Map3DMetalView.useModels` 在 `updateUIView` 裡對每個模型 `makeBuffer`，把約 253 MB 複製進 GPU 緩衝，換上模型的那一幀會停住。
3. **列車展示是第二份**：`TrainShowcaseScreen` 自己 `useModels(Map3DModelPack.standard)`，3D 地圖開過再開展示（或反過來），GPU 上就是兩份。

## 做了什麼

1. **背景上傳一次**（`Map3DUploadedModels`，`RailwayGameApp/Views/Map3D/Map3DPreviewScreen.swift`）：模型包照決策 546 預先做好，用背景工作 `Map3DTrainModels`，`.utility`，不提高優先度。CPU 那份留到第一次有人要用：3D 地圖或列車展示第一次打開（`Map3DTrainModels.make()`）時，才另開一個同樣是 `.utility` 的背景工作。這個工作：
   - 在系統的 Metal 裝置（`MTLCreateSystemDefaultDevice()`，iOS 上每個 3D 畫面用的就是這一個）為每個模型建一個 `storageModeShared` 緩衝；
   - 用完整的頂點做好透明玻璃的快取（`Map3DTransparentGlass.Cache`，它要的是玻璃三角形本身，留下）；
   - 留下不含頂點的模型包（`Map3DModelPack.withoutVertices()`）；
   - 叫 `Map3DModelPack.letGoOfStandardVertices()`，`standard` 從此也不含頂點。完整的那份最後一個參考在這個工作裡，所以也在背景放掉，不在主執行緒。
   緩衝做好就不再改，任何執行緒都可以讀（`@unchecked Sendable` 的 `final class`，全是 `let`）。
   - **為什麼不在預先做模型包時就上傳**：第一版就是這樣做，`MapInteractionTests/testPinchingCloseOpensTheThreeDMapAndPinchingOutComesBack` 在六支 3D 測試的組合裡紅了三次（run 42125321805 兩次、42140345310 一次），同樣的六支在 main（run 42140330949）是綠的。探針看到：上傳完成後約 2 秒的第一次捏合，模擬的手指一直沒有移動，2 秒後被取消；主執行緒照常在畫（longest gap 294 ms）。這支測試一定要兩次捏合才會交給 3D，所以少一次就紅。改成上傳延到 3D 打開時，2D 地圖上的狀態就和決策 608 之前一樣：只有 CPU 那份，沒有 GPU 緩衝，也沒有在放記憶體。
2. **主執行緒只接結果**：`Map3DMetalView.useModels(_:)` 只拿共用的緩衝、模型包與玻璃快取，檢查緩衝與畫面是同一個 Metal 裝置；不再複製頂點。
3. **App 期間共用**：`Map3DTrainModels.shared.uploaded` 留到 App 結束；3D 地圖與列車展示都用它，GPU 上只有一份。列車展示原本用 `.userInitiated` 自己做一份，現在等同一個工作（`.utility`，決策 546：做模型包時提高優先度曾讓 Simulator 的主執行緒停 61 秒）。UI 測試的暖機（`-ui-test-3d-models-first`）只做模型包（`makePack`），和玩家一樣，上傳留給打開的 3D 地圖。
4. **CPU 留下什麼**（`Map3DModelPack.Model.withoutVertices`）：每個模型的名字、頂點數（新的 `vertexCount`，`triangleCount` 改由它算）、外框（`minimum`、`maximum`，長度由它算），模型的順序不變（渲染器用索引找模型）；模型包的車燈（`lights`：每輛車頭尾燈的三角形與窗戶模型的編號，`Map3DTrainLights.add` 每幀讀）、目的地牌（`headSigns`）、鎖住的編組（`locked`）。
   - 先查過每個在執行期讀頂點的地方：`Map3DTrainLights.add` 只讀 `lights`；`Map3DTransparentGlass.Cache` 在做的時候讀，之後只用自己的三角形；`Map3DMotionBudget` 的 `triangles(in:)`、渲染器的 `drawPrimitives` 只要頂點數；`Map3DSignalTiming.Models`、`Map3DPedestrianSignal.Models`、`Map3DProp.modelsLeftOut`、各處的 `index(of:)` 與 `layout` 只要名字與外框。其他讀頂點的（配方、烘影、各 kit、`Map3DSimplifiedCache`、輸出工具）都在做模型包的時候或只在測試與工具裡。
5. **`standard` 改成可以放掉頂點**：`static let` 放不掉，所以改成第一次用時做一次、加鎖保存（和 `static let` 一樣只做一次；同時要的人等它做完），App 上傳完叫 `letGoOfStandardVertices()` 換成不含頂點的那份。測試與工具從不叫它，拿到的永遠是完整的模型包（`Map3DModelPackLockTests` 不變）。叫之前拿到的複本照樣有頂點（值語意），用完就放掉。`Map3DView.models`（`static let`）改成 `makeModels()`，只由上傳的工作叫一次。

## 證明

- `Map3DModelPackLockTests`（Linux）不變：每個模型的頂點雜湊、順序、車燈與目的地牌都和以前一樣。
- 新增 `Map3DModelPackSlimTests`（Linux）：`standard` 與 `studies` 的每個模型，不含頂點的那份名字、頂點數、三角形數、外框、長度都和原模型包相同，頂點是空的；車燈、目的地牌、鎖住的編組相同；每個車種與編組的 `models(forType:)`、`layout`、省電時拿掉的模型相同。
- `ui-test` trace（Debug、`-ui-testing`）印出每次捏合的開始與結束、放手時交接的四個條件，以及 `map3D.models uploaded`，下次紅可以直接看是哪一個條件。
- 畫面：列車、燈、玻璃用的是同一批頂點（同樣的緩衝內容、同樣的頂點數），畫面應該完全一樣；iOS 的 3D UI 測試照跑（CI）。
- 實機（UNVERIFIED，等作者用 TestFlight 量）：第一次打開 3D 之後，常駐記憶體應少一份模型包（main `99b9e44` 約 253 MB）；在那之前和以前一樣。換上模型那一幀不再停住；只開過列車展示的、兩個都開過的各量一次。

## 沒做的與為什麼

| 選項 | 為什麼沒做 |
| --- | --- |
| 把模型包改成 `MTLHeap` 或一個大緩衝 | 少的是緩衝的個數，不是記憶體；渲染器各處用「一個模型一個緩衝」，要改的地方多。等 B 改頂點格式時一起看。 |
| 記憶體警告時放掉 GPU 那份 | 放掉後要整包重做（決策 546 量到 4 核 0.72 s、Simulator 更久），玩家正開著 3D 時列車會變回方塊；以前的 `static let` 也從不放掉，這次不改行為。 |
| B：窄頂點（24 B）、C：每幀緩衝輪替 | 研究 §12 排在這個之後，各一個 PR，等這個合了、有作者的實機數字再派（`docs/HANDOFF.md`）。 |
