### 420. 網格自動簡化：先量，再決定；太魯閣與 EMU800 的程式版遠景車

2026-10-26，遊戲規劃 session_01TS89hbaHPJiFJycqrKiK5z 派工，實作 session_014ZfTTK2BTKfrpKBYMPKmpP（`claude/mesh-lod-qem`）。號碼依 #1041：決策 420；存檔版本、golden schema 不動。GameCore 不動，只動 GamePresentation、測試、`tools/mesh-lod-420/` 與文件。

作者 2026-10-26 問：低畫質時列車用三角形簡化版、高階機型完整直出？還是把簡化工具搬進遊戲、跟著畫質調，保證一個模型有多個等級？遊戲規劃五方評分後（全做成系統 2.60、只量 3.48、量＋程式版遠景車 3.58）定的範圍是：**先量**，自動簡化器只留在比較與測試；再把兩款沒有遠景模型的車，用它們自己的建模程式做遠景版，照決策 408 的接法接上。

**做了什麼**：

1. **簡化器**（`Map3DMeshSimplifier`，GamePresentation，沒有接進畫面）：Garland–Heckbert 1997 的二次誤差邊收縮，照決策 408 的 `tools/hsr-trains-408/decimate.py` 搬成 Swift，數字都沿用：
   - 角落相距 0.1 mm 內的焊成一點；只做「一個點收到鄰點上」（half-edge），不生出新的點，模型的包圍盒不變（車長照舊排車）。
   - 顏色以三角形為單位（模型本來就這樣上色）：兩色交界的邊、只有一個三角形的邊（開放的邊、零件輪廓）是縫，縫上立一個垂直的平面拉住，權重是表面的 50 倍。縫上的點只能沿著縫滑到同一條縫的鄰點；幾條縫相交的點（窗角）不動。
   - 會翻面、轉超過 60°、變成細針（面積比最長邊平方小於 0.02），或讓兩個面黏在一起（link condition）的收縮不做。
   - 每個三角形保留原本每個角的顏色，法線照新的三角形重算（平塗），方向跟原本的一樣。
   - 決定性：照代價、再照點的編號排，同樣的模型每次、每台裝置都得到一樣的結果。
   - 有 `Map3DModelPack.Model.simplified(to:)` 與 `Map3DMesh.simplified(to:)`。
2. **程式版遠景車**（照 `Map3DE500.model(far:)` 的做法）：
   - 太魯閣：`Map3DTEMU1000.model(_:far:)` 從原本的建模程式產生，車頭十圈留六圈（車頭斜度、肩線與鼻尖的鼓起）、鼻蓋七列減成三列、腰帶分段減少、車輪 8 邊、每側一片長玻璃（門蓋在上面）、拿掉輪轂、轉向架側樑、冷氣頂蓋與門上的小窗與細線。新的 train set `tarokoFar`，`taroko` 的 `far` 指向它。近景的四種車廂逐位元和 main 一樣（`Map3DFarSets420Tests.testTheNearTarokoIsUnchanged` 釘了 main 的三角形數與雜湊）。
   - EMU800：決策 410 已經有的 `Map3DTrainShell` 遠景細節（`detail: .far`，決策 408 的高鐵遠景用的同一套），新的 set `emu800Far`。
   - 兩款都加進 `Map3DTrainSet.nearOnly`：500 m 內完整，500–900 m 遠景車，900 m 外盒子，和 700T、N700S-G、EMU3000、E500 一樣。選用的程式（`Map3DModelPack.model(_:forType:count:at:)`、`Map3DTrains.swift`）沒改。

**建議**：

- 自動簡化現在不接進畫面。理由：(1) 只有 50 % 每款都安全，25 % 以下要逐款看；(2) 程式版遠景車用 38–40 % 的三角形就比自動 50 % 好看（車輪、玻璃、腰帶都是乾淨的）；(3) 全包 4.6 s 不能在開 App 時做。
- 若之後實機的除錯數字顯示瓶頸是三角形（不是 draw call 或填色），先給其他沒有遠景的車照這次的做法做程式版遠景車；自動簡化只當沒有建模程式的模型（作者的網格、外部轉進來的）的工具，而且只用 50 %。
- 列車建模的面數上限之後若要照「最強設備近景＋簡化時間＋快取大小」定，三個數字這樣量：最強設備近景 = 實機 3D 除錯數字裡跟車時一列的三角形與幀時間；簡化時間 = `MAP3D_LOD_REPORT=1` 那個報告（release 版）的總秒數與最慢的一個；快取大小 = 同一份報告每個等級的 MB（頂點 40 bytes、三個一個三角形）。

**五方**：

- 玩家：500–900 m 的太魯閣、區間車看起來和近景同一款，畫面上的列車多了也不比之前重；不改任何操作。
- 鐵道迷：遠景車保留太魯閣的白車身、綠腰帶與車頭斜度，EMU800 的藍臉與藍帶；自動 25 % 把 EMU800 的窗收歪、10 % 把車收成碎片，所以不用。
- 開發：沒有新依賴；簡化器是決策 408 的工具搬進 Swift 的同一套規則，有 Linux 測試；遠景車用已有的 far 接法，選用的程式不改，#1271 的五個檔沒動。
- 美術：對照圖六款車都看過正側與斜前；程式版遠景車的平塗與色票和近景相同（測試釘了遠景的顏色是近景的子集）。
- 音樂：無。

**參考與前例**：參考庫 `OpenWorld/reference_snapshot/play/src/world/train-blender-visual.js` 的列車只有一個手做的遠景等級（`head-lod1`、`body-lod1`，近景的 8–22 % 三角形，`manifest.json`），手機 150 m、桌機 300 m 外換——和這裡「程式做一個遠景等級」的結論相同；`Railway/street_scene_reference_clean` 的 LOD 是換手做的模型，沒有簡化演算法。開源：meshoptimizer（MIT）的 `meshopt_simplify`（點的種類：manifold／border／seam／locked，只看想法，沒有加依賴）、three.js 的 `SimplifyModifier`（MIT，沒有顏色縫）、Blender Decimate（GPL，只看想法）。
