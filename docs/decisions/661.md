## L13-4：幀緩衝會縮

決策 608 續二的三組幀緩衝，太小就重做大的，但從來不縮。畫過一次大的幀（列車展示、玻璃多的景）之後，三組都一直佔著那麼大，記憶體警告也不放。

改法（`Sources/GamePresentation/Map3DFrameBuffers.swift`）：
- 每個緩衝記「這一輪用得夠不夠」：要的位元組換算成容量後，乘 4 仍大於現有的容量，才算夠。
- `advance()` 進到一組時，看那一組上一輪的紀錄。連續 `shrinkAfter`（120）輪不夠，就放掉。下一次要的時候照需要的大小重做。
  - 一組每三幀輪到一次，120 輪約 6 秒（60 fps）。
  - 進到這一組時，GPU 已經用完它（view 的信號量），所以這時放安全。
- `release()`：三組全放。記憶體警告時呼叫。正在畫的幀所讀的緩衝，由 command buffer 自己留著（Metal 預設的 `makeCommandBuffer()` 會保留；Vulkan 也要在 fence 前留著），所以任何時候放都安全。
- 只用平台中立的寫法：泛型的 `Buffer`，沒有 Metal 才有的功能。

**留著的**（L13-4 前半）：每幀仍會建 CPU 的陣列（`carsSorted`、`lifeSorted`、`flatMap(\.floats)`、`glassVertices`、光暈的 `trainSpots`）。有上限、量小，沒量就不改；要改的話，下一步是把它們變成 view 的成員、用 `removeAll(keepingCapacity: true)`。

## L13-6：立面的 GPU 緩衝離開近景就放

決策 610 說立面「不畫時放掉」，但區塊離開近景時只把 `frontsUp` 變 false，`facade` 的 GPU 緩衝留著，只有記憶體警告、改畫質、區塊被換掉時才放。在密集市區拖過一輪，曾經進過近景的每一塊都還佔著（每塊最多約 0.9 MB）。

改法：`frontsUp` 由 true 變 false 的那一幀放掉 `facade`。`drawsClose` 本來就有遲滯（`wasClose`），所以在邊上的區塊不會每幀放了又做。再進近景時，照決策 610 續每幀最多做 `uploadsAFrame` 塊。

**留著的**：標準以上的等級，CPU 那份（`Chunk.facadeMesh`、場景快取、`built`）照決策 610 續二常駐，因為再進近景時要立刻能上傳。低耗電模式與過熱仍會蓋立面、只放 GPU 那份，也照舊。

## L13-7：隧道口的配對和順序無關

`roadPortals` 照端點的順序貪婪配對：每個端點找第一個合格的另一個。串流與局部重蓋讀的 tile 集合和整個蓋不同，端點的順序也不同；三個以上的快速道路端點擠在一起時，兩種蓋法可能配出不同的洞口。

改法（`Sources/GamePresentation/Map3DRoadTunnels.swift`）：
- 找到的端點先照位置（x、z，再照方向）排序。
- `pairedCarriageways`：所有合格的對（兩邊都是非匝道的國道、方向差 10° 內、橫向 6–14 m、縱向 12 m 內，兩個方向都試）照距離由近到遠取，平手照索引。
- 洞口照排序後的順序輸出，一對在它排前面的那一端。

一般成對的端點，結果和以前一樣（雪山隧道頭城那兩個洞口的測試照舊過）。

新測試（`Map3DRoadTunnelTests`）：
- `testCrowdedCarriagewaysPairTheClosestWhateverTheirOrder`：三個擠在一起的端點，六種順序都配出最近的那一對。
- `testThePortalsAreTheSameWhateverTheEndsOrder`：頭城 3 km 內的真實端點，反過來、轉半圈，洞口都一樣。
- `testChunksBuiltApartStandTheWholeScenesPortals`：頭城的 6×6 區塊分四塊串流蓋，洞口的頂點（洞口頂蓋的顏色）和整個場景一樣。L13-7 說的「串流與整個蓋沒有比對」補上了。

## L13-9：step 提早結束後，真實列車的時鐘跟上

`MapView` 與 `Map3DPreviewScreen` 在 `glidesOnThroughTheStep` 為真時不更新真實列車（與公車、纜車）的時鐘，之後只在 `clock.now` 變的時候更新。step 中途 loop 停了、或來了一個指令（暫停讓 `finish` 提早 return），旗標變回 false，但 `clock.now` 沒變，於是時鐘停在 step 中間之前，到下一個 tick 才跟上。

改法：
- `GameSession.RealClockKey`：`now`（遊戲時鐘）與 `goesOn`（`glidesOnThroughTheStep`），`session.realClockKey`。
- 兩個畫面的 `onChange` 改看它，`goesOn` 時照舊不更新。旗標變回 false 時 key 會變，於是拿到當下的時鐘。

先寫會紅的測試：`CabViewStepGlideTests.testTheRealTrainsClockIsTakenWhenAStepEndsEarly`，照畫面的寫法跟 key。把 key 的相等先寫成只比時鐘（等於 main 的觸發方式）時紅：拿到 0 秒，應該 1 秒（**VERIFIED**，Linux）。改成連 `goesOn` 一起比之後綠。

3D 的高度與標籤只在 step 結束時更新（看 `glideKey`），不受影響。
