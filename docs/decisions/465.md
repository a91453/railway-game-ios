**為什麼**：玩家 3 從 80.1 起每版回報卡頓。91.1（iPhone 15 Plus）蓋車站、開路線、買列車、改時刻後卡住；92.1（iPad A16）連接轉乘站時卡住。回報的心跳在 84 站、5 線的局最高 704.9 ms／727.6 ms，幾乎都在「其他」，也就是沒有計時的工作：`.onChange`／`.task` 的動作，與沒有計時的面板的 body。

**量法**（diagnosing-bugs 第一步）：新報告測試 `EditStallReportTests`，只在要求時跑：

    EDIT_STALL_SAVE=<存檔> swift test -c release -Xswiftc -enable-testing --filter EditStallReportTests

路線面板拆開：軌道數 24–40、路線選擇 16–27、人力 15–17、班次 7–13、涵蓋 4–7，其餘不到 2。

開路線、改時段、蓋車站之後站長建議只要 0 ms，原因沒查（可能是記住的那一份還能用）。連接轉乘與改時段後，乘客路線（`passengerPlan`）重算，下一個 tick 在背景花 6 秒；主執行緒不等它，但這 6 秒裡列車不動。

**結論**：沒有單一兇手。一次編輯之後，主執行緒在同一次畫面更新裡疊了幾段沒計時的 50–90 ms：站長建議、評等、路線提示，路線面板開著時再加上它。再加上 SwiftUI 重建畫面，在 iPad (A16) 上可能到 0.5 秒左右，跟回報的「其他」吻合。

**做了什麼**：

1. **站長角落**（`StationMasterView`）：原本用 `.onChange(of: stationMasterRefreshKey)` 在主執行緒算建議與 `CompanyRank`，改成 `.task(id: stationMasterRefreshKey)` 呼叫新的 `GameSession.stationMasterLook()`（`SecretaryRoom.swift`）。
   - 它在 `Task.detached` 裡算建議（`AdviceProbe`，與迴圈同一份程式）與稱號。
   - 回到主執行緒時，`commandRevision` 沒變才記進 `hourAdvice` 與 `lineLossLeaderMemo`（決策 459 的記憶）；變了就只顯示，不記。
   - 同一小時、同一個 revision 已有 `hourAdvice` 時，不重算建議。
   - 鍵再變時 `.task` 取消舊的，結果丟掉。
2. **路線提示卡**（`ContentView` 的 RouteHintCard）：`.onChange(of: RouteHintWatch)` 改成 `.task(id:)` 呼叫 `GameSession.watchRouteHintOffTheMainActor()`（`RouteHint.swift`），在背景找平行路段，回主執行緒套上同一段判斷（`noteRouteHint(legs:)`，由原本的 `watchRouteHint()` 拆出）。

**結果不變**：建議、稱號、提示都由同一個世界、同一份程式算出，只是換了執行緒。`LineLossFixesTests.testTheCornerLooksAgainOffTheMainActorAfterAnEdit` 改三次線色，每次比對 `stationMasterLook()` 與另一個 session 在主執行緒算的建議、`StationMasterAdvice(world:)` 現算的建議、`CompanyRank` 的稱號，三者相同；主執行緒算建議的次數是 0。`RouteHintTests.testASecondTrackLookedForOffTheMainActorBringsTheCardUp` 釘住背景那條路一樣把卡片叫出來。

**之後**（新做法在主執行緒上）：站長建議、評等、路線提示各為 0（只剩把結果放回去）。主執行緒每次編輯少了約 120 ms（改站名、連接轉乘、買列車）或約 65 ms（開路線、改時段、蓋車站）。
