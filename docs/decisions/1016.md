### 1016. TestFlight 拆成三個 job，失敗只重跑那一段；只有發版能用作者 Mac 上的專用 runner（TESTFLIGHT-SPLIT）

2026-11-26，規劃3 工作串「拆開 TestFlight 上傳避免整個重跑」，分支 `claude/project-thread-370t7u`，協調者派工。號碼依 #2118 的登記。存檔版本、golden schema、GameCore、遊戲程式都不動；疊在決策 1014（#2750）之上。

作者 11-26：148 的 TestFlight 在 45 分鐘上限被停掉（封存 41 分，接著在同一個 job 上傳地圖包），「以後能分開跑嗎」「好 不然失敗都要等超久」。同一天又問 Mac 能不能自己上傳，「我有登入開發者帳號就沒差」，協調者轉達：照最安全又最簡單的做法，只有從 main 手動按的 `testflight.yml` 跑在 Mac，PR 的 job 碰不到簽章。

## 1. 做了什麼

1. **`testflight.yml` 的 release job 拆成三個**（preflight、processing 不變）：
   - `archive`（Archive, sign, export and check）：封存、匯出、檢查 IPA，和以前一樣，最後把 archive 加密成 artifact 交給 upload。build number 仍在這裡依這個 job 的 attempt 算（決策 616）。
   - `map-packs`（Upload the map packs that changed）：原本的地圖包步驟原封不動搬過來，和 archive 同時開始。
   - `upload`（Upload the build to App Store Connect）：`needs: [archive, map-packs]`，兩個都成功才傳 build。決策 858（該傳的地圖包沒傳成功就不傳 build）與 DEBUG-138（地圖包先、App 後）照舊成立，因為 upload 等 map-packs 成功。
   - 失敗時按「Re-run failed jobs」：地圖包失敗只重跑地圖包（再自動跑 upload），不用再封存 40 分；upload 失敗只重跑 upload，用同一份 archive、同一個 build number；archive 失敗才重封存（拿新的號碼 `N.2`，和以前一樣）。
2. **archive 怎麼交給 upload**：GitHub 的 job 各在不同機器，archive 只能用 artifact 傳。這個 repository 公開，登入 GitHub 的人都能下載 artifact，而 archive 裡是帶正式名稱的 App（決策 783），所以不能原樣放。`.github/scripts/testflight-bundle.sh`：
   - 把 archive 和上傳用的 ExportOptions 打成 tar，用 `openssl enc -aes-256-cbc` 加密；金鑰是「這次 run 的 ID ＋ `ASC_PRIVATE_KEY`」的 SHA-256，只有 `testflight` environment 的 job 算得出來，從不寫進 log、output 或指令列（放在 600 權限的暫存檔）。
   - archive job 把加密檔的 SHA-256 當 output；upload job 先比對雜湊，對了才解密，所以拿到的一定是 archive job 做的那一份。
   - artifact 留 3 天（隔天只重跑 upload 也找得到），不壓縮。
   - 以前〈安全設計〉寫的「archive、IPA 不存成 artifact」改成「只存加密過的 archive」。
3. **What to Test 的「上次是哪個 build」**（`testflight-changes.py`）：以前看「上傳 job 成功的那個 attempt」；拆開後號碼是 archive job 給的，所以改看「上傳成功的 attempt 之前、最後一次成功的 archive 的 attempt」。150 以前的 run 照舊用舊的 job 名稱。
4. **Mac**（決策 1014 的延伸）：新的 `pick` job 呼叫 `pick-mac.yml`，`label: chien-mac-release`（`pick-mac.yml` 加了 `label` 輸入，預設仍是 `chien-mac`）。作者 Mac 上**另一個標準帳號**（`cirelease`）的 runner 在線又有空時，archive、map-packs、upload 三個 job 都在 Mac 跑；不在線、在忙、或任何一步出錯，照舊用 hosted `xcode-27`。設定步驟在 `docs/MAC_RUNNER.md` §6。
   - 在 Mac 上，archive job 最後把工作目錄的品牌還原成中性名稱（`git reset --hard`、`git clean -ffdx`）；暫存 keychain、key 檔、archive 照舊由 `testflight-signing.sh cleanup` 刪，`RUNNER_TEMP` 也由 runner 在 job 前後清空。
   - 簽章不用作者 Xcode 裡登入的 Apple 帳號：和 hosted 一樣用 `testflight` environment 的 App Store Connect API key（雲端管理的發佈憑證），所以 `cirelease` 帳號不用登入 Apple ID。
5. **檢查**：`testflight-selftest-bundle.sh`（假的 archive 與 secret：原樣還原、連結保留、錯的雜湊、別的 run、別的 secret、改過的檔、不覆蓋都擋下）在 `testflight-checks.yml` 的 Linux job 與 macOS dry run 都跑；macOS dry run 另外把真的（未簽章）archive 加密、刪掉、解回來，逐檔比對。

6. **TestFlight Checks 的 macOS dry run 只封存一次**：以前 internal、external 各封存一次（11-18 是 32 分和 28 分以上，#2423 在第二次被 60 分上限停掉）。archive 本身和 TestFlight 範圍無關，只有 ExportOptions 不同，所以 external 改成 `TESTFLIGHT_OPTIONS_ONLY=1`：對同一份 archive 重寫選項再檢查（`testflight-archive.sh`；發版從不設它）。job 上限 100 分改 70 分。

## 2. 安全：為什麼是另一個帳號

- PR 的 iOS build 在 `cirunner` 帳號跑 PR 的程式碼（決策 1014）。self-hosted runner 不像 hosted 用完就丟：一個 PR 的程式可以在那個帳號留下東西（登入腳本、背景程式），等下一個在同帳號跑的發版 job 寫出 API key 時讀走。所以發版不和 PR 共用帳號。
- `cirelease` 只掛 `chien-mac-release` 標籤，不掛 `chien-mac`：PR 的 build（`runs-on` 要 `chien-mac`）永遠不會排到它；`testflight.yml` 只要 `chien-mac-release`，也永遠不會排到 `cirunner`。
- 還剩的風險（照實寫）：個人帳號的 repository 沒有 runner group，所以 GitHub 不能限定「只有 testflight.yml 能用這個標籤」；有寫入權限的人（只有作者和作者的工作串）在 PR 裡新寫一個 workflow 指名 `chien-mac-release`，就能在 `cirelease` 跑程式。fork 的 PR 要作者核准（決策 1014 §3），拿不到 secret。不信任的人不給寫入權限（`docs/TESTFLIGHT_GITHUB_ACTIONS.md`〈安全設計〉本來就這樣寫）。
- secret 仍只在 `testflight` environment，只有 `main` 手動觸發拿得到；PR 拿不到，不論在哪台機器。

## 3. 五方理由

- 玩家：無直接影響；發版失敗時少等 40 分，修正早一點到手上。
- 鐵道迷：無。
- 開發：地圖包或上傳失敗只重跑那一段；Mac 在線時封存從 hosted 的 35–41 分降到 Mac 的建置時間（PR 的 build 在 Mac 9.8 分、hosted 29.9 分，決策 1014），也不用排 hosted 的隊。代價：多兩次 runner 啟動與一次 artifact 上下傳（數分鐘），多一支腳本。
- 美術：無。
- 音樂：無。

## 4. 沒有選的

- **只把地圖包搬出去，build 還在 archive job 裡傳**：archive job 要等地圖包 job 成功才能傳（決策 858），只能在 job 裡輪詢；地圖包失敗時 archive job 也得算失敗，「重跑失敗的 job」會連封存一起重跑，等於沒拆。
- **archive 不加密直接當 artifact**：公開 repository 的 artifact 任何登入的人都能下載，會洩漏正式名稱（決策 783）與發佈描述檔。
- **改用 `altool --upload-app` 傳 IPA**：upload job 就不用 keychain，但上傳方式換了，要重新驗證；照舊用同一份 archive 以 `destination=upload` 匯出（真實執行 #2 驗過）。
- **發版和 PR 共用 `cirunner`**：最簡單，但有 §2 第一點的風險。
- **發版 runner 平常關著、發版前才手動開**：最安全，但每次發版要多一步，作者忘了就會改用 hosted（不會壞，只是慢）。保留為作者想要時的做法：`cirelease` 帳號 `./svc.sh stop`。
- **全部用 Mac、不退回 hosted**：Mac 關機或睡著時發版會卡一整天。

## 5. 驗證

- VERIFIED（Linux 雲端）：actionlint 1.7.12、shellcheck 0.10.0；`testflight-selftest.sh`、`testflight-selftest-retry.sh`、`testflight-selftest-processing.py`（34 個，含兩個新的）、`testflight-map-packs.py --selftest`、`testflight-selftest-bundle.sh`。
- 交給 CI：`testflight-checks.yml` 的 macOS dry run（LibreSSL、bsdtar、bash 3.2 下的加密與還原）。
- UNVERIFIED（要真的發版）：三個 job 的真實執行、artifact 在「只重跑 upload」時找得到、Mac 上的封存與上傳。第一次真實執行就是驗證；作者可以先在 0.7.0 送審前按一次 `internal` 的 TestFlight 試。

## 6. 其他 workflow 還有哪裡是「一個長步驟、失敗就全部重來」（11-26 盤點）

作者問「還有哪裡要拆開嗎」。逐一看了每個 workflow 的 job 與步驟：

| workflow | 現況 | 建議 |
| --- | --- | --- |
| `testflight.yml` | 封存＋地圖包＋上傳在一個 job | 本決策拆成三個 |
| `testflight-checks.yml` dry run | 同一份專案封存兩次 | 本決策改成一次（約少 30 分） |
| `ci.yml` | 已經是建一次、14 個分片各自跑；紅了只重跑那一片 | 不用拆 |
| `ios-build.yml` full lane | 已經拆成 build、ui-full-lane、ipad-tutorial 三個 job | 不用拆 |
| `ios-build.yml` PR 的 build job | 建置（hosted 約 20 分）和 gate 的 UI 測試在同一個 job，UI 測試已在步驟內自動重試一次；整個 job 紅了重跑要重建 | 可以拆成「建置」與「UI 測試」兩個 job，用 artifact 傳 Debug 的 App（中性名稱，公開也沒關係）。Mac 上線後建置只要約 10 分、又有編譯快取，省下的變少，多一次模擬器開機；**先不做**，Mac 上線一週量完（決策 1014 下一步 2）再決定 |

| `release-archive.yml` | 一個封存步驟（45 分上限），每晚與改設定的 PR | 只有一步，沒有東西可拆 |
