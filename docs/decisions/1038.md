### 1038. 發車問路少做重工：找軌道一猜再猜、跟車截斷只算一次停哪、反向保護少掃列車（台灣寫實的發車問路）

2026-11-27，雲端工作串「讓台灣大地圖跑滿 60 倍」（協調者派工，接 TICK-HOLDERS-BY-CLAIM 的下一步，`docs/handoff/TICK-HOLDERS-BY-CLAIM.md`「還留下什麼」第 1 點）。
起因同決策 1036：玩家回報大地圖 60 倍跑不滿（`docs/handoff/BIG-MAP-SLOW.md`），台灣全買・寫實（開閉塞）最慢，08 時一個 tick 約 3.5 s。
只改 GameCore 裡「怎麼算」，規則一條都沒改：存檔版本、golden schema、`GoldenScenarios/`、`SaveFixtures/`、`ReplayFixtures/` 都不動。待避計畫的那一半是決策 1039。

**量到什麼。** main `8e185c34` 的台灣全買・寫實，08 時取樣（`perf record -g`，量法見 `docs/handoff/TICK-HOLDERS-BY-CLAIM.md`）：
發車問路（`askingAnyDeparture`）15 %，其中最貴的不是交接寫的決策 980 第 3 步（開閉塞時「只避開站著的車」那次找路），而是它周圍每問一次都重做的幾件事：

1. 用編號找一段軌道（`RailwayNetwork.edgeIndex`）約佔 8 %。路網編號照順序發，所以「第一段的編號加差距」那一格先猜；但台灣全買時早期有編號被拿掉，5,943 段裡 5,204 段第一猜就錯，每次都退回二分搜尋。
2. 「這列車照真實時刻表跑嗎」（`followsRealTimetable`）約 5 %：每問一次就把每條路線（連同它所有班次）整個複製一次；而且在待避計畫裡對每一對車問兩次。
3. 決策 562 的跟車截斷（`followerCutOff`）約 4 %：對每一列別的車都重算一次「這列車要停在哪、停的地方蓋到哪些道岔」（`stopsOn`），而那只跟這列車本身有關。
4. 改完前三項再量一次，發車問路裡最貴的變成反向保護（`opposingParts`，7.5 %）：每秒列車都動，所以每列被擋的車每秒都要重算一次「別的車與路線要走哪些方向」。裡面四分之一是每列車每一段的路線偏好（`routePreference`，每問一段就把時刻表對路線的停站順序整個重算一次），四分之一是每條路線的每個班次都把它的車一列列從所有列車裡找出來（`train(id:)`）。

**做了什麼。**

1. `RailwayNetwork.index(of:count:numberAt:)`：第一猜的編號比要找的大 `d` 時，要找的那段一定在它前面至少 `d` 格（編號遞增而且不重複，往前一格至少少 1），先試那一格，再在兩格之間二分搜尋；第一猜比要找的小時，前面每一格都更小，直接回「沒有」。
2. `followsRealTimetable` 用索引讀路線，不複製；待避計畫的 `planTrafficOvertakes` 對每一列車只問一次，存成陣列給每一對共用。
3. `followerCutOff` 第一次要用時才算「這列車停在哪」（`stopping(_:fouling:)`，`Stopping.isOn` 就是原本的 `stopsOn`），之後每一列別的車都用同一份。
4. `workedOutOpposingParts`：每一列放在路網上的車的車長先照車號記一次（車號不重複），路線的每個班次照車號查；`workedOutServiceDirections` 的路線偏好用新的 `legRoutePreferences(for:on:)` 一次算完每一段：停站順序（`runOrder`／`routeOrder`）只讀列車的時刻表與路線，和第幾段無關，所以算一次給每一段用。

**為什麼結果一樣。**

- 找軌道：編號在路網裡是驗證過的嚴格遞增，所以一個編號最多一格有；新的兩猜只是在二分搜尋之前縮小範圍，縮掉的格子都證明了不可能有，找到的是同一格，找不到時也都是 `nil`。`NetworkIndexLookupTests` 拿三百多組有空號、有極端值（會溢位）的編號，對每個編號比「一格格找」的答案。
- `followsRealTimetable`：讀的是同一個 `lines` 陣列裡同樣的欄位，只是不複製；待避計畫裡一次規劃中列車與路線都不變，所以每一對問的答案和先問好的相同。
- 跟車截斷：「停在哪、蓋到哪些道岔」只讀這列車（`arrived(_:)`、`occupied`、`bodyStretches`、`foulingNodes`）與路網，迴圈裡都不變；原本 `stopsOn` 在前兩個條件之後才問，現在也一樣在那之後才算，所以問到的情況與順序相同。
- 反向保護：一個班次的車長集合原本是「班次的車號 → 找到那列車 → 放在路網上的 → 車長」，排除候選車；新的照車號查一張只收放在路網上、不是候選車的車長表，集合相同。路線偏好每段的答案是同一個 `first { from、to 對上 }`，順序只算一次。
- 硬證明：五個全買世界（香港、台灣各簡單與寫實；羅瓦涅米這次沒跑）新舊 build 每 60 tick 的世界雜湊逐行相同，見下表；台灣全買・寫實另開 `SAVED_WORLD_AUDIT=1` 跑 600 tick。
