### 439. 列車的遮蔽陰影烘焙進頂點顏色

2026-10-27，遊戲規劃 session_01YGNNunheBBBwyekk4Pq7b4 派工（派工單 AD，NEXT_PRIORITIES §22.16 第 2 項），實作 session_01YGNNuoLcfAoBA6h9zn3q2t（`claude/train-ao-bake-ad`）。號碼依 #1041：決策 439；存檔版本、golden schema 不動。GameCore、`GoldenScenarios/`、`SaveFixtures/`、`ReplayFixtures/`、著色器不動，只動 GamePresentation、測試、`tools/train-models/hashes.lock.json` 與文件。

**為什麼**：作者 2026-10-27 問「做了更多列車模型與引擎，怎麼改善 3D 製作模組讓畫面更好看」。列車只吃頂點顏色、塗裝帶（alpha）和發光頂點（`map3dInstancedVertex`），沒有遮蔽陰影：車底、轉向架、車間、車頂設備旁看起來和車側一樣亮，車像塑膠積木。城市那邊有太陽陰影（357）、色調（349）、反光（356），列車沒有自己的明暗。

**做了什麼**：

1. **一個函式，做 pack 時烘一次**：`Map3DTrainOcclusion.baked`，在 `Map3DModelPack.init(styles:)` 最後對整個 pack 跑一次。所有列車模型（名字不是 `prop-`、`life-` 開頭的：程式畫的五款、`Map3DTrainSet` 的每一套、各車配方註冊的靜態模型）近景、遠景都套；街道設施、行人、機車、汽車、公車、垃圾車不套。著色器讀的還是同一個頂點顏色，畫的時候不多花任何成本。
   - 配方本身不動，所以各車測試釘的**配方雜湊不變**；變的是 pack 裡的模型（`tools/train-models/hashes.lock.json`）。
2. **怎麼算**（每個模型自己）：
   - 把模型放進立方格子（近景 0.25 m、遠景 0.5 m 一格）。模型的面經過的格子記 2；鐵軌下面一層是地面，記 1（地面比牆亮，遮一半）。
   - **中間車**（名字沒有 `cab`、`head`、`tail`、`leading`、`trailing`、`rear`、`single`、`formation`、`locomotive`、`ed`、`dm`、`e1000`、`e200`、`steam`、`duplex` 的）兩端 0.6 m（`Map3DTrains.carGap`）外各加一面「隔壁車的車端」，記 2：車間的端面會暗。頭尾車的後端不加：平頭車的車頭（EMU800、C341）從形狀分不出是車頭還是貫通道，加錯會讓車頭變髒。
   - 每個頂點沿它面的法線往外放兩個盒子（半邊 0.4 m、0.8 m），用三維累加表（summed-area table）八次查表數出盒子裡有幾面牆的量 `w`，遮蔽 `k·w／(1 + k·w)`（k = 1.3），兩個盒子取平均。開闊的車側是 0；車底下的盒子碰到地面、轉向架、裙板，會暗。
   - 顏色乘上 `1 − 0.42 × 遮蔽`：最多暗 42%。
3. **照畫風（art-style §1）保持扁平、柔和**：
   - 一條邊長過 2.5 m 的面（車側、車頂的長條）三個角都取最亮的那個，車側不會變成一條長漸層。
   - 發光的三角形（`Map3DVertex.glowing`：頭燈、尾燈）不變暗。
   - 塗裝帶：alpha 小於 1 的頂點，線色那一份由著色器混進來，不變暗；只有 RGB 那一份變暗。
4. **做 pack 的時間**（Linux 雲端機，4 核，release）：整個 pack 1.43 s，其中烘焙約 0.34 s。
   - 一模一樣的模型（反向的雙胞胎、套件複製配方的車，例如 `set-emu800-*` 與 `emu800-*`）只算一次。
   - 其餘的分到各核同時算（`DispatchQueue.concurrentPerform`）。結果和順序無關，每次相同。
   - debug 版慢很多（Linux 測試約多 7 秒）。
   - **iPhone 上開 3D 的時間 UNVERIFIED**：pack 在第一次開 3D 時於主執行緒做（`Map3DView.models`），要 TestFlight 實機看。

**改了的雜湊**：
- `hashes.lock.json` 373 個模型：351 個列車模型全部變了（三角形數都沒變），20 個街道與車輛模型不變。
- `life-garbageTruck`、`life-recyclingTruck` 是決策 437 新加、main 的鎖還沒有的兩行，這次一起鎖進去，不烘焙。
- 逐款的改前／改後列在 PR。
- Swift 測試裡拿 pack 的模型去比配方或釘雜湊的，改成比烘焙後的配方（`Map3DTrainOcclusion.baked(配方)`）或新雜湊，逐項寫在 PR。

**五方**：
- **玩家**：拉近看時，車底和車間有陰影，車有重量，不像塑膠積木；遠看幾乎一樣。
- **鐵道迷**：轉向架、裙板下、車間連接處、車頂冷氣旁看得出凹凸，比較像真車。只是光的效果，車型、編組、塗裝都沒有改。
- **開發**：
  - 只有一個函式、一個呼叫點，配方都不用改；新車自動套用。
  - 執行時零成本，做 pack 時多約 0.34 s（4 核 release）。
  - Linux 上測得到。
  - 著色器不動，不用等 macOS 才知道能不能編。
- **美術**：還是扁平藏青的畫風，只多了柔和的明暗。最多暗 42%；長面一個色，不起漸層；車燈、塗裝帶不變暗。
- **音樂**：無。

**沒選的**：
- (A) 列車改用貼圖材質（每款畫一張遮蔽圖）：每款都要畫貼圖、佔記憶體，和「整座城一種材質」（決策 229）不合。
- (B) 即時算遮蔽（畫面處理的 SSAO）：多一道 pass，手機掉幀；效果和烘焙差不多，也照不到車與車之間。
- (C) 每個頂點對模型射線取樣：比格子準，但 pack 有 110 萬個三角形，release 估計要好幾秒，開 3D 會卡。
- (D) 每個面一個遮蔽值（不做頂點漸層）：更扁平，但轉向架、設備邊這種小面會變成一塊一塊的。改成只有長面取一色。
- (E) 頭尾車的後端也加隔壁車：要先分得出車頭和貫通道。用名字分會漏掉平頭車，用形狀分會讓平頭車頭變髒，所以不做。
- (F) 改著色器、把遮蔽放進 UV 另外乘：塗裝帶也會跟著暗，但要改 `.metal`（只有 macOS CI 能編），而且多一個乘法。留給第 3 項（車窗與車身質感）改 `map3dInstancedVertex` 時一起考慮。
