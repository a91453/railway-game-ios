#### 一、號碼檢查進 CI（DOCNUM-CI）

1. `ci.yml` 的 changes 工作多一個輸出 `docs`（`swift-shards.sh decide` 印 `docs=true|false`）。
   改到 `doc_numbers.py` 讀的檔就是 true（`swift-shards.sh doc_paths`）：`docs/`、工具本身、
   `Sources/GameCore/World/SavedGame.swift`（存檔版本）、`Tests/GameCoreTests/GoldenScenario.swift`（golden schema）、
   `SaveFixtures/`、`GoldenScenarios/`、`ReplayFixtures/`（個數）。檔案列不出來時（手動、夜間、push 找不到比較基準）也是 true。
2. 新工作 `doc-numbers`（「Decision and document numbers (doc_numbers.py)」）：先 `--selftest`，再 `--check`；差異寫進 job summary。
   約 10 秒，不用 Swift。
3. **放在 gate 裡判**：`Swift CI (gate)` 名字不變，多 `needs: doc-numbers`；`swift-shards.sh gate` 多讀 `DOCS_NEEDED`、`DOCS`：
   要跑就要 success，不用跑就要 skipped，偵測沒說就紅。docs-only 的 PR 原本 Swift 工作全跳過、gate 直接綠，
   現在 gate 等這個檢查，紅了 gate 就紅，main 的分支規則擋得住。夜間 run 若因這個 commit 已跑過完整一輪而整個跳過，`docs=false`。
4. 只在改到它讀的檔時跑，不是每張 PR 都跑：main 上的文件號碼若壞了，不碰文件的 PR 不會被別人的錯卡住；
   碰到文件的 PR 會紅，那就順手修（修法通常一行）。
5. 測試：`swift-shards-selftest.sh` 加 14 個 decide 情境與 8 個 gate 情境（docs-only 綠／紅、Swift 全綠但號碼紅、
   需要卻跳過、沒結果、不需要卻跑了、偵測沒答案）。

#### 二、衝突的 PR 自己被叫醒（CONFLICT-WATCH）

1. 新 workflow `conflict-watch.yml`：每次 push 到 main（與手動）跑 `tools/ci-watch/conflict_watch.py --main <sha>`。
   權限只有 `contents: read`、`pull-requests: write`（讀 PR、在 PR 上留言）。照 `full-lane-watch.yml`（決策 329）的寫法：
   只讀 API、只留言、留言是 github-actions[bot] 的、**絕不帶 at 符號**（`@` 換成全形，並 assert）、不寫 PR 標題或分支名。
2. 看所有 base 是 main 的 open PR（draft 也算：實作 session 的 PR 常是 draft）。
   GitHub 在 main 動了之後，要有人問那張 PR 才開始算能不能合（`mergeable` null、`mergeable_state` `unknown`），
   所以逐張問，沒算好的每 15 秒再問，最多 8 輪；還沒算好的寫進 log，留給下一次 push。
3. 衝突的判斷：`mergeable` 是 false，或 `mergeable_state` 是 `dirty`（draft 的 `mergeable_state` 不一定是 `dirty`，所以兩個都看）。
4. **同一個 head 只留一則**：留言最後有隱藏標記 `<!-- conflict-watch head=<sha> -->`；那張 PR 上 github-actions[bot]
   最新一則標記的 head 就是現在的 head，就不再留。session 併過 main，head 換了，之後又衝突就再留一則。
5. 留言：「**和 main 衝突，CI 不會跑，請併 main。**」、PR 的 head、main 的 commit、做法（`git merge origin/main`、本機快檢、推）。
6. 一次只跑一個（concurrency `conflict-watch`），兩次 push 不會對同一個 head 各留一則。
7. `ios-build.yml` 的 paths-ignore 與 key 的排除清單加上這個 workflow 檔（app 看不到它）。
8. 測試：`python3 -I tools/ci-watch/conflict_watch.py --selftest`（衝突判斷、draft、一個 head 一則、只算 bot 的留言、
   留言沒有 at 符號、重問的輪數與等待、中途關掉或改 base 的 PR），workflow 每次跑先跑它。

**前例。** 先看本專案：`full-lane-watch.yml`／`full_lane_watch.py`（決策 329）照著寫。參考倉庫放的是遊戲的程式與資料，這件是本 repository 自己的 CI，沒有去翻。
網路上找到現成的 action：codytseng/auto-comment-merge-conflicts（push 到 main 後對衝突 PR 留言）、
eps1lon/actions-label-merge-conflict（加標籤，有等 GitHub 算好的重試）、prince-chrismc/label-merge-conflicts-action
（標籤加選用留言）。它們都證實了兩件事：push 後 `mergeable` 先是未知、要重問；從 push 到 main 觸發才有寫入權（fork 的 PR 也行）。
沒有用它們：多一個第三方 action 等於加相依套件（要作者同意），而且要的只是幾十行標準函式庫就做得到的事；
程式是本專案自己寫的，沒有搬外部程式碼。
