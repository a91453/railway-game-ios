# MAP3D-CAP：3D 靜態場景的三角形與記憶體上限

- 派工單：MAP3D-CAP（2026-11-13，Mac 本機 session，由 FPS-DEVICE 的 session 開），分支 `claude/map3d-hard-cap`。
- 決策：[711](../decisions/711.md)（原因、改法、沒選的、限制都在那裡）。
- 存檔版本、golden、SaveFixtures、ReplayFixtures、`Sources/GameCore/`：不動。
- 接 `docs/research/FPS_DEVICE_2026-11-12.md` 第 8 節第一件：畫質階梯降到最低，實機仍畫 564–892 萬三角形、記憶體 2,888–3,327 MB。

## 做了什麼

1. **原因**：收購來的真實路線，軌道幾何約每 0.65 m 一個點，3D 每兩點之間都建一段道床、鋼軌、隧道壁或橋面，而且軌道屬於任何距離都全畫的地面層。作者的存檔 B（103 站 150 列車）一個場景光軌道就 1,264 萬個三角形、1,600 MB 緩衝。另外兩個缺口：階梯的預算只管會動的東西，靜態場景沒有預算；記憶體警告時一個區塊都不卸。
2. **軌道抽稀**（`Map3DScene.Builder.thinned`）：直線回到 16 m 一段，彎道差 3 cm 以內。
3. **每格靜態場景的三角形預算**（`Map3DSceneBudget`，高階 240 萬／標準 160 萬／低階 100 萬，硬上限是兩倍）：超過時由遠到近改畫簡化版、再只畫地面、再不畫。階梯往下降，靜態場景現在會跟著少畫。
4. **記憶體**：警告或剩餘記憶體不足時，卸掉比鏡頭看得到的還遠的區塊（場景本體的也卸）；區塊緩衝超過上限（400／700／1,000 MB）時也卸。鏡頭移過去或拉遠時會重建。

## 量到的數字

Mac 重算（作者的存檔 B，`Map3DFrameLoadReportTests`）：見決策 711 第 3 節。

iPhone 模擬器（iPhone 17 Pro 的模擬器，用 Mac 的 GPU，所以格率不能當實機的；三角形數與記憶體可以比）。存檔 B，從 2D 地圖直接按 3D（開在三重一帶），讀畫面右上的效能數字；同一個地點、同樣的手勢，先裝 main 的版本量一次，再裝這個分支量一次：

| | 改之前（main） | 改之後 |
| --- | ---: | ---: |
| 剛開 3D 的視野：三角形／draw | 2,825,748／341 | 760,571／341 |
| 拉到最遠：三角形／draw | 10,954,782／1,210 | 1,787,594／662 |

（另外在劍潭開 3D 量過 main 一次：1,363,450 → 拉到最遠 7,428,379，2,952 MB，和實機的 564–892 萬、2,888–3,327 MB 是同一個量級，所以模擬器重現得出來。）

拉到最遠時看得出差別：模擬器沒有裝置分級，用的是最低的預算（100 萬，上限 200 萬），所以離鏡頭中心遠的區塊只剩地面、道路、軌道，沒有建築。實機的預算是 240 萬，會留比較多；決策 709（#2098）合併後遠景建築本身變少，就更少動到。

## 還留下什麼

- 預算數字（240／160／100 萬、400／700／1,000 MB）沒有在實機上調過；實機量完若還有餘裕或仍然卡，改 `Map3DSceneBudget` 的數字就好。
- 和 #2098（PERF-FAR，決策 709）改到 `Map3DMetalView.swift` 同一段畫區塊的迴圈，後合併的那個要解衝突（機械性的：709 決定遠景建築畫哪些，711 決定每塊畫到哪一級，兩者不互斥）。
- 決策 711 第 7 節列的限制：預算邊界沒有遲滯、太陽陰影那一遍不算在預算內、畫面開著時 CPU 那份場景網格不放。
- **不在這張單的線索**：
  - 開 3D 第一格的停頓（270 ms–1.8 s）：沒有查。抽稀後建場景要處理的軌道點少了九成以上，可能順帶變短，沒有量。
  - TICK-L1／L2：同一份每 0.65 m 一點的收購路線幾何，tick 裡凡是沿幾何走的計算也在付這個成本；沒有量，也沒有動 GameCore。
- 模擬器量測用的存檔是作者的實機備份（在作者的 Mac 上，不在 repo）。
