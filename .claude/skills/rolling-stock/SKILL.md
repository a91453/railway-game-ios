# 3D 城市的列車

城市畫面（ARCHITECTURE 決策 152、161）裡的列車全部由 `Web/CityView/src/world/trains.js`
畫出來。這份寫下做一款新車要知道的約定、要跑的檢查，以及 2026-10-11 做台灣高鐵 N700ST
時踩過的坑。

## 1. 四種東西，不要搞混

出貨的車有兩條路，都是我們自己做的：**程式放樣**（`trains.js` 的 `shellGeometry`）或
**Blender 建模**（`tools/trains/build_train.py`）。生成的模型和參考庫的模型永遠只是量尺。

| | 用途 | 可信的部分 | 不可信的部分 |
| --- | --- | --- | --- |
| **程式放樣的** | 出貨（沒有 GLB 時的底子） | — | — |
| **Blender 建的** | 出貨（指名的車） | — | — |
| **參考庫的模型** | 量尺 | 顏色（材質是作者刻意命名的）、尺寸（對照 catalog） | 形狀（都標 `illustrative`，沒有車頭） |
| **生成的模型** | 量尺 | 形狀的**比例與順序** | 絕對尺寸、面數、貼圖 |
| **作者的照片** | 最高依據 | 全部 | — |

**照片優先於模型，包括作者自己的模型。** 2026-10-11 做 EMU3000 時，作者的 GLB 畫了一條很寬的暗紅腰帶，
照片顯示真車根本沒有——車身是素白加窗下一條細線，命名編組的顏色只是車端上方一小塊。
顏色可信不等於塗裝佈局可信。

### 生成的模型什麼時候有用

早先這一節寫著「預設用程式畫」並舉兩次 Meshy 失敗為證（照片版比例錯、文字版 391,054 個三角形
且橘帶幾乎消失，共 45 點）。**那個結論下得太早。** 同一天作者先把一張車頭照**去背**再生成，
得到的形狀是一台真的新幹線頭車：鴨嘴鼻、車窗排、轉向架都對。

決定成敗的是**輸入圖乾不乾淨**，不是生成本身。失敗的兩次用的是雜亂的發表會現場照（白車配白坡道、
背景有螢幕和人）。這和 img2threejs 的 admission gate 擋下同一張照片是同一件事。

所以：**要生成之前，先把參考圖去背、只留主體。** 選**白模**就好——顏色我們另有更可靠的來源，
而貼圖正是這類模型最不準的部分。格式選 **GLB**（`measure.cjs` 和 `preview.cjs --reference` 都直接讀）。

### 從生成的模型只拿「正規化」的東西

量 2026-10-11 那個 Meshy 模型（710,186 個三角形）：把長度縮到真車的 27.35 m 之後，
**車身寬 4.01 m**（真車 3.36，胖 19%），**車頭只佔車長 18%**（真車的 N700S 是 39%）。

所以**絕對尺寸一律來自 catalog 或工程資料，不要從生成的模型讀**。可以拿的是形狀的相對關係，
例如「鴨嘴車頭主要收在高度、不是寬度」「寬度最後才收」這種順序。

**生成的網格不進 repo。** 它和參考庫的模型一樣是量尺。從別人的宣傳照生出來的網格更是如此：
量形狀、寫自己的程式可以，檔案本身不要提交。

## 2. 兩條路合起來用（2026-10-11 之後的做法）

「程式畫」和「Blender 建」不是二選一，是**各做一半**：

- **塗裝永遠是 `trains.js` 畫的 canvas。** 一條色帶要落在指定的高度，這件事擴散式貼圖做不到
  （Meshy 兩次都失敗），而 canvas 上畫一條橫線就是了。
- **幾何可以是 Blender 建的。** 程式放樣給不了的是**站出車身的面**（膠囊窗、塞拉門）
  和**圍著它們積起來的環境遮蔽**——那正是一台車看起來像遊戲裡的車的另一半。

接得起來，是因為兩邊用**同一組座標**：

| | 誰寫 | 給誰 |
| --- | --- | --- |
| `uOf(m, L, u0)`（trains.js） | 塗裝與幾何共用的縱向對應：車尾起算 m 公尺 → 圖上的 `u` | 畫家、`shellGeometry`、Blender |
| **UV0** `"UVMap"` | Blender 照 `uOf` 與斷面高度 `f` 寫死 | `material.map`（那張 canvas） |
| **UV1** `"AO"` | Blender 投影打包，每個面有自己的 texel | `material.aoMap`（`channel = 1`） |

**為什麼要兩層 UV**：UV0 左右兩側共用同一塊圖（塗裝本來就左右對稱），而且窗板和它背後的車身
落在同一個 texel。烘焙要的正好相反——車身被窗板擋住的地方幾乎全黑，窗板本身不是，
同一個 texel 存不下兩個值。所以塗裝用寫死的 UV0，遮蔽用投影打包的 UV1，各取所需。

**畫家與模型用同一個 `perM`。** 2026-10-11 第一版畫家用 `HALF / stock.length`、幾何用
`0.492 * TEX_W / (length - 0.6)`，差 0.8% 加 0.2 m 的原點位移，結果是**窗玻璃畫在窗板旁邊**，
整排窗看起來灰白一片。兩邊改成都走 `uOf` 就對了。

### 一定會踩的那個翻轉

Blender 的 `v` 從圖的下緣算，glTF 從上緣算（匯出時會自動寫 `1 - v`），而 `CanvasTexture`
在 three.js 裡又是翻過來上傳的。兩次翻轉抵成一次，所以 **Blender 裡要存 `1 - v`**
（`build_train.py` 的 `written()`）。存錯的徵狀是**整台車變成純白**——看起來像貼圖沒載到，
其實是座標差了半張圖。另外 `aoMap` 是自己用 `TextureLoader` 載的 PNG，UV 來自 glTF，
所以要 `flipY = false`。

### Blender 那一步

```sh
pip install bpy                                   # Blender 當 Python 模組，CPU 就夠
python3 -I tools/trains/build_train.py n700st-cab n700st-car
```

寫進 `Web/CityView/public/models/trains/`：GLB、遮蔽 PNG，以及併入 `index.json`
（`front` 是車頭朝的軸，`fit: false` 表示模型已經是遊戲的公尺，只轉向不縮放）。
`trains.js` 的 stock 加上 `models: { cab, car }` 就會在載入後換掉放樣的殼。

**不要用 smart project 做 UV0。** 它不理會你選了哪些面——切換成面選取模式這個動作本身會把
選取「沖」成全選，於是整台車被重新投影，塗裝落到隨機的地方。UV0 一律自己寫，
UV1 才用投影；而且 `unwrap()` 寫完要跑 `audit()`，確認每個面都落在自己那一條裡。

### 能站出來的面，和不能的

窗板、門板是**站出來**的（`proud` 約 2 cm），不是凹進去的。凹進去沒有用——車身是封閉的殼，
一個整個在殼裡面的盒子根本看不見。站出來才有邊，烘焙才有接觸陰影可以鋪。

**而且要順著車身，不能是方盒子。** 斷面在稜線最寬、往車頂收，所以一個放在最寬處的方盒子，
到了門板頂端會離車身 19 公分，看起來像一塊歪掛在車側的板子。`add_panel` 把板子沿高度切成
幾段，每一段貼著當地的 `flank()`。

**車頭上不要放盒子。** 車側接近平面，一塊板貼得上去；鴨嘴是雙曲面，六個盒子排下去會變成
一道階梯。車頭的駕駛窗、頭燈維持用畫的——但駕駛窗要畫在車頭自己的圖表裡（下一節）。

### 車頭頂自己的一張圖表（`NOSE`）

「按高度上色」畫不出擋風玻璃：同一高度的一圈都會上色，結果是一條橫跨車頭的黑色護目鏡。
所以車頭頂那一條（中線左右各 `NOSE.rings` 圈）另外攤成一張**由上往下看**的圖表，
玻璃在裡面照它真正的形狀畫。兩件事要注意：

- **`across` 要用實際的橫向位置，不是圈上的點序號。** 斷面是超橢圓，車頂幾乎是平的，
  中線兩側三圈裡有兩圈擠在最外側五分之一——用序號當座標，玻璃畫出來寬度會差一倍以上。
- **放樣要把這一條另外鋪一次。** 一個頂點只能帶一組貼圖座標，所以 `shellGeometry` 跳過
  這些面，再用自己的頂點鋪一遍（Blender 不用，它的座標是每個 loop 一組）。

沒有 `cab.screen` 的車（EMU3000 整個車頭是一塊深色面罩）不用這張圖表，按高度上色就夠。

## 3. 約定（照著做，不要自己發明）

- **座標**：`+Z` 是行進方向（車頭朝 +Z），`+Y` 上，軌面 `y = 0`。`dummy.lookAt` 已經假設 +Z 朝前。
- **尺寸**：車身寬 2.9 m；車頂 3.75 m；地板 1.0 m（方塊車）或裙擺下緣 0.62 m（放樣的殼）。
  每節車的幾何長度是 `stock.length - 0.6`（留車間縫）。
- **一個 stock 一個材質**，貼圖是一張 2048 × 512 的 canvas：
  - 最上面 16 px 是純色色票（`plainUv(geo, u)`：`u = 0.25` 車身色，`u = 0.75` 深色底盤）；
  - 16–256 px 是車側；其餘留白。
  - 方塊車：車側佔滿寬度，車頭另外畫在左下角。
  - 放樣的殼：**左半是頭車、右半是中間車**，`u` 沿車身、`v` 沿斷面高度。
- **第二張貼圖是夜間發光**（`emissiveMap`）：車窗、頭燈、方向幕畫在上面，白天也還有 0.2 強度。
  **所以每款車都要自己給 `window.lit`。** 用預設的亮白，白天會把深色玻璃洗成淺灰——
  N700ST 的墨綠玻璃就是這樣在太陽下變成一排白膠囊的。玻璃越深，`lit` 要越暗。
- **第三張是遮蔽**（`aoMap`，只有 Blender 建的車有）：吃 UV1，只影響間接光，所以陽光下不會整台變暗。
- **面數預算**：一節車 3,500 個三角形（`preview.cjs` 的 `budgetFor`）。依據是作者自己的近景
  網格約 7,200、EMU3000 的 GLB 約 16,000；取他最輕的一半。

### 放樣的殼（有車頭的車）

`shellRing(z, t)` 回傳一圈點，`t` 是沿車頭的參數（0 在車身交界、1 在鼻尖）。每個點帶著
**自己在那一圈裡的相對高度**，那就是貼圖的 `v`。所以貼圖上畫一條**直的**橫帶，到了車頭會
自己被斷面的收縮拉成往前下方掃的曲線——和真車上漆的方式一樣，不用手算曲線。

斷面是超橢圓，稜線以下比以上飽滿（真車車身是圓角矩形，不是橢圓），稜線處微微外鼓成翼線。
最後 12% 收口（`cap`），否則鼻尖會是一個平切面，**只有正面角度看得出來**。

## 4. 先去參考庫拿數字

作者的參考庫（`a91453/railway-reference-private`，CLAUDE.md 授權直接取用）裡有做好的車隊資料。
開工前先接上：`add_repo` 之後 `git clone --depth 1 … /home/user/railway-reference-private`。

| 路徑 | 是什麼 | 信不信 |
| --- | --- | --- |
| `Railway/…/memories/*/fleet/catalog.json` | 13 款車的工程尺寸（`pitchM`／`widthM`／`heightM`／`roofM`／`floorM`／`role`）**每筆附出處** | **信**。這是第一手的尺寸來源，比網路搜尋可靠 |
| `OpenWorld/…/taiwan-tra/*.glb` | 作者做的整列模型（EMU3000、普悠瑪、太魯閣） | **顏色信，形狀不信**（見下） |
| `Railway/…/rail-3d/assets/blender-map-v1/` | 40 款車的 LOD 網格與 `manifest.json`（含 700T） | 同上；`manifest.json` 標 `illustrative: true` |
| `Railway/…/data/tra_special_trains.json` | 作者寫的車種說明 | 信（塗裝的文字描述） |

**參考模型不是拿來出貨的，是拿來量的。** 作者的 EMU3000 GLB 是 199,588 個三角形，
這裡整列 12 節約 3,300 個。但它比照片好用：沒有透視、不會把反光讀成塗裝、沒有看不到的另一側。

**而且要分辨它哪裡可信。** 2026-10-11 量 EMU3000 的 GLB：斷面在整列 245.7 m 裡從未收窄到
流線型該有的程度，每節車兩端都是圓頭——它沒有車頭，是示意用的地圖模型（manifest 自己標了
`illustrative`）。材質名稱卻是刻意分部位命名的（`Pearl_Livery`、`Signature_Red`、
`Smoked_Blue_Glass`…），顏色是作者的決定。**結論：顏色照抄，形狀另外找依據。**
量完一定要算圖看一眼再決定信哪部分。

```sh
node .claude/skills/rolling-stock/measure.cjs <reference.glb> \
  [--metres <真實全長>] [--pitch <車距>] [--slices 120] [--json]
```

它印出：整體尺寸、每個材質的顏色與**高度帶**（色帶的 row 從這裡讀）、以及沿車身的斷面。
參考模型通常是**整列**而不是一節，斷面會每一節車縮腰一次；`--pitch` 會把整列**折成**
一節頭車和一節中間車的斷面表，那就是放樣的 station。沒給 `--pitch` 它會自己從縮腰間距猜。

模型常常不是以公尺為單位（EMU3000 那個是 1/6.5）。寬度或高度小得不像車時用 `--metres`
給真實全長來換算，不要直接採用。

## 5. 流程

0. **先去參考庫量**（第 4 節）。沒有可用的形狀參考時，把一張乾淨的照片去背再生成一個白模來量（第 1 節）。
1. **照片是最高依據**，和模型衝突時以照片為準。驗照片：一張雜亂的照片會讓後面全白做。要求：主體佔畫面大部分、背景和車身分得開、
   整節車入鏡。白車配白背景（發表會的白坡道、亮螢幕）是最糟的組合。
2. **逐區看，不要整張看**。把照片切成九宮格逐區放大檢查，再放大鼻尖與車側兩處。
   整張看會漏掉東西——N700ST 車頭下半那一大片灰，就是這樣漏掉的。
3. **寫下識別特徵**，以及**這個視角看不到什麼**（車頂、車尾、另一側、轉向架通常都看不到）。
   看不到的就寫成假設，不要假裝知道。
4. **改 `trains.js`**：加一筆 stock、需要的話加塗裝分支。先只用程式放樣，塗裝調到對為止——
   塗裝不對的時候加幾何只會讓問題更難找。
5. **跑檢查**（下一節）。有紅的先修，不要先看圖。
6. **跑預覽，自己先看**（Read 那張 PNG），再用 SendUserFile 給作者。
7. **值得的話再進 Blender**（第 2 節）：指名的車、玩家會看久的車值得；塗裝已經對了才做。
   在 `build_train.py` 的 `STOCK` 加一筆，跑一次，給 stock 加 `models`，再算一次圖。
8. **重新建置 App 的網頁**並提交（`trains.js` 或 `public/models/` 一改，
   `RailwayGameApp/Resources/CityView/` 的 bundle 就過期了）。臺中的圖塊資料不在雲端容器裡，
   所以只能重跑 vite 那一步，輸出到暫存再把 `assets/`、`models/`、`index.html` 複製回去，
   `tiles/` 和 `textures/` 不要動。

### 塗裝的四個坑（N700ST 四個都踩到了）

1. **車窗形狀**：先假設是方窗就錯了。新幹線是**小而直立的膠囊形、綠色玻璃**。
2. **門與色帶的先後**：門有深色框，而且**色帶是橫過門面的**。順序必須是
   門 → 色帶 → 車窗，寫反了色帶會被門切斷。
3. **下半身**：不是底部一條窄邊，是**一大片灰色**，而且車頭下半也是灰的。
4. **頭車的色帶不是水平的**：N700ST 的橘帶往車頭俯衝，上面壓一條深藍帶；中間車才是水平的。
   做之前先確認這款車的頭車和中間車塗裝是不是一樣。

## 6. 檢查與預覽

```sh
# 先裝一次 Web/CityView 的套件
(cd Web/CityView && npm ci)

NODE_PATH="$(npm root -g)" node .claude/skills/rolling-stock/preview.cjs \
  --stock hsr --out <scratchpad>/sheet.png          # 檢查 + 一張對照圖
NODE_PATH="$(npm root -g)" node .claude/skills/rolling-stock/preview.cjs \
  --stock hsr --check-only                          # 只跑檢查
NODE_PATH="$(npm root -g)" node .claude/skills/rolling-stock/preview.cjs \
  --stock tra --reference <ref.glb> --reference-metres 245.7 \
  --out <scratchpad>/compare.png                    # 和參考模型用同一組鏡頭並排
NODE_PATH="$(npm root -g)" node .claude/skills/rolling-stock/preview.cjs \
  --stock hsr --check-only --atlas <scratchpad>/livery.png   # 只要那張塗裝圖
```

**車身顏色不對時先看 `--atlas`。** 它把畫家畫出來的那張圖原樣存下來，一眼就分得出是
**圖畫錯了**還是**圖是對的、幾何取錯位置**——這兩件事在算圖上長得一模一樣，猜是猜不出來的。

`--stock` 是 `hsr`、`tra`，或任何路線名稱（選車是依路線名稱，和畫面裡一樣）。
用環境內建的 Chromium，不下載東西。有檢查紅掉會以 exit 1 結束。

檢查都是**量實際算出來的幾何**，不是看宣告值：

| 檢查 | 它抓什麼 |
| --- | --- |
| 建得起來、沒有 console error | 寫錯的 stock 欄位 |
| 整列在面數預算內 | 一節車暴增到幾十萬面 |
| 沒有東西低於軌面 | 車沉進軌道（側面看不出來） |
| 每節車長度接近 `stock.length` | 縮放寫錯 |
| 沒有超出限界（寬 ≤ 3.2 m） | 同上 |
| 頭車有收窄（最小／最大**斷面積** ≤ 0.6） | 車頭做成一根粗細不變的管子 |
| 小的那端朝 +Z | 車頭裝反 |

斷面積而不是寬度：鴨嘴車頭**故意**到鼻尖都還很寬（照片為證），只是很扁；
用寬度判斷會把形狀推離真車。（這條檢查的想法來自 img2threejs 的 taper gate。）

對照圖有六格：斜前方、頭車正側、**正面**、中間車正側、整列、夜景，最後一格是模糊後的剪影。
給了 `--reference` 時每一列變成「我們的／參考的」並排，鏡頭完全相同——這是判斷形狀對不對
最可靠的方式，比對照片準。
**正面那格要看**——鼻尖的平切面只有從正面看得出來，N700ST 就是這樣抓到的。
剪影那格是因為玩家在城市畫面裡只會掃一眼，剩下剪影還認得出來才算數。

## 7. 現在做不到的事

- **車身的貼圖沒有橫向座標**。`v` 只帶斷面高度，所以同一高度的一圈都會上到色。
  **車頭頂已經有解**（第 2 節的 `NOSE` 第二張圖表），車身其他地方還沒有：想畫一塊
  「只在某一側、不繞過去」的東西還是做不到。
- **硬稜線做不出來**。翼線目前只靠貼圖上一條淡影線，不是幾何的折邊。
- **駕駛窗是畫的不是幾何**。真車的擋風玻璃嵌在一塊**隆起的罩殼**裡，四周有折邊，
  我們的車頭是一顆平滑的蛋，玻璃只是畫在上面。所以從正前方幾乎看不到它
  （它貼在頭頂，真車的朝向更往前）。要解得改放樣的斷面，不是改貼圖。
- **車頂冷氣是純色色票**，沒有自己的塗裝位置；需要車頂花色的車要另外在圖上開一條。
- **遮蔽是烘焙的**，所以只對那台車本身有效：車與車之間、車與月台之間的陰影要靠即時陰影。
- **城市畫面沒有環境反射**（`environment.js` 的 `installSkyLight` 把環境貼圖反射關掉了，
  天光改由 light probe 提供）。亮面感只能靠色調映射和天光，不要指望反射。

## 8. 驗證怎麼寫

Linux 上能做的：`npm test`、`vite build`、這份 skill 的檢查與算圖。這些可以寫 **VERIFIED**。
App 裡的實際畫面要 macOS CI 與 TestFlight，寫 **UNVERIFIED**（CLAUDE.md）。
算圖用的是城市畫面相同的 ACES 色調映射與近似天光，但**不是** App 本身，不要寫成 App 驗過了。

## 9. 外部工具

- **Meshy**（`.claude/skills/meshy-3d-generation/`、`tools/meshy/README.md`）：生白模當量尺用，
  見第 1 節。要先去背，選白模、GLB。生出來的網格不進 repo。
- **[img2threejs](https://github.com/img2threejs/img2threejs)**（Apache-2.0）：照參考圖用程式重建 3D 的
  Claude skill。2026-10-11 跑到 blockout pass。**它的檢查值得學**（這份的照片驗收、逐區掃描、
  收窄檢查都來自它），而且它擋下雜亂參考圖這件事，後來被「去背之後生成就成功了」反過來證實。
  但它的幾何語彙不適合列車：斷面只能是橢圓、重複系統只支援環狀排列（排不出車窗列）、
  無法表達硬稜線，一節車 10,440 個三角形。模型不用它做。
- 找現成模型：GitHub 上的 Shinkansen repo 都沒有 LICENSE 檔，CC0 素材庫沒有高鐵，
  Sketchfab 的 CC-BY 標示和說明互相衝突。**沒有授權可用的現成模型**（2026-10-11 查）。
- 畫 App 裡的 2D 圖（圖示、角色）是另一回事，看 `.claude/skills/art-style/SKILL.md`。

## 10. 這份是怎麼來的

每一條規則都對應一次做錯。改這份時請保留這個性質：寫「為什麼」，而不只是「要怎樣」。

- 車窗形狀、門與色帶的先後、下半身灰色範圍、頭車色帶是斜的 ← N700ST 四個都做錯
- 鼻尖不能是平切面 ← 只有正面視角看得出來，而我做了一整天沒從正面看過
- 收窄用斷面積不是寬度 ← 鴨嘴故意到鼻尖都還很寬
- 照片優先於作者自己的模型 ← EMU3000 的暗紅腰帶
- 生成的模型要先去背 ← 兩次失敗、45 點
- 絕對尺寸不要從生成的模型讀 ← 寬了 19%、車頭短了一半
- 三角形預算要有依據 ← 我設了 400，作者自己的模型是 7,200
- 畫家與模型要共用 `uOf` ← 差 0.8% 和 0.2 m，整排窗玻璃就畫到窗板旁邊
- Blender 存 UV 要先翻 `v` ← 存錯整台車變純白，看起來像貼圖沒載到
- UV0 不可以用 smart project ← 切到面選取模式會把選取沖成全選，整台車被重投影
- 窗板要站出來不是凹進去 ← 凹進封閉的殼裡等於不存在
- 車頭不放盒子 ← 六個盒子排在鴨嘴上變成一道階梯
- 深色玻璃要自己調 `window.lit` ← 白天的 0.2 發光把墨綠洗成淺灰
- 顏色不對先看 `--atlas` ← 圖畫錯和取錯位置，在算圖上長得一樣
- 車頭頂要自己一張圖表 ← 按高度畫的擋風玻璃，從正面看是一條護目鏡
- 圖表的 `across` 要用公尺不是點序號 ← 超橢圓把點擠在外側，玻璃寬了一倍
- 板子要順著車身切段 ← 方盒子的頂端離車身 19 公分，像歪掛上去的
- 裙擺要畫在門之後 ← 門板把灰色裙擺開了一個白洞
